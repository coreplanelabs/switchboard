# Self-improvement proposals

Switchboard turns the run-friction **analysis** ([run-friction.md](run-friction.md), #105) into **action**: it keeps every finished run's diagnosis in a ledger, clusters the friction that recurs *across* recent runs, and files the top recurring patterns as labeled GitHub issues — each with the evidence (the friction data, the affected runs) and a concrete suggested fix — deduped against the proposals already open. This is the second piece of Area 7b ([#84](https://github.com/coreplanelabs/switchboard/issues/84)): *observe → diagnose → **propose***. It is **human-gated by construction**: the only side effect is opening a labeled issue for a person to triage. It never opens PRs and never merges anything.

**Built on the analyzer, not beside it (locked design).** Every pattern is made from the `FrictionFinding`s `analyzeRunFriction` already emits; the proposer adds no per-run detection. The one signal it adds — `long_run`, a run whose wall time is ≥2× the median of recent runs — cannot exist per run by definition, and stands in for **cost spikes** until per-run token accounting exists (AGENTS.md known gap). The clustering, ranking, rendering, and dedupe step is a pure function of the ledger records (no clock, no I/O), so it is tested against recorded runs exactly as #105 intended.

**Where recent runs live.** The live registry evicts a finished run 60s after it ends, so "friction across recent runs" needs a ledger: after every run the dispatcher analyzes the run's own event stream and records `{ runId, label, agent, finishedAt, diagnosis }` to the `FrictionLedger`. **With run history configured ([run-history.md](run-history.md), #157) the ledger is READ from the run store**: `RunStoreFrictionLedger` serves `recent()` from `RunStore.list` (never `get` — the listing carries the diagnosis, so no event stream is loaded), projecting each row field-explicitly to the five ledger fields above (message text and platform ids never reach a `FrictionRunRecord` or an issue body) and unioning the legacy ledger's rows for one retention window (deduped by run id, the run-store row wins); `record()` keeps forwarding to the legacy ledger — `FrictionDO` receives its small diagnosis write until the deferred decommission, so a defect in the new write path has a rollback (KD3). `selectFrictionLedger(store, legacy)` returns the legacy ledger unchanged when no run store is configured. `runHistory.retentionDays`/`maxRuns` then bound the friction population, and `validateConfig` warns when `selfImprovement.ledgerMax` is set alongside `runHistory`. The legacy implementations (AGENTS.md invariant 2): **`WorkerFrictionLedger` — the production choice** — an HTTPS client to the `FrictionDO` on the state Worker (`deploy/cloudflare-memory/`, the same Worker and `MEMORY_TOKEN` bearer as memory; one SQLite Durable Object per ledger key `friction:<repo>`, so the ledger survives bot restarts and redeploys — AGENTS.md invariant 6); the JSONL `FileFrictionLedger` under `data/` (used when no `selfImprovement.worker` is configured — the same durability as `data/overrides.json`, i.e. **ephemeral on Cloudflare Containers**; startup warns loudly); and `InMemoryFrictionLedger` (tests/dev). The record carries the run id (not the view token), so a ledger row or an issue body can never grant live-view access.

## Behavior

1. **Ledger.** After every agent run (fast paths excluded — they never run an agent) the dispatcher records `analyzeRunFriction(events)` over the run's own event copy (a ring of the newest 5000 events, so a pathological run's terminal notes are never the part dropped), with the registry run id, the runs-index label, the agent name, and the finish time. Best-effort: a ledger failure is a `[friction]` warning line, never a failed run or a delayed reply. `recent({ limit?, sinceMs? })` returns runs oldest-first as copies; the ledger is bounded (500 runs — the oldest fall off; the file compacts at 2× that, the DO trims on every write in one transaction). **Every implementation upserts by run id** — a retried or duplicated `record` replaces, never double-counts (the in-memory store replaces in place, the append-only file resolves a repeated id to its last line on read and materializes that at compaction, the DO uses `ON CONFLICT(run_id) DO UPDATE`); an empty run id is rejected as a record everywhere. Corrupt or foreign rows/lines are skipped, never fatal. **Durable ledger** (`WorkerFrictionLedger`): `record` → `POST /friction/record {ledgerKey, record}` (upsert by run id, so a retried write is idempotent; 400 on a malformed/oversized record — the bot logs it), `recent` → `POST /friction/recent {ledgerKey, limit?, sinceMs?}` (records shape-checked on the way back; any failure throws → the friction command replies ⚠️). `buildFrictionLedger` (startup): `selfImprovement.worker.baseUrl` + its bearer (`tokenEnv`, default `MEMORY_TOKEN`) → Worker ledger keyed `friction:<selfImprovement.repo>`; otherwise the file ledger with a warning naming the path (and the missing env var, when a worker was configured). Runs are recorded whether or not `selfImprovement` is configured.
2. **Signatures.** Each finding maps to a stable key `<kind>:<signature>`. Tool findings are keyed **shell-aware**, because real agents chain the same work differently every run (`cd /tmp/ws/repo && npm ci --silent 2>&1 | tail -2 && …` vs `cd ~/switchboard && npm ci --silent >/dev/null 2>&1; (npm test …)` — the first real capture proved an exact-command key never recurs): the analyzer's label prefix and the ` → result` tail are dropped, the command is split into shell segments (`&&`, `||`, `;`, `|`), and each segment reduces to its `program [subcommand [script]]` head (`npm ci`, `git checkout`, `npm run typecheck`, `npx vitest`) with navigation/echo/pipe-filter programs (`cd`, `echo`, `tail`, `grep`, …), redirections, env assignments, wrappers (`sudo`), quoted strings, and volatile tokens (URLs → `<url>`, hashes → `<sha>`, numbers → `<n>`) removed; the ordered, de-duplicated heads (≤4) form the signature (`slow_tool:git checkout, npm test`). `setup_install` keys on the install segment alone plus the flags that change what is installed (`pnpm install --frozen-lockfile`; `--silent`/`--no-audit`-style flags dropped), so every `npm ci` run is one pattern. An unknown-tool failure (tool misuse) keys on the tool name. Note findings key on their kind, never their free text: `budget_hit:time|turns`, `wrap_up:wrap_up`, `infra_failure:sandbox_dead`, `infra_failure:mid-tool <cmd>`, `infra_failure:<cmd>`.
3. **Clustering.** A pattern is a key seen in ≥ `minRuns` **distinct** runs (default 2) — a finding repeated within one run counts once toward recurrence (recurring means a process problem, not one bad run) but every occurrence is counted and its time summed. Ranking: distinct runs ↓, peak severity ↓, attributed time ↓, key — a total order, so the output is deterministic. Each pattern keeps up to 5 examples, most recent first, each anchored to its run. `long_run`: among runs with `runMs`, those ≥ max(2× median, 10 min) are outliers, grouped per agent (`long_run:<agent>`); a fleet where every run is long has no outliers.
4. **Proposals.** The top `top` patterns (default 3) become issue proposals: title `[friction] <kind> recurs in N of M runs: <signature>` (≤120 chars), body = the dedupe marker `<!-- switchboard-friction-pattern: <key> -->`, a "proposal for a human to triage" preamble linking #84, **Pattern** (kind, signature, recurrence with share, occurrences, attributed time, peak severity), **Evidence** (a table of the example runs: run id + label, finish time, the redacted finding, its time; plus the remaining run ids), **Suggested fix** (kind-specific and sharpened by the evidence — e.g. a failing `--frozen-lockfile` install → regenerate the lockfile / document the install command / onboard as a resident; `command not found` → add to the sandbox image; unknown tool → align the agent's toolset; `budget_hit:turns` → `maxTurns` or batch calls; `sandbox_dead` → container sizing), and **Provenance**. One label, `selfImprovement.label` (default `self-improvement`), created in the repo when missing.
5. **Dedupe.** Open issues carrying the label are listed (PRs excluded, paginated) **plus the 30 newest open issues unfiltered** — GitHub's label-filtered list can lag creation by a few seconds, which would let an immediate re-run refile a pattern — and matched by **marker**, never title (titles change with run counts) or label. A matched proposal is reported as already open and not refiled; a closed proposal's pattern can be proposed again. When no pattern recurs, GitHub is never consulted.
6. **Filing and failure.** Fresh proposals are filed one by one through the `IssueTracker` (REST, App installation token — App `issues:write`; never `gh`; bodies clipped to GitHub's limit). A create failure is reported per proposal and later proposals still file. `dryRun` computes and reports everything (including what would be filed) and files nothing; it still lists open issues for the dedupe. With **no repo** at all (the CLI without `--repo`) the pass is a pure dry run that never consults GitHub — no credential needed.
7. **Triggers.** (a) The command registry ([command-registry.md](command-registry.md) item 17): `friction.report {sinceMs?, limit?, minRuns?}` (`friction:read`, chat gate `open`) shows the ranked recurring patterns; `friction.propose {dryRun?, top?, minRuns?, repo?}` (`friction:write`, chat gate `repoManager` — the same fail-closed rule as repo management: `permissions.repoManagement`, admins only when unset) files. Both are one registration reachable on every surface with the same JSON (`SelfImprovementReport`) and the same text (`formatSelfImprovementReport`): chat — inline, channel-agnostic, never a model turn — as `friction report [--since-ms <n>] [--limit <n>] [--min-runs <n>]` / `friction propose [--dry-run] [--top <n>] [--min-runs <n>] [--repo owner/name]` (the registry's derived grammar; an unknown flag or a non-positive number is a named usage reply that never echoes the value; the refusal is the shared 🚫 wording and an unset `selfImprovement.repo` is a hint); HTTP `GET /api/friction.report?limit=5` / `POST /api/friction.propose`; MCP `friction_report` / `friction_propose`; CLI `npx tsx src/cli.ts friction report --json`. Machine callers hold no friction scope implicitly. A channel-pinned caller analyzes only its channel's runs (the run-store ledger filters; bare-record ledgers yield nothing under a pin). (b) CLI, no bot process: `npx tsx src/cli.ts friction propose --dry-run [--top N] [--min-runs N] [--repo owner/name]` — the same registration over the same ledger/run store the bot reads (a fresh process reads persisted history), and `npx tsx src/cli.ts friction analyze <run.jsonl | capture.sse> [--slow-ms n] [--in-progress]` for the read-only diagnosis of ONE saved stream ([run-friction.md](run-friction.md) item 6). The former standalone `frictionProposeCli` — proposing over saved capture files auto-detected per file — is retired (phase 4b, KTD29): recent runs live in the run store, not in files on a laptop. (c) **Scheduled — as an ordinary run ([#244](https://github.com/coreplanelabs/switchboard/issues/244))**: the `self-improvement` entry of the schedule registry ([`src/core/schedules.ts`](../src/core/schedules.ts), Mondays 14:00 UTC, `0 14 * * 1`) is fired by the Worker shim (`deploy/cloudflare/worker.ts`) as a `POST /ingress` of the text `friction propose` with the `cron` identity's bearer — the `{"subject":"cron","channel":"cron"}` entry of `SWITCHBOARD_INGRESS_TOKENS`; **no bespoke route and no dedicated secret**. The dispatcher sees `http:cron` and answers it exactly like chat, so the firing is a run: a registry record (`input` → `answer`) on `/runs`, a receipt `{run:{id,status}}` in the ingress response, and a firing record (fired-at, run id, outcome) on the state Worker's `ScheduleDO` that the `/runs` "Scheduled" panel shows ([live-view.md](live-view.md) item 14). **The `cron` identity must be granted `permissions.repoManagement`** — `friction propose` is behind that fail-closed gate, so without the grant the firing runs and finishes `failed` with the 🚫 reply as its answer (visible on the panel), and nothing is filed. Fail-closed on identity: no `cron` entry in the token map → the shim sends nothing and records the firing as `misconfigured`; ingress 401/503/5xx → `ingress-error`. The per-minute keep-alive cron is the registry's `internal` `healthz` schedule: it never becomes a run and is not shown on the panel. The issues are the notification — no channel post.

# Agent: coding

Takes a task from Slack, scopes fast, implements the change in its sandbox, and ships a PR. Its unit of delivery is a PR URL, not prose.

- **Code**: `src/agents/registry.ts` (`CODING_SYSTEM`; resident-path variant `CODING_SYSTEM_RESIDENT`)
- **Docs**: [README — Agents](../README.md#agents)
- **Budgets**: 60 turns / 45 min / 64k tokens · no built-in effort — set it per deployment/channel/user/thread/message through the config layers ([routing-and-config.md](routing-and-config.md) item 2; e.g. `config set channel efforts.coding=medium` — the wall clock is the real budget, and a 31-min live run at the model's default effort spent 97 % of it thinking between one-line greps) · toolset `full`
- **Receipts**: https://github.com/coreplanelabs/switchboard/issues/222

## Behavior

1. **Scope first, hard rule (≤5 tool calls)**: identify the target repo and surface; genuinely ambiguous → ask ONE question and stop the turn. Never clones multiple repos or maps the org to avoid asking.
2. Workflow: get the repo in place (cold path: clone, ≤1 repo/task; resident path: the warm worktree is already attached — see 7) → branch → implement matching surrounding style → run quick tests/linters if present → commit → push → open a PR (`gh pr create` on the cold path; GitHub REST API on the resident path) with a templated body (see 3).
3. **Templated PR description by default**: every PR the agent opens is described from a fixed template (`PR_DESCRIPTION_TEMPLATE` in [`registry.ts`](../src/agents/registry.ts)) — the user never has to ask for review guidance in the description. Right after implementing, the agent understands the change better than anyone, so it brings that context forward. Sections, each a `##` heading (the TL;DR included — no headingless opening paragraph): **TL;DR** (two sentences for a naive reader), **What & why** (linked to the triggering issue/request), **Tour** (below), **Decisions** (alternatives/trade-offs), **Risks & implications** (blast radius, migration/rollout/compat, or "none" and why), **Validation** (what was tested + actual results, and how the reviewer verifies it). Rules baked into the prompt: default for EVERY PR (not on request); prose unwrapped (no hard line breaks); the triggering issue/request always hyperlinked; validation states exactly what was run, never fabricated; concise, not padded. The resident variant folds its diff digest into this body.
   - **The Tour** (supersedes the prose **Changes** and **How to review** sections): a guided walkthrough of the change in reading order (entry point → core logic → tests → docs). Each step is reader-first: a `### N. <what this change is>` heading, one short paragraph on what the hunk does and why it matters, an optional bold **Look for:** line naming what to scrutinize, and *last* the line permalink to the hunk at the PR head — `https://github.com/<owner>/<repo>/blob/<40-char head sha>/<path>#L<from>-L<to>`, which GitHub renders as embedded code inside the body — so the reader knows what they are looking at before the code appears; anchors stay ≲25 lines (a big hunk becomes two steps); markdown structure (headings, bold labels, lists) over prose. A final `### N. Remaining changes` step lists every touched file no step covered. The author writes it right after implementing, so it costs no extra model call and carries the most context anyone has. Because a permalink pins a sha, the Tour is **regenerated on every push that changes the head** (amend, rebase, force-push, review fix-ups), in the same step as the push — stale anchors are a lie about the PR. Modeled on Ramp Inspect's hunk-anchored Tour; the rendering is GitHub's own.
4. Reads task context itself (`gh issue view`, `gh pr view`) — requires the GitHub App's Issues permission (see [execution.md](execution.md) §5).
5. Maintains the status-card checklist (outcomes, never commands; nothing pre-marked).
6. Reports faithfully: failing tests and skipped steps are stated plainly; final message leads with outcome + PR link.
7. **Resident-path variant** ([resident-repos.md](resident-repos.md) §31): when the run lands in a resident repo environment, the dispatcher swaps in `CODING_SYSTEM_RESIDENT` via `RunOptions.system` (the AgentDef is never mutated). It replaces scope-first/clone with: the workspace is a READY git worktree on the thread's bound branch, deps installed, build warm — no cloning, no installing, no repo discovery. `gh` is not in the resident image: push with git, open the PR via the GitHub REST API using the token in `.git/github-credentials`; if credentials aren't provisioned, push and report the branch compare URL honestly instead of claiming a PR.

## Roadmap (gaps)

- `[gap]` ([#332](https://github.com/coreplanelabs/switchboard/pull/332) — the model + GitHub renderer; [pr-description.md](pr-description.md)) **The PR description as data, rendered per surface.** The template above makes the agent write GitHub markdown directly; the same content (TL;DR, what & why, Tour steps with their anchors, decisions, risks, validation criteria + receipts) must also render in the run page's review panel and in whatever replaces GitHub later, without a second copy of the logic. Target: a typed `PrDescription` the coding agent submits through a structured tool (`submit_pr_description`, validated like `submit_verdict`), stored as a run artifact, with one renderer per surface — `renderPrDescriptionMarkdown` for the GitHub body (the system opens/edits the PR from it, and re-renders the Tour anchors at the new head on every push so the repush rule becomes code, not prompt) and the panel renderer over the same object. Until then the markdown template is the contract and this item is the debt.

# Switchboard — agent guide

Agent gateway: messages arrive over a channel, get routed to an agent, which runs on an inference provider and executes tools through an executor. Slack is one channel, not the architecture. Engineering docs and diagrams: [README.md](README.md) — keep both in sync when you change architecture. Human-facing docs (tutorials/how-to/reference/explanation, for people who use, watch, or run Switchboard rather than build it): [docs/README.md](docs/README.md) — update these too when a change affects what a Slack user, a dashboard viewer, or an operator sees or does.

## Invariants (do not break)

1. **The core dispatcher never imports a platform SDK.** All Slack/Bolt code lives in `src/channels/slack.ts`. If you need something platform-specific in the core, extend `ChannelIO`/`IncomingMessage` instead.
2. **Every boundary is an interface with ≥2 implementations.** Channel (`ChannelIO`), provider (`Provider`), executor (`Executor`), agent (`AgentDef` data). New capability = new implementation behind the existing seam, not a special case in the core.
3. **Permission gates run against the *resolved* agent, post-resolution** (`dispatch()` in `src/core/dispatcher.ts`). Never add a code path that runs an agent without passing `config.canRunAgent`.
   *Corollary — registry commands never start an agent run.* Anything that runs an agent goes through `dispatch()`; a `CommandRegistry` handler (`src/core/commands/*`) that reaches for the runner is a bug, and the command scope/gate vocabulary deliberately has no class that could authorize one (#157 KTD16) — `<group>:exec` (`repo test|build`) runs a repo's ONBOARDED command with zero model turns, which is an operation, not an agent run (KTD30). The CLI's `ask` and MCP's `dispatch` are channel built-ins beside the derived commands, never registrations (KTD22).
4. **IDs are platform-namespaced**: `slack:C0123` (channel scope), `slack:U0123` (user scope), `slack:C0123:<ts>` (thread key). Config scopes and permissions key on these. New adapters must namespace with their own prefix.
5. **Tools never touch the host directly** — they call `ctx.executor`. `LocalExecutor` is the only place local process/fs access is allowed for tool execution. Resident environments keep this invariant by being remote: `ResidentExecutor` speaks HTTPS to the resident Worker, and even the dispatcher's repo/PR resolution uses the GitHub REST API — never a `gh` shell-out from the bot process.
6. **State must survive restarts**: conversation context rebuilds from channel history; workspaces/sandboxes are recreatable (repos re-clone). Never introduce in-memory state a restart would lose silently.
7. **Model refs are `<provider>/<model>` strings** resolved through config layers (request directive > thread > user > channel > defaults). Never hardcode a model in an agent or the core. **Effort (`low | medium | high`, `src/effort.ts`) rides the same layers** (`effort:` directive, `effort` / `efforts.<agent>` per scope, `defaults.efforts`); an agent definition's `effort` is only the floor under them, never the setting.

## Feature specs — the behavioral contract (`features/`)

[`features/`](features/README.md) is the versioned behavioral contract: one file per feature stating expected behavior, validation criteria, and how each criterion is proven — `[unit]` (a named test), `[agent]` (written instructions an agent runs against the live deployment), or `[gap]` (known-unproven, a work item). Because the files live in the repo, **any git SHA ties the code to the validation criteria that described it at that moment** — agents can reference behavior for any point in history.

Non-negotiable discipline:

1. **Same-PR updates.** Any PR that changes behavior updates the matching feature file in that PR (criteria added/edited/pruned). A feature file describing removed code is a bug.
2. **TDD from the spec.** New behavior: write/extend the feature file's criteria → write failing tests → implement to green. Prefer unit tests; use `[agent]` instructions only where a unit test genuinely can't prove it, and make those instructions literally executable (exact messages/commands + expected observable result).
3. **Receipts live in the tracker, never in the spec.** Each feature file links its receipts issue on the [Golden Product project](https://github.com/orgs/coreplanelabs/projects/1); a live validation is a comment there (criterion, date, deploy SHA, evidence link). Feature files carry no dates, run links, incident narratives, or "validated on …" notes — those are tracking, they change on every prod check, and in VCS they conflict with parallel work. Gaps, incidents, and test campaigns are issues on the same project (e.g. [#81](https://github.com/coreplanelabs/switchboard/issues/81) for the Claude Tag parity matrix).
4. Milestones live in `features/README.md`; current: [milestone 1 — agents work as designed, obviously better than Claude Tag](features/milestone-1-vs-claude-tag.md).

## Working on this repo

- **Node ≥22 required:** `undici@8` calls `webidl.util.markAsUncloneable`, which only exists on Node 22+ — under Node 20 the test suite fails at load (`src/core/dispatcher.test.ts`). Enforced via `engines` in `package.json` (and the `deploy/cloudflare*/` packages) and `.nvmrc`; Dockerfile and CI already run Node 22.
- **Verify:** `npm run typecheck` and `npm test` (vitest, `src/**/*.test.ts`) must both pass. The web app has its own pass: `npm run typecheck && npm test` in `web/` (its tests are the rendering proof layer), and `npm run build` there produces the `web/dist` that `src/index.ts` loads — `npx tsx scripts/web-preview.ts` previews the built app over fixtures. Tests are the proof layer for feature specs — see the section above. For exploratory smoke tests, `npx tsx src/cli.ts ask "…"` drives the full pipeline and `npx tsx src/cli.ts runs list --status all` the command registry.
- **Local run without Slack:** `npx tsx src/cli.ts ask "agent:review ..."` — full pipeline including executor selection.
- **`execution.type: e2b` paths need `E2B_API_KEY`** and have not been live-tested until someone runs one CLI request against a real sandbox.
- **Trust model:** agent `bash` executes model-generated commands. With `execution.type: local` the boundary is the container the bot runs in; with `e2b` it's the per-thread sandbox. Never put `GH_TOKEN` or other write-capable credentials on the bot host when `e2b` is enabled — they belong in the sandbox env only (`src/execution/factory.ts`).
- **Docs discipline:** architecture changes update README diagrams *and* this file. Deployment changes update the Deployment section + `deploy/`.
- **Polylane topology discipline:** this repo is mapped into the [coreplanelabs Polylane workspace](https://console.polylane.com/coreplanelabs) — the context graph behind the "Polylane production impact" PR check and blast-radius/impact queries, so a stale graph under-reports what a change can break. Cloud resources (Workers, DO namespaces, domains) sync automatically; **cross-Worker call paths do not** — they are asserted logical edges. A PR that adds/removes a Worker, a Durable Object, or a call path between Workers (or changes what a path carries) asserts the delta in the same change cycle: `polylane api call cloud_infra.edges.post --body-file <edge.json>` (schema via `polylane api describe cloud_infra.edges.post`; an edge is `{workspaceId, source, target, relationship, properties}` with each node keyed `{id: "<script name>", provider: "cloudflare", account: "3c7b28f23cc93f09e77bb0a9ffcb7e6f", region: "earth", type: "cf.workers.script"}`; put the routes + auth bearer in `properties`), and a removed path is deleted with `cloud_infra.edges.delete`. Asserted edges as of 2026-08-30: `switchboard` → {`switchboard-memory`, `switchboard-resident`, `switchboard-sandbox`}, all `invokes`. Verify: `polylane service graph "cloudflare/3c7b28f23cc93f09e77bb0a9ffcb7e6f/earth/cf.workers.script/switchboard" --direction outbound`. Needs the signed-in `polylane` CLI (a scoped MCP credential may lack `cloud_infra:read`; the CLI user credential works).
- **Bot deploys are preflighted too:** `npm run deploy` in `deploy/cloudflare/` runs its own `preflight.mjs` first and refuses while `GET /healthz` reports runs in flight or `draining: true`, or while the `switchboard-switchboardserver` container application is mid-rollout (`wrangler containers list --json` state not `active`/`ready`). A rollout SIGTERMs the container and the bot drains for up to 15 min, so ONE deploy over a run is fine — but a second deploy on a draining instance kills it at once (incident 2026-08-29 23:51Z: a review died at 153 s, card frozen, run gone from `/runs`). Needs no token (`/healthz` is public); fails closed on an unreachable bot, a wrangler failure, or a pre-item-8 Worker (bare `ok` body); `SWITCHBOARD_DEPLOY_FORCE=1 npm run deploy` bypasses with a warning. Live cards show `⏸ deploy in progress …` during a drain, and the next container's reconnect sweep closes any card a killed process left spinning as `❌ interrupted`. The drain closes the Slack socket at once and Cloudflare boots the replacement only after exit, so a deploy during an in-flight run **blacks Slack out for the run's remaining duration** (7.5 min observed); mentions posted in that gap are recovered by the reconnect catch-up, which covers up to its 30-min window (`DRAIN_DEADLINE_MS` + cold start ≤ window, `src/core/drain.ts`, #272) — prefer deploying at a quiet moment. `/healthz` reports `drainDeadlineMs` and, while draining, `drainStartedAt`. Details: `features/slack-channel.md` items 7–8.
- **Deploy order is codified — use `npx tsx src/cli.ts deploy all`** (`deploy plan` shows what it would do): memory (state Worker, DO migrations first) → bot → resident → sandbox, from a clean checkout at `origin/main`, with the ambient `CLOUDFLARE_*` env stripped and the account asserted (`coreplane-infra`). Preflight refusals are waited out (retry every 60 s, ≤30 min, a heartbeat per poll), never forced unless `--force` is passed explicitly; the bot step is done only when the NEW container is live (`/healthz` not draining + `build.commit` == the deployed commit). Never deploy the four Workers by hand in parallel — the bot must not write to a Durable Object whose migration has not landed. Plan (`src/deploy/plan.ts`) and live decision (`src/deploy/liveGate.ts`) are pure and unit-tested; runner is `src/deploy/run.ts` behind the `deploy.all` command. The plan's check line reports which deploy dirs lack `node_modules` (the runner `npm ci`s them first) — it needs no `config/config.yaml`, so it runs from any worktree. **Rotating any bot secret requires a container restart**: `wrangler secret put` creates a new Worker version but the running container keeps the env it started with (a rotated `MEMORY_TOKEN` 401'd for ~2 h on 2026-08-30). Rotation runbook: `npm run secrets` (or `wrangler secret put`) in `deploy/cloudflare/`, then `npm run cli -- deploy restart` — no image build: the Worker's `POST /admin/restart` (bearer `$SWITCHBOARD_DEPLOY_TOKEN`, a `SWITCHBOARD_INGRESS_TOKENS` identity with `deploy:write`) makes the Container DO `stop()` the bot (SIGTERM → drain), and the next request (keep-alive cron, or the CLI's poll) starts it on the current env; refused while runs are in flight unless `--force`; done once `/healthz` reports a later `startedAt` (~30 s idle). `deploy all --only bot` also works but rebuilds the image for nothing.
- **Resident deploys are preflighted:** `npm run deploy` in `deploy/cloudflare-resident/` runs `preflight.mjs` first and refuses while any resident has work in flight (a Worker deploy swaps the DO isolates and kills running threads). It needs a resident bearer in the env (`RESIDENT_ADMIN_TOKEN`, or operator/read) and fails closed without one or when the Worker is unreachable; `RESIDENT_DEPLOY_FORCE=1 npm run deploy` bypasses with a warning. Details: `features/resident-repos.md` item 44.

## Current state / known gaps

- Cores and parallelism, as of this audit: every container here is one Node process on a fractional/single vCPU — the bot on `basic` (¼ vCPU / 1 GiB, `max_instances: 1`), the resident on 1 vCPU. Node is single-threaded, so "using the cores" means (a) never serializing independent I/O and (b) not oversubscribing the one core with worker pools. What is in place: the runner executes side-effect-free tools from one turn concurrently and the Anthropic adapter caches the prompt prefix (`features/run-loop.md` items 9–10); the dispatcher overlaps memory retrieval with repo resolution + executor attach, coalesces status-card edits, and sends the answer before the resident `/detach`; the Slack adapter fetches a follow-up's thread once, downloads a message's attachments concurrently, and scans catch-up channels with bounded fan-out; the HTTP server listens before the Slack handshake; SSE frames are serialized once per event and resumable (`id:`/`Last-Event-ID`). The resident image sets `CI=1`, `VITEST_MAX_WORKERS/THREADS/FORKS=1`, `UV_THREADPOOL_SIZE=2`, `NODE_OPTIONS=--max-old-space-size=1536` as environment defaults so a repo's test runner sizes its pool for the ONE vCPU it has, not the host's core count (a repo's own config still wins). Grow the bot from `basic` only on evidence — the event-loop CPU it burns is redaction regexes over tool output and JSON serialization, both now paid once per event; nothing here measured it CPU-bound.
- Container sizing: thread-sandbox Worker `standard-3` (2 vCPU / 8 GiB — lives only for one run, so cents; observed peak 75% CPU / 1.4 GiB, so do not drop to standard-2), resident Worker custom `1 vCPU / 4 GiB / 8 GB` (effectively always-on; Cloudflare bills vCPU on active use only and memory/disk on provisioned size while awake, so memory is the 24/7 cost — ~$26/mo per resident at 4 GiB — and vCPU is free until used; `standard-1` was outgrown by a resident pinned at 100% of ½ vCPU with 2.2 GiB in use, and `basic` (1 GiB) dies running switchboard's vitest suite). Grow resident memory only on real OOMs. The resident pool is 16 users and runs release theirs via `/detach` on finish — `features/resident-repos.md` item 16a; the hourly sweep releases clean idle trees, a deploy that grows the pool self-applies via `reconcileImage`, and unused residents park their refresh so the container sleeps (item 16b). Residency GC (#50, items 45–46): every refresh cycle reclaims worktrees whose ref is finished (branch pruned from the mirror, or PR merged/closed — a poll, since the GitHub App has webhooks off), and an over-cap `repo onboard … --evict-coldest` offboards the coldest eligible warm resident instead of 429 (admin opt-in per request, default off). `RESIDENT_CAP` is 6 (the team's concurrent-repo count); to exercise the over-cap path on prod without touching the constant, the admin debug op `set-test-overrides` lowers the effective cap/floor for the current build only (item 49) — never raise it that way, it can't.

- The Cloudflare execution path is live: the resident Worker (`deploy/cloudflare-resident/`) runs at switchboard-resident.coreplanelabs.dev with public and private repos onboarded; its attach/exec/read/write plane and the onboard/offboard/rebuild lifecycle are proven — receipts on the `features/resident-repos.md` receipts issue.
- `GITHUB_APP_*` secrets are set on the resident Worker (a second copy of the bot's App credential — rotate both). Onboard's installation-membership check runs for real: private repos clone via minted installation tokens, and a repo outside the installation is refused with `not-in-installation: …` and nothing created. Still `[gap]` in `features/resident-repos.md` ([#262](https://github.com/coreplanelabs/switchboard/issues/262)): the cross-repo token-scope proof and a push from a resident thread.
- The E2B executor path is typechecked but not exercised against a live sandbox.
- The Slack app has DM support wired but the recommended rollout keeps `im:*` scopes off initially.
- No token/cost accounting per request yet — the self-improvement proposer (#84) uses `long_run` outliers (≥2× the median run time) as the cost-spike proxy until there is.
- The friction ledger (`features/self-improvement.md`) is durable in prod (`FrictionDO` on the state Worker, `selfImprovement.worker`); without that config it falls back to `data/friction.jsonl` on the host disk (ephemeral on Cloudflare Containers) and warns at startup.

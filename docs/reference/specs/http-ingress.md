# HTTP ingress: authenticated channel adapter #3

The core is channel-agnostic: a channel is only a transport that turns an inbound request into an `IncomingMessage`, calls the core `dispatch()`, and provides a `ChannelIO` to reply through. Slack (adapter #1) and the CLI (adapter #2) already prove this; HTTP is adapter #3 — the same request from an HTTP client reaches the same agents under the same permissions, satisfying the AGENTS.md ≥2-implementations invariant for the channel boundary. MCP ingress is a separate follow-up.

HTTP is single-shot request/response, unlike Slack's long-lived threads. The endpoint is our own service (not behind a platform's auth), so it owns its security in-band: bearer-token auth, **fail-closed**, constant-time compares, identity mapped from the token into the namespaced `IncomingMessage` so the existing `canRunAgent`/`canUseRepo` gates apply unchanged.

- **Code**: `src/channels/http.ts` (`authenticate` pure auth, `handleIngressRequest` transport gating, `HttpIO` single-shot `ChannelIO`, `readBody` size cap, `createIngressHandler` node:http wrapper, `parseIngressTokens` env→config); `src/index.ts` (wires `POST /ingress` into the existing http server alongside the health probe; the coordinator routes beside the other `/admin/*` handlers); `src/channels/adminCoordinator.ts` (item 9: the coordinator's steps behind the `coordinator` bearer — `handleCoordinatorRequest` pure over a parsed request, `createAdminCoordinatorHandler` the node:http adapter); `src/core/coordinator/instancesRoute.ts` (item 9: the pure halves of the shim's instance route, both directions) and `src/core/coordinator/contract.ts` (the names, patterns, paths and key); `src/core/coordinator/briefs.ts` (item 9: the child's turn composed bot-side from a spawn's brief); `src/core/coordinator/driver.ts` (item 9: the plan runner's driver — the Workflow's `run()` body over a structural step runner and a bot client, node-free); `deploy/cloudflare/coordinator.ts` (item 9: the `ShipCoordinator` Workflow entrypoint over a narrowed env, binding the platform's step and the container to the driver), `deploy/cloudflare/shared.ts` (the container instance and internal origin the entry and the Workflow both address) and `deploy/cloudflare/worker.ts` (`POST /admin/coordinator/instances`, the re-export the binding resolves); `deploy/cloudflare/wrangler.template.jsonc` (the `SHIP_COORDINATOR` binding).

## Behavior

1. **Pure transport, same core.** `POST /ingress` with a JSON body `{ text, channel?, thread?, history? }` becomes an `IncomingMessage` and is handed to the unchanged `dispatch(deps, msg, io)` — no dispatcher, runner, or permission change. Identities are platform-namespaced (invariant 4), mirroring Slack: `userId` = `http:<subject>`, `channelId` = `http:<channel|default>`, `threadKey` = `http:<channel>:<thread|default>`. Once the caller is identified and the body parsed, the adapter starts the request's root and stamps the message `receivedAt`, handing both to `dispatch(deps, msg, io, { trace })` — the `DispatchFn` seam's optional fourth argument ([tracing.md](tracing.md) item 18); the async path's root ends when the background dispatch does.
2. **Single-shot `ChannelIO`.** `reply()` collects text and the collected text is the HTTP response body (`{ reply }`); `status()` is an honest no-op handle (no live surface to edit in one shot); `history()` replays the optional `history` array from the body, else `[]`. **Run receipt:** when the core created a run for the request — an agent run, or an inline command run such as `friction propose` — the core calls `ChannelIO.runFinished({ id, status })` once the run is finished in the registry, and the response carries it as `run: { id, status }` (`status` ∈ `completed | failed | stopped_soft | stopped_hard`). The receipt names the run (`/runs/<id>`), it never carries the view token. A request that produced no run (a config reply) has no `run` field. This is how the Worker shim learns which run a scheduled firing became.
3. **Bearer auth, fail-closed.** `authenticate(headers, config)` requires `Authorization: Bearer <token>`; a missing, malformed, or unknown token yields `null` → `401`. If **no tokens are configured** the endpoint is **disabled** → `503 {error:"disabled"}`, never open. The map is `token -> { subject, channel?, scopes? }`; the mapped subject becomes the `userId`, so a token can only ever act as its assigned identity and existing gates apply unchanged. `scopes` (default `["dispatch"]` = this endpoint only) additionally names the command-registry actions the token holds — they are the grants of the `http:<subject>` (and `mcp:<subject>`) actor, e.g. `["dispatch","runs:read"]`, and the policy table decides every registry command from them on every surface, a text command sent through this endpoint included ([authorization.md](authorization.md) item 9, [command-registry.md](command-registry.md) item 6); a malformed `scopes` skips the entry rather than widening it. **Starting a run requires the `dispatch` scope**: a token whose `scopes` omit it (a registry-only credential such as `["runs:read"]`) is refused at this endpoint with `403 {error:"forbidden", code:"unauthorized"}` — decided from the headers (`requireDispatchScope`, before the body is read) and `dispatch()` is never called. A token may pin a `channel` that overrides the body's channel (locks the config scope).
4. **Constant-time compares, no token logging.** Tokens are compared with `crypto.timingSafeEqual` over equal-length buffers (length guarded first); the loop checks every configured token without short-circuiting, so neither the presence nor the position of a match is a timing oracle. Token material is never logged.
5. **Input hardening.** The body is size-capped at read time (~1 MB, `413` before it is fully buffered); invalid JSON, a non-object body, a missing/blank `text`, or a malformed `history` entry return `400`; a non-POST method returns `405`. Malformed env token config is treated as "no tokens" (disabled), never as open.
6. **Authorization precedes body-buffering.** Method (405), the disabled check (503), and bearer auth (401) are decided from headers alone (`authorizeRequest`) *before* the body is read, so an unauthorized/wrong-method/disabled caller never buffers a body — shrinking the pre-auth request surface.
7. **Async mode (`"async": true`).** A machine caller (e.g. an automation dispatching a coding brief) that only needs the acknowledgement can add `"async": true` to the body: validation and authorization are **exactly** the sync path's (the async branch is only reached after `authorizeRequest`, `requireDispatchScope`, and `parseBody`; a non-boolean `async` is a `400`, and the token's scopes and channel pin apply unchanged), then `dispatch()` is *started, not awaited*, and the response is `202 Accepted` with `{ runId, runUrl, threadKey }` the moment the core has created the run in the registry (the new optional `ChannelIO.runStarted({ id })` hook, fired at every `registry.create` site). `runUrl` is `<PUBLIC_BASE_URL>/runs/<id>` (path-only when unset). The run continues to completion in the background: its reply text goes to the run record — never to any HTTP response — and its history record lands as usual, including for failed and hard-stopped runs (the dispatcher's own finally owns the record). The shutdown drain awaits async runs exactly like synchronous ones because `dispatch()` increments the in-flight counter on its first line, before the `202` is written. An async request the core answers *without* creating a run (a config reply) falls back to the sync `200 { reply }` shape rather than hanging. Without `async` (or with `"async": false`) the behavior is byte-identical to before.
8. **Wiring keeps health working.** The `PORT` server routes `/ingress` to the ingress handler and every other path to the existing `ok` health probe. With no tokens configured the startup log says ingress is DISABLED.
9. **The coordinator's steps — the same token map, a dedicated bearer, one policy action** ([record 0029](../../decisions/0029-durable-objects-store-workflows-schedule.md), [record 0031](../../decisions/0031-the-coordinator-runs-a-plan-not-a-pull-request.md); [run-history.md](run-history.md) items 47–49; [authorization.md](authorization.md) item 2). A ship coordinator is a Workflow instance in the bot's shim Worker (`ShipCoordinator`, `deploy/cloudflare/coordinator.ts`, re-exported by `worker.ts` for the shim's own same-script `SHIP_COORDINATOR` binding; `run()` is the plan runner's driver, below) that holds no model, Slack or GitHub credential: its env is narrowed by type to the container binding and the token map, and a source scan holds it to that. Every fact and every child is the bot's, behind routes the shim forwards to the container like every `/admin/*` path (`src/channels/adminCoordinator.ts`; the `authorize` question, `spawn`, `read-record`, `pr-check`, and the plan runner's own `plan`, `unit-start`, `branch`, `round`, `unit-end`, `merge` and `finish`), plus one the shim answers itself, `POST /admin/coordinator/instances` (`{ id, params? }` → `201 { ok, id, created }`; a taken id `409 duplicate_instance` with the existing instance's status; a create the engine refuses `502 create_failed`; the pure halves in `src/core/coordinator/instancesRoute.ts`). **The door** is one bearer: the `coordinator` entry of `SWITCHBOARD_INGRESS_TOKENS` (a name; `COORDINATOR_IDENTITY`), whose actor `http:coordinator` the policy table admits on `coordinator:step` — a `service` kind holding the grant — and nothing else does: no bearer `401`, a bearer without the grant `403` naming the grant, no token map `503`, on every route. The door is decided from the headers alone, in order — the step (`404` for an unknown one), the method (`405` for a non-POST), then the bearer — before a body is read, so a refused caller, an unknown step or a wrong method never buffers one (the ingress's own rule, item 6), and the bearer is looked at once per request (`decideCoordinatorDoor`, then `answerCoordinatorStep` over the body). The shim's instance route authenticates the bearer against the map it holds (an unknown bearer never touches the container), relays it to the bot's `POST /admin/coordinator/authorize`, and creates only on a `200 { ok, subject }`; any answer it cannot read is `503`, fail-closed. **`spawn`** `{ parentInstanceId, step, preset, budget?, prompt | brief, unit? }` never takes an actor from its caller: a `userId` or `channelId` in the body is ignored; the requester, channel, thread, repository and branch come from the parent ship record (run-history item 49 — an unknown instance is `404 unknown_instance`), the child's text is the message the requester would have typed (`agent:<preset> [budget:<n>] in <owner/name>: <prompt>`, item 20 of [routing-and-config.md](routing-and-config.md)), and the child is a `dispatch()` as that user into the unit's thread with `DispatchOptions.coordinator = { parentInstanceId, idempotencyKey: "<parentInstanceId>:<step>" }`, so the agent gate, the profile gate and the repository gates judge it with that person's grants — a gate's refusal answers `403` with the gate's own name (`agent_allowlist`, …) and what the thread was told; a preset the registry does not know, the `ship` preset (a child is a round, never a pipeline), an empty prompt, a budget under two minutes or a step with a colon are `400`. **Safe to retry**: before anything starts the route reads the thread — a live run on it carrying the same key (here, or on another generation's ledger row) answers `200 { runId, alreadySpawned: true }`; a live run without the key (another step's child, a person's run) answers `409 busy` naming it; a finished run in the thread carrying the key since the instance was created (the channel's finished runs paged newest first, up to the default retention's page count) answers `alreadySpawned` — so a retry that lands after a quick child ended never spawns a second one; and a run that takes the thread between that read and the claim is refused by admission as `coordinator_thread_live` ([thread-admission.md](thread-admission.md) item 8), which the route answers from the live run the same way. The route answers `200 { runId, threadKey }` the moment the child registers; a dispatch that ended with no run and no gate's name is `502 spawn_failed`; an instance whose channel no thread can be rebuilt on is `503 no_channel`. **A `brief` in place of a `prompt`** (`{ kind: contract | review | fix, unit, … }` — ids only: the unit, the pull request, the review run; a brief beside a prompt, of the wrong preset for its kind, or malformed is `400`) is composed into the child's turn by the bot itself (`src/core/coordinator/briefs.ts`): a contract brief is the unit's contract from the plan, exactly the specs the unit names and the rules file, read at the base ref, with the unit's board issue (`contractFromPlan`; a task unit's from the ship request read back from the thread, `contractFromTask`); a review brief is the review turn over the pull request and the head to pin, a re-review carrying the prior review run's findings and the fix run's dispositions from their records (`buildShipReviewTurn`); a fix brief is the fix turn from the review run's verdict and final words, answering exactly its finding ids (`buildShipFixTurn`, `DispatchOptions.fixRound`) — so no prompt text ever crosses from the Workflow, and the child's text names the unit's branch (`agent:<preset> [budget:<n>] in <owner/name> on branch <ref>: …`). A brief for a unit whose thread `unit-start` has not opened is `409 unit_not_started`, a passing condition the runner asks again on; one the bot cannot compose (the plan missing at the base, a run the history lacks) is `502 brief_failed`, a failed spawn the machine ends the unit on as an abort naming the reason — both stamped `at` like every answer. **`read-record`** `{ parentInstanceId, runId, unit? }` answers a run's facts — `id, finished, status?, agent?, startedAt, finishedAt?, activity?, parentInstanceId, idempotencyKey?, ownerGen?` and, once finished, `finalReply` (the last `answer` event's text) and the typed artifacts its record carries: `pr` (a coding child's `pr_opened`: number, url, created), `verdict` and `reviewHead` (a review child's; [run-history.md](run-history.md) items 2 and 3), `reviewPosted` (with `unit`: whether a review by the bot's own GitHub identity, pinned to that head and starting with the verdict's token, stands on the unit's pull request — absent, never guessed, when GitHub or the identity is silent), `dispositions` (a fix child's) and `handoff: true` when one was submitted — only for a run whose own `parentInstanceId` matches; a run of another instance, a run of none and an unknown id are `404 not_found` alike, byte-identical. **`pr-check`** `{ parentInstanceId, unit? }` runs `findOpenPrByHead` for the record's repository and branch (the unit's, with `unit`, and the pull request found is remembered on the unit's row) and answers `{ state: "none" }` or `{ state: "open", prNumber, url, headSha? }`; GitHub unreachable is `502 github_unavailable`. What every step reads is the one `RunsService` every surface reads and the App's GitHub identity — the same code paths a person's `runs get` and a coding run's PR post take. **The plan runner's own steps** — every answer carries `at`, the bot's clock, the only time the machine reads: `plan` `{ parentInstanceId }` answers the instance's `planId?`, `repo`, `base`, `caps`, the children's own budgets (`childMinutes`) and its unit rows ([run-history.md](run-history.md) items 49 and 50); `unit-start` `{ parentInstanceId, unit }` opens a plan unit's thread through the requesting thread's channel (`ChannelIO.openThread`, the lead naming the unit, its title, the requester, the run it comes from and the branch — `503 no_channel` without a channel that can, `502 thread_failed` on a failed open with the row unchanged), finds the open board issue titled by the unit id, writes the row (`threadKey`, `sourceUrl`, `issue`, `startedAt`) and answers `{ threadKey, branch, base, issue? }` — idempotent, a started unit answers its thread again; a task unit runs in the requesting thread; `branch` `{ parentInstanceId, unit? }` creates the unit's branch from the base on origin and answers `{ ok: true, branch, base }` or `{ ok: false, reason }`, never a throw; `round` `{ parentInstanceId, unit, index, agent, outcome }` appends the boundary (the `ship_round` vocabulary) to the row and redraws the card from the instance's card handle with one line per unit; `unit-end` `{ parentInstanceId, unit, ending: { kind, report }, pr? }` writes the ending and the pull request on the row, posts the report in the unit's thread and redraws the card; `finish` `{ parentInstanceId, outcome: completed | failed }` writes the parent's run record from the rows under the instance's run id (`run_meta`, one `ship_round` per boundary, the plan's summary as the answer), closes the card and tells the requesting thread the summary. An unknown instance or unit is `404`; a malformed boundary, ending or outcome is `400`. A unit's ending is its handoff to the board ([agent-ship.md](agent-ship.md) item 14's destination): when the row names a board issue, `unit-end` leaves the report there too under a line naming the unit, the ending and the pull request — a merge GitHub refused, a cap, a stop — best effort like the thread's. **`merge`** `{ parentInstanceId, unit, prNumber, headSha }` — [record 0031](../../decisions/0031-the-coordinator-runs-a-plan-not-a-pull-request.md)'s merge grant as a step: the runner's squash of a unit's pull request, executed only when every guard holds and refused by reason otherwise so a person decides, never a throw. In order: the bearer's actor must hold `plan:merge` ([authorization.md](authorization.md) item 2; decided here beside the door's `coordinator:step` — withdrawn, every merge is a person's, named as the refusal); the unit's branch must be a plan branch (`plan/<plan-id>/<unit-slug>`) of THIS instance's plan — a task string's ship branch, another shape or another plan's branch "waits for a person's merge"; the pull request, read from GitHub (`fetchPullRequestFacts`), must not be the release pull request (release-please's head branch or a `chore(main): release` title — refused by name, always a person's merge), must be open, head the unit's branch and stand at exactly the approved head (`sameCommit` against `headSha`, so a head that moved after the approval is refused naming both); the bot's own approving review must be pinned to that head (`fetchPullRequestReviews` by the App's identity, the body starting with the LGTM token — the review agent's verdict is the guard's carrier: the verification guard's `removed` class is a finding at minor, so an approval stands only where it passed); every check at the head must be green (`fetchCommitChecks`: a run that ended in anything but success, skipped or neutral is a refusal naming the runs; runs still queued or in progress, or none reported yet, answer `pending` for the machine's five-minute poll); then the squash — `mergePullRequest`, `PUT …/pulls/{n}/merge` with `merge_method: squash`, `sha` the approved head, `<title> (#n)` as the commit's title and an empty body, the shape the repository's own squash setting gives a person's merge — answers `{ outcome: "merged", sha }`, and GitHub's refusal (405 a conflict or a branch protection, 409 a head that moved between the check and the merge, 422) answers `refused` in GitHub's words. Every answer is `200 { ok: true, outcome: merged | pending | refused, … }`; GitHub unreachable — the facts, the reviews, the checks or the merge call — is `502 github_unavailable`, a passing condition; a malformed body is `400`, an unknown instance or unit `404`. No merge endpoint is reachable from any other code path: the in-process ship pipeline still never merges. **The Workflow's body** (`src/core/coordinator/driver.ts`: `runPlan(step, bot, instanceId)` over a structural step runner and a bot client, node-free and proven in plain Node; the shim's `coordinator.ts` binds the platform's step and the container — every bot call is `POST /admin/coordinator/<step>` through the container binding, its only fetch, presented with the `coordinator` bearer from the token map, the container instance and internal origin shared with the entry through `deploy/cloudflare/shared.ts`). The first step reads the plan back; units run one at a time in the plan's order once their in-play dependencies are done ([agent-ship.md](agent-ship.md) item 15's cursor), each as `unit-start`, then the machine's own steps under the machine's own names (`<unit>/branch`, `<unit>/<round>/<kind>`, `…/wait/<n>`, `…/read/<n>`, `…/pr-check`, `…/busy/<n>`) so a replay meets the same step, every round boundary told as `round` (`<unit>/note/<n>`) and the ending as `unit-end` (`<unit>/end`) in `renderUnitReport`'s words, then `finish`. Every `do` runs under one retry policy — twelve retries, two minutes apart, constant, so a bot deploy and its rollover fit inside — the spawn alone with a fifteen-minute timeout (an attach can take minutes); a call that throws is the platform's to retry and the driver never catches it. Every wait is `waitForEvent` typed `run finished:<runId>` ([run-history.md](run-history.md) item 47) for the child's clipped budget plus five minutes, and every wait — event or timeout alike — is confirmed by `read-record`. A step stores the bot's reply as the wire carried it (status and text); a bot answer is a JSON object stamped `at`, at any status (a gate's `403` and a `busy` `409` are answers), and anything else — the door's refusal, the shim's own error page, a container mid-restart — is not: the client throws it for the retry, a `401`/`403` the bot did not stamp as final since no retry changes a token map; the answers the bot itself calls passing (`github_unavailable`, `no_channel`, `thread_failed`, `unit_not_started`) are a retry, and an answer the runner cannot read fails the instance at once rather than twelve times over. The branch decides who merges: a plan branch runs under `merge: runner` — an approve is followed by the `merge` step at the approved head under `<unit>/merge/<n>`, `pending` sleeps the machine's poll and asks again, `merged` ends the unit `merged` and frees its dependents, whose coding children are briefed with the rebase onto the base that now carries it — and a task string's ship branch runs under `merge: person`, ending `merge_ready` without a merge asked. A unit that ended any other way blocks its dependents: each is `blocked`, told so as its own `unit-end` without a thread — naming the unit it waits on and how it ended (a refused merge, a cap, a person's merge-ready), or that the unit it waits on is blocked itself, whatever order the plan lists them in — and the plan finishes `failed`, `completed` only when every unit ended merged or merge-ready; a walk that threw past the retries asks `finish` as `failed`, best effort, and rethrows so the instance's status says what happened. What hands a request to the runner is [agent-ship.md](agent-ship.md) item 16.

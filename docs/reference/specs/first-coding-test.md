# First coding baseline

An operator can require a bounded baseline command before a coding model starts. Readiness still checks prerequisites; `firstAction` explicitly selects execution of the configured `testCommand`. The runner executes it in the attached coding checkout after patch preparation, before opening the harness. It never selects a command from the request or model output and never uses a disposable operation checkout.

| Automatic reconciliation of a possibly executed operation requires a shared typed backend operation lookup. This implementation deliberately holds unknown intent; it cannot recover an unreceived result automatically. | `[gap]` Backend operation lookup is not available. | The deployed resident and seeded paths preserve a completed receipt through controlled restore/recycle, and expose an exact operation/workspace/head receipt before the first model event. | `[gap]` Source tests do not prove live restore/recycle behavior. Obtain a controlled receipt under separate live-validation authorization after deployment. |

Command-scope enforcement beyond the explicit operator declaration is unproven; it requires a typed repository-operation policy, not parsing shell text.

Seeded receipt reuse needs a backend-owned workspace identity readback that includes the current dependency archive. Cached seed responses depend on that marker and cannot authorize even a first baseline attempt. Until authoritative readback exists, an operator must stop the held seeded run before authorizing a fresh attempt; the runner never trusts the workspace marker as a completion or current-identity receipt.

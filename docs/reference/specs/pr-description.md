# PR description as data

Everything a reader needs about a change — the PR title, a fixed-size **map** for the reader (the TL;DR, the why, at most seven linked **pointers**, the feedback wanted, the risk, one line of verification) and, collapsed under it, the decisions, the validation criteria with their proofs and notes for agents — is one typed object, `PrDescription`, and every surface that shows it (the GitHub PR body today; the run page's review panel; whatever replaces GitHub after that) is a **renderer over that object**. There is never a second copy of the content to keep in sync, and because anchors are stored as `(path, from, to)` and rendered against the PR head at render time, regenerating a body after a repush is a re-render, not a rewrite. Every field is capped in the schema, so the map is the same size for a 3-file and an 80-file PR; the shape and its numbers are argued in docs/decisions/0050.

This is the data half of the coding agent's PR description ([agent-coding.md](agent-coding.md) item 3 describes the submission contract as the prompt states it); item 5 below is the pipeline that turns the submitted object into the PR. It was motivated twice by a PR body nobody could consume: first the prose Changes list gave way to a hunk-anchored Tour with embedded code, then the Tour, grown to twenty embedded blocks on a large PR, gave way to the capped map.

- **Code**: `src/core/prDescription.ts` (`PR_DESCRIPTION_CAPS`, `visibleLength`, `fitToCap`, `describeDescriptionIssues`, `recordedJson`, `PrDescriptionSchema` / `parsePrDescription`, `renderPrDescriptionMarkdown`, `anchorUrl`, `MAP_LABELS`, `FOLD_SUMMARIES`, `parsePrDescriptionMarkdown`, `redactPrDescription`) with the zod-free shapes in `src/core/prDescriptionTypes.ts` (`Pointer`, `RenderedPointer`), the title gate's predicate `src/core/prTitle.mjs` (`checkPrTitle`, `TITLE_MAX_LENGTH`), the generated `src/core/prTitleVocabulary.json` it judges against and the repository scoping (`TITLE_GATE_REPOSITORY`, `titleGateApplies`, `prDescriptionSchemaFor`; `ToolContext.repo` in `src/tools/runnableTool.ts`, bound in the run loop); `src/tools/submit.ts` (`submit_pr_description`); `src/execution/githubPulls.ts` (`findOpenPrByHead` / `openPullRequest` / `updatePullRequest`); the coding PR post-step in `src/core/codingPrPostStep.ts` (`trackPushedBranch` / `pushedBranchOf`, `observeCodingWorkspace`, `runCodingPrPostStep`), wired from `src/core/dispatch/runLoop.ts` and `src/core/shipPipeline.ts`; the description turn in `src/core/descriptionTurn.ts` (item 5); `scripts/render-pr-description.ts`; fixture + golden `src/core/testing/goldenMap.description.json` / `goldenMap.body.md`.

## Behavior

1. **The object.** `PrDescription = { title, tldr, why, pointers: Pointer[], feedbackWanted, risk, verified, decisions: {title, rationale}[], validation: { criteria: {criterion, proof}[] }, agentNotes? }`. `title` is the PR title's single source — metadata for the PR's own title field, never rendered into the body. A `Pointer` is `{ label, text, risk?, anchor: { path, from, to } }` — the linked label naming the thing, one sentence, an optional risk (rendered as ⚠), and the lines the label links to. **Every field is capped** (`PR_DESCRIPTION_CAPS`, the one table the schema, the prompt and the tool descriptions read): `title` 72 on every repository (the whole line counted raw, a link's target included — GitHub renders no markdown in a title — exactly as the title gate counts it; `PR_DESCRIPTION_CAPS.title` reads the gate's own `TITLE_MAX_LENGTH`), and **on the repository that carries the title gate** — this project's own, `TITLE_GATE_REPOSITORY` (`SWITCHBOARD_REPO`), matched case-insensitively against the `owner/name` the dispatcher resolved (`ToolContext.repo`, off `RepoContext.repo`) — judged as the CI title gate judges it: `prDescriptionSchemaFor(repo)` swaps in `checkPrTitle` from `src/core/prTitle.mjs`, the one predicate `scripts/check-pr-title.mjs` runs, against the generated `src/core/prTitleVocabulary.json` ([release-and-deploy.md](release-and-deploy.md) item 22) — the `type(scope)!: description` grammar, a type from the release config, a scope from the code map's Areas or none, no trailing period, the cap with the bots' scopes and a `revert:` exempt — every problem one issue at `title` in the gate's own sentence (the cap's too, so one wording per repository), so a run cuts and resubmits inside its turn and CI's `title` check never sees a title the tool accepted — the last tool call of a run whose loop was cut has no shell left to ask the gate itself. The vocabulary is one repository's house convention and the refusal names that repository's code map, so any other repository, or a run with no repository, keeps the universal schema and the cap alone (`fix(api): …` on another repository is never told to use this repository's Areas); the migration note behind `!` needs files only the gate can read, so the gate alone judges it, `tldr` 300, `why` 400, `pointers` 1–7 with `label` 60 / `text` 160 / `risk` 100, `feedbackWanted` 200, `risk` 300, `verified` 200; collapsed, `decisions` 0–10 with `rationale` 400, `criteria` 1–30 with `criterion` 200 / `proof` 300, `agentNotes` 2000. A cap counts **visible characters** (`visibleLength`: a markdown link `[label](target)` counts its label only, so a why with three issue links is not punished for their URLs); a violation names the cap and the count (`at most 300 visible characters (got 305)`, `at most 7 pointers (got 12)`), never zod's generic element count. Every text field is non-empty after trimming; `title`, a pointer's `label`, `text` and `risk` are single-line; an anchor's `path` is repo-relative (no leading `/`, no `..` segment), lines are positive with `to ≥ from`. `parsePrDescription(unknown)` is the one validating entry point (zod; a violation throws naming the path) — the `submit_pr_description` tool and any JSON file go through it. The map's worst case is under 3,800 visible characters and the whole body under 26,000 (both pinned by a test), against an unbounded contract before.
2. **The sha is a render-time input.** `renderPrDescriptionMarkdown(desc, { repo, headSha })` refuses anything but `owner/name` and a full 40-char lowercase sha: a pointer's link lands on the exact lines whatever the branch does next only for a commit ref. Because the object holds no sha, re-rendering at a new head is the whole repush story.
3. **The GitHub rendering.** No headings. The map first: the `tldr` as the opening paragraph; `**Why:** <why>`; `**Where to look**` then one numbered row per pointer, `N. [label](https://github.com/<owner>/<repo>/blob/<sha>/<path>#L<from>-L<to>) <text>` with ` ⚠ <risk>` appended only when a risk is set (a `]` in a label is escaped); `**Feedback wanted:** …`; `**Risk:** …`; `**Verified:** …`. **Every permalink sits inside link syntax, never bare on its own line** — a bare permalink is what GitHub embeds as a code block, and the map is links, not code. Then the folds, each a `<details>` with its `<summary>`, a blank line (GitHub renders markdown inside only after one), the body and `</details>`, present only when there is content: `Decisions (N)` as `- **Title.** rationale` (exactly one trailing period on the title), `Validation (N criteria)` (`1 criterion`) as a `| Criterion | Proof |` table with `|` escaped and newlines flattened inside cells, `For agents` as the notes. The body ends with the generated-with footer.
4. **The golden is a real PR.** `src/core/testing/goldenMap.description.json` is a real pull request's description as data (the one that introduced the map, rewritten onto the fixture repo `acme/api`); `goldenMap.body.md` is its rendering at the fixture head; the suite asserts they are byte-identical, and the PR's live body is the same object rendered at its real head and repo — the PR body, the golden and the test are one artifact by construction. `scripts/render-pr-description.ts <json> --repo <owner/name> --head <sha>` prints the rendering for the operator path.
5. **The coding agent submits the object; the system renders it and ships the PR.** `submit_pr_description` (`full` toolset only — readonly/web/none never carry it) validates with `parsePrDescription`; a violation comes back as a string error naming EVERY failing zod path at once (never a throw) — on this project's own repository a title the gate would refuse among them, `title: <the gate's sentence>`, the tool reading `ToolContext.repo` to know — and **the refusal carries the cut**: each cap issue says how many characters to remove (visible ones; raw for the title, whose cut is offered in the gate's own sentence on the gated repository too) and quotes the longest prefix of the field that fits (`describeDescriptionIssues` over the cap params the schema puts on the issue; `fitToCap(s, max)` beside `visibleLength`: cut at a word boundary under the same count, never inside a `[label](target)` link — a link that does not fit is dropped whole — with the orphaned separator trimmed; already-fitting text unchanged; the empty string, and no quote, when not even the first word fits), so the model takes the prefixes verbatim and the second submit lands — an overshoot is one to five characters and a trim that shortens a URL removes nothing the counter sees, which is why the count alone cost a turn per field. The refused object is on the record: before it answers, the tool publishes a `description_refused` run note whose summary counts the fields over their cap and names them (or the issues, when none is a cap), carrying the object as submitted — redacted as a JSON value through `mapStringLeaves`, since the input need not be a valid `PrDescription`, then clipped by `recordedJson` to the four-level `RecordedJson` the run store's RPC typing accepts (a description is three deep; a deeper object is stored as its JSON text) — and the issues with their cuts, so the ledger says what the model changed between one submit and the next. So the model fixes the object and retries within its own budget, and the last valid call wins — a resubmit after a fix-up push supersedes the earlier one. **The PR's head branch is the branch the run's own `git push` named**, read off the run's bash calls and results as they stream by (`trackPushedBranch` over the run events: only the result of a bash call whose command invoked `git push`, paired by `callId`, is read — a transcript printed by another command is not a push; the command is judged on the event's FULL `command` field, which the runner puts on every bash `tool_call` (redacted, `COMMAND_CAP` 4000 chars), because the 200-char `summary` routinely loses a chained `checkout && add && commit && push`'s `push` past the cap — a single chained command does exactly that, and judged on the summary the post-step would fall back to the checkout; an older record without `command` is judged on the summary, where that shape is a known false negative; `pushedBranchOf` parses that result: git's `To <url>` header followed by per-ref status lines — ` * [new branch] feat/x -> feat/x`, `abc..def feat/x -> feat/x`, a forced `+` update, an `= [up to date]` answer; the block ends at the first line that is not a status line; rejections, deletions and tags name nothing; `git fetch`'s look-alike block sits under `From` and never counts; the last push wins) — the checked-out branch stands in only when no push was observed. The checkout is not the record of what was pushed: anything that moves HEAD between the push and the post — a second run's `git checkout -b` in a shared sandbox, the agent itself checking out another branch after pushing — would otherwise make the post ask the remote for a branch nobody pushed and orphan the pushed work. After the run — before the workspace is released (a resident re-attach would show the ref's tip, not what the run pushed) — the dispatcher observes the workspace: HEAD (`git rev-parse HEAD`), the checked-out branch (`--abbrev-ref HEAD`), the head branch's upstream (`@{u}`, or `<branch>@{u}` when a push named the branch) and, when a push named the branch, that branch's local tip (`git rev-parse refs/heads/<branch>`) concurrently, then the remote's own head for the head branch (`git ls-remote --exit-code origin refs/heads/<branch>`, through the same executor — and so the same credential — the agent's push used); on the cold path a root probe that fails discovers the single cloned subdirectory and re-probes there, and when the dispatch resolved no repo slug the `owner/name` comes from the workspace's own origin remote (GitHub URL forms only). The observed head is the head branch's tip — HEAD when it is checked out, the local `refs/heads/<branch>` when HEAD moved on (never HEAD then: that is another branch's commit); a pushed branch whose local ref is gone too has no observable head. **A branch counts as pushed only when the remote's `refs/heads/<branch>` equals that observed head** — pushed is an observation of the remote, never an inference from names or from the clone's tracking state: a `--depth`/`--single-branch` clone (the cold sandbox's usual `gh repo clone … -- --depth N`) never creates the remote-tracking ref for a pushed branch, so `@{u}` fails after a successful `git push -u`; a remote that answers "no such branch" (exit 2) is final, and `@{u}` — the local record of the last push — stands in only when the remote probe itself failed (network, auth, an origin the thread user cannot read). The body renders at the observed 40-char head and the PR opens in the bot process over GitHub REST (`src/execution/githubPulls.ts`, App installation token, never a `gh` shell-out) — **open-or-edit**: the open PR for the head branch is always looked up first and edited when it exists, so a repush re-renders and edits, never duplicates. Inputs are typed end to end: `title` from the validated object, head from the observed head branch, base in this order — the PR's true base ref when the thread's context came from a PR (a fix round repushes the PR's own head branch, whose binding ref is not the merge base), else the base a coordinator's spawn put on its child's tag (`CoordinatorTag.base`, [http-ingress.md](http-ingress.md) item 9: a plan unit's child is dispatched AT its unit branch so the resident attaches there, which makes the binding ref the branch itself — the plan's base is the only signal that names the target, and only the tag carries it), else the thread's resident binding ref, else the dispatch's resolved ref — prose can alter none of them. The render + open happen before the run's stream finishes: the accepted object is published as a typed `pr_description` event (every string leaf redacted) and the outcome as a typed `pr_opened` event (url, number, created), so the PR facts live in the run record, not only in the reply. The reply carries the PR URL (opened vs. updated wording). A repush re-renders the title too — the object's `title` is the single source, so a hand-edited PR title is overwritten by the next submit. **Failure honesty**: a proven-pushed branch with no valid description first asks GitHub whether that branch already heads an open PR (the same `state=open` + `head=owner:branch` lookup open-or-edit starts with) — a follow-up on an existing PR repushes the PR's own head branch, and the push itself updated the PR — and when it does, the note names that PR as **updated by the push** and flags, as a warning, that its description was not resubmitted (title and body untouched, since there is no description to render — and [agent-coding.md](agent-coding.md) item 3 requires a resubmit after every push to an existing PR, so this is a defect of the run, never an accepted outcome) and the record carries `pr_opened` with `created: false`; only a branch with no open PR (or a lookup that failed — logged, never thrown) gets the branch compare URL and the plain "no PR was opened" statement. **The description turn** (`src/core/descriptionTurn.ts`) enforces the rule before the note is ever needed: when a coding run's model loop ends with no submitted description, a push the remote proves onto a branch that is not the base, and an open PR heading that branch (the same lookup; a failed lookup means no turn), the dispatcher — and a ship coding round for the pipeline's own PR ([agent-ship.md](agent-ship.md) item 7), which runs the identical turn on a copy of the round's messages — after the model is done, before the answer lands or the workspace is released, never after a hard stop, publishes a `description_turn` run note and prompts the run's own pi session ONE more time (a follow-up naming the PR, the pushed head, `github_issue_get` as the way to read the current title and body, the three steps, and the two prohibitions: no further push, no PR opened) under a clip below the coding def's budgets (at most 8 turns / 5 minutes, never the shared AgentDef), with the same tool context — so the description arrives through the same `submit_pr_description` hook, relayed, and the ledger row sees it — under a `run.description_turn` span, through the seam the run stage hands over (`followUp`; [harness-pi.md](harness-pi.md) item 14); a run resumed as a `finish` plan ([run-history.md](run-history.md) item 37) has no session to prompt, so its note says so and nothing is submitted — the warning below then stands; the workspace is observed again afterwards, and the post-step then opens-or-edits as for any submitted description ("PR updated: `<url>`" — the head it was re-rendered at follows at verbose, routing-and-config item 28). A turn that still submits nothing leaves the warning standing, worded to say the turn was given ("even in the dedicated description turn this run was given"); a turn that fails is logged and reported the same way. The turn's tool events join the run record like any other; its steps are not ledgered (a kill mid-turn resumes the run from the main loop's transcript, as the re-review turn does); a failed render/open is reported with the branch compare URL and the plain reason; an unproven push (the branch not on the remote, unpushed commits, unobservable head) gets an honest note and NO compare URL — a URL implying a remote branch that may not exist is a fabrication — but never a false "no PR was opened" over a pull request that exists: when the remote holds the branch at an older commit, or the pushed head is unobservable while the branch is known — the budget wind-down ends runs exactly there, a rebase in flight or a cut probe leaving the push unprovable minutes after it landed — the post-step first asks whether an open PR heads the branch (the same lookup) and, found, renders the description at THAT pull request's head as GitHub reports it — never the workspace's unproven tip — and edits it by number: the reply "PR updated … body re-rendered at its head `<sha>`" with the workspace's state kept beside it, the record `pr_opened` `created: false` with no `head` (the run's own push is unproven, so the release has no branch to remember) plus the `submitted` artifact; a lookup answer with no head commit, or a failed edit, names the PR and says the description was not re-rendered; a branch the remote said is absent is never asked (no same-repo open PR can head it), and null or a failed lookup leaves the honest note standing — "no PR was opened" is reserved for a branch no open PR heads; when the pushed branch and the checkout disagree, the note names both (the branch the push named, and the branch the workspace was checked out on) so the reader knows which branch was asked about; **a branch that is its own base says so** — a description submitted while the observed branch IS the resolved base (a workspace that never left the default branch; a run dispatched at a branch the thread's binding names as its base too) makes no PR call and offers no compare URL, and is never silent: the post-step publishes a `run_note` of kind `pr_not_opened` naming the branch and returns the reply note ("the branch `<b>` is the base branch the pull request would target, so no PR was opened"), so the card and the record — and a plan runner's `pr-check` reading them — show why no pull request followed; **unless the thread's own pull request is known** (`CodingPrTarget.ownPr`: the pull request the thread's own run opened, inherited off the run record with the head commit the resolver fetched — `recordPrOf` in `repoContext.ts`, `prFromRecord`; [resident-repos.md](resident-repos.md) item 29 — never a PR a person named): a workspace on the base is a run that pushed nothing (a push would have named its branch, and the base is not one the gate lets it push), so the description is for that pull request — edited by number (`updatePullRequest`, the same REST PATCH open-or-edit uses), the body rendered at ITS head and never at the base's tip the workspace shows, the reply the "PR updated" wording, the record `pr_opened` with `created: false` and no `head` (nothing was pushed, so the release has no branch to remember) plus the `submitted` artifact; a failed edit is said with the pull request's URL and the reason, never a fabricated success. The refusal stands for a run with no known pull request, and a run that pushed a branch keeps open-or-edit from that branch whatever the thread's PR. The thread's own pull request stays the target once it is merged or closed (`recordPrOf` state `merged` / `closed`, off the resolver's `closedRecordPr` — the fail-closed rule binds no ref and posts no review to it, but its body is still the record of the change): a description resubmitted with nothing pushed past that pull request's head edits its body by number and the reply says the pull request is merged (or closed) and its description edited in place — a thread rebound onto the pull request's own head branch (resident-repos.md item 16) reaches the same edit, since a base resolved off the binding is then the branch itself, never a refusal calling that head "the base"; a push of the pull request's own head branch past that head is new work, which a closed pull request cannot take — no edit, no open call, a `pr_not_opened` note and the compare URL. Only that branch can be pushed past it (`recordPrOf`'s `headBranch`: the head GitHub names for the pull request — the ref bound from an open one, `closedRecordPr.headRef` for a closed one whose head lives on this repository; none for a fork's): the observation cannot tell a run's push from a checkout at the remote's tip, and a tree on the base at origin's tip — the thread returned to the default once the branch was gone ([resident-repos.md](resident-repos.md) item 16's second movement) — is exactly that, so the base is never reported as pushed and a description from it edits the closed pull request like any run that pushed nothing, the reply saying so with no word of a push and no compare URL; a tree on some other branch describes that branch, not the closed body, and takes the ordinary path — opened or edited from the branch against the base when the remote holds it, the unpushed note when it does not. With no description submitted the same workspace has nothing to report, and the agent's own report stands. **The identities on the pull request** ([record 0062](../../decisions/0062-the-requester-authors-the-commits-the-bot-commits-and-opens-them-and-a-run-keeps-the-requester-who-started-it.md)): the identity rewrite runs before the open or edit of the pushed branch ([agent-coding.md](agent-coding.md) item 2 — on `unreadable` nothing opens, on `rewritten` the pull request pins the rebuilt tip and the note and `pr_opened` carry the count; a run whose repo only the workspace's origin named recorded no start state — the dispatch fired no read at attach — so its rewrite fails closed with a reason saying no read was attempted, and that path opens no pull request), the rendered body gains ONE bot-written line in the agents block — `Requested by @<login> in <surface>`, the steerers' names joining when any — only when a binding names the requester's login (`RenderContext.requestedBy`, `requestedByLine`; the agent's description object is unchanged, and no binding means no line), and the requester's bound login is added as assignee after the pre-check answers 204 and skipped with one log line after a 404.

6. **The inverse: a rendered body back into the object.** `parsePrDescriptionMarkdown(body)` → `{ description: Partial<PrDescription> & { pointers: RenderedPointer[] }, complete, problems }` reads a body by the contract item 3 writes: the `tldr` is every line before the first bold label (headings dropped); each of `**Why:**`, `**Feedback wanted:**`, `**Risk:**`, `**Verified:**` owns the lines from its label to the next label, the `**Where to look**` list or the first `<details>` (case-insensitive; a label inside a fence is code; a duplicate label keeps the first, drops the second's lines and is a problem; a bold phrase that is not a label stays in the field it sits in); pointers by their numbered rows `N. [label](permalink) text ⚠ risk` — the path percent-decoded, the anchor validated by `PrAnchorSchema`, the permalink's sha riding on the anchor as `RenderedPointer.anchor.sha` so a reader can tell whether it is at the head being looked at, the text and the risk split on ` ⚠ `; the folds by their `<summary>` text (`Decisions`, `Validation`, `For agents`; an unknown fold is skipped), decisions by `- **Title.** rationale`, validation by the `| Criterion | Proof |` table with `\|` / `\\` unescaped. **A body under the previous contract** (a `## Tour` heading outside a fence) is read by that grammar: `## TL;DR` (else the leading paragraph) → tldr, `## What & why` → why, each `### N.` step's bare permalink line → a pointer with the step's title as label and its description (a `**Look for:**` appended) as text, `## Risks & implications` → risk, `## Decisions` and the `## Validation` table as today; `Remaining changes` and the validation summary have no home and are dropped; `legacy Tour shape` is always a problem, so `complete` is false. **Strict where the renderer is strict, lenient where a person would be, never a throw**: a row without a github permalink, with a schema-invalid anchor (absolute or traversing path, `to < from`) or a malformed percent escape is a problem and is dropped; a 7–40-hex sha and a single-line `#L<a>` are accepted; a body without either shape takes its first text as `tldr`; every missing label or fold is a problem; `complete` ⇔ `problems` is empty. Round trip on the golden: `tldr`, `why`, `pointers` (plus each anchor's sha = the render head), `feedbackWanted`, `risk`, `verified`, `decisions`, `validation` and `agentNotes` come back equal. **Lossy by construction**: the PR title is not in the body; a decision title that ended in a period loses it (the renderer's normalization); a newline inside a validation cell was flattened to a space when rendered. This is what a review run publishes for a PR no coding run described ([reading-diff.md](reading-diff.md) item 7).

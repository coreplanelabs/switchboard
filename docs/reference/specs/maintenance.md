# Maintenance

An operator can close selected capabilities through one durable episode. The client owns scheduled activation. Maintenance has no automatic expiry or recovery estimate.

## Behavior

1. `maintenance announce` saves an announced episode and posts a notice to the selected Slack channel. The default channel is `switchboard-dev`. A timestamp must include an offset. The notice renders that start in Pacific time; without a timestamp it uses the caller's timing text or `in a few minutes`. It names unavailable actions and asks readers to follow the thread. It gives no recovery estimate.
2. Announce returns the exact CLI command and MCP tool arguments for activation, plus `schedule.installed: false`. The caller's client schedules that call. Switchboard installs no timer. Announcement alone never closes access.
3. `maintenance start --id <id>` activates the saved episode without changing its scope. An immediate `start` without an ID creates an active episode. Start and end are idempotent for the exact saved phase and ID. A delayed activation cannot revive an ended episode. A delayed end cannot clear a newer episode.
4. `all` blocks new agent work and user commands and serves a public maintenance page. `agents` blocks new agent work. `residents` blocks all new agent work, including alternate executors, and deterministic repository execution. `web` blocks public pages. Multiple scopes can be named as a comma-separated list; `all` must stand alone.
5. The shared registry checks maintenance after normal authorization and before confirmation or execution. CLI and MCP maintenance commands and status remain available. A maintenance operator retains authorized reads, run/pipeline stop and resident administration. Native private Slack requests and clicks remain closed; operators use CLI or MCP for recovery. A maintenance grant never replaces the command's normal grant.
6. Dispatch checks before routing. During a hold, command-shaped input completes through the deterministic registry path, including usage errors. Saved agent proposals cannot use a command prefix to bypass the hold. Refusals carry the maintenance reason and system cause in history and traces. Organization admission refuses new receipts during an applicable hold. Saved command approvals re-enter the registry; saved agent approvals re-enter dispatch. No surface or child dispatch can use another executor to bypass a resident hold.
7. The versioned state Worker document survives process restarts. Reads do not cache an open state. A configured store failure closes applicable admission. A malformed document, including a missing document at a nonzero version, is an error. Concurrent writes require the exact version.
8. The Worker and bot HTTP gates return HTTP 503 with `Cache-Control: no-store` on public pages, including unknown routes, during `all` or `web` maintenance. The page escapes public text. HTTP ingress and GitHub webhook intake return a structured maintenance refusal during an agent or resident hold. Health, MCP, command transport, the authenticated approval page, and authenticated existing-work callbacks retain their normal handlers and authorization. Both Bot restart routes retain their deployer authorization during an active hold or failed maintenance-state read. Artifact copy and PR-image publication callbacks remain available under their existing bearer checks. Public image reads remain closed. The page uses the native approval layout, brand mark, theme tokens and lime update control. It needs no dashboard script or asset request.
9. Browser page reads also receive the same self-contained page from the Cloudflare Worker when the bot throws, returns HTTP 5xx, or does not return headers within five seconds. This fallback does not need a saved maintenance episode or bot assets. One shared selector admits only dashboard document routes, including Home, completed work, thread discovery and pipeline pages. A failed maintenance-state read also returns HTML only for these document requests. Fixed reports, downloads, assets, event endpoints and query-selected streams retain their structured refusal, even when they accept HTML. The response remains HTTP 503 with `Cache-Control: no-store`. A new page request can reach the recovered bot; no bot retry, maintenance-state write or Slack notice is made. API, health, approval, streaming and write requests keep their existing response contracts. Fallback warnings identify the page with a fixed route template, without private identifiers or query tokens. DNS, Cloudflare Worker and Access availability remain prerequisites.
10. The state transition commits before Slack publication. A durable `sending` notice prevents concurrent phase changes, updates, or replacement episodes from overtaking the post. Follow-up notices use the verified original thread. A failed or unknown publication leaves the hold in place and marks the notice unverified. A start/end retry does not automatically repost. An explicit `update` posts another message; it refuses an unverified root thread. An operator can use `end --without-notice` to restore access when a notice remains unresolved; an earlier notice can still arrive, and the operator owns the Slack correction.
11. Existing work is not killed, reset, settled or proved idle by maintenance. Status reports current work in flight and states that resident workload proof is still required. The operator ends maintenance explicitly; the episode has no expiry.

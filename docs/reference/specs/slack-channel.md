# Slack channel

Slack is a pure transport: it turns Slack events into `IncomingMessage`s, renders replies/status back, and adds nothing else. All Slack-specific behavior — triggers, receipts, formatting, attachments — lives here.

- **Code**: `src/channels/slack.ts`, `src/channels/slack/` (the adapter's concerns that stand apart: `attachments.ts` — which files reach the model and their budgeted downloads; `requester.ts` — who asked: the sender, or the person an app relayed for (item 13); `threadTurns.ts` — the pure thread-page-to-turns mapping `history()` and the conversation reader share; `references.ts` — the conversation reader of record 0037: this workspace's permalink grammar, the closed fresh classifier, the text-only fetch, the requester's standing; `statusCard.ts` — the [card](../vocabulary.md#card)'s Block Kit frame and the live-card record; `dedupe.ts` — the handled-set and the redelivery guard; `lookups.ts` — the cached display-name, email and team-URL reads and the permalink), `src/core/dispatch/messages.ts` (`turnContent`: the attachment assembly of a model turn), `src/channels/slackTriggers.ts` (pure trigger gating), `src/channels/slackCatchUp.ts` (reconnect catch-up + orphaned-card sweep), `src/channels/slackCatchUpStatus.ts` (catch-up status record + bot-scope check), `src/channels/mrkdwn.ts`, `src/channels/health.ts` (`/healthz` body), `src/channels/processMetrics.ts` (`/healthz.process`), `src/core/drain.ts` (drain deadline + catch-up window minimum), `deploy/cloudflare/preflight.mjs` (bot deploy preflight), `src/deploy/restart.ts` + `deploy/cloudflare/worker.ts` (`deploy restart`: `/admin/restart` authorization + refusal decision; the Container DO `stop()`)

## Behavior

1. **Triggers**: (a) channel mention (`@switchboard …`); (b) DM — the app's Messages tab is enabled by the manifest (`features.app_home.messages_tab_enabled`, not read-only; `docs/public/slack-app-manifest.yaml`), since a Slack app without it refuses every DM at the composer and the `message.im` subscription never fires; (c) a [thread](../vocabulary.md#thread) follow-up in a thread the bot participates in, when the intake gate admits it (item 15) — no re-mention needed. Top-level channel posts still require a mention; a bot's un-mentioning message and non-`file_share` subtypes are ignored (no bot loop), while a bot's post that mentions the bot is handled like anyone's — its requester resolved per item 13. Participation is re-derived from the thread itself (`threadIfBotInIt`), never from in-memory state — and the thread page that check reads is handed to `SlackIO.history()` (`SlackEvent.thread`), so a [follow-up](../vocabulary.md#follow-up) costs one `conversations.replies`, not two identical ones; the mention path, which has no such check, fetches in `history()` as before.
2. **Acceptance receipt**: the moment a message is accepted for handling — for an unmentioned thread follow-up, once the intake gate has admitted it (item 15) — the bot reacts 👀 (`eyes`) on it, before any model/tool work. Fire-and-forget: missing `reactions:write` scope or a duplicate reaction logs and never blocks handling. The adapter starts the request's root the moment `handle()` runs — before the redelivery guard — and everything it does before `dispatch()` (the guard, this ack, the catch-up note, the downloads, the display names) is one `slack.receive` span with `dedupe` (`fresh`/`duplicate`), `caughtUp` and `files` attrs; a dropped redelivery is a root with that one child and no [run](../vocabulary.md#run) ([tracing.md](tracing.md) item 18). The message carries `receivedAt` (our clock at entry) and `originAt` (the message `ts`), so the card can say `queued 6m 00s before we saw it` after a restart.
3. **Status card**: one bot message per run, edited in place — spinner + agent + elapsed seconds headline (the model joins the label at `verbose`, [routing-and-config.md](routing-and-config.md) item 28); body is the [agent](../vocabulary.md#agent)'s own ✓/✱/○ checklist (via `update_status`). A ticking card means the run is alive; error paths mark ❌. Slack's native shimmer status is re-upped every 75s during long runs. The shimmer is one Slack-side status per thread, so with two runs in one thread (a plan runner's coding child finishing as its review child starts) the newest run to start owns it: a run that finishes while the shimmer is its own clears it at once — the thread stops saying the bot is working for that run the moment its card closes to its done state — while a run whose sibling started during its finish still closes its own card to done but skips the clear, never wiping the live sibling's status; the sibling sets its own phrase with its first frame, and only the owner's 75s re-up speaks. The closed card's total is the run's own — the card shell is frozen at the registry's finish stamp (`CardShell.freeze`, [tracing.md](tracing.md)), so a close painted after a slow reply reads the same seconds as the run page and the index — and a run whose loop threw closes its card after the finish, from the same stamp. The card's clock is the request's receipt, and through setup a 5 s heartbeat repaints it with the step in flight — `◐ *coding* · 42s — attaching the workspace…` — until the run loop's own heartbeat takes over; every close carries the request's elapsed time (`📦 … · not started (repo access) · 12s`, `❌ setup failed · … · 184s`), and when the card's gate passes the shape line (`32s getting ready · 2m 30s thinking · …`) and the queued caption lead the closed card's detail above the checklist at `debug` ([tracing.md](tracing.md) item 18). A [pipeline](../vocabulary.md#pipeline)'s card prints each [unit](../vocabulary.md#unit)'s standing in the user's words ([record 0066](../../decisions/0066-a-user-meets-twelve-nouns-and-no-others-the-vocabulary-is-a-reference-page-bound-to-the-code-and-the-consistency-check-fails-a-user-surface-that-prints-an-internal-word.md); [agent-ship.md](agent-ship.md) item 12a): the ending word `merge-ready` or `round cap reached` and the round-outcome word `checks failed`, through `endingWordOf`/`roundOutcomeWordOf` (`src/core/pipelineStanding.ts`), never an internal token like `merge_ready`.
4. **Formatting**: agents write standard Markdown; the adapter converts to mrkdwn (bold/strike/headers/links/bullets) and **never rewrites code** (fenced or inline). Asterisk emphasis renders **bold whichever dialect the model wrote** — `**x**` collapses to `*x*` and a single `*x*` is already mrkdwn bold — because mapping `*x*` to italic (standard-Markdown semantics) made the same verdict line arrive bold or italic depending on the model's dialect of the moment; `_x_` is the one italic form. This also matches the ingress reading (`humanizeMessageText` treats Slack `*x*` as bold). Replies over 3500 chars are chunked at line boundaries.
5. **Attachments**: files on the triggering message and thread history are downloaded (needs `files:read`) and passed to the model, budgeted and spent newest-first over thread history. Within one message the downloads run concurrently (candidates are chosen first — type, declared size, count budget — then fetched together, then the byte budgets are applied in the original order, so the file that gets cut on overflow is the same one the serial loop cut) and the image and document passes overlap; messages stay sequential because each one's spend decides the [budget](../vocabulary.md#budget) left for the next. Two families, each with its own budget:
   - **Images** (`image/jpeg|png|gif|webp`): ≤10/message, ≤5MB each; thread-wide ≤20 images/24MB. Sent as provider-native image blocks.
   - **Documents** — PDFs and text/code/CSV/log files (`text/*` plus a small allowlist of text-ish mimetypes; generic types resolved by filename extension): ≤10/message, ≤10MB each; thread-wide ≤20 docs/32MB. A **PDF** rides as base64 to a provider-native document block (Anthropic; `@anthropic-ai/sdk` 0.39 supports it in the stable Messages API); OpenAI-compatible endpoints get an inline-text placeholder naming the file (their binary-PDF support is inconsistent). A **text/code file** is decoded to UTF-8 and inlined as a fenced text part labeled with its name — provider-agnostic, no SDK dependency.
   - **Secret-file denylist** (defense against credential exfiltration to the model, including third-party OpenAI-compatible providers): a file whose *name* looks like credentials, a private key, or secret config is **never inlined** — it is skipped-with-note and its bytes are never downloaded or decoded into the prompt. The denylist **overrides** text classification (checked before the mimetype/extension allowlist), because the whole risk is a secret file whose type/extension otherwise reads as harmless text. Matched on the filename, case-insensitive, independent of `path.extname` (which returns `""` for dotfiles like `.env`): `.env` in any position (`config.env`, `.env.local`, …), `id_rsa*`, `credentials.json`, `*service-account*.json`, `*-key.json`, and the extensions `.pem` `.key` `.p12` `.pfx` `.npmrc` `.netrc` `.ini` `.cfg` `.conf`. Relatedly, `application/json` and `.json`/`.jsonl` are **not** inlinable-by-default (JSON is a common secret container), so a JSON file is never "fair game" just by its mimetype or extension.
   - Skipped attachments (unsupported type, secret-file denylist, oversize, over-budget, failed download) are named to the model so it never claims a file "didn't come through". A file is only reported skipped when it is neither a usable image nor a usable document.
   - On a generated hosted ship task, an accepted inline image/document keeps its Slack by-reference source beside its bytes and is persisted once as the generated unit's stable seed event. The coordinator's ordinary attachment fold gives the first coding child both forms: the provider media and a staging reference whose original zero-based Slack slot puts the file at `attachments/0-<name>`, appends that path to the prompt and records the file in the artifact catalogue. The seed is consumed only after that child registers; a failed spawn keeps it for retry, a replay stages no second file, a review spawn gets none, and a later coding round gets none after successful consumption. The Worker client applies the event cap before transport, so valid provider-sized media over the durable cap becomes the existing dropped-attachment note instead of HTTP 413; a triggering message without accepted media changes no hand-off bytes.
6. **Display-name resolution**: the adapter resolves the channel's name (`conversations.info`, needs `channels:read`/`groups:read`) and the sender's display name (`users.info`, needs `users:read`; `profile.display_name` → `real_name` → handle) — and, with `users:read.email`, their email (`resolveUserEmail`, uncached), which the costs page's **me** toggle and the MCP connect ticket match the Access identity by and passes them to the core as `IncomingMessage.channelName`/`userName` (for the live-view run label), plus `sourceUrl` — the message's Slack permalink (`slackPermalink`: `<team url>/archives/<C>/p<ts>` with the thread qualifier for a reply), built from the `auth.test` URL resolved once per process — so the run page's Request block can link back to the thread ([live-view.md](live-view.md) item 13). Best-effort and **cached** (module-level `Map`s, one API call per new id, bounded to 1000 entries FIFO): a lookup failure leaves the field undefined — the core falls back to the raw id — and never delays or fails a dispatch. The core stays channel-agnostic; these are optional hints.
   - 6a. **Channel visibility for authorization** ([authorization.md](authorization.md) item 7): `SlackChannelDirectory` ([`src/channels/slackChannelDirectory.ts`](../../../src/channels/slackChannelDirectory.ts)) implements the core's `ChannelDirectory` seam over the same `conversations.info` call — `is_im` / `is_mpim` → `dm`, `is_private` → `private`, else `public` — and the bot wires it as the dispatcher's channel facts (`src/index.ts`), so every run is stamped with its channel's visibility and a public channel's runs are readable by everyone while a private channel's or DM's stay grants-only. Unlike the name lookup this one is a **fact the policy relies on**, so it fails closed: any error, missing scope, or empty reply is `unknown` (grants-only, never public), remembered for the TTL (ten minutes, bounded to 1000 channels) and logged once per channel per window under `[authz]`; a `slack:D…` id is `dm` without an API call; non-Slack ids are the static mapping's. Scopes: `channels:read` for public channels and `groups:read` for private ones — both already in `REQUIRED_BOT_SCOPES`, so the startup scope check (item 7) names a missing one; the bot receives no group-DM events (`message.mpim` is not subscribed), so `mpim:read` is not needed and a missing scope only ever degrades to `unknown`, never a crash. The dispatcher waits at most `CHANNEL_DIRECTORY_TIMEOUT_MS` (1.5 s) for the answer and otherwise stamps `unknown` — one cold `conversations.info` per channel per TTL is the whole cost on the message path. The same directory supplies **membership** (authorization.md item 7): `channelsOf(slack:U…)` pages `users.conversations` for the person (public and private channels the bot is also in, archived excluded; the same two scopes), cached per person for `MEMBERSHIP_TTL_MS`, and the bot keeps it fresh from the events the manifest subscribes — `member_joined_channel` / `member_left_channel` forget that person (everyone, when the member is the bot itself), `channel_left`, `group_left`, `channel_archive`, `group_archive`, `channel_deleted`, `group_deleted` and every socket `connected` forget everyone — so the TTL is only the bound on a missed event. An installation whose app predates those events still works: its cache simply ages out on the TTL alone.

7. **Reconnect catch-up**: Socket Mode does not queue or replay events while the app is disconnected, so every bot rollover (deploy → graceful drain closes the socket → cold start) was a silent blackout — mentions posted in it got no 👀, no run, and the caller waited forever. On **every websocket `connected`** (first start and each reconnect) the adapter scans every channel the bot is a member of (`users.conversations`, needs `channels:read`/`groups:read`) and re-dispatches what it never saw, through the same `handle()` as a live event (👀, status card, run). **Slack is the durable "was this handled" record** (invariant 6 — no persisted last-seen `ts` an ephemeral container would forget): a message counts as handled when the bot has posted in its thread after it (a status card or answer), **or** it carries the bot's own 👀 reaction and is younger than `ACK_GRACE_MS` (30 s — the card is on its way). A 👀 alone on an older message is a run that died between the ack and its card (a rollover can kill the process seconds after it acked a thread reply; treating 👀 as terminal would make the reply vanish) and is re-run (the ack can be lost to a missing `reactions:write`; a status card cannot). A bounded same-process seen-set (`channel:ts`, 5000 FIFO) additionally stops a message that arrived live *and* appears in the scan from running twice. Selection mirrors the live triggers exactly via the shared `slackTriggers.ts`: a top-level message needs a mention; a thread reply needs a mention or a bot-participating thread; bot messages and non-`file_share` subtypes never count. **Window**: messages inside the last 30 min (`slack.catchUp.windowMinutes`, default `DEFAULT_WINDOW_MS`) — older unanswered mentions are left alone, because re-running a stale request is worse than the human re-posting it. **The window is bound to the drain**: the graceful drain closes the socket the moment SIGTERM arrives and holds the container until in-flight runs finish (`DRAIN_DEADLINE_MS` = 15 min, `src/core/drain.ts`), and Cloudflare boots the replacement only after exit — so a deploy over a run in flight blacks Slack out for the run's remaining duration, and the catch-up on the next connect is the ONLY recovery for mentions posted in that gap. The default window is therefore derived from the deadline: `DEFAULT_WINDOW_MS ≥ MIN_CATCH_UP_WINDOW_MS = DRAIN_DEADLINE_MS + COLD_START_ALLOWANCE_MS` (15 + 5 = 20 min), asserted at module load and by a unit test. A configured `windowMinutes` below that minimum (or non-positive) is kept as given — never clamped — and warned about at startup naming the drain deadline (`catchUpWindowWarning`). Keeping the socket open during the drain was rejected: a mention accepted at minute 14 would be killed at the 15-min cap with a frozen card, whereas the catch-up re-runs it intact. **A replayed message says so in its thread** (a request that sat minutes through a drain with no 👀 is indistinguishable to the caller from being ignored): the catch-up hands `handle()` the event with `caughtUp: true`, and before the run starts the thread gets `⏱ Picked up <N min | under a minute> after it was posted: the bot was restarting … Handling it now — no need to re-send.` (`catchUpDelayNote`, pure; a negative/clock-skewed delay renders as "under a minute"). Best-effort like the 👀 ack — a failed note is logged, never fails the run. Thread parents are scanned 7 days back (≤5 pages of 200) so a follow-up in a days-old PR thread is found; replies are fetched only for threads whose `latest_reply` is inside the window, and paged in full (≤5 pages of 200) because Slack returns replies oldest-first — a single page of a long thread would drop exactly the newest, in-window messages. **Scope and bounds** (each fails toward a message staying un-run, with one bounded exception toward a re-run, noted below — never toward a silent drop): **DMs are not caught up** (only `public_channel`/`private_channel`; catch-up is about channel mentions and `im:*` scopes are off in the recommended rollout); a channel with >1000 top-level messages in 7 days, or a thread with >1000 replies, is truncated at the page cap — in such a truncated thread an acked-and-answered message older than the grace whose bot reply sits on a dropped page is re-run (its 👀 is not terminal; >1000 replies inside a 30-min window is the accepted trade-off); a broadcast reply whose parent is older than the 7-day lookback is never seen; and a caught-up run that dies before posting anything is re-dispatched on each reconnect inside the window regardless of the 👀 (with or without `reactions:write` — an ack past the grace is by design not a receipt), bounded by the window. Missed messages are dispatched oldest-first; a channel whose scan fails is logged and skipped, never blocking the others or the connect. **The act phase reads the intake receipt before `handle()`** (`actOnMissedMessage` in `src/channels/slack.ts`; item 15's catch-up half, [record 0058](../../decisions/0058-a-thread-reply-is-read-before-it-is-answered-intake-decides-whether-the-bot-was-addressed.md)): a candidate carrying a mention — including an edit that gained one, which arrives live as a subtype the live path skips and is caught up here inside the window — and one in an `always` thread are dispatched exactly as today, no read; any other unmentioned follow-up in a bot thread gets its stored receipt read first — a `silent` row marks the pair seen and is counted under `silenced` on the `slack.catch_up` root (read, never re-run); an `addressed` row dispatches the replay with `SlackEvent.intakeDecided`, so the gate never decides it twice; and no row (a failing read decides as if none) runs `decideIntake` over the thread's tail the scan already paged (`MissedMessage.thread`, the newest twelve turns, with the same evidence the live gate assembles) and proceeds by the stored verdict — a fresh ordinary `silent` is counted and marked seen like a stored one, while a fresh typed provider failure posts its one safe sentence before it is counted and marked. The same-process seen-set is re-checked AFTER the read (the scan's `alreadyHandled` ran at scan time and the read awaited since), so a live claim that landed between the scan and the act is skipped, never run twice. A `thread_broadcast` reply is never a candidate (a non-`file_share` subtype, in the thread and in the channel echo), and a deleted message is simply absent from the fetched history. Only the hand-off — the read and the [verdict](../vocabulary.md#verdict) — is awaited; the dispatch through `handle()` stays fire-and-forget like a live event. The scan is two phases: READ — channels are scanned with bounded concurrency (`CATCH_UP_CHANNEL_CONCURRENCY` = 4 channels at once; within a channel `CATCH_UP_THREAD_CONCURRENCY` = 4 replies fetches at once; `src/core/mapLimit.ts`), so a busy workspace's scan costs the longest scan, not the sum of every round trip — this runs on every reconnect while a caller may be waiting for a receipt; then ACT — in the original channel order, so re-dispatch order is exactly the serial loop's. Default on; `slack.catchUp.enabled: false` removes the hook. **Observable without container logs**: the container's stdout is not in Workers Logs, so a scan that cannot run (the token lacking `channels:read`/`groups:read` makes `users.conversations` fail `missing_scope` and the whole catch-up a silent no-op) must show somewhere else. Each scan records its outcome in an in-process, live-only record (`slackCatchUpStatus.ts` — a restart starts empty and the next connect refills it; not durable state, so invariant 6 holds): `lastRunAt`, `channels`, `missed`, `skippedChannels` (per-channel scan failures), and `error` when the channel listing — or the `auth.test` before it — failed; a clean scan clears `error`. On the first `connected` the adapter also compares the token's granted scopes (`response_metadata.scopes` on the `auth.test` result) with the adapter's required set (`REQUIRED_BOT_SCOPES`: `app_mentions:read`, `chat:write`, `channels:history`, `groups:history`, `files:read`, `reactions:write`, `channels:read`, `groups:read`, `users:read`), logs any missing ones at `error` level and keeps them as `missingScopes` (absent when none, or when the grant is unknown — advisory, never a false alarm). `GET /healthz` carries the record as `catchUp` with undefined fields omitted, and the bot deploy preflight (item 8) prints a WARNING — never a refusal, the deploy may be the fix — naming `catchUp.error` and the missing scopes. The pass is one `slack.catch_up` root on the span log ([tracing.md](tracing.md) item 20), its counts as attrs — `channels`, `missed`, `silenced`, `orphans`, `skipped`.

8. **Rollover-safe status cards**: a `wrangler deploy` in `deploy/cloudflare/` rolls the bot container. Cloudflare's rollout sends SIGTERM and allows up to 15 min before SIGKILL, and the bot's graceful drain (`src/index.ts`) uses that window to finish in-flight runs — so one deploy on top of a run is survivable. A second deploy while the first is still draining replaces the draining instance at once: the run dies, its card freezes mid-spin, and the run vanishes from `/runs` (the registry is in-memory) — an **invisible state** where the reader cannot tell "slow" from "dead". Three layers, each independent: (a) **Deploy preflight** — `npm run deploy` runs `preflight.mjs` first. Since the run ledger's handoff ([run-history item 39](run-history.md)) it **no longer refuses for runs in flight**: `GET /healthz` reporting `inFlight > 0` or `draining: true` is a WARNING naming the count and the handoff (a resumable run continues on the next generation under its own card; a ship pipeline still in flight is what the drain warning names), and the deploy proceeds — nobody waits on a run. It still refuses while `wrangler containers list --json` shows the `switchboard-switchboardserver` application in a non-settled state (`provisioning`/`updating`/unknown — a rollout still in progress; a second rollout landing on one in progress kills the draining run) — `deploy all` retries every minute up to its budget and then **fails by name** (`preflight still refusing after N min (…) — NOT deployed; re-run the deploy once it clears (a CI job: gh run rerun RUN_ID --failed), or --force …`, `preflightGaveUpLine`), never a deploy over what refused — and fails closed: unreachable bot, a bare-`ok` body (a Worker predating the preflight), an impossible `inFlight`, a wrangler failure, or an app missing from the listing all refuse; `SWITCHBOARD_DEPLOY_FORCE=1` is the explicit, warned bypass. `deploy restart`'s decision (`decideRestart`) follows the same rule: runs in flight and a drain under way warn, only the fail-closed cases refuse. The live gate judges a container by its identity (`build.commit`, or `startedAt` after a restart) whether or not it is draining: one that already serves the deployed identity IS live, whatever is rolling it next; when the identity is the old one, the reason names the drain — and names what is actually held when the body carries `held` (`old container still draining — holding N registry-active run(s): <id> (not handed off) …`) instead of an `inFlight` count that can read 0 while a registry row holds; the drain's own hold line (`drainHoldLine`) names the same rows. A body without usable `held` rows falls back to the count. A **same-commit rollout** (a Worker recovered with `--only bot`, a forced `all` with no code change) drains an old container that serves the deployed commit too, so a draining same-commit container counts only with a `startedAt` later than the one `deploy all` read before the upload; without that reading it waits. (b) **Drain is visible** — on SIGTERM the process sets a shutdown notice and every live card's heartbeat frame carries `· ⏸ deploy in progress — this run continues through the bot restart`; the closed card never does. Since the handoff ([run-history item 39](run-history.md)) the notice tells the truth for both kinds of run: a resumable run is handed to the next generation and continues there under the same card, a ship pipeline finishes here before the exit. `/healthz` is JSON (`{ok, inFlight, draining, drainDeadlineMs, build, slack, process}`, plus — while draining — `drainStartedAt` and `held`, the registry-active runs not handed off as `{id, why}` rows: what the drain actually waits for, which `inFlight` (the dispatcher's count) can miss — a registry row whose dispatcher-side run is gone reads `inFlight: 0` while holding the drain for its full deadline — and `generation` — the run ledger generation this process writes under, [run-history.md](run-history.md) item 35 — when the ledger is on) so the preflight can read the same facts; `process` is `{rssMb, heapUsedMb, eventLoopLagP99Ms}` from `src/channels/processMetrics.ts` — the bot is one Node process and under many concurrent runs it is the first thing to fail, so the load harness ([load-harness.md](load-harness.md) item 12) reads memory and event-loop lag here, the lag being the p99 over the window since the previous poll (the Worker's keep-alive and the deploy `wake` check only the HTTP status). `slack` is the Socket Mode state (`src/channels/slackSocketStatus.ts`, in-process and live-only like the `catchUp` record): `{connected}` plus, once known, `since` (ISO of the last transition) and `connects` (lifetime count for this process — 1 is the boot handshake, more means reconnects). The HTTP server starts BEFORE the Slack handshake, so on a cold start `/healthz` legitimately answers `slack: {connected:false}` until the socket lands — which is exactly how the listen-before-connect ordering is observable from outside (no container stdout needed), and how a silently dead socket (HTTP fine, bot deaf) shows off-box. `build` is `{ commit, builtAt? }` — the commit the image was built from, stamped by `deploy/cloudflare/write-build.mjs` into a gitignored `build.json` that `npm run deploy` writes and the Dockerfile COPYs (optional glob: an image built by hand reports `commit: "unknown"`; a dirty tree gets a `-dirty` suffix). It exists because **deployed ≠ live**: after `wrangler deploy` the old container keeps answering `/healthz` while it drains, so `npx tsx src/cli.ts deploy all` treats the bot step as done only when a non-draining container reports the deployed commit (`src/deploy/liveGate.ts` `decideLive`: not JSON / draining / no build identity / `unknown` / other commit / `-dirty` → waiting with the reason; past the drain deadline + cold start → timeout, exit non-zero; live only on a commit match), and its preflight wait prints a heartbeat per poll (`still waiting — N run(s) in flight (draining: yes/no), waited Xm of 10m`) so a long wait is never silent. (c) **Orphan sweep** — the reconnect catch-up (item 7) also scans, in threads active within the last 2 h, for the bot's own cards still wearing a live glyph (the spinner or the 👀 setup card — `LIVE_CARD_PREFIXES`, kept next to the glyphs in the dispatcher) whose run is live nowhere this process knows of — not driven here, and not leased on the run ledger by another generation ([run-history.md](run-history.md) item 36, `isLiveCard`) — and closes each with `chat.update` as `❌ interrupted · <label> · <elapsed>` plus a detail saying the bot restarted mid-run and to re-send. Slack is the durable record here too (invariant 6): the card is the only trace of a run whose process died. Cards this process is driving (`ownsLiveCard`) are never touched, so a websocket reconnect without a restart cannot close a running run's card; a card older than 2 h is left alone rather than mislabeled; a failing close is logged and the sweep continues. The `/runs` index does not resurrect the dead run — the card is the user-facing state. (d) **Restart without a build** (`deploy restart`): a rotated bot secret needs the container restarted, not rebuilt — `wrangler secret put` updates the Worker env but a running container keeps the env it started with, and Cloudflare rolls a container only on an image/config change. The Worker's `POST /admin/restart` authenticates a `SWITCHBOARD_INGRESS_TOKENS` bearer and compares its subject with `SWITCHBOARD_RESTART_DEPLOYER`, a Worker var rendered from the deployment profile's `restart.deployer` (or set directly on the Worker); it never asks the container or runtime config, so a refusal-only generation cannot lock out recovery. Before the CLI reaches the route it proves the profile's current config source equals the state Worker's `base` document and names that document's `vN` generation; a missing or changed base says to run `deploy config` first. The authorized route has the Container DO check `/healthz` with `decideRestart`'s rules (409 only for the fail-closed cases — no JSON body, an impossible `inFlight` — unless `{force:true}`; runs in flight and a drain under way are warnings and the stop proceeds, per the handoff of [run-history item 39](run-history.md)), then `stop()` — SIGTERM, the same graceful drain as a rollout — and the next request (the keep-alive cron within a minute, or the CLI's 15 s poll) starts it again with envVars computed AT START from the DO's current env (`deploy/cloudflare/worker.ts` `containerEnv`). Because the image is unchanged, `build.commit` cannot identify the new instance: `/healthz` carries `startedAt` (process start, ISO) and the CLI (`npm run cli -- deploy restart`, CLI only like `deploy all`) is done only once a non-draining container reports a LATER `startedAt` (`decideRestarted`, sharing `decideLive`'s waiting/timeout core); a 409 is waited out with the same heartbeat as `deploy all`. The drain's count starts at `dispatch()` entry, not after executor attach: an acked message is in flight before anything slow (a SIGTERM one second after the 👀 would otherwise see 0 in flight and exit).

9. **Redelivered events are deduped — one message, one run**: Slack re-delivers an event whose original delivery was never acked. The shape: a mention posted seconds into a deploy drain is answered by the reconnect catch-up (⏱ note, card, answer) and then **re-delivered by Slack minutes later** through the live socket path — a bare `[event]`+`[run]` for the same `channel:ts` with no `[catch-up]` line and no ⏱ note, while `/healthz`'s `catchUp.lastRunAt` still reads the earlier scan. Unguarded, that path runs everything unconditionally — `handle()` *marking* the same-process seen-set is not enough when only the catch-up scan ever *reads* it — and the duplicate run repeats every side effect (a second review verdict, a second auto-approve). The guard (`dedupeDelivery`, first thing in `handle()`): (a) **same-process** — the (channel, ts) pair is already in the seen-set (handled live or by this process's catch-up) → dropped, `[redelivery] … dropped: already handled in this process`, no API call; the pair is claimed *before* the guard's only await, so concurrent deliveries of the same pair serialize onto check (a) however the awaits interleave, and catch-up's `onMissed` re-checks the set after its receipt read, just before dispatch (its scan-time `alreadyHandled` read may predate a live claim). (b) **cross-process** (the first handling belonged to a container that is gone): a live delivery older than `STALE_DELIVERY_MS` (60 s — live deliveries arrive in seconds; only redeliveries and blackout flushes are older) pays ONE `conversations.replies` fetch and is dropped when the bot has already posted in the thread after the message (`botRepliedAfter`, the same predicate the catch-up trusts — invariant 6: Slack is the durable record). A stale event with 👀 but no bot reply after it still runs (item 7's ack-then-killed shape — re-running it is the point), fresh events pay nothing, and an unfetchable thread fails OPEN (a lost request is worse than the duplicate this guard prevents; the worst case is exactly the pre-guard behavior). Catch-up replays (`caughtUp: true`) skip both checks — the scan already judged the message unanswered against the same Slack state — but still claim the pair.

10. **Long command output is a Markdown file in the thread** ([command-registry.md](command-registry.md) item 27). `SlackIO.attach({ name, text, lead })` uploads `text` with `files.uploadV2` into the thread (`channel_id`, `thread_ts`, `filename`/`title` = `name`, `initial_comment` = the lead in mrkdwn): Slack renders a `.md` upload as formatted Markdown (bold, lists, inline code, links) in a collapsed preview with an expand control — one message where a 12 000-char `mcp show` used to be four chunks. The dialect translation is the dispatcher's (`toMarkdownDocument`), not the adapter's: the adapter uploads the document it is handed. Needs `files:write` (now in `REQUIRED_BOT_SCOPES`, so `/healthz` names it when the app lacks it); an upload that fails for any reason falls back to the chunked text reply carrying lead + text, so the output always arrives. Its binary sibling, `SlackIO.attachFile({ name, bytes, lead })` ([agent-coding.md](agent-coding.md) item 10), uploads the bytes as the file through the same `files.uploadV2` (`file` = the bytes, `filename`/`title` = `name`, the lead as `initial_comment` in mrkdwn) — a PNG renders inline in the thread. Bytes have no text fallback, so a failed upload propagates and the tool behind it reports the platform's message. Its by-reference sibling, `SlackIO.uploadTicket({ name, size })` ([agent-coding.md](agent-coding.md) item 10, [record 0033](../../decisions/0033-artifacts-move-by-reference-through-r2.md)), is the external-upload flow the bot process never carries bytes through: `files.getUploadURLExternal({ filename, length })` mints a one-shot URL for exactly `size` bytes (a ticket answered without an `upload_url` and `file_id` is refused by name; a refused mint propagates), the run's container POSTs the file to it, and the ticket's `complete(lead)` shares the file into this thread with `files.completeUploadExternal({ files: [{ id, title: name }], channel_id, thread_ts, initial_comment })` — nothing is shared until the POST succeeded. Same `files:write` scope. *Inbound, with a store* ([execution.md](execution.md) item 20): the files neither ingestion pass could carry — a video, an image over the 5 MiB cap, a PDF over the 10 MiB cap, an archive — are not lost: `stagedFiles` leaves them on Slack by reference (`IncomingMessage.staged`: name, size, mimetype, `url_private`, the message `ts`) for a run with a workspace to stage, each within Slack's 1 GiB per-file ceiling, at most ten per message and within `artifacts.inbound.maxBytesPerMessage`; the ones that still cannot travel keep their place in the "could not be passed through" note with the reason, and the secret-file denylist refuses staging as it refuses inlining. The inline caps do not move. Without a store the note reads exactly as before.
11. **A child run's thread of its own** ([thread-admission.md](thread-admission.md) item 6; [agent-conductor.md](agent-conductor.md)). `SlackIO.openThread(lead)` posts `lead` (Markdown converted to mrkdwn) **top-level** in the conversation's channel with `chat.postMessage` — a Slack thread hangs off a top-level message, never off a reply, so a child's thread cannot be a reply in its parent's — and hands back the thread key `slack:<channel>:<ts>` of the posted message, its permalink as the thread's `sourceUrl` when the team URL is known, and a `SlackIO` built from the posted `ts` the way `resumeSlackIO` builds one from a row's parts: the same requester, the same clients and status budget, no triggering event. The child's replies, card, shimmer and history are the new thread's; the lead itself is skipped by `history()` like any triggering message. A `chat.postMessage` answer without a `ts` is refused by name (the spawn relays it as `spawn_failed`), never a thread keyed on `undefined`.
12. **The conversation reader** ([record 0037](../../decisions/0037-a-linked-thread-is-quoted-not-joined.md); `src/channels/slack/references.ts`, `SlackConversationReader`, registered in `src/index.ts` beside the channel directory; the core's contract is [routing-and-config.md](routing-and-config.md)'s references step). `parseConversationUrl` recognises `https://<this workspace's auth.test host>/archives/<C|G|D…>/p<16 digits>` and nothing else — a link on another workspace's host, a files path or a malformed ts is plain text, and until `auth.test` has answered nothing parses, because a guess about which host is ours would be exactly the cross-workspace confusion the grammar refuses; a reply's permalink (`thread_ts`) names its whole thread, a bare permalink names one message. `classifyConversation` is one fresh `conversations.info` per call under a 30 s cache of its own (never the directory's ten-minute stamp cache, which is fail-open for a read): `is_im`, `is_mpim`, `is_shared`, `is_ext_shared`, `is_org_shared`, `is_pending_ext_shared`, a missing channel or any error is `never`; otherwise `public`/`private` by `is_private`, `botIsMember` from `is_member`, and the fresh `name` for the block's header. A failure is not cached. `readConversation` asks `conversations.replies` for up to 1000 replies in one call, maps them through `threadTurns` (no skip ts, no mention strip — a linked thread has no triggering message; the Slack app footer is stripped from every quoted line exactly as it is from the request text and the current thread's history, so a plugin-posted message quotes the user's words and a footer-only message quotes nothing), keeps a bare permalink's one message — matched by its own `ts`; a permalink to a message the mapping dropped, or to a `ts` the thread does not carry, yields no messages and the step refuses rather than quoting the thread the link did not name — or the parent plus the newest replies under the caller's cap, names authors through the cached `users.info` lookup (an unresolvable user by id, an app as `app`) and humanises text as the current thread's is; it never returns files. `requesterIsFullMember` is `users.info`'s `is_restricted` and `is_ultra_restricted` both false; a failure is false. No new scope: the four the startup check already requires plus `users:read` cover it.
13. **Who asked is the person, never `unknown`** (`src/channels/slack/requester.ts`, `resolveSlackRequester`). A message a person typed names them in `user` and that is the requester (`slack:U…`). A message an app posted has no `user` — only a `bot_id` and the name the app chose — and by 2026-09 those were the largest "requester" in the run history: every review a Claude Code session asked for from its owner's thread. The person is still findable and the adapter finds them, in order: (1) the message's own `user`; (2) the **relay footer** the Claude Slack app appends to a post it makes from a session — `Sent by Claude in <#C…|name> on behalf of <…> · <permalink|thread>`, delivered in a `context` block rather than the message's `text` (so the adapter reads the message by `rawTextOf(text, blocks)`, the text plus the block lines it lacks) — **read only when the posting app's `bot_id` is one the operator named in `slack.relayApps`** (a list of Slack bot ids, validated at load; absent or empty means no footer is ever honoured): the `on behalf of` mention IS the requester, with no API call; an older footer without it names only the person's own thread (`thread_ts` when the relayed message was a reply, the bare `p<ts>` otherwise), and one `conversations.replies(limit: 1)` reads that thread's parent, whose `user` is the requester; (3) the app itself, named — `slack:bot:<bot_id>` with the app's display name as `userName` — so a run nobody can be found behind still says who posted it. A footer is message text and any app can write one, so from an app that is not a configured relay — footer or not — the app is the requester, and a thread's parent is never read for an app's reply: the person who started a thread did not ask what an app posted into it (a person's own reply names them in `user` and needs no parent). A footer thread whose parent is itself an app's post, or that cannot be read, falls through to the app; a resolved thread parent is remembered (bounded FIFO, 1000) since one session posts many requests from one thread and a parent's author never changes, and a failed read is never remembered. A resolved relay keeps the poster: `IncomingMessage.relayedBy` → `RunRecord.relayedBy` (the app's display name), so a record can say "alice, via Claude [fixing the build]" without lying about either. The relay footer is chrome like the `Sent using` footer: read for the requester from the raw text, then removed by the same `stripAppFooter` (`slack/threadTurns.ts`) the request text, the thread history and a quoted thread all pass through. The `slack.receive` span carries `requester: message | relay-footer | bot`. Authority is not identity: the person was named by message text, and text is forgeable (the relay gate above stops an unlisted app; the configured relay app's own footer is still its claim, not the person's signature), so the run's actor is the **app on the person's behalf** — `IncomingMessage.postedBy` (`slack:bot:<bot_id>`) makes `resolveChatActor` return an `agent` actor with the app's own grants and `onBehalfOf` the person, whose effective grants are the intersection ([authorization.md](authorization.md) item 14): never more than the Slack baseline plus whatever config grants that app id by name, never more than the person — and every dispatch gate (the agent and repository gates, the GitHub write gate, the router, a steer) decides on that actor, not on the person's id ([authorization.md](authorization.md) item 14). The attribution itself stays as the footer says; an operator who wants a relay app to hold more names its `slack:bot:<id>` in `grants`. The catch-up scan (item 7) replays people's mentions only: an app's relayed mention that lands during a blackout is not re-dispatched, since a scan cannot resolve its person after the fact — the posting session sees no card and re-sends. Cost by user ([costs.md](costs.md) item 10a) bills the run to them and the **me** toggle claims it (a `slack:bot:…` id is never looked up by email), and the run's label and Request block name them. Records written before this keep `slack:unknown`; their stored `input` text still carries the footer, so a backfill can re-resolve them later.
14. **A confirmation is two buttons in the thread** ([record 0044](../../decisions/0044-a-routed-write-is-confirmed-in-proportion-to-its-blast-radius.md), "The confirmation"; [routing-and-config.md](routing-and-config.md) item 25; `SlackIO.offer`, `handleConfirmClick`, `clickSlackIO` in `src/channels/slack.ts`). Slack is the first adapter to implement `ChannelIO.offer`. **The offer** is one `chat.postMessage` in the thread whose blocks are a `section` carrying the exact line to run as a code span (a fenced block when the line itself holds a backtick, which a span cannot; `&`, `<`, `>` escaped, as in every text the adapter posts), a `context` with the risk line when the command declares one (no context block otherwise, and no footer — [routing-and-config.md](routing-and-config.md) item 28); config risk is the platform-neutral line rendered once from the accepted target and caller display origin — own settings, the named channel or `this channel`, every channel for the organization, or the affected person's GitHub setting — and the stored row, fallback text and Block Kit context carry that same line, followed by an `actions` block with **Run** (`action_id: confirm.run`, primary) and **Cancel** (`confirm.cancel`), both with `value` = the offer's id: the channel carries the id and nothing else, and the message's `text` is the offer's text (`renderOffer`), so a client without blocks still shows the line to type. **A question's offer** ([record 0054](../../decisions/0054-a-refusal-the-person-caused-is-one-question-with-a-best-guess.md); [routing-and-config.md](routing-and-config.md) item 21) sets `offer.question` and posts the refusal's sentence as its own `section`, `Did you mean:` over the corrected line as the code span in a second, the evidence as the `context`, and **Yes** (`confirm.run`, primary) and **No** (`confirm.cancel`) carrying the offer's id — the same two actions, so one intake serves the confirmation and the question alike and Yes consumes the row exactly as Run does; the fallback `text` is the question as a channel without blocks reads it, the line to type in it. The taken-offer note reads the pressed button's own label off the payload (`*Yes* clicked by <@U…> · running…`, `takenOfferNote`), falling back to Run and Cancel on a payload without one. **The click** is a `block_actions` payload Bolt delivers over the same Socket Mode connection as the events, matched by `app.action(/^confirm\./)`, and the intake runs in this order and no other: (1) `ack()` — Slack gives a listener three seconds, and nothing below may cost them; (1a) **the offer is taken**: one `chat.update` on the offer message drops its `actions` block and adds a context line naming the button and who pressed it (`*Run* clicked by <@U…> · running…`, `takenOfferBlocks`), so a second press has nothing to press and Slack's brief grey flash never turns back into live buttons while the command runs — Slack has no disabled state for a button, and removing it is the idiom; a take that fails is logged and the click proceeds, since the core's consume is single-use whatever the message shows; (2) the clicker resolved as a message's requester is — `resolveSlackRequester` on the payload's `user.id`, then `chatActorOf` with the offer's channel and thread as origin — identity, never authority: the adapter compares nothing, the core's consume judges the requester against the actor ([authorization.md](authorization.md) item 16); (3) the handle, `clickSlackIO`, built on `resumeSlackIO`'s shape for the offer's channel and thread, with the offer message (`message.ts`, its text, its blocks) taken from the payload — no store of posted messages, the click carries everything; (4) `dispatchClick(deps, { kind: confirm | cancel, id: action.value, actor, io })`; (5) the core's first reply through the handle **completes the offer message** with `chat.update`: the offer's own blocks minus the `actions` block — the line stays above the answer, because the core's refusals say "type the line to run it" — and the answer as one `section` under them (an answer longer than a section's 3000 characters continues in the thread), so a confirmed run reads the receipt and the command's text, a cancel reads `Cancelled; nothing ran`, and a refused click reads its named line; a later reply on the same handle — a deferred command's settle follow-up — posts in the thread as a typed command's does. Nothing thrown leaves the handler: a failure is logged under `[confirm]` and the offer message is completed with `this click could not be handled; type the line to run it`, best-effort; a payload the adapter did not post — no value, an unknown `confirm.*` id, no message — is acked, logged and ignored. **The app setting is human-gated** ([release-and-deploy.md](release-and-deploy.md) item 30): the manifest (`docs/public/slack-app-manifest.yaml`) turns interactivity on (`settings.interactivity.is_enabled`; with Socket Mode no request URL), and an app created from an earlier manifest needs *Interactivity & Shortcuts* switched on by hand. With it off nothing regresses: the offer message posts with its buttons, a click never reaches the bot (Slack tells the clicker the app is not configured for it), the message still carries the line, and the person types it, as before. **The offer is the only message Slack renders for a held write** ([record 0069](../../decisions/0069-the-one-door-has-one-execution-path-a-bind-runs-clicks-or-routes-a-violation-is-re-asked-a-disagreement-floors-and-no-chat-surface-hands-back-a-line-to-retype.md)'s table; the one-execution-path plan's click unit): no `To run this:` line accompanies the click, whichever caller minted it, and a mint the core could not make reaches the channel as a refusal naming why ([routing-and-config.md](routing-and-config.md) item 25), never a line to retype.

15. **The intake gate before the 👀** ([record 0058](../../decisions/0058-a-thread-reply-is-read-before-it-is-answered-intake-decides-whether-the-bot-was-addressed.md); [routing-and-config.md](routing-and-config.md) item 27; `receiveSlackMessage`, `gateThreadReply` and `wireIntakeGate` in `src/channels/slack.ts`; the verdict itself is the core's `decideIntake`, `src/core/intake.ts`). An unmentioned thread follow-up (`SlackEvent.trigger: "thread-follow-up"`) gets its verdict before anything visible or costly: after `dedupeDelivery` has claimed the pair (item 9) and before the 👀 ack, the ⏱ note and the file downloads. A mention, a DM and a top-level post never pass through the gate in any mode, and a message a stored receipt already decided (`SlackEvent.intakeDecided`) is never decided twice — the catch-up's act sets the flag on every gated replay it dispatches (item 7, `actOnMissedMessage`): it reads the receipt — or decides receipt-less candidates itself over the paged thread — before `handle()` and acts on the stored verdict, so a replayed addressed reply whose run died is re-run instead of refused as another caller's row (the silent drop the old blanket `caughtUp` bypass existed to prevent; that bypass is lifted). A caught-up replay reaches the gate only when it arrives undecided — a mode flip between the scan and the act — and is then decided fresh like a live reply (its `trigger` labelled truthfully, item 7). **The modes** (`intakeModeFor`: thread scope > user > channel > the `intake` block's default, `classify` when unset): `always` — the adapter never calls intake and never touches the ledger for that reply, today's path byte for byte; `mention` — `silent` with `source: mode`, no model call, a receipt written; `classify` — one forced tool call over the thread's newest turns. The turns are the page `threadIfBotInIt` already fetched for a thread of 50 replies or fewer; past that, the gate cursors forward from the prefetched page's end (`conversations.replies` pages oldest-first, so a `latest`-bounded page would return the thread's head) — up to `INTAKE_TAIL_PAGES` more pages, duplicates dropped — and keeps the newest turns (best-effort — a failed or truncated fetch judges over what is in hand). The labeller compares each turn's `user` to the bot's own user id (`threadTurns` is unchanged): `bot` is the bot's own post, `requester` the person of the thread's newest addressed run (`requesterOf` over the runs page, read once and handed on to `dispatch()` as `DispatchOptions.thread` so the eight-run page is read once per reply), `person` anyone else; the facts computed by code ride beside them — the live run off the runs page, replier-is-requester, the bot's last turn, another person mentioned, the person a pending confirmation waits on (`pendingByThread`), the bot-started parent, and the operator's own pending question off the same runs page (`pendingQuestionOf` — [routing-and-config.md](routing-and-config.md) items 27 and 29, issue 2046: the one fact that decides `addressed` without a model turn, so an answer to the bot's own question needs no mention) — both store reads best-effort, an empty fact never blocking the verdict. **The verdict acted on is the stored one**: only the caller whose insert stood — `inserted`, or the degraded `failed`/`absent` — acts on `addressed`; a row another caller stored means no action here, whatever the verdict reads. On `addressed` the 👀 lands after the receipt's write was attempted and the reply proceeds exactly as today; on an ordinary `silent` nothing happens — no reaction, no download, no card, no run — and the reply's only trace is the receipt and the span; on a provider failure the receipt carries `providerFailure`; the live path renders its no-lease sentence only for `inserted`, `failed` or `absent`, never for `existing`, and no reaction, download, card or run follows, so the intake door never drops an outage invisibly. Delivery is a separate durable fact: `claimIntakeDelivery` atomically names the receipt key, the unique poster and a bounded claim before a stored failure may post; success closes it permanently, rejection releases it, and catch-up may claim an existing undelivered receipt. The Slack snapshot reconciliation runs only after that claim, so concurrent processes cannot both post; an owner that dies before finishing is recoverable after the claim bound. **Degraded, never silent by accident**: a failing read decides as if no receipt; a failing write still dispatches with `intakeReceipt: failed`; the null ledger acts with `absent`, and the startup log prints `degradedIntakeLine()` exactly once (`wireIntakeGate`, wired in `src/index.ts` — where a missing model ref leaves the gate unwired and thread replies run as `always`, degrade open). **The span says what happened**: every verdict sets `intake`, `intakeSource` and `intakeReceipt` on the `slack.receive` span — three identifier-valued keys of the closed attribute table; the reason is free text and lives on the receipt row and the `[intake]` log line, never on a span.
16. **A person's actor id renders as a mention Slack resolves** (`mdToMrkdwn`, `src/channels/mrkdwn.ts`). The core prints a person's platform-namespaced id (`slack:U…`, AGENTS.md invariant 4) as plain text everywhere it names someone — a refusal's admin hint (`adminsHint`, `src/config.ts`, plain ids joined `, `), a child or unit thread's lead naming the requester (`childThreadLead`, `unitLead`), `config show`'s restricted lines — and only this adapter turns the id into platform syntax: `mdToMrkdwn`, the one renderer every outbound message passes through (`SlackIO.reply`/`post`/`openThread`, the file leads, the index posters), rewrites a bare `slack:U…` standing alone as a word — and repairs a stray pre-wrapped `<@slack:U…>` — into `<@U…>`, stashed as structural syntax so the prose escape leaves the mention live. Non-Slack surfaces (the web dialect, HTTP, MCP, the CLI, model prompts such as the fold and follow-up attributions of `threadEvents.ts`) keep the plain id or the display name they use today. Word-bounded and deliberate: an id inside a longer token (`user:slack:U…` scope keys), inside a code span or fence, or inside a URL — a markdown link's (stashed) or a bare one (the lookbehind excludes URL-structural chars: `=`, `/`, `?`, `#`, `&`) — stays literal, and a non-person id (`slack:C…`, `slack:bot:B…`) is untouched. The guard: no text the adapter sends may carry `<@slack:` or a bare `slack:U…` id — enforced suite-wide by the shared client wrapper (`guardOutbound`, `src/channels/testing/outboundGuard.ts`) the slack tests construct their fake Web API clients through, so a send site outside `mdToMrkdwn`'s funnel (the status card's `escapeMrkdwn` path, `SlackIO.offer`) is scanned too.

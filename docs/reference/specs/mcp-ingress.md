# MCP ingress: authenticated channel adapter #4

The core is channel-agnostic: a channel is only a transport that turns an inbound request into an `IncomingMessage`, calls the core `dispatch()`, and provides a `ChannelIO` to reply through. Slack (#1), the CLI (#2), and HTTP ingress (#3) already prove this; MCP is adapter #4 — an MCP client drives Switchboard exactly like the HTTP ingress does, so the same request reaches the same agents under the same permissions. The [HTTP ingress](http-ingress.md) came first; MCP reuses its shape.

The maintained official MCP SDK handles modern and legacy Streamable HTTP. Authentication and body limits run before protocol handling. Clients declaring form elicitation receive confirmation inside their MCP host. Clients without form support use URL elicitation when advertised, or a saved browser link when the authenticated browser approval route is configured. Without a usable display path they cannot mint fresh consent. Browser connection setup remains separate. Personal credentials live in the existing digest store. No parallel session or approval store is introduced.

## Behavior

Hosted Access device approval may pin the Access issuer, app audience, fixed organization and exact subject as version 1 public metadata from server configuration. No JWT or grant snapshot is stored. Normalization does not fill missing realm proof; an occupied digest cannot acquire or change it, so old or changed-realm devices use the visible revoke/reissue path.

The composed request thread key must fit the ledger's 256-character claim key after the five-character `#host` suffix. A longer channel/thread pair is refused before dispatch.

1. **Pure transport, same core.** A `tools/call` for the `dispatch` tool becomes an `IncomingMessage` and is handed to the unchanged `dispatch(deps, msg, io)` — no dispatcher, runner, or permission change. For machine credentials, the tool requires the configured `dispatch` grant (an unlisted credential holds nothing): a registry-only token (e.g. `["runs:read"]`) gets JSON-RPC `-32001` with `data.code:"unauthorized"` and `dispatch()` is never called, while its registry tools keep working. Identities are platform-namespaced (invariant 4), mirroring HTTP but with the `mcp:` prefix: `userId` = `mcp:<subject>`, `channelId` = `mcp:<channel|default>`, `threadKey` = `mcp:<channel>:<thread|default>`, `messageId` = a fresh `mcp:`-prefixed UUID (40 characters) per admitted dispatch. The message id is retained by the in-flight async dispatch and reaches the original-unit recovery caller with the user and thread identities; it is not derived from mutable text/thread or the reusable JSON-RPC id. A repeated call, even with identical arguments and JSON-RPC id after a lost response, receives a new message id: ingress does not deduplicate or replay the first recovery action. Confirm the first run's outcome before any intentional new attempt; this identity prerequisite alone does not make lost-response retry safe. Before either key is composed, every supplied `channel` and `thread` is validated as its own component: it must be a string, non-empty, at most 128 characters, and contain neither `:` nor `#`; the identity-pinned channel is checked by the same rule, and the call's channel is still checked before a valid pin overrides it. A refusal is JSON-RPC `-32602` and nothing is dispatched, so two component pairs cannot collapse to one key and a caller cannot forge the reserved `#host` suffix.
2. **SDK methods.** The maintained MCP server SDK owns framing and negotiation. Legacy requests use its stateless JSON transport; current requests use its per-request handler.  `initialize` returns the protocol version, `capabilities.tools`, and `serverInfo`. `tools/list` advertises the hand-written `dispatch` tool — description "send a request to Switchboard", `inputSchema` `{ text: string (required), thread?: string, channel?: string, async?: boolean }` — FIRST, followed by every [command registry](command-registry.md) command exposed to MCP (`runs_list`, `runs_get`, `runs_events`, `runs_friction`, `runs_stop`, `steer_run`, `friction_report`, `friction_propose`, `repo_list`; name = `<group>_<verb>`, `inputSchema` derived from the command's zod input, `annotations` the definition's blast radius in MCP's own `ToolAnnotations` names — [command-registry.md](command-registry.md) item 29: `readOnlyHint` when the effect is read, `destructiveHint` when `blastRadius(def)` is `destructive` (false for a read and for an exec-class write such as `repo_test`, whatever they declare), `idempotentHint` and `openWorldHint` as the definition declares them, each false unless it says otherwise, because MCP presumes a non-read-only tool destructive when the hint is absent; the shape is the bot's own client type `McpToolInfo.annotations`, and the hand-written `dispatch` tool carries none). The channel also advertises `approval_resume` and `approval_cancel`, which return a saved offer to the shared core click path; neither accepts changed arguments or a confirmation boolean. `tools/call` for `dispatch` runs the request and returns `{ content: [{ type: "text", text: <reply> }] }`. A JSON-RPC notification (no `id`, e.g. `notifications/initialized`) is accepted and never answered (HTTP 202, empty body).
   **Registry tools.** `tools/call` on a registry name invokes the command with caller `{ kind:"mcp", id:"mcp:<subject>", actor: <the service Actor whose grants come from config>, channel?: "mcp:<pinned channel>" }` — the raw arguments go to `invoke` unchanged; authorization (the policy table: an unlinked `dispatch`-only credential holds no registry command; a server-verified Slack or Access account with `dispatch` may cancel only its own run after exact destructive consent, while foreign targets and read-only credentials remain refused) and input validation live in the registry, not here. Success → `{ content: [{ type:"text", text: "<group>.<verb>: ok\n" + JSON.stringify(output) }] }` (the JSON is byte-identical to the HTTP and CLI surfaces); failure → a JSON-RPC error with `data.code` ∈ `unauthorized|invalid_input|not_found|conflict|internal` (codes `-32001`, `-32602`, `-32002`, `-32003`, `-32603`). No output ever contains a [run](../vocabulary.md#run)'s capability token.
3. **Single-shot `ChannelIO`.** `McpIO.reply()` collects text and the collected text is the tool result content; `status()` is an honest no-op handle (no live surface to edit in one shot); `openThread()` opens a stable job thread for a coordinator unit; `history()` is `[]` (a tool call carries no prior turns — conversation state, if any, rides on `threadKey`).
4. **Bearer auth, fail-closed.** `authenticate(headers, config)` requires `Authorization: Bearer <token>`; an operator token maps through `SWITCHBOARD_INGRESS_TOKENS`. If it does not match, a 64-hex personal bearer is hashed and looked up in the personal store before the body is read. Unknown or revoked tokens return `401`; a store failure returns `503`. With no token path or SSO verifier configured the endpoint returns `503`. The mapped subject becomes the credential id, so a token can only act as its assigned identity and existing gates apply unchanged. Operator tokens may pin a `channel`. No bearer is logged or stored in the personal store.
5. **JSON-RPC framing.** Malformed JSON → `-32700` (id `null`); a non-object / array / method-less message → `-32600`; an unknown method → `-32601`; an unknown tool or a missing/blank/non-string `text` argument → `-32602`. Post-auth JSON-RPC responses carry HTTP `200`; transport gating uses `405` (non-POST) / `401` / `403` (cross-site SSO) / `503`.
6. **Input hardening.** The body is size-capped at read time (~1 MB via http.ts's `readBody`, `413` before it is fully buffered, request destroyed). Malformed env token config is treated as "no tokens" (disabled), never as open (proven by http.ts's `parseIngressTokens` tests, reused unchanged).
7. **Wiring keeps health + HTTP ingress working.** The `PORT` server routes `/mcp` to the MCP handler, `/ingress` to the HTTP handler, and retains the existing health probe alongside the other HTTP routes. Static `SWITCHBOARD_INGRESS_TOKENS` credentials work on both routes; with none configured the startup log says `static ingress tokens absent`, and HTTP ingress returns `503`. The log separately says personal MCP approval is `available with grant` when Access is configured (otherwise `unavailable without Access`). An already approved personal bearer can still authenticate on `/mcp` with its grant when static ingress tokens are absent; HTTP ingress never accepts personal bearers.
8. **Verified requester and bounded authority.** A server-verified personal connection names one immutable user, selected at browser approval: the exact authenticated Access account. A matching email cannot select a Slack identity. The `mcp:` credential remains `authenticatedAs`. The same policy table must admit both the user and the delegated credential. This preserves native conditional personal rights without lending a read-only connection write authority. Code access, repo-memory ownership, private visibility and author bindings retain their separate checks. A configured email link that cannot be verified is refused; it never falls back to broader machine rights. Unlinked machine credentials retain their explicit grants. The `personal:` subject family authenticates only through the durable digest store, not a static token claiming that prefix.
9. **Job-shaped dispatch.** HTTP and MCP call the same `dispatchSingleShot` lifecycle. `dispatch` with `async: true` validates the same text, identity and grants, starts the normal core run and returns an MCP tool result with `structuredContent: { runId, runUrl, threadKey }` as soon as `runStarted` fires. The tool result's text points to `runs_get`; `runs_events` reads progress. A request with no run returns its ordinary answer. Without `async`, the reply remains synchronous. Both adapters give Ship a job thread capability: a coordinator unit supplies its stable instance/unit key to `openThread`, which derives the same child thread key across retries and bot restarts. Unrelated children get distinct keys. Replies after the one-shot request are recorded on the run; a person with dashboard access can use the run page. To observe through MCP, grant the credential `runs:read` and its machine channel in addition to `dispatch`; to steer by run id, grant `steer:write` (the named run's owner rule and live agent allowlist still apply); restricted agents and repos need their own grants. Ship's coordinator and run history must be enabled independently of ingress.
10. **Personal setup.** `switchboard connect <host>` assumes HTTPS; `connect --url <origin>` remains valid. It creates a 256-bit bearer locally and opens `/settings/connect?challenge=<sha256>`; the URL contains no bearer. The dashboard gate verifies the signed-in person and email. The page shows a short code derived from the digest; a same-origin POST approves the digest in the ConfigDO (or a mode-600 file for a local installation). A single `mcp:personal:*` grant supplies the team's policy without adding each person to config or the static 1Password map. The CLI polls `initialize`, calls `runs_list` as a real permission check, then writes the bearer to its mode-600 client profile and adds a stdio MCP proxy to Codex config. The stored user id is the exact authenticated Access subject, never client supplied or selected by email. Repeated approval preserves the original account, creation time and metadata. A digest already bound to another account or an explicit legacy Slack identity cannot be rewritten; a new connection is required. Protected legacy records without a user id normalize only to the Access account named by their immutable personal subject. Explicit Slack or mismatched Access records cannot authenticate; they remain visible for owner revocation with a reissue notice. The state Worker stores the user id and checks digest collisions atomically. Revocation deletes the digest immediately. The stdio proxy reads the private profile and forwards JSON-RPC envelopes; Codex needs no bearer environment variable.

11. **Same SSO as the browser.** The MCP handler receives the existing `DashboardVerifier`. After static and personal bearer checks, the `access` strategy verifies the edge's signed assertion; the `token` strategy verifies its configured credential. A named session resolves through the same `callerFor` and `resolveAccessActor` as the browser: `access:<sub>` grants, verified Slack link and channel membership. No `mcp:personal:*` grant or new token store is needed for SSO. SSO dispatch reaches the core agent and repository gates just like browser chat; only machine credentials need the transport-level `dispatch` action. MCP uses one case-insensitive, whitespace-normalizing bearer parser for personal-token classification, digest lookup and saved-confirmation connection binding. A stored personal bearer keeps its own identity and delegated limits even beside an SSO credential; revocation and store failure cannot borrow an Access assertion. A 64-hex bearer absent from the personal store can authenticate only if the token strategy proves that exact configured dashboard credential. Missing, forged, expired, wrong-issuer or wrong-audience assertions return `401`; verifier faults return `503` and log their cause with presented credentials and known secret formats redacted. Service assertions and `none` do not authenticate an MCP browser session. The existing browser origin guard rejects cross-site session requests with `403` before body read. Static and personal bearers retain their existing policy. Saved SSO forms bind to the OAuth bearer, or the verifier's signed assertion header when no bearer exists; resume re-verifies the credential before consuming the saved action. Cloudflare Managed OAuth on the existing browser Access application handles discovery, browser sign-in and refresh outside Switchboard. Other SSO providers use the same verifier interface.

## Approval flow

Both prose/typed dispatch and direct command tools reach the registry's confirmation policy. MCP annotations are client hints, not permission or consent. A model-supplied `confirm: true` or a bare elicitation acceptance cannot approve an operation. A schema-valid host form response is accepted only for a server-minted form challenge bound to the exact saved action and originating credential. The host owns its human interaction; form acceptance is not independent proof of a physical human click.

On a current client declaring form elicitation, the official SDK returns an input-required result with an opaque saved-offer id, exact action and risk, and an approve/cancel choice. The host returns the user's choice outside tool arguments. The server validates the response schema, requester, credential and original tool/argument hash, then records transport-neutral consent in the existing row. Atomic consumption executes the stored action once through the shared click path. Decline or cancel removes the offer without execution.

`approval_resume` can request the same form for a pending saved action; calling it alone cannot create consent. Already-approved exact rows resume directly without another form or browser, including legacy browser rows. A client without form support receives URL elicitation when advertised, otherwise an ordinary result containing the saved browser link, offer id and expiry. Both require the configured authenticated browser route, a verified requester and an available confirmation store. Opening the URL or accepting a URL prompt is not consent. The browser POST records consent only; the original MCP connection resumes the stored action. The saved browser/form mode cannot change when client capabilities change. Without a usable display path or verified requester, the request is refused before minting an offer. An SSO browser can approve only a browser-bound row whose saved credential and authenticated actor equal its verified `access:<sub>` and whose person matches the saved requester. Browser authentication does not attest the original OAuth credential: the original MCP resume re-verifies its own credential and exact connection digest before execution. Static and personal browser approvals retain their credential lookup and revocation checks. Expiry, cancellation, requester/connection mismatch, changed request arguments, lost permission and duplicate confirmation cannot execute the action. The store survives restart. After an uncertain result, the id is not replayable: inspect the original run history before requesting another action.

The State Worker must expose the confirmation `get` and atomic `approve` routes before the new bot accepts offers. These extend the existing table and execution path. Source, CI/review, deployment and live acceptance remain separate stages.

## Native admission receipts and current credential proof

A failed optional final receipt refresh cannot erase the receipt this invocation already obtained. The adapter returns that original receipt when only refresh is unavailable. Explicit current refusal, fencing and conflict keep their existing dispositions. An unavailable initial admit-store result remains unknown; no receipt or owner is invented. Unconfirmed admission says “Admission could not be confirmed,” rather than claiming that nothing was admitted.

The MCP SSO verifier registry retains a current revalidation function for the exact native identity, credential digest and checked actor/connection binding. It does not key authentication by a request hash or conversation thread, and it never caches an allowed decision. Every use revalidates the exact credential. Original references and context-specific source authorities remain unchanged; the resolver rebuilds current grants for each original context. Without fresh exact-credential proof after restart, the original source stays unavailable. A different credential, expiry, revocation or a foreign binding cannot unlock it or replay an unknown owner. Different-credential historical recovery remains unqualified.

MCP and HTTP responses add a call-local diagnostic with the real request trace ID, closed admission stage/reason and receiptObserved. True means a receipt was observed; false does not prove no commit. A blocked historical source can also report its source family and same/different/unknown credential relation, without an identity or digest. The existing authorized trace reader accepts that trace ID. Unavailable or thrown admission ends the request trace as error; a known receipt with lost optional refresh keeps its admission result and records the refresh gap. Its existing request-root event also carries the receipt ID, refresh stage and a closed refresh failure class. Unclassified exceptions stay unknown; raw exception names and prose are never copied. Diagnostics contain no request body, actor, credential, epoch or raw exception, and cannot change admission when observers throw, reject or attempt mutation. No Worker wire result, durable schema or permission gate changes.

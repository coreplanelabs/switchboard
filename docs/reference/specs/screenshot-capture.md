# Screenshot capture infrastructure

This prerequisite extends the default capture contract in [Docs site](docs-site.md), item 20. It changes no product route, component, fixture data or organization behavior. Existing surfaces keep their desktop light/dark outputs. A future isolated preview registers its own server and inputs; it does not extend the legacy fixture server merely to register a capture.

- **Code**: [`scripts/screenshots.mts`](../../../scripts/screenshots.mts), [`scripts/web-preview.ts`](../../../scripts/web-preview.ts), [`src/docs/screenshotManifest.ts`](../../../src/docs/screenshotManifest.ts).
- **Tests**: [`src/docs/screenshotManifest.test.ts`](../../../src/docs/screenshotManifest.test.ts).

## Contract

A surface declares its local fixture server and extra configuration files. Its captures default to desktop, 1440×900 at 2×, in light and dark, with the existing `<surface>-<theme>.png` filenames. Explicit profiles select their own dimensions and suffixes (for example a phone viewport with `-phone`). A profile describes viewport capture, not mobile user-agent or touch emulation. Only supported configuration is accepted; surface names, profiles, suffixes, themes, repository input paths and local preview routes are validated before generating, deleting or overwriting outputs. Output uniqueness is checked across the entire registry.

The manifest records every resolved capture, its theme, dimensions, output filename and screenshot options, together with the fixture configuration and deterministic browser settings. Its configuration hash is canonical and surface-local. The registry is literal data: adding an independent row does not change another surface's hash. All executable capture/manifest mechanics remain shared hashed inputs. The declared fixture server and configuration files, their import dependencies, the page's imports, shared renderer, styles and tokens remain tracked. Dependency hashes select the renderer, build and capture packages and their resolved lockfile graph (including installed optional and peer dependencies), not unrelated CLI dependencies or scripts. CSS imports/plugins, bundled icon collections and the capture launcher participate too. Relevant dependency declarations and build/capture scripts remain hashed; package release labels and unrelated lockfile entries do not. Binary inputs are hashed as bytes. Missing required dependencies fail closed.

Generation and checking use the same resolver, manifest constructor and drift predicate. The clock, locale, timezone, theme initialization, reduced motion, font readiness and settle behavior stay deterministic. Compatible captures reuse the historical warm browser context per fixture and theme/profile so cold font loading does not race scroll-to-result rendering. Each fixture server accepts `PORT` and `SWITCHBOARD_PREVIEW_NOW`; captures explicitly select full capabilities and the local web bundle. Captures whose decoded pixels equal the existing PNG retain the original PNG bytes. A changed image requires a before/after comparison and an explanation, not blind acceptance of a golden.

## Validation criteria

| Criterion | Proof |
|---|---|
| Existing profiles, viewport and all existing output names are unchanged | `[unit]` `src/docs/screenshotManifest.test.ts::capture profiles::preserves all existing desktop outputs and themes` |
| Desktop and phone select declared viewports and deterministic suffixes | `[unit]` `src/docs/screenshotManifest.test.ts::capture profiles::resolves desktop and phone into the browser and output options used by generation` |
| Duplicate profiles, suffix collisions and unsafe or unsupported configuration fail before writes | `[unit]` `src/docs/screenshotManifest.test.ts::capture profiles::rejects ambiguous profiles and outputs`, `src/docs/screenshotManifest.test.ts::capture profiles::rejects unsafe paths and unsupported configuration` |
| Resolved dimensions, profile, theme, route and output behavior are deterministically hashed | `[unit]` `src/docs/screenshotManifest.test.ts::capture profiles::hashes every resolved capture setting deterministically` |
| Registering an isolated fixture/profile leaves existing hashes unchanged; executable mechanics remain tracked | `[unit]` `src/docs/screenshotManifest.test.ts::surface isolation::adding an isolated fixture and profile registration leaves existing hashes unchanged`, `src/docs/screenshotManifest.test.ts::surface isolation::does not exclude executable registration code or capture mechanics` |
| Local inputs invalidate only their consumers; shared renderer and tokens invalidate every affected surface | `[unit]` `src/docs/screenshotManifest.test.ts::surface isolation::invalidates only consumers of a surface-local dependency`, `src/docs/screenshotManifest.test.ts::surface isolation::invalidates all consumers of shared rendering inputs` |
| Actual imported dependencies and missing declared inputs cannot silently disappear | `[unit]` `src/docs/screenshotManifest.test.ts::surface isolation::tracks fixture and shared runtime import closures and fails on missing inputs` |
| Warm-context grouping preserves the historical theme ordering without mixing fixtures or viewports | `[unit]` `src/docs/screenshotManifest.test.ts::capture profiles::reuses one context per fixture and resolved browser profile in historical theme order` |
| Dependency versions and binary inputs stay tracked without invalidating on package release labels | `[unit]` `src/docs/screenshotManifest.test.ts::surface isolation::tracks dependency versions without making a package release invalidate pictures`, `src/docs/screenshotManifest.test.ts::surface isolation::hashes binary local inputs by bytes rather than lossy text decoding` |
| Dependency drift follows only the rendering/build/capture graph, resolves nested packages and optional/peer edges, and ignores unrelated dependencies/scripts and JSON key order | `[unit]` `src/docs/screenshotManifest.test.ts::capture dependency graph::ignores unrelated dependencies, scripts and lockfile entries`, `src/docs/screenshotManifest.test.ts::capture dependency graph::tracks renderer, build, capture, styles, icons and resolved transitive dependencies`, `src/docs/screenshotManifest.test.ts::capture dependency graph::tracks only the surfaces importing a local package`, `src/docs/screenshotManifest.test.ts::capture dependency graph::fails closed on missing required packages but allows absent optional edges`, `src/docs/screenshotManifest.test.ts::capture dependency graph::canonicalizes dependency metadata instead of hashing JSON key order` |
| Bundled tarballs and linked workspace dependencies remain tracked without following unrelated hoisted packages or workspace release labels | `[unit]` `src/docs/screenshotManifest.test.ts::capture dependency graph::tracks bundled packages through the owning tarball instead of a hoisted namesake`, `src/docs/screenshotManifest.test.ts::capture dependency graph::follows workspace links without hashing their release labels` |
| Unrelated CLI dependency and script edits leave every registered surface's hashes unchanged | `[unit]` `src/docs/screenshotManifest.test.ts::capture dependency graph::leaves every registered surface current after an unrelated CLI dependency or script changes` |
| Every generated output is recorded, missing or extra output detected, and generation/check agree | `[unit]` `src/docs/screenshotManifest.test.ts::capture profiles::records every output and uses the same drift predicate for generation and check`; `[unit]` `src/docs/screenshotManifest.test.ts::the repository's screenshots::each surface's manifest inputs equal the tree's, and every picture is present` |
| Pixel-identical recaptures keep original PNG bytes | `[unit]` `src/docs/screenshotManifest.test.ts::PNG preservation::retains original bytes only when decoded dimensions and pixels match`; `[agent]` the generation receipt must report byte retention for identical pixels, and a forced repeat must leave PNG bytes unchanged. |
| Existing images have been compared, and repeated captures remain deterministic | `[agent]` Run `npm run screenshots:gen`, compare all existing PNGs against the base in decoded RGBA pixels, explain any changed pixels, then force a second generation and compare again.

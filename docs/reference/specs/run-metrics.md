# Run metrics

Every finished run writes one flat metrics point into a Workers Analytics Engine dataset, beside the one commit its record already makes ([decision 0063](../../decisions/0063-every-finished-run-writes-one-metrics-point-and-a-metrics-page-reads-the-trend.md)). The bot computes the point (`pointOf` in the node-free `src/core/runMetrics.ts`) and sends it beside the record on `POST /runs/put` and `POST /runs/finish`; the state Worker's `RunHistoryDO` — the only writer of finished records — decides whether the row *turned final* on that write (`pointTurnsFinal`) and writes the point to the dataset AFTER its transaction, so a run is counted at most once however many times its record is written (the tombstone, the finish, a review-artifact rewrite, a retry). The binding is optional on the Worker and the whole path is advisory: without it, without a point, or with a sink that throws, every answer is byte-identical. The record itself is untouched — the point travels beside it, never on it ([run-history.md](run-history.md) items 27, 33 and 44 name the three writes this rule governs). The price table is [costs.md](costs.md)'s `costs.prices`; the reader over the dataset is later work of the same decision.

## Behavior

1. **The point.** `RunMetricsPoint = { indexes: [string]; blobs: string[]; doubles: number[] }` — the platform's own positional shape. `POINT_COLUMNS` is the ONE ordered table naming every position: sixteen blobs (`schema` — the literal `"1"` — `agent`, `preset`, `model`, `status`, `failure kind`, `dominant friction`, `channel`, `repository`, `machine class`, `route class`, `reply`, `lineage`, `requester`, `identity`, `run id`) and twenty doubles (`wall` = `finishedAt − (receivedAt ?? startedAt)`; the seven partition terms of `diagnosis.shape`, zero when absent; `turns`; the four token counts summed over `usage.byModel`; `dollars` = `llmUsdOfUsage(usage, prices).usd`; `steps`; `tool calls`; `events` = `eventCount`; `unpriced tokens` = `llmUsdOfUsage(...).unpricedTokens`; `minutes` — the profile's, zero when absent; `finished at`), the index the agent name (`unknown` for a record naming none). It is typed so a position added without a name fails to compile, and `blobColumn`/`doubleColumn` resolve a name to its `blob<n>`/`double<n>` — a reader's query never carries a magic number. `pointOf(record, prices?)` returns `undefined` for a record with `provisional: true` and for nothing else; an absent optional field is the empty string (blobs) or zero (doubles); `route class` is `routed` when the record carries a `route`, else `chosen`; `reply` is `ok`/`failed`/`none` off `replyOk`; `lineage` is `child` when `parentRunId` is present, else `root`; `dominant friction` is the `FrictionCategory` with the largest `durationMs` among those with a count (`dominantFriction`), empty when none has one. Every blob and the index are capped at 96 bytes, and `pointOf` never reads `activity`, `label`, `events`, `verdict`, `handoff`, `dispositions` or `diagnosis.verdict` — no free text reaches the dataset. `isRunMetricsPoint` accepts exactly one index, sixteen strings each at most 96 bytes, twenty finite numbers, and nothing else; the Worker validates an incoming point with it and answers `400` by name (`point must be a RunMetricsPoint`) for anything else.
2. **The emission rule.** `pointTurnsFinal(existing, stored)` is true exactly when `stored.provisional` is absent and `existing` is `undefined` or carries `provisional: true` — there is deliberately no `finishedAt > startedAt` term (a plain `put` of an `interrupted` record over no row is a run counted once). `upsertInTransaction` reads `summary_json` beside the three columns it already reads for the existing row, parses ONLY its `provisional` field (never the whole summary), and returns `turnedFinal` beside `stored`, `retained` and `rewritten`. `put` and `finish` call `sink.write(point)` AFTER their transaction — the `sendRunFinished` placement — when `turnedFinal && stored` and a point was sent; a review-artifact rewrite ([run-history.md](run-history.md) item 44) and an identical retry land on a final row, so they write no second point, and a record the write itself trimmed (`stored: false`) writes none.
3. **The guard: a provisional record never overwrites a final row.** `upsertInTransaction` answers a `put` of a `provisional: true` record over an existing non-provisional row as `{ ok, stored: true, retained, rewritten: false, turnedFinal: false }` and writes NOTHING — the row, its events and the sessions table stay exactly as the final write left them. This is the store-side floor under [run-history.md](run-history.md) item 27's in-process stand-down (which is unchanged): without it, a tombstone or drain write landing after the finish would flip the row back to provisional and let a later final write count the run twice.
4. **The wire.** `POST /runs/put` and `POST /runs/finish` accept an optional `point` beside `record` (`parseRunPut`); a body without one is exactly today's, and the answers of both routes are byte-identical with and without the binding, with and without a point, and when the sink's write throws (`turnedFinal` stays internal — the put route strips it). `WorkerRunStore.put` and `WorkerRunLedger.finish` compute `pointOf(record, prices)` and send it when defined; `buildRunStore` and `buildRunLedger` take `prices?: ModelPriceTable` in their deps and `src/index.ts` passes the same table `RunsService` prices with. `InMemoryRunStore` and `FileRunStore` are unchanged — they send no point.
5. **The off state and the sink.** `RunMetricsSink` (`write(point): void`) has two implementations: `AnalyticsEngineSink` over the optional `Env.RUN_METRICS` binding and `NullSink`, selected at the object's construction — the `SHIP_COORDINATOR?` shape: the Worker deploys without the binding and nothing changes. The write sits in a `try` whose catch is ONE `console.warn` line carrying the run id and the error's constructor name, never the point's contents; it can fail no put and no finish. `GET /healthz`'s `features` gains `runMetrics:<dataset>` when the binding is present (`featuresOf`), the name from the `RUN_METRICS_DATASET` var rendered beside the binding, so the bot's boot probe can compare names.

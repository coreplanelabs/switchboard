# Run metrics

Every finished run writes one flat metrics point into a Workers Analytics Engine dataset, beside the one commit its record already makes ([decision 0063](../../decisions/0063-every-finished-run-writes-one-metrics-point-and-a-metrics-page-reads-the-trend.md)). The bot computes the point (`pointOf` in the node-free `src/core/runMetrics.ts`) and sends it beside the record on `POST /runs/put` and `POST /runs/finish`; the state Worker's `RunHistoryDO` — the only writer of finished records — decides whether that write is the run's *terminal close* on an unlatched run (`pointEmits`, [record 0097](../../decisions/0097-every-run-row-carries-its-outcome-and-workspace-and-the-review-dashboard-is-six-queries-over-them.md)) and writes the point to the dataset AFTER its transaction, so a [run](../vocabulary.md#run) is counted at most once however many times its record is written (the tombstone, a `restarting` close, the finish, a review-artifact rewrite, a retry), and an unclaimed restart is closed by the store's own sweep. The binding is optional on the Worker and the whole path is advisory: without it, without a point, or with a sink that throws, every answer is byte-identical. The record itself is untouched — the point travels beside it, never on it ([run-history.md](run-history.md) items 27, 33 and 44 name the three writes this rule governs). The price table is [costs.md](costs.md)'s `costs.prices`. On the read side, `metrics trend` answers the trend report on every command surface from the dataset over the Analytics Engine SQL API — three weighted queries per read, no snapshot — behind the `metrics` capability (items 7–9), and `GET /metrics` serves the same report as an Access-gated page in the costs dash's shape with a JSON twin at `/metrics.json` (item 10).

## Behavior

1. **The point.** `RunMetricsPoint = { indexes: [string]; blobs: string[]; doubles: number[] }` — the platform's own positional shape. `POINT_COLUMNS` is the ONE ordered table naming every position: twenty blobs (`schema` — the literal `"1"` — `agent`, `preset`, `model`, `status`, `error type`, `dominant friction`, `channel`, `repository`, `machine class`, `route class`, `reply`, `lineage`, `requester`, `identity`, `run id`, and, appended by [record 0097](../../decisions/0097-every-run-row-carries-its-outcome-and-workspace-and-the-review-dashboard-is-six-queries-over-them.md) so no position changes meaning, `surface`, `workspace`, `setup reason`, `outcome`) and twenty doubles (`wall` = `finishedAt − (receivedAt ?? startedAt)`; the seven partition terms of `diagnosis.shape`, zero when absent; `turns`; the four token counts summed over `usage.byModel`; `dollars` = `llmUsdOfUsage(usage, prices).usd`; `steps`; `tool calls`; `events` = `eventCount`; `unpriced tokens` = `llmUsdOfUsage(...).unpricedTokens`; `minutes` — the profile's, zero when absent; `finished at`), the index the [agent](../vocabulary.md#agent) name (`unknown` for a record naming none). It is typed so a position added without a name fails to compile, and `blobColumn`/`doubleColumn` resolve a name to its `blob<n>`/`double<n>` — a reader's query never carries a magic number. `pointOf(record, prices?)` returns `undefined` for a record with `provisional: true` and for nothing else; an absent optional field is the empty string (blobs) or zero (doubles); `route class` is `routed` when the record carries a `route`, else `chosen`; `reply` is `ok`/`failed`/`none` off `replyOk`; `lineage` is `child` when `parentRunId` is present, else `root`; `dominant friction` is the `FrictionCategory` with the largest `durationMs` among those with a count (`dominantFriction`), empty when none has one. `outcome` and `error type` are `outcomeOf(record)`: the terminal status decides first, then the first matching row of record 0097's table — `cancellation` for a stop; `error` with `restart_unclaimed` or `interrupted` for an interrupted run; for a failed run `failure` with `policy_refusal`, else `error` with the failure kind, the setup result's lost word, `reply_failed`, else `timeout` with a budget ending, else `error` with `unclassified`; for a completed run `timeout` with a budget ending, `error` with `answer_interrupted`, `cancellation` after a stop, else `success`. Error type is empty exactly for `success` and `cancellation`. `surface` is the channel's namespace when it is `slack`, `mcp`, `web`, `http` or `cli` (`surfaceOf`), else empty; `workspace` folds the setup result into one word (`workspaceWordOf`: `resident`, `resident_restored`, `sandbox_snapshot`, `sandbox_fresh`, `sandbox_seed_failed`, `sandbox_cold`, `sandbox_blank`, `local` or `e2b` for a run on that backend, `none` for a lost word, empty without a setup result); `setup reason` is the setup result's `reason` or empty, so a cancellation keeps it. Every blob and the index are capped at 96 bytes, and `pointOf` never reads `activity`, `label`, `events`, `verdict`, `handoff`, `dispositions` or `diagnosis.verdict` — no free text reaches the dataset. `isRunMetricsPoint` accepts exactly one index, sixteen or twenty strings (`RUN_POINT_BLOB_WIDTHS`: this item's width and the width [record 0097](../../decisions/0097-every-run-row-carries-its-outcome-and-workspace-and-the-review-dashboard-is-six-queries-over-them.md) widens the row to, accepted together so a deploy's old and new writers both land) each at most 96 bytes, twenty finite numbers, and nothing else; the Worker validates an incoming point with it and answers `400` by name (`point must be a RunMetricsPoint`) for anything else.
2. **The emission rule: the terminal close** ([record 0097](../../decisions/0097-every-run-row-carries-its-outcome-and-workspace-and-the-review-dashboard-is-six-queries-over-them.md), amending 0063's first non-provisional close). A close is terminal when it is neither `provisional` nor `restarting` (`isTerminalClose`). `pointEmits(latched, stored)` is true exactly when `stored` is a terminal close and the run's **emission latch** is unset — there is deliberately no `finishedAt > startedAt` term (a plain `put` of an `interrupted` record over no row is a run counted once). The latch is the `runs` row's `metrics_emitted` column, set in the same transaction as the write that emits and never cleared by a later write; rows a store kept before the column existed start latched unless they are provisional, since 0063's rule had already counted them. `upsertInTransaction` reads the row's `provisional` and `restarting` alone from `summary_json` (never the whole summary) and returns `emits` beside `stored`, `retained` and `rewritten`. `put` and `finish` call `sink.write(point)` AFTER their transaction — the `sendRunFinished` placement — when `emits && stored` and a point was sent; a `restarting` close, a review-artifact rewrite ([run-history.md](run-history.md) item 44) and an identical retry write no point, and a record the write itself trimmed (`stored: false`) writes none. A `restarting` close's point is kept on its row (`restart_point_json`) for the sweep in item 3a.
3. **The guard: a provisional record never overwrites a non-provisional row, and a `restarting` record never overwrites a terminal one.** `upsertInTransaction` answers either as `{ ok, stored: true, retained, rewritten: false, emits: false }` and writes NOTHING — the row, its events and the sessions table stay exactly as they were. This is the store-side floor under [run-history.md](run-history.md) item 27's in-process stand-down (which is unchanged): without it, a tombstone or drain write landing after a close would replace the run's end, or erase a `restarting` row's deadline and kept point so the sweep could never count it, and a `restarting` close a refused ledger finish falls back to `put` with, landing after the successor's finish, would replace the run's terminal close.
3a. **An unclaimed restart is closed by the store.** The store's alarm (`closeUnclaimedRestarts`) finds each unlatched `restarting` row whose `restartUntil` has passed while no `live_runs` row holds its id, and in one transaction per row — re-checking the same deadline and the absent live row — rewrites it as an `interrupted` terminal close with `failure.kind: restart_unclaimed`, `restarting` and `restartUntil` removed, latched. After the commit it writes the point the `restarting` close carried, with `status` `interrupted` and `failure kind` `restart_unclaimed`; the store never prices a record itself. A successor still holding the id keeps the sweep a no-op, and its own terminal close emits the run's only point.
3b. **The review row and the store's failed writes** ([record 0097](../../decisions/0097-every-run-row-carries-its-outcome-and-workspace-and-the-review-dashboard-is-six-queries-over-them.md), "Rows and columns"). A review run's terminal close with a verdict also writes a **review row** (`reviewPointOf`), under the run row's emission decision and latch: index `review`, its own schema word `review-1` (so 0063's reader, filtering on `"1"`, never counts it), eight blobs (`schema`, `run id`, `repository`, `pull request number`, `head revision`, `verdict`, `requester`, `surface`) and seven doubles (`finished at`, `duration`, `findings`, `blocking`, `major`, `minor`, `nit`) named in `REVIEW_POINT_COLUMNS`. The target is the run record's own — `repo`, `targetPr` (the repository context's pull request, resolved before the model starts), `reviewHead` falling back to `headSha` — never `reviewPost.target`; a branch review with no pull request writes an empty number. The verdict reads `approved` or `changes_requested`. The store computes the row from the record it committed — its clamped stamps, never the input's — after the commit (it needs no price), so an older client's runs get one too. Every row the sink refuses is counted by kind (`run`, `review`) in `metrics_write_failures`, and `POST /runs/metrics-health {storeKey}` answers `{ failedWrites: { run, review } }`: delivery stays at most once and best effort, and a drop after an accepted write is not detectable here.
4. **The wire.** `POST /runs/put` and `POST /runs/finish` accept an optional `point` beside `record` (`parseRunPut`); a body without one is exactly today's, and the answers of both routes are byte-identical with and without the binding, with and without a point, and when the sink's write throws (`emits` stays internal — the put route strips it). `WorkerRunStore.put` and `WorkerRunLedger.finish` compute `pointOf(record, prices)` and send it when defined; `buildRunStore` and `buildRunLedger` take `prices?: ModelPriceTable` in their deps and `src/index.ts` passes the same table `RunsService` prices with. `InMemoryRunStore` and `FileRunStore` are unchanged — they send no point.
5. **The off state and the sink.** `RunMetricsSink` (`write(point): void`) has two implementations: `AnalyticsEngineSink` over the optional `Env.RUN_METRICS` binding and `NullSink`, selected at the object's construction — the `SHIP_COORDINATOR?` shape: the Worker deploys without the binding and nothing changes. The write sits in a `try` whose catch is ONE `console.warn` line carrying the run id and the error's constructor name, never the point's contents; it can fail no put and no finish. `GET /healthz`'s `features` gains `runMetrics:<dataset>` when the binding is present (`featuresOf`), the name from the `RUN_METRICS_DATASET` var rendered beside the binding, so the bot's boot probe can compare names.
6. **The binding in the deploy, and the name held on both sides.** The deployment profile's optional `metrics: { dataset }` ([release-and-deploy.md](release-and-deploy.md) item 14; Analytics Engine's own dataset-name rule — 1–64 letters, digits and underscores, not starting with a digit — refused by field) is what the state Worker template's `{{#if metrics}}` block renders `analytics_engine_datasets: [{ binding: "RUN_METRICS", dataset }]` and the `RUN_METRICS_DATASET` var from, the `{{#if artifacts}}` shape: a profile without one renders today's file byte for byte, and the committed example names none. `deploy plan` names the binding in the memory step when the profile names a dataset; no resource is created ahead of the deploy — the platform creates a dataset on first write — and the step needs no extra credential capability. On the other side, the bot's boot probe of the state Worker (the same `/healthz` read that checks `runs`) compares its configured `metrics.dataset` (the `metrics:` config block; only `dataset` is read until the reader lands) with the Worker's `runMetrics:<dataset>` feature (`metricsDatasetWarning`) and logs ONE `[runs]` warning when the two differ or when only one side names one — saying which side is missing what — and nothing when both agree or both are absent; neither side refuses to start.
7. **The reader's config and capability.** `metrics: { dataset, days? }` is a config block, validated at load by `parseMetricsConfig` and refused by field: `dataset` under the platform's dataset-name rule (item 6's), `days` a whole number in 1..90 (default 30). The `metrics` capability is on exactly when the block names a dataset AND the `costs` block with its Cloudflare analytics token are present — the reader queries the SQL API on the same read-only credential the spend dashboard holds, so no new secret exists ([capabilities.md](capabilities.md) item 1). The three installation fixtures carry the axis (`cloud-full` on, the others off).
8. **The source and the three queries.** `MetricsSource` is `query(sql) → Promise<MetricsRow[]>` with three implementations: `AnalyticsEngineSqlSource` POSTs the text to the account's `analytics_engine/sql` endpoint with the bearer in the header ONLY and `FORMAT JSON` appended, parses `data`, and turns a non-2xx into a `MetricsSourceError` carrying the status and never the token; `InMemoryMetricsSource(points)` evaluates the same texts over held points (each stamped at its `finished at` double, weight 1); `NullMetricsSource` is the off state. `metricsQueries({ sinceMs, untilMs, agent? }, dataset)` returns three texts — `byDayStatus` (day, status, `sum(_sample_interval)`), `byAgent` (runs, `sumIf(_sample_interval, … = 'failed')`, `quantileExactWeighted(0.5/0.95)` of the wall, dollars, unpriced tokens and turns as `sum(double × _sample_interval)`), `byDayAgentP50` — each over `timestamp >= toDateTime(<since>) AND timestamp < toDateTime(<until>)`; every aggregate is `_sample_interval`-weighted (no query counts rows or averages a raw column) and every column position resolves from `POINT_COLUMNS`. The agent filter is the ONLY user string a query can carry: validated against the agent-name rule before interpolation and quoted; the range is two integers.
9. **The report and the command.** `buildMetricsReport(rows, range)` is pure: the tiles (runs, failed, failure rate, p50/p95 wall — the runs-weighted mean of the per-agent quantiles — dollars, unpriced tokens, turns), `byDay` zero-filled for every UTC day in range with a count per status, `byAgent` largest first, `p50ByDayAgent`, and a `range` naming `bucket: "write time"`, `retentionDays: 90`, `pricing: "at finish"`, `completeness: "at most once"`; an empty result is a zero-filled report, never an error. `metrics.trend` is a registry command (action `metrics:read` — the `costs.by` grant shape: a browser session's baseline, a grant for a Slack user or a token, never a chat baseline — effect read, `enabledWhen: caps.metrics`), options `--days` 1..90 and `--agent`; derived forms `metrics trend` in chat and on the CLI, `GET /api/metrics.trend`, the `metrics_trend` MCP tool; the JSON is the report exactly, and the text render is a header (range, agent filter, dataset), the tiles as one ` · `-joined bullet, one line per agent row largest first, then the footer sentence (bucket, pricing, completeness). Off is `unavailable` with `METRICS_OFF_MESSAGE`; a source error is `unavailable` naming the error's class. `MetricsService.report({ days?, agent? })` reads whole UTC days ending today (today included, still filling), the default range from config; `NullMetricsService` is the off state the catalogue binds without the capability.
10. **The page.** `GET /metrics` and its JSON twin `GET /metrics.json` (`?days` 1..90, `?agent` under the agent-name rule — both validated in the handler before any read, a malformed one refused `400` in the validator's words) sit in the same fail-closed Access branch as `/costs*` in `src/index.ts`, GET-only. The handler (`src/channels/metricsView.ts`) serves the shared web shell with the report as the `MetricsSeed`; the twin answers the seed's report exactly, so the page renders nothing the twin does not carry. Off — the Null service — answers `503` with `METRICS_OFF_MESSAGE` (the costs dash's off shape); a failing source answers `503 metrics by run unavailable: <class>`, the error's class and never its detail, the query or the token. The startup log states `GET /metrics (<dataset>)` or the reason it is off. `web/green/pages/Metrics.vue` renders, in the costs page's tokens and layout: the eight tiles (runs, failed, failure rate, p50/p95 wall, dollars, unpriced tokens, turns); a runs-per-day chart stacked by status (`CostChart.vue` reused over a count-labelled model — a 90-day report is ninety x-axis buckets, the zero-filled `byDay` guarantees it); a failure-rate-per-day line and a p50-wall-per-day line per agent (`TrendLineChart.vue` — a day without a value is a gap, never a zero); the by-agent table largest first, each agent linking to its own filter; the range pills (7, 30, 90) and an agent filter, each pill keeping the other; and a footer carrying the report's `bucket`, `pricing`, `completeness` and `retentionDays` as four sentences (`footerSentencesOf`). `navSections` gains the Metrics section shown on the `metrics` capability only ([live-view.md](live-view.md) item 18); `/metrics` is a page of the app, navigated in place. The dashboard screenshots gain the `metrics` surface over a 30-day fixture (`scripts/web-preview.ts`; [docs-site.md](docs-site.md) item 20).

11. **Intake telemetry.** An opted-in `POST /runs/intake` emits one `intake-1` point to the existing `RUN_METRICS` binding after a measured receipt is inserted. Both addressed and silent decisions are emitted; receipt replay, legacy callers and unmeasured receipts emit nothing. Sink failures cannot change the committed decision. New clients opt in with `telemetry:true` only after their run-metrics reader isolates schema `1`, so the memory-first rollout cannot contaminate an older bot's completed-run reports. Points carry experiment, arm, model, coordinates, verdict, failure source, latency, usage, estimated cost and Jev probabilities; no prompt, message text or model-written reason. Probe rows are marked separately. Analytics Engine retains telemetry independently of the receipt cleanup policy. The intake report uses sampling weights for event counts, sums and percentiles, names distinct threads as observed when sampling can omit them, and returns unknown cost as null. Optional samples are bounded; explicit thread exclusions keep operator tests separate from ordinary traffic.
12. **The review report** ([record 0097](../../decisions/0097-every-run-row-carries-its-outcome-and-workspace-and-the-review-dashboard-is-six-queries-over-them.md), "The reader and the page"; `src/core/reviewsReport.ts`, `src/core/reviewsService.ts`). `reviewsQueries(range, dataset)` builds the eight query texts for a half-open range of at most 90 days over the review agent's run rows (`schema = "1"`, index `review`) and the review rows (`review-1`): runs by finish day, outcome, surface and requester with the time spent and the largest sample interval; weighted p50/p95 duration of successes by requester, by surface and overall; a whole-minute duration histogram with an open last bucket; review rows by repository, pull request and verdict with findings by severity; runs by finish day, workspace, setup reason and error type; and p50 duration and time to ready by workspace. Every count is `sum(_sample_interval)` and every quantile `quantileExactWeighted`, and every function a query calls is one Analytics Engine's SQL reference documents (the histogram's open bucket is an `if`); every aggregate filters and groups on the row's own `finished at`, and the scan is bounded by write time a day wider on each side. `buildReviewsReport` is pure over their rows: a `usage` section (runs, successes, time spent, durations, by day and surface, by requester, by surface, the histogram, pull requests, reviews per pull request — absent when any row was sampled — verdicts and findings) and a `system` section (four tiles as good over total — run success rate without cancellations and unrecorded outcomes, warm-start share over runs that asked for a resident and got a workspace (a local or E2B run whose setup reason is a fallback word included), lost at setup, reviews with a verdict — the unclassified and unrecorded counts, outcomes, workspaces by day, setup reasons by class, error types, and the per-workspace durations). Setup reasons are classed by `setupReasonClass`: every lost word is a failure, record 0097's design words are design, every other word a defect. `createReviewsService` runs the eight reads in parallel and reuses an answer for five minutes while its range includes today (`REVIEWS_CACHE_OPEN_MS`) and a day once it ended, holds at most 32 ranges, and never reuses a failed read; `NullReviewsService` refuses with `METRICS_OFF_MESSAGE`. `metrics.reviews` (action `metrics:read`, hidden when `caps.metrics` is off) answers the report on every surface — `metrics reviews` in chat and on the CLI, `GET /api/metrics.reviews`, the `metrics_reviews` MCP tool — for `--from` and `--to`, whole UTC days with both included (default the seven days ending today, at most 90); a day the calendar does not have, a range that ends before it starts or one that runs past 90 days is `invalid_input` before any read, the off state and a failing source are `unavailable`, and its text render is a header, a usage bullet, the four tiles as good of total, one line per requester and the footer, chat-safe.

13. **Exact human review feedback.** `metrics.feedback.enabled` opts the bot into a minute refresh loop over the existing durable run-history Worker. `excludedActorIds` names automation User node IDs and `excludedPullRequests` names disposable `owner/repository#number` acceptance cohorts. The native review invitation asks whether the review helped decide what to change. The original run's matching pending-to-accepted transaction retains a compact receipt, including missing optional native identity as a tracking gap, independently of ordinary run retention. Only accepted invitation-bearing publications belong to this cohort; old receipts and uncertain writes do not. The retained receipt is the index and repair source, unique per repository/native review ([record 0107](../../decisions/0107-retain-exact-review-feedback-with-the-publication-owner.md)).

    The feedback seam is `src/core/reviewFeedback.ts`, with the in-memory implementation and `src/core/reviewFeedbackWorker.ts`; `deploy/cloudflare-memory/reviewFeedbackStorage.ts` owns SQLite retention, leases and snapshots through the Worker's authenticated `/runs/review-feedback/{list,claim,complete,cooldown}` routes. `src/execution/githubReviewFeedback.ts` reads GitHub using the bot credential, never a model tool. It verifies the exact review ID, repository, PR, head and body, then fetches every reaction page before replacing the current votes. Partial errors, changed body, inaccessible nodes and pagination failures preserve the previous complete snapshot with an unavailable/changed status. Shared rate-limit cooldown and fenced, expiring collection leases survive restart. Recent publications refresh hourly for seven days; older retained publications refresh daily. Each pass and request is bounded by `src/core/budgets.ts`. Page loads never read GitHub. Reporting clamps to 90 days; physical cleanup obeys the existing run-history maintenance gate. Required acceptance-journal failure keeps the existing uncertain/no-repost behavior; optional reaction collection cannot change publication or approval.

14. **Human usefulness on the existing metrics report.** `src/core/reviewFeedbackReport.ts` builds exact counts over accepted publications in the same half-open UTC range as the operational report. Only complete snapshots within the report's explicit freshness limits enter usefulness ratios. Each review counts once: positive-only, negative-only or mixed when effective votes exist; otherwise ambiguous-only, unknown-only or unrated. A human using both signs on a review is ambiguous and supplies no effective vote. Bot and configured automation reactions are excluded; missing actor identities remain unknown. Helpful share among clear ratings is positive-only / (positive-only + negative-only), with mixed reviews alongside it. Vote positivity is secondary. Rating coverage is rated reviews / complete fresh reviews; native-link and complete-sync coverage use all eligible tracked publications, including missing identity and failed reads. No denominator yields `null`, never a zero quality score. Last-known ratings on stale, inaccessible or edited reviews stay separate. Configured acceptance PRs are excluded before any count.

    The same optional `feedback` object rides `MetricsService.report`, the Access-gated `/metrics` page and `/metrics.json`, and `metrics trend` on command surfaces.     `run` retrieves one retained publication and its current/last-known raw reaction snapshot over the full 90-day retention. It is separate from list filters. Exact detail includes native review identity and URL, original review run ID, reviewed head and body hash, read/completion stamps, reaction IDs, actor IDs/types and signs, plus the automation actor IDs excluded from counts. Reading feedback does not start that investigation or authorize a fix; repository/run access and dispatch authorization remain their existing gates.

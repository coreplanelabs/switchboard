# Run metrics

Every finished run writes one flat metrics point into a Workers Analytics Engine dataset, beside the one commit its record already makes ([decision 0063](../../decisions/0063-every-finished-run-writes-one-metrics-point-and-a-metrics-page-reads-the-trend.md)). The bot computes the point (`pointOf` in the node-free `src/core/runMetrics.ts`) and sends it beside the record on `POST /runs/put` and `POST /runs/finish`; the state Worker's `RunHistoryDO` — the only writer of finished records — decides whether the row *turned final* on that write (`pointTurnsFinal`) and writes the point to the dataset AFTER its transaction, so a [run](../vocabulary.md#run) is counted at most once however many times its record is written (the tombstone, the finish, a review-artifact rewrite, a retry). The binding is optional on the Worker and the whole path is advisory: without it, without a point, or with a sink that throws, every answer is byte-identical. The record itself is untouched — the point travels beside it, never on it ([run-history.md](run-history.md) items 27, 33 and 44 name the three writes this rule governs). The price table is [costs.md](costs.md)'s `costs.prices`. On the read side, `metrics trend` answers the trend report on every command surface from the dataset over the Analytics Engine SQL API — three weighted queries per read, no snapshot — behind the `metrics` capability (items 7–9), and `GET /metrics` serves the same report as an Access-gated page in the costs dash's shape with a JSON twin at `/metrics.json` (item 10).

## Behavior

1. **The point.** `RunMetricsPoint = { indexes: [string]; blobs: string[]; doubles: number[] }` — the platform's own positional shape. `POINT_COLUMNS` is the ONE ordered table naming every position: sixteen blobs (`schema` — the literal `"1"` — `agent`, `preset`, `model`, `status`, `failure kind`, `dominant friction`, `channel`, `repository`, `machine class`, `route class`, `reply`, `lineage`, `requester`, `identity`, `run id`) and twenty doubles (`wall` = `finishedAt − (receivedAt ?? startedAt)`; the seven partition terms of `diagnosis.shape`, zero when absent; `turns`; the four token counts summed over `usage.byModel`; `dollars` = `llmUsdOfUsage(usage, prices).usd`; `steps`; `tool calls`; `events` = `eventCount`; `unpriced tokens` = `llmUsdOfUsage(...).unpricedTokens`; `minutes` — the profile's, zero when absent; `finished at`), the index the [agent](../vocabulary.md#agent) name (`unknown` for a record naming none). It is typed so a position added without a name fails to compile, and `blobColumn`/`doubleColumn` resolve a name to its `blob<n>`/`double<n>` — a reader's query never carries a magic number. `pointOf(record, prices?)` returns `undefined` for a record with `provisional: true` and for nothing else; an absent optional field is the empty string (blobs) or zero (doubles); `route class` is `routed` when the record carries a `route`, else `chosen`; `reply` is `ok`/`failed`/`none` off `replyOk`; `lineage` is `child` when `parentRunId` is present, else `root`; `dominant friction` is the `FrictionCategory` with the largest `durationMs` among those with a count (`dominantFriction`), empty when none has one. Every blob and the index are capped at 96 bytes, and `pointOf` never reads `activity`, `label`, `events`, `verdict`, `handoff`, `dispositions` or `diagnosis.verdict` — no free text reaches the dataset. `isRunMetricsPoint` accepts exactly one index, sixteen strings each at most 96 bytes, twenty finite numbers, and nothing else; the Worker validates an incoming point with it and answers `400` by name (`point must be a RunMetricsPoint`) for anything else.
2. **The emission rule.** `pointTurnsFinal(existing, stored)` is true exactly when `stored.provisional` is absent and `existing` is `undefined` or carries `provisional: true` — there is deliberately no `finishedAt > startedAt` term (a plain `put` of an `interrupted` record over no row is a run counted once). `upsertInTransaction` reads `summary_json` beside the three columns it already reads for the existing row, parses ONLY its `provisional` field (never the whole summary), and returns `turnedFinal` beside `stored`, `retained` and `rewritten`. `put` and `finish` call `sink.write(point)` AFTER their transaction — the `sendRunFinished` placement — when `turnedFinal && stored` and a point was sent; a review-artifact rewrite ([run-history.md](run-history.md) item 44) and an identical retry land on a final row, so they write no second point, and a record the write itself trimmed (`stored: false`) writes none.
3. **The guard: a provisional record never overwrites a final row.** `upsertInTransaction` answers a `put` of a `provisional: true` record over an existing non-provisional row as `{ ok, stored: true, retained, rewritten: false, turnedFinal: false }` and writes NOTHING — the row, its events and the sessions table stay exactly as the final write left them. This is the store-side floor under [run-history.md](run-history.md) item 27's in-process stand-down (which is unchanged): without it, a tombstone or drain write landing after the finish would flip the row back to provisional and let a later final write count the run twice.
4. **The wire.** `POST /runs/put` and `POST /runs/finish` accept an optional `point` beside `record` (`parseRunPut`); a body without one is exactly today's, and the answers of both routes are byte-identical with and without the binding, with and without a point, and when the sink's write throws (`turnedFinal` stays internal — the put route strips it). `WorkerRunStore.put` and `WorkerRunLedger.finish` compute `pointOf(record, prices)` and send it when defined; `buildRunStore` and `buildRunLedger` take `prices?: ModelPriceTable` in their deps and `src/index.ts` passes the same table `RunsService` prices with. `InMemoryRunStore` and `FileRunStore` are unchanged — they send no point.
5. **The off state and the sink.** `RunMetricsSink` (`write(point): void`) has two implementations: `AnalyticsEngineSink` over the optional `Env.RUN_METRICS` binding and `NullSink`, selected at the object's construction — the `SHIP_COORDINATOR?` shape: the Worker deploys without the binding and nothing changes. The write sits in a `try` whose catch is ONE `console.warn` line carrying the run id and the error's constructor name, never the point's contents; it can fail no put and no finish. `GET /healthz`'s `features` gains `runMetrics:<dataset>` when the binding is present (`featuresOf`), the name from the `RUN_METRICS_DATASET` var rendered beside the binding, so the bot's boot probe can compare names.
6. **The binding in the deploy, and the name held on both sides.** The deployment profile's optional `metrics: { dataset }` ([release-and-deploy.md](release-and-deploy.md) item 14; Analytics Engine's own dataset-name rule — 1–64 letters, digits and underscores, not starting with a digit — refused by field) is what the state Worker template's `{{#if metrics}}` block renders `analytics_engine_datasets: [{ binding: "RUN_METRICS", dataset }]` and the `RUN_METRICS_DATASET` var from, the `{{#if artifacts}}` shape: a profile without one renders today's file byte for byte, and the committed example names none. `deploy plan` names the binding in the memory step when the profile names a dataset; no resource is created ahead of the deploy — the platform creates a dataset on first write — and the step needs no extra credential capability. On the other side, the bot's boot probe of the state Worker (the same `/healthz` read that checks `runs`) compares its configured `metrics.dataset` (the `metrics:` config block; only `dataset` is read until the reader lands) with the Worker's `runMetrics:<dataset>` feature (`metricsDatasetWarning`) and logs ONE `[runs]` warning when the two differ or when only one side names one — saying which side is missing what — and nothing when both agree or both are absent; neither side refuses to start.
7. **The reader's config and capability.** `metrics: { dataset, days? }` is a config block, validated at load by `parseMetricsConfig` and refused by field: `dataset` under the platform's dataset-name rule (item 6's), `days` a whole number in 1..90 (default 30). The `metrics` capability is on exactly when the block names a dataset AND the `costs` block with its Cloudflare analytics token are present — the reader queries the SQL API on the same read-only credential the spend dashboard holds, so no new secret exists ([capabilities.md](capabilities.md) item 1). The three installation fixtures carry the axis (`cloud-full` on, the others off).
8. **The source and the three queries.** `MetricsSource` is `query(sql) → Promise<MetricsRow[]>` with three implementations: `AnalyticsEngineSqlSource` POSTs the text to the account's `analytics_engine/sql` endpoint with the bearer in the header ONLY and `FORMAT JSON` appended, parses `data`, and turns a non-2xx into a `MetricsSourceError` carrying the status and never the token; `InMemoryMetricsSource(points)` evaluates the same texts over held points (each stamped at its `finished at` double, weight 1); `NullMetricsSource` is the off state. `metricsQueries({ sinceMs, untilMs, agent? }, dataset)` returns three texts — `byDayStatus` (day, status, `sum(_sample_interval)`), `byAgent` (runs, `sumIf(_sample_interval, … = 'failed')`, `quantileExactWeighted(0.5/0.95)` of the wall, dollars, unpriced tokens and turns as `sum(double × _sample_interval)`), `byDayAgentP50` — each over `timestamp >= toDateTime(<since>) AND timestamp < toDateTime(<until>)`; every aggregate is `_sample_interval`-weighted (no query counts rows or averages a raw column) and every column position resolves from `POINT_COLUMNS`. The agent filter is the ONLY user string a query can carry: validated against the agent-name rule before interpolation and quoted; the range is two integers.
9. **The report and the command.** `buildMetricsReport(rows, range)` is pure: the tiles (runs, failed, failure rate, p50/p95 wall — the runs-weighted mean of the per-agent quantiles — dollars, unpriced tokens, turns), `byDay` zero-filled for every UTC day in range with a count per status, `byAgent` largest first, `p50ByDayAgent`, and a `range` naming `bucket: "write time"`, `retentionDays: 90`, `pricing: "at finish"`, `completeness: "at most once"`; an empty result is a zero-filled report, never an error. `metrics.trend` is a registry command (action `metrics:read` — the `costs.by` grant shape: a browser session's baseline, a grant for a Slack user or a token, never a chat baseline — effect read, `enabledWhen: caps.metrics`), options `--days` 1..90 and `--agent`; derived forms `metrics trend` in chat and on the CLI, `GET /api/metrics.trend`, the `metrics_trend` MCP tool; the JSON is the report exactly, and the text render is a header (range, agent filter, dataset), the tiles as one ` · `-joined bullet, one line per agent row largest first, then the footer sentence (bucket, pricing, completeness). Off is `unavailable` with `METRICS_OFF_MESSAGE`; a source error is `unavailable` naming the error's class. `MetricsService.report({ days?, agent? })` reads whole UTC days ending today (today included, still filling), the default range from config; `NullMetricsService` is the off state the catalogue binds without the capability.
10. **The page.** `GET /metrics` and its JSON twin `GET /metrics.json` (`?days` 1..90, `?agent` under the agent-name rule — both validated in the handler before any read, a malformed one refused `400` in the validator's words) sit in the same fail-closed Access branch as `/costs*` in `src/index.ts`, GET-only. The handler (`src/channels/metricsView.ts`) serves the shared web shell with the report as the `MetricsSeed`; the twin answers the seed's report exactly, so the page renders nothing the twin does not carry. Off — the Null service — answers `503` with `METRICS_OFF_MESSAGE` (the costs dash's off shape); a failing source answers `503 metrics by run unavailable: <class>`, the error's class and never its detail, the query or the token. The startup log states `GET /metrics (<dataset>)` or the reason it is off. `web/src/pages/MetricsPage.vue` renders, in the costs page's tokens and layout: the eight tiles (runs, failed, failure rate, p50/p95 wall, dollars, unpriced tokens, turns); a runs-per-day chart stacked by status (`CostChart.vue` reused over a count-labelled model — a 90-day report is ninety x-axis buckets, the zero-filled `byDay` guarantees it); a failure-rate-per-day line and a p50-wall-per-day line per agent (`TrendLineChart.vue` — a day without a value is a gap, never a zero); the by-agent table largest first, each agent linking to its own filter; the range pills (7, 30, 90) and an agent filter, each pill keeping the other; and a footer carrying the report's `bucket`, `pricing`, `completeness` and `retentionDays` as four sentences (`footerSentencesOf`). `navSections` gains the Metrics section shown on the `metrics` capability only ([live-view.md](live-view.md) item 18); `/metrics` is a page of the app, navigated in place. The dashboard screenshots gain the `metrics` surface over a 30-day fixture (`scripts/web-preview.ts`; [docs-site.md](docs-site.md) item 20).

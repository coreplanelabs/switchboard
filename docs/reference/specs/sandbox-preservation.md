# Seeded sandbox preservation

A sandbox's idle deadline must not erase an unpublished seeded checkout. The Worker is the protective boundary; attaching a future run, verified restore, publication and terminal-owner cleanup are separate work. This source change is not a deployed durability receipt.

- **Code**: `deploy/cloudflare-sandbox/worker.ts`, `src/execution/sandboxIdle.ts`, `src/execution/sandboxCheckpoint.ts`
- **Tests**: `src/execution/sandboxIdle.test.ts`, `src/execution/sandboxCheckpoint.test.ts`, `src/execution/sandboxLifecycle.test.ts`

| Criterion | Proof |
|---|---|
| Before idle or stuck teardown, a seeded writer's checkout is retained when quiescence, ownership, the incarnation or a complete backup cannot be proved. An in-flight stop and an SDK expiry share this fence; a failed backup never licenses either clean or forced destruction. | `[unit]` `src/execution/sandboxIdle.test.ts::IdleGuard preservation::retains an idle seeded writer when preservation is uncertain`; `::retains a stuck in-flight writer when preservation is uncertain`; `::retains on failed backup and a concurrent request during preservation`; `src/execution/sandboxLifecycle.test.ts::sandbox Worker wiring (static)::fences both idle and SDK expiry teardown before SDK destroy or platform kill` |
| A checkpoint includes the checkout and its .git, excludes nothing by ignore rule, is tied to one owner and container incarnation, and is retained beyond the maximum Ship idle window with grace. A failed upload, changed owner or incomplete verification retains the container; deletion requires a separate verified terminal owner (not implemented here). | `[unit]` `src/execution/sandboxCheckpoint.test.ts::checkpointIfSafe::backs up the complete checkout for longer than the Ship idle window`; `::retains when backup fails or the owner or incarnation changes`; `[gap]` The live bucket lifecycle policy and an authorized natural paused-run receipt require a deployed Worker and separate operator authorization. |
| A passive read-only receipt requires the exact run, requester, thread, repository, ref, head, seed and container incarnation. It returns bounded present/lost/unknown facts only from durable metadata and R2 existence; a stopped container is never awakened for inspection or replaced. | `[unit]` `src/execution/sandboxCheckpoint.test.ts::preservationReceipt::refuses every wrong owner or incarnation without disclosing a checkpoint`; `::distinguishes present lost and unknown without reading checkout contents`; `::a stopped-container receipt reads only durable facts and never wakes or starts replacement work`; `::rejects malformed identities and arbitrary file or command fields`; `src/execution/sandboxLifecycle.test.ts::sandbox Worker wiring (static)::the stopped-container receipt bypasses getSandbox StartGate and exec` |

A checkpoint is only eligible when the Worker can establish quiescence *without* trusting a model assertion; the SDK's tracked-process list does not see detached writers, so this Worker currently retains seeded containers rather than claiming a safe snapshot during a paused run. An unbound legacy seed also stays retained rather than being destroyed on uncertainty. The receipt does not wake a container, authorize recovery, delete a backup, or claim live durability. Operators must verify bucket retention and a natural paused-run receipt after deployment; no source-only test substitutes for those observations.

# The session log — a thread-and-agent conversation outlives its runs

[Record 0035](../../decisions/0035-a-session-log-outlives-its-runs-compaction-is-a-pointer.md) decides that a run's transcript lives in its **session's log**: one Durable Object per session — a thread and an agent, the pair [record 0034](../../decisions/0034-one-agent-per-unit-a-run-continues-a-transcript.md) defines — holding the transcript rows of every run of the session in order, each run a range of it, kept when a run finishes, indexed for search, and dropped only when its last kept run leaves retention. This spec covers the store half of that record (its rollout (1)): the object and its routes, the run's range on its ledger row and its record, the write path under the ledger's fence, the resume read, the tail read a follow-up will seed from, the byte policy, pi's compaction entry as a row, and the sweep. The seed a follow-up starts from — the log's tail within the seed budget, the gap marker after a `broken` run, the lines since, the request — is item 9; the `recall` and `notes` tools, the notepad in the prompt and the steer after a compaction are item 10 (the record's rollout (2), whole). The ledger this extends is [run-history.md](run-history.md) items 28–37; the harness whose compactions it stores is [harness-pi.md](harness-pi.md) item 8.

## Behavior

1. **One object per session.** `SessionLogDO` (`SESSION_LOGS` binding, migration `v9`) is named `sessionKey(threadKey, agent)` = `<threadKey>:<agent>` (a run with no resolved agent keys on `-`), matching `SESSION_KEY_PATTERN`; two agents in one thread, or one agent in two threads, never share an object. The name is stable for the life of the thread — every run of the session derives the same key and finds the same log. Its tables: `owner(run_id, gen)` — the live writer; `meta` — the byte budget; `turns(id INTEGER PRIMARY KEY, idx, part, kind, bytes, trimmed, json, text, UNIQUE(idx, part))` — one row per content part exactly as `run_messages` stores them (run-history item 32), plus the row's kind, its UTF-8 size and the text the index sees; `turns_fts`, an external-content FTS5 table over `turns(id, text)` (item 8); `attachments(ref, media_type, data, bytes)` — base64 over `ATTACHMENT_REF_BYTES` stored once and referenced, as the transcript object does; and `notepad(text, updated_at)`, one row, the session's notes as the `notes` tool last wrote them (item 10). The routes — `POST /runs/session/tail {key}`, `owner {key, runId, gen, maxBytes}`, `write {key, gen, rows, attachments}`, `read {key, from, to?}`, `read-tail {key, maxBytes}`, `clear-owner {key, runId, gen}`, `search {key, query, limit}`, `notepad {key}`, `notepad/write {key, gen, text}` — sit among the ledger routes: the same bearer, the same body fences (`write` shares `/runs/put`'s 2 MiB), a malformed key, generation, index or row is `400` before any object call. `RunTranscriptDO` and its routes stay: a row claimed before this log existed still resumes from and finishes on its own object, and no new run writes there. Its `deleted_classes` migration waits until no live row lacks `session` and at least seven days have passed since the release that stopped writing it — never a release count alone.
2. **A run is a range of its session's log.** At the claim of a run with a conversation of its own (`OpenRunRequest.seed`; a ship pipeline has none and no session), the write-through reads the log's tail, claims the history row with `meta.session = { key, seedFrom: tail, request: tail + requestIndex(seed), range: { from: tail } }`, and THEN takes the log's owner (`/runs/session/owner`) — the history claim is the admission, so a refused claim never steals a live run's log; the three requests are one claim and any failure retries them all. The seed's turns are appended as rows `seedFrom..seedFrom+n-1` under the same `INSERT OR REPLACE` on `(idx, part)` (a new generation overwrites a zombie's late row); the request is the seed's last user turn (`requestIndex`, as `splitSeed` reads it). A thread's first run of an agent starts at 0; the next run of the same agent starts where the last left off, and its own `messages` still count from 0 — every row of a run is at `seedFrom + localIndex`, so the step records' `turnIndex` and the completeness rule are unchanged. Every write of the run names its log — the seed, the seed record's (item 35: a step with no turns, whose rows write is the fence probe before the record), and every step — under the run's generation fence, the assistant turn before its tools run, as item 35 says; a write from another generation is `409 fenced`, one before any owner `409 unknown-run`. A run with a session owns no transcript object of its own, so a write of it that names no log is refused `unknown-run` and detaches the run; the reference ledger (`InMemoryRunLedger`) owns a per-run object only for a claim without a session — a row from before the log existed — so the same miss is refused in a test as it is live. Finish clears nothing: the rows stay for the thread's next run; the owner is released (`clear-owner`, fenced to the owner, best-effort) so a zombie of a finished run is refused; the record carries `session` with the range closed at the last turn written — `{ key, seedFrom, request, range: { from, to } }`, validated by `isRunRecord`, `to` absent when the run wrote no turn. A detach (a refused or twice-failed write; item 35) keeps today's behavior and marks the record's range `broken` — on the record only, since the live row's writes are what failed; a record without `session` (older, or a run without a conversation) validates and reads exactly as before. An adopted row (a resume) continues appending at its indices and closes its range at finish; a reclaim re-owns the row's log as it re-owns a transcript object. **A message with no parts is not a turn**: it would write no row and still spend an index, and the next reclaim would read that hole as an incomplete transcript — so the mirror reports nothing for it and its index stays, and the bridge hands the mirror no message for the assistant message pi settles a failed model call with ([harness-pi.md](harness-pi.md) item 8: the failure is a note, never a turn).
3. **A resume reads the range.** `transcriptSource(meta)` says where a reclaimed run's rows are: its session log from `seedFrom` (`readSession(key, seedFrom)`, the rows re-based so the conversation counts from 0) for a row with `session`, the run's own transcript object for one without; the boot's completeness verdict reads accordingly and `planResume` is unchanged, the system prompt still the live row's (item 29). The plan carries the transcript's `compactions` (item 6) to the harness.
4. **The tail read.** `read-tail {key, maxBytes}` answers the newest whole turns whose bytes fit the budget, oldest first, with `from` — the index they start at; a turn is every part of one `idx`, so no tool call is parted from its result; when even the newest turn is over the budget, no rows and the tail index. The seed budget, and the cut before a user text turn, are the dispatcher's in rollout (2); the object's rule is the byte cut at a turn boundary.
5. **The byte policy.** `RetentionPolicy.sessionLogMaxBytes` (default 200 MiB, clamped to [16 MiB, 2 GiB] like every policy field; `runHistory.sessionLogMaxBytes` in the config, validated as `maxBytes` is; ignored by a Worker that predates it) bounds one object's rows and attachments — `maxBytes` bounds the run records alone. The client sends the clamped budget on every owner claim and the object stores it; after each write, while the total exceeds it, the object replaces the oldest un-replaced tool-result rows (`planSessionTrim`, oldest first) with a marker (`droppedToolResultRow`: the same role and call id so the conversation stays valid, the error flag, the dropped size, and that the run record keeps the first 8,000 characters), updating the index; user and assistant text is never dropped, so a log whose text alone exceeds the budget keeps it all. The total counts the attachments' bytes too, and the policy can reclaim them: a candidate's bytes include the attachments only that row references (`attachmentRefsOf`, a part's own reference and a tool result's nested ones), and once the marker replaces the row those attachments are deleted — one another row still shows stays, as does the user's own image. The reference ledger (`InMemoryRunLedger`) holds a session to the budget its `claimSession` carries by the same plan, so the two implementations agree. The `sessions` registry row (item 7) carries the object's byte count, refreshed at finish.
6. **pi's compaction entry is a row.** pi's `compaction_end` carries `result.summary`, `firstKeptEntryId`, `tokensBefore` and `estimatedTokensAfter`; the bridge hands the entry to the harness (`BridgeObservation.compaction`) and the mirror writes it as its own step report — the results pending since the last assistant turn as the user turn they would have been, then the entry as the row after them (`StepReport.compaction`, a `TranscriptTurn` with `compaction` in place of `message`, stored as `{ compaction: { summary, tokensBefore?, firstKeptEntryId? } }` at its own index), nothing in flight. The row counts as one turn. `assembleTranscript` keeps the conversation as `ChatMessage`s and reports each entry in `compactions` as `{ before, entry, keptBefore? }`; `piSessionFile` renders it as pi's `compaction` entry between the messages it sat between, on the same branch. pi keeps the entries from `firstKeptEntryId` to the compaction and everything after it: with `keptBefore` known that id names the kept message's entry; without it pi's own id — which names no entry in a rebuilt file — leaves the window the summary and the turns after it. `keptFrom` (the log index of the entry pi kept first) is in the row's shape and rendered when present, and nothing produces it yet: pi's message events carry no entry id, so the mirror has no map from `firstKeptEntryId` to a turn.
7. **The registry and the sweep.** `RunHistoryDO` keeps `sessions(key, thread_key, agent, last_finished_at, bytes)`, upserted at a claim naming a session and at every record write naming one, and `runs.session_key`, the session a finished record was a range of (null for one without). The 6-hourly sweep, inside its transaction, trims the runs and lists the sessions no remaining run row names; after the transaction, each drop awaits the session object, so a claim or a finish can land between two drops and the list can go stale; the decision is therefore taken per key on what the object re-reads right before that key's drop — `SELECT 1 FROM runs WHERE session_key = ?` and `SELECT 1 FROM live_runs WHERE thread_key = ?` — through the pure rule `sessionsToDrop`, which takes exactly those two facts per candidate and answers `drop`, `kept-run` or `thread-live`. A candidate a fresh record or a live run has overtaken is skipped and keeps its registry row; any live run on the thread blocks every session of that thread, whichever agent it runs. A dropped session goes through the object's `drop()`: the owner row first, so a write racing the drop is refused, then every row, index entry, attachment, the notepad and the budget; the registry row goes once the object is empty. A session with a kept run, or a live thread, stays whole.
8. **The full-text index.** `turns_fts` is an external-content FTS5 table over `turns(id, text)`, so a row is stored once. A replaced row's old text is removed with the FTS `delete` command before the new row is written and indexed — the table learns of a replacement only when told — and the byte policy's markers are indexed the same way. What a row indexes (`textOfStoredRow`): a text part's text; a tool result's text, string or parts, so a failing test's name in a report is findable; a tool call's name and arguments, so a command is findable; a compaction row's summary; an image, a document, a thinking block or an unreadable row, nothing. `SessionLogDO.search(query, limit)` answers the matching rows in relevance order — FTS5's bm25 `rank`, the order the memory store's search uses, the newest first among equals — each with its turn, part, role (`roleOfStoredRow`), kind and indexed text, over the memory store's `MATCH` expression (`ftsMatchExpr`: every word quoted, at most 24, OR-joined); the `search` route (item 1) answers them with the gap markers (item 9) whose turn lies between the oldest and the newest hit (`gapsBetween`), and `recall` (item 10) reads it.
9. **A follow-up seeds from its session** ([record 0034](../../decisions/0034-one-agent-per-unit-a-run-continues-a-transcript.md) "The seed", [record 0035](../../decisions/0035-a-session-log-outlives-its-runs-compaction-is-a-pointer.md) "The seed"; `src/core/dispatch/thread.ts`, `src/core/dispatch/seed.ts`, the messages stage of `dispatch()`). For a reply in an existing thread — a message with thread history; a thread starter, a spawn, a coordinator's child, a resume and a restart read nothing — the dispatcher reads the thread's newest runs **once** (`readThread`: one `listRuns` by thread key, `THREAD_READ_LIMIT` newest, live and finished, under no visibility predicate) and derives from that page the lineage ([agent-conductor.md](agent-conductor.md) item 10), the sticky agent by transcript ([routing-and-config.md](routing-and-config.md) item 3) and the previous run of the agent the request resolved to. **The seed source** is then exactly one of four, and the record's `seed` names it ([run-history.md](run-history.md) item 52): a resume continues its own plan; a spawned child starts from its parent's text turns (`parent`); a follow-up whose resolved agent runs on the pi harness (`effectiveHarness`) and whose thread has a log of that agent (`sessionKey(threadKey, agent)`, one with rows) starts from that log (`session`); anything else starts from the channel's history as before (`channel`). **The session seed** (`sessionSeed`, pure; `sessionSeedFor` reads the ledger) is, in order: the log's newest whole turns within the **seed budget** — `SEED_BUDGET_TOKENS` = 60,000 at four characters a token, `SEED_BUDGET_BYTES` on the object's tail read (item 4) — beginning after the newest compaction row (item 6; that entry's summary is carried for the system prompt and is never a row) and cut forward to the first user turn that carries text, so the conversation opens as providers require and no tool call is parted from its result; thinking blocks dropped from the tail's assistant turns, an assistant turn of nothing but thinking keeping one text part so every row keeps its place; a tail that ends on calls in flight answered with one error `tool_result` per call saying the run ended before the result landed, as a resume settles them; a gap marker as a user turn when the previous run's record says `broken`; the channel's **lines since** — the user turns whose time (`HistoryItem.at`, epoch ms; the Slack adapter sets it from the message `ts`) is after the previous run's `finishedAt`, the bot's own posts left out because the run's final reply is the tail's last assistant turn — and the request as the last user turn. Nothing is merged across the tail's end: every message after it is a new row. **The rows the seed reuses** ride the ledger's open request (`OpenRunRequest.seed.log = { from, turns }`): the first `turns` messages are the log's rows from `from`, so the claim sets the row's `seedFrom` to `from` and its `range.from` to the tail (item 2 as amended: `seedFrom ≤ range.from`), the seed write appends only the messages after them, and every row of the run is still at `seedFrom + localIndex` — the resume's read from `seedFrom` (item 3) is the conversation the model saw, the tail's thinking blocks aside (the seed drops them, the log keeps them). Named rows that do not end at the tail (the log moved under the seed) are written whole as new rows from the tail, with one warning. What wins over the budget: a newest turn alone over it, or a tail with no user text turn, yields the lines since and the request with a `seed` note; a `broken` predecessor the marker and the tail past it; an unknown previous end (no finished run of the agent in the page) the tail and the request with a note; a log that cannot be read — no route, a failed request — the channel, `seed: channel`, and a note naming the log. Every note is a `run_note` of kind `seed` on the record before the first turn; the run itself is never changed by one. `runs list --thread <key>` lists one thread's runs newest first through the same store filter, live and finished.
10. **`recall`, `notes` and the notepad** ([record 0035](../../decisions/0035-a-session-log-outlives-its-runs-compaction-is-a-pointer.md) "Recall" and "The notepad"; `src/tools/session.ts`). Two tools join the toolsets of the presets that have a workspace and so can run on the pi harness (`full`, `readonly`, `explore` — `SESSION_TOOLS` in `src/tools/workspace.ts`), relayed to pi like every other bot tool ([harness-pi.md](harness-pi.md) item 7) and present on the native loop too. **The capability** (`SessionCapability`, `sessionCapabilityFor`): the dispatcher builds it right after the ledger claim from the row's place in the log (`LedgerRun.session`) over the write-through's session reads and its notepad write under this generation (`readSession`, `searchSession`, `readNotepad`, `writeNotepad`), and hands it to the run loop, the tool context and the pi harness; a run without a session — untracked, a ship pipeline, a process with no ledger — has none, and the tools say they are not available. **Both read under the requester's `runs:read`**: the same point read on the run itself `get_run_status` makes ([authorization.md](authorization.md) item 5); a read the requester may not make is an empty result, never an error. **`recall { query, limit? }`** searches the caller's own session log through item 8's search — `limit` 5 by default, 50 at most — and answers `{ hits: [{ turn, role, snippet }], gaps?, note? }`: the hits in relevance order, each turn's log index, its role and a one-line snippet of at most 300 characters; `gaps` names the gap markers the hits straddle; `note` says when no turn matches (and points at the notepad) and, in a first run (`seedFrom` 0), that the log begins with it. **`recall { turn }`** reads that turn whole (`readSession(key, turn, turn)`): `{ turn, role, content }` with every part, under the relay's tool-result cap; a turn the log lacks is named. A call with neither is refused by name. **`notes { text }`** replaces the notepad whole — one document per session, at most `NOTEPAD_MAX_BYTES` (8,192 UTF-8 bytes; over it the tool refuses naming the size and writes nothing) — through the object's `notepad/write` route under the owner's fence (`unknown-run` before an owner, `fenced` for another generation, `400` over the size), says the size it saved, and publishes the whole text, redacted like every narrative event, as a `notes` event on the record (`RunEvent`, a narrative event like `answer`; the record's last one is the final text; the run page shows it as a note row of kind `notes`, [live-view.md](live-view.md)); a fenced write says the notes were not saved. **`notes {}`** reads the notepad back, or says it is empty. The tool's call and its result are turns in the log like any other, so the notepad's history is the log's. **`recall` knows the thread's files** ([record 0033](../../decisions/0033-artifacts-move-by-reference-through-r2.md); [execution.md](execution.md) item 20): on a deployment with an artifact store the capability carries the thread's catalogue read (`SessionCapability.assets`, `readThreadAssets` fresh on each call, so a file this run just received or attached is in it) and this run's workspace paths (`workspacePathOf`, `WorkspaceFiles`); a hit whose turn names one of the files — an attachments line, an `attach_file` call — carries `files`: each file's name, size, type, the run that received or produced it, its key and where it is for this run (`whereIs`: in this workspace at its `attachments/` path when this run pulled it, on its run's page for a produced file, no longer in the store when its retention passed, or that the store could not be asked); the join is by name at a word boundary (`filesNamedIn`: `2-clip.mp4` in an attachments line names `clip.mp4`, `myclip.mp4` does not), under the name the person saw and the spelling the workspace gives it (`safeBasename`); the catalogue is read only when some hit carries an attachments line or an `attach_file` call, never for prose alone. **`recall { assets: true }`** lists the catalogue outright in that shape instead of searching — an empty one says no run of the thread received or produced a file, a deployment without a store says the files are not catalogued, a denied read is an empty list — and a call with none of `query`, `turn` or `assets` is refused by name. **The notepad's three read points**: (a) the system prompt at every run start — `sessionSeedFor` reads it beside the tail and the dispatcher hands it, with the newest compaction's summary, to `composePrompt`, which renders `sessionNotesBlock` right after the memory block ("YOUR NOTES FOR THIS THREAD …", then "SUMMARY OF THE EARLIER CONVERSATION …", then "FILES OF THIS THREAD …" — the thread's files one line each as `describeAsset` writes them, for any run in a thread with files, seeded or not ([execution.md](execution.md) item 20) — each only when present; `makeSystemComposer`'s `notes` block); a notepad that cannot be read is a `seed` note and the run starts without it; (b) a steer after every `compaction_end` that carried a summary, at pi's next turn boundary (`compactionSteer`: the notes as they stand, or that they are empty and how to keep them, and that `recall` reaches every earlier turn) — never during the write-up, after a hard stop, or while a re-attach catches up on history ([harness-pi.md](harness-pi.md) item 6); the steer is advisory, so a notepad read that fails there (a ledger blip, a Worker without the route) costs it its notes and never the run — the steer says the notes could not be read just now, and a `harness_error` note says why; a resumed run keeps its row's prompt, so notes written after it started reach a resumed pi by the steer alone; (c) `notes {}` on demand. **The prompt says what belongs there**: every workspace prompt (`coding` and `review`, both variants, `explore`) carries the `NOTEPAD` paragraph verbatim (`src/agents/registry.ts`) — decisions and their reasons, the names of things found, what is not yet proven, written when decided and not only at the end — and that `recall` reaches every earlier turn; the workspace-less prompts carry nothing of it.

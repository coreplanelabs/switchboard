# The session log — a thread-and-agent conversation outlives its runs

[Record 0035](../../decisions/0035-a-session-log-outlives-its-runs-compaction-is-a-pointer.md) decides that a run's transcript lives in its **session's log**: one Durable Object per session — a thread and an agent, the pair [record 0034](../../decisions/0034-one-agent-per-unit-a-run-continues-a-transcript.md) defines — holding the transcript rows of every run of the session in order, each run a range of it, kept when a run finishes, indexed for search, and dropped only when its last kept run leaves retention. This spec covers the store half of that record (its rollout (1)): the object and its routes, the run's range on its ledger row and its record, the write path under the ledger's fence, the resume read, the tail read a follow-up will seed from, the byte policy, pi's compaction entry as a row, and the sweep. The seed budget, the `recall` and `notes` tools, the notepad's injection and the gap marker a follow-up appends after a `broken` run are the record's rollout (2) and are not built here. The ledger this extends is [run-history.md](run-history.md) items 28–37; the harness whose compactions it stores is [harness-pi.md](harness-pi.md) item 8.

## Behavior

1. **One object per session.** `SessionLogDO` (`SESSION_LOGS` binding, migration `v9`) is named `sessionKey(threadKey, agent)` = `<threadKey>:<agent>` (a run with no resolved agent keys on `-`), matching `SESSION_KEY_PATTERN`; two agents in one thread, or one agent in two threads, never share an object. The name is stable for the life of the thread — every run of the session derives the same key and finds the same log. Its tables: `owner(run_id, gen)` — the live writer; `meta` — the byte budget; `turns(id INTEGER PRIMARY KEY, idx, part, kind, bytes, trimmed, json, text, UNIQUE(idx, part))` — one row per content part exactly as `run_messages` stores them (run-history item 32), plus the row's kind, its UTF-8 size and the text the index sees; `turns_fts`, an external-content FTS5 table over `turns(id, text)` (item 8); `attachments(ref, media_type, data, bytes)` — base64 over `ATTACHMENT_REF_BYTES` stored once and referenced, as the transcript object does; and `notepad(text, updated_at)`, one row, created now and written by nothing until the record's rollout (2). The routes — `POST /runs/session/tail {key}`, `owner {key, runId, gen, maxBytes}`, `write {key, gen, rows, attachments}`, `read {key, from, to?}`, `read-tail {key, maxBytes}`, `clear-owner {key, runId, gen}` — sit among the ledger routes: the same bearer, the same body fences (`write` shares `/runs/put`'s 2 MiB), a malformed key, generation, index or row is `400` before any object call. `RunTranscriptDO` and its routes stay: a row claimed before this log existed still resumes from and finishes on its own object, and no new run writes there. Its `deleted_classes` migration waits until no live row lacks `session` and at least seven days have passed since the release that stopped writing it — never a release count alone.
2. **A run is a range of its session's log.** At the claim of a run with a conversation of its own (`OpenRunRequest.seed`; a ship pipeline has none and no session), the write-through reads the log's tail, claims the history row with `meta.session = { key, seedFrom: tail, request: tail + requestIndex(seed), range: { from: tail } }`, and THEN takes the log's owner (`/runs/session/owner`) — the history claim is the admission, so a refused claim never steals a live run's log; the three requests are one claim and any failure retries them all. The seed's turns are appended as rows `seedFrom..seedFrom+n-1` under the same `INSERT OR REPLACE` on `(idx, part)` (a new generation overwrites a zombie's late row); the request is the seed's last user turn (`requestIndex`, as `splitSeed` reads it). A thread's first run of an agent starts at 0; the next run of the same agent starts where the last left off, and its own `messages` still count from 0 — every row of a run is at `seedFrom + localIndex`, so the step records' `turnIndex` and the completeness rule are unchanged. Every write of the run names its log — the seed, the seed record's (item 35: a step with no turns, whose rows write is the fence probe before the record), and every step — under the run's generation fence, the assistant turn before its tools run, as item 35 says; a write from another generation is `409 fenced`, one before any owner `409 unknown-run`. A run with a session owns no transcript object of its own, so a write of it that names no log is refused `unknown-run` and detaches the run; the reference ledger (`InMemoryRunLedger`) owns a per-run object only for a claim without a session — a row from before the log existed — so the same miss is refused in a test as it is live. Finish clears nothing: the rows stay for the thread's next run; the owner is released (`clear-owner`, fenced to the owner, best-effort) so a zombie of a finished run is refused; the record carries `session` with the range closed at the last turn written — `{ key, seedFrom, request, range: { from, to } }`, validated by `isRunRecord`, `to` absent when the run wrote no turn. A detach (a refused or twice-failed write; item 35) keeps today's behavior and marks the record's range `broken` — on the record only, since the live row's writes are what failed; a record without `session` (older, or a run without a conversation) validates and reads exactly as before. An adopted row (a resume) continues appending at its indices and closes its range at finish; a reclaim re-owns the row's log as it re-owns a transcript object.
3. **A resume reads the range.** `transcriptSource(meta)` says where a reclaimed run's rows are: its session log from `seedFrom` (`readSession(key, seedFrom)`, the rows re-based so the conversation counts from 0) for a row with `session`, the run's own transcript object for one without; the boot's completeness verdict reads accordingly and `planResume` is unchanged, the system prompt still the live row's (item 29). The plan carries the transcript's `compactions` (item 6) to the harness.
4. **The tail read.** `read-tail {key, maxBytes}` answers the newest whole turns whose bytes fit the budget, oldest first, with `from` — the index they start at; a turn is every part of one `idx`, so no tool call is parted from its result; when even the newest turn is over the budget, no rows and the tail index. The seed budget, and the cut before a user text turn, are the dispatcher's in rollout (2); the object's rule is the byte cut at a turn boundary.
5. **The byte policy.** `RetentionPolicy.sessionLogMaxBytes` (default 200 MiB, clamped to [16 MiB, 2 GiB] like every policy field; `runHistory.sessionLogMaxBytes` in the config, validated as `maxBytes` is; ignored by a Worker that predates it) bounds one object's rows and attachments — `maxBytes` bounds the run records alone. The client sends the clamped budget on every owner claim and the object stores it; after each write, while the total exceeds it, the object replaces the oldest un-replaced tool-result rows (`planSessionTrim`, oldest first) with a marker (`droppedToolResultRow`: the same role and call id so the conversation stays valid, the error flag, the dropped size, and that the run record keeps the first 8,000 characters), updating the index; user and assistant text is never dropped, so a log whose text alone exceeds the budget keeps it all. The total counts the attachments' bytes too, and the policy can reclaim them: a candidate's bytes include the attachments only that row references (`attachmentRefsOf`, a part's own reference and a tool result's nested ones), and once the marker replaces the row those attachments are deleted — one another row still shows stays, as does the user's own image. The reference ledger (`InMemoryRunLedger`) holds a session to the budget its `claimSession` carries by the same plan, so the two implementations agree. The `sessions` registry row (item 7) carries the object's byte count, refreshed at finish.
6. **pi's compaction entry is a row.** pi's `compaction_end` carries `result.summary`, `firstKeptEntryId`, `tokensBefore` and `estimatedTokensAfter`; the bridge hands the entry to the harness (`BridgeObservation.compaction`) and the mirror writes it as its own step report — the results pending since the last assistant turn as the user turn they would have been, then the entry as the row after them (`StepReport.compaction`, a `TranscriptTurn` with `compaction` in place of `message`, stored as `{ compaction: { summary, tokensBefore?, firstKeptEntryId? } }` at its own index), nothing in flight. The row counts as one turn. `assembleTranscript` keeps the conversation as `ChatMessage`s and reports each entry in `compactions` as `{ before, entry, keptBefore? }`; `piSessionFile` renders it as pi's `compaction` entry between the messages it sat between, on the same branch. pi keeps the entries from `firstKeptEntryId` to the compaction and everything after it: with `keptBefore` known that id names the kept message's entry; without it pi's own id — which names no entry in a rebuilt file — leaves the window the summary and the turns after it. `keptFrom` (the log index of the entry pi kept first) is in the row's shape and rendered when present, and nothing produces it yet: pi's message events carry no entry id, so the mirror has no map from `firstKeptEntryId` to a turn.
7. **The registry and the sweep.** `RunHistoryDO` keeps `sessions(key, thread_key, agent, last_finished_at, bytes)`, upserted at a claim naming a session and at every record write naming one, and `runs.session_key`, the session a finished record was a range of (null for one without). The 6-hourly sweep, inside its transaction, trims the runs and lists the sessions no remaining run row names; after the transaction, each drop awaits the session object, so a claim or a finish can land between two drops and the list can go stale; the decision is therefore taken per key on what the object re-reads right before that key's drop — `SELECT 1 FROM runs WHERE session_key = ?` and `SELECT 1 FROM live_runs WHERE thread_key = ?` — through the pure rule `sessionsToDrop`, which takes exactly those two facts per candidate and answers `drop`, `kept-run` or `thread-live`. A candidate a fresh record or a live run has overtaken is skipped and keeps its registry row; any live run on the thread blocks every session of that thread, whichever agent it runs. A dropped session goes through the object's `drop()`: the owner row first, so a write racing the drop is refused, then every row, index entry, attachment, the notepad and the budget; the registry row goes once the object is empty. A session with a kept run, or a live thread, stays whole.
8. **The full-text index.** `turns_fts` is an external-content FTS5 table over `turns(id, text)`, so a row is stored once. A replaced row's old text is removed with the FTS `delete` command before the new row is written and indexed — the table learns of a replacement only when told — and the byte policy's markers are indexed the same way. What a row indexes (`textOfStoredRow`): a text part's text; a tool result's text, string or parts, so a failing test's name in a report is findable; a tool call's name and arguments, so a command is findable; a compaction row's summary; an image, a document, a thinking block or an unreadable row, nothing. `SessionLogDO.search(query, limit)` answers matching rows newest first over the memory store's `MATCH` expression; its route and the `recall` tool are rollout (2).

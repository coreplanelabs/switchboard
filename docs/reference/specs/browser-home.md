# Browser Home

Home presents durable work independently of the process that most recently worked on it. The organization is fixed by the installation; browser input cannot select another organization's inventory or grant authority.

- **Code**: `src/core/home/service.ts`, `src/core/coordinator/inventory.ts`.
- **Tests**: `src/core/home/service.test.ts`, `src/core/coordinator/inventory.test.ts`, `deploy/cloudflare-memory/inventory.test.ts`.

## Behavior

1. **Durable discovery.** Home reads paginated coordinator records and their unit rows, rather than discovering work through recent runs. Held work, missing verdicts, spent budgets and stopped runs remain unresolved until durable completion or the confirmed pipeline stop settles them. Merged and already-landed units appear in separate history. Seeded dependencies and existing unit owners remain intact.
2. **Current authorization.** Every instance is admitted with the same requester, channel, repository and unknown-visibility predicate as the existing unit listing. Denied instances contribute no identifiers, text or counts. Private workers retain the existing redacted unit facts and omit source conversation labels, links and conditions.
3. **Honest completeness.** A failed inventory page, unit read, condition read, repeated cursor or read bound yields partial data, or unavailable when nothing could be read. A failed, malformed, foreign or ambiguous condition read retains even an apparently completed unit as unresolved with unknown next action; incomplete conditions never prove absence of an obligation. Empty authorized data and a fully filtered read are distinct. Supported local proof includes more than one thousand unresolved units. A complete inventory census is not a simultaneous transaction over every unit's changing state.
4. **Personal attention.** Only an open durable condition explicitly assigned to the current actor enters personal attention. Original requester attribution, an idle outcome and run health never invent that assignment. Automation, another person, external dependencies and unknown conditions remain visible without personal urgency. Condition reads do not change unit ownership or authorize an answer.
5. **Live work and next action.** A supplied current-authorized live-unit read identifies moving work. Absent recorded conditions, the next action is unknown. The projection never invents a retry, recovery or continuation instruction from a display status.
6. **Separate history.** Completed history is independently paginated, ordered by stable unit key and re-authorized on every read. The ordered inventory preserves its original insertion watermark; a continuation resumes the inventory page, instance and last scanned unit, so unresolved prefixes and read bounds cannot make later completed work unreachable. The cursor encrypts those internal positions with a persistent installation-owned 32-byte AES-GCM key and authenticates the organization and reader. It contains no transcript or grants and cannot be used by another reader or organization. The service never generates a startup key. If continuation is needed without a configured key or a fixed-census resume position, the result is partial with no continuation. A pending, uncertain condition or active unit effect keeps even a merged record unresolved until that obligation settles.

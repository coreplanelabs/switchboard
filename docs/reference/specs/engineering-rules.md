# Engineering rules

Coding and review use one portable engineering policy before work starts. Task skills add methods under that policy. Policy delivery does not prove compliance or grant execution permission.

- **Code**: `src/engineering.ts`, `src/engineeringBundle.ts`, `src/core/reviewRound.ts`, `src/core/dispatch/provision.ts`, `src/core/runEvents.ts`, `src/index.ts`, `src/cli.ts`, `engineering/`, `Dockerfile`, `packages/switchboard/build.mts`.
- **Tests**: `src/engineeringBundle.test.ts`, `src/core/reviewRound.test.ts`, `src/core/dispatcher.test.ts`, `src/deploy/affected.test.ts`, `src/ciPlan.test.ts`, `packages/switchboard/build.test.mts`, `packages/switchboard/smoke.test.mts`.
- **Decision**: [Engineering rules compose before work](../../decisions/0110-engineering-rules-compose-before-work.md).

## Behavior

1. **Portable source.** `engineering/manifest.json` has `schema: 1` and a non-empty ordered `files` list. Each name is a unique plain Markdown filename. Every required file is a regular file with non-empty UTF-8 text. Missing or malformed inputs fail startup with the original cause. The combined text is at most 8,000 UTF-8 bytes.
2. **Content identity.** The loader hashes each filename, a NUL byte, its exact UTF-8 content and a NUL byte, in manifest order, with SHA-256. It returns an immutable snapshot with `files`, `sha256` and the rendered text. The text trims each file's outer whitespace and joins files with two newlines. Changes to file contents or order change identity.
3. **Before work.** Service and CLI startup load the bundle and supply it to the shared prompt composer. Coding and review receive one engineering block after the effective agent prompt and before skill guidance. This applies to cold, resident and seeded workspaces and literal configured prompts. It does not depend on a skill store or a `use_skill` call. General and research receive no block.
4. **Provenance.** Bot startup logs the selected filenames and digest once, without rule contents. A coding or review dispatch records the selected filenames and digest in `run_meta.engineeringRules`. A resumed run keeps its saved system prompt and original provenance; it must not stamp the current process bundle as newly delivered. An already running harness keeps its original instructions. The build stamp identifies the process's source revision. Missing historical provenance remains unknown.
5. **Extension and scope.** Edit the owning topic or add a file to the flat manifest. Baseline rules cover idiomatic coding, SOLID, small structural changes, explicit error handling, telemetry and scoped verification. Repository instructions provide concrete error types and helpers. Skills provide task methods and do not repeat this bundle. A conflict needs an explicit disposition before dependent work. Authorization remains enforced by the existing controls.
6. **Distribution.** The loader resolves `engineering/` under the existing package asset root, independently of the operator working directory. The npm package ships its manifest and each rule selected by that manifest under `dist/assets/engineering/`. The bot image copies `engineering/`; manifest-only and rule-only changes select bot tests, the bot image and npm package verification in CI, and the bot in deployment selection. External clients can import the manifest and source files from a full commit and verify the digest. Generated client instructions must contain the selected rules and retain their own size limit. No runtime network fetch or dependency on a local checkout is required.

## Validation criteria

| Criterion | Proof |
| --- | --- |
| Ordered loading, stable content identity and changed identity after an edit | `[unit]` `src/engineeringBundle.test.ts::engineering rule bundle::loads required files in manifest order with stable content identity` |
| Duplicate, unsafe and empty lists are refused | `[unit]` `src/engineeringBundle.test.ts::engineering rule bundle::refuses duplicate, unsafe or empty file lists…` |
| Missing and empty required files fail without a partial bundle | `[unit]` `src/engineeringBundle.test.ts::engineering rule bundle::reports a missing or empty required file instead of loading partial rules` |
| Loading is independent of the operator working directory; the installed tarball carries all required rules, boots and logs its filenames/digest once | `[unit]` `src/engineeringBundle.test.ts::engineering rule bundle::loads the shipped policy independently of the operator working directory`; `packages/switchboard/smoke.test.mts::the tarball::*`, `packages/switchboard/smoke.test.mts::the installed CLI::*` |
| The shipped bundle and its bot image input are present | `[unit]` `src/engineeringBundle.test.ts::engineering rule bundle::ships every listed rule in the bot image…` |
| One policy block reaches all coding variants, configured prompts and review; general is unchanged | `[unit]` `src/core/reviewRound.test.ts::makeSystemComposer…::delivers engineering rules once before work across workspace variants and configured prompts` |
| A resumed coding run keeps its saved system and does not stamp the current bundle | `[unit]` `src/core/dispatcher.test.ts::run ledger write-through…::a resume re-attaches its recorded resident worktree…` |
| The first model request contains policy without a skill load and metadata records its identity | `[unit]` `src/core/dispatcher.test.ts::skill loading / progressive disclosure::supplies engineering policy before the first review turn without skill use and records its identity` |
| Manifest-only and rule-only changes select npm package verification, the bot image and root tests | `[unit]` `src/ciPlan.test.ts::selective CI::verifies the shipped npm package for engineering-only changes…`; `src/ciPlan.test.ts::selective CI::runs root tests when other workspaces change files those tests inspect`; `src/deploy/affected.test.ts::classifyPath…::a Worker's own directory…` |
| Local client adapters preserve a pinned export and verify actual startup adoption | `[agent]` Import from a full source commit with the client's projection tool. Verify its imported digest against the source and generated instruction files; reject an edited import. Open a fresh client session and confirm the engineering rules are loaded before a coding task. Source checks alone do not prove session adoption. |

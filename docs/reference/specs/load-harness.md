# Load harness

The repeatable measurement of Switchboard under many concurrent runs, and the receipt every capacity change is judged by: each change is a before/after number from these commands, never an estimate. The harness measures infrastructure — the bot process, the resident, the cold sandbox fleet, the Slack card path — never a model: the end-to-end command drives the bot with a scripted provider that never thinks. One command is the exception by design: the pi driver (items 13–15) measures an alternative agent harness on real coding tasks, so it is the one command that spends model tokens — and its dry run uses the same scripted provider. One command measures nothing: the door report (item 19) counts the front door's decisions off the run store's records.

## Behavior

1. **One sample per operation, one summary per run.** Every command records a `Sample` per operation it performs (`op`, start, duration, ok, and on failure the refusal's machine token as `reason`) and reduces them with `summarize`: per operation the count, successes, failures and p50/p95/p99/max latency — **over the successful samples only**, because a refusal answers in milliseconds and would flatter every percentile it joined; an operation with no success reports NaN, never 0. Failed samples are counted by `reason` (`unnamed` when the client threw without one). Percentiles are nearest-rank.
2. **Checks are the plan's D10 lines.** `evaluateSlo(summary, spec)` turns `<op> p<p> ≤ N ms`, `zero <reason>` and `zero failed <op>` rules into pass/fail lines carrying the actual number; a latency or zero-failures rule on an operation with no samples FAILS with `no samples` rather than passing vacuously. `zero failed <op>` is the structural form for a command whose failure reasons are open-ended (`load -- e2e`: a run's terminal status or an HTTP status), so an unanticipated reason can never pass by omission. Each command has its own spec in `scripts/load.ts`; the exit code is non-zero when any check fails.
3. **The receipt is markdown.** `renderMarkdown` writes the parameters, the per-op table, refusals by reason, each check as ✅/❌ with the actual and the limit, a `Verdict: PASS|FAIL|no checks` line, and free-text notes. Every command writes `load-results/<command>-<runId>.json` (the samples, the summary, the checks) and `.md` beside it; `load-results/` is gitignored — receipts go on the tracking issue.
4. **`load:history` reproduces the baseline.** It pages the state Worker's `POST /runs/list` newest-first with the `(finishedAt, id)` cursor, drops the provisional start-of-run tombstones (`finishedAt === startedAt`, [run-history.md](run-history.md) item 27), and sweeps the half-open `[startedAt, finishedAt)` intervals for the peak number of simultaneously live runs (overall and per UTC day) plus the duration mean and percentiles. A run finishing exactly when another starts does not overlap it.
5. **One driver, guaranteed teardown.** `runThreads` starts N threads spread evenly over the stagger window (the first at once, the last at the window's end), runs each thread's `setup → iterate… → teardown` until the hold ends or the run is aborted, and ALWAYS runs teardown — with the setup or iteration error that ended the thread — so whatever setup acquired (a pool seat, a sandbox, a card) is released. A setup failure counts and never iterates; an iteration error ends its thread and counts; a teardown that throws counts and never stops the other teardowns; an abort signal ends every thread at its next iteration boundary.
6. **The scripted provider never thinks.** `startScriptedProvider` serves `POST /chat/completions` in the OpenAI wire shape the `openaiCompat` provider parses; the answer is the script step at index = the number of tool results already in the conversation, so one server serves fifty conversations with no per-conversation state. A tool step answers one `tool_calls` entry (`call_<index>`, JSON arguments) with `finish_reason: tool_calls`; a text step answers content with `stop`; past the script's end the answer is its trailing text (`Done.` when none); a tool the request did not declare is removed from the script for that request (the step index stays the tool-result count), so each declared tool is called exactly once. The `coding` profile reads, inspects, burns CPU (`cpuBurnCommand`: one core, pure compute, `--cpu-seconds`), writes under `.load-harness/` in the worktree and answers; the `review` profile reads, inspects, burns and answers. **Neither ends with a terminal tool by default** (`submit_pr_description`, `submit_verdict`): a load run has no GitHub side effect; `terminal: true` opts in for a fixture repo.
7. **The fake Slack enforces the published limits.** `FakeSlack` answers `chat.postMessage`, `chat.update` and `conversations.replies` in Slack's shapes, refuses `chat.update` with `ratelimited` + `retryAfterS` when either budget is spent — a per-app token bucket at the Tier 3 rate (default 50 a minute) and a per-channel bucket at the coalescer's cited ~1 edit a second — and records for every accepted edit the lag from the frame's production time (`frameAt`) to acceptance, so a refused frame's lag keeps counting through its retries. `stats()` reports posts, updates, refusals, distinct cards edited, and lag p50/p95/p99/max.
8. **`load:resident` drives the bot's own client.** N `ResidentExecutor`s with thread keys `load:<runId>:<i>`, each attaching (timed as `attach`) then looping the profile: `read` README.md, `exec` a short git command, `exec-cpu` the CPU burn, `write` under `.load-harness/` (coding only; the review profile attaches read-only and never writes), a pause; teardown `release("always")` timed as `detach`. Refusals count by token (`user-pool-exhausted`, `mirror-busy`, `disk-pressure`). Guards (plan D9): the run refuses to start unless the operator `GET /status` reports exactly 0 in flight (unknown is refused); more than `RESIDENT_LOAD_MAX_THREADS` (16, one resident's pool) needs `--override`; and after the run the admin `purge-bindings` op removes the run's evicted bindings under `load:<runId>:` — a purge failure is reported in the receipt, never thrown, so the measurements always come back.
9. **`load:cards` is a simulation over the real coalescer.** The HTTP ingress `status()` handle is a no-op ([http-ingress.md](http-ingress.md) item 2), so an end-to-end run exercises zero card traffic; `simulateCards` instead runs N cards through `coalesceStatus` (the production floor, 3 s) against `FakeSlack` in **virtual time**: each card produces the dispatcher's 5 s heartbeat frames and a tool event every 7 s for the hold, then a terminal frame; the edit path mirrors the Slack adapter — one `chat.update`, on `ratelimited` wait Retry-After and re-send the same frame up to the WebClient's retry budget (10), give up after it; a retry whose frame has since been superseded is dropped as `staleDropped` (a real client would have spent it on a stale card). Deterministic and instant. **What it shows at the published limits, fifty cards, ten minutes:** edits refused, retries served first-come so most cards never get an edit at all (lag is measured over accepted frames only, so starvation hides in it — the surviving frames wait past the coalescer floor while the starved cards contribute nothing), and **terminal frames lost** — the adapter's `done` swallows the failed edit the same way, so a card past the retry budget stays a spinner forever. Lifting the limits gives every card sub-floor lag and every terminal frame: the limit, not the coalescer, is the ceiling. This is the number the plan's status budget (D3) has to fix.
10. **`load:e2e` runs the whole bot.** N threads each post `POST /ingress` synchronously (`{text, channel: "load", thread: <runId>-<i>}`, the bearer from `SWITCHBOARD_LOAD_INGRESS_TOKEN`) and record one `run` sample per request from the response's run receipt (`ok` iff `completed`; the terminal status is the reason otherwise; a transport failure is `transport`, a client timeout `timeout`). Between a thread's runs it pauses `--pause`; **after a failed request it pauses at least `failurePauseMs` (5 s)** so a dead endpoint is never hammered at full speed. While threads run, `GET /healthz` is sampled every 15 s for `inFlight` and the process metrics (item 12). The model is the scripted provider (`npm run load -- provider`, item 6) configured on the bot as an `openai-compatible` provider; the resident and sandbox Workers are whatever that bot is configured with. The receipt's check is `zero failed run` (item 2), and the run ends when the last thread does: the health sampler's sleep is raced against completion, never adding its interval to the tail.
11. **`load:sandbox` proves the cold path and measures the fleet ceiling.** N `CloudflareSandboxExecutor`s with keys `load:<runId>:sandbox:<i>`; the first command per thread (`first-exec`) is what creates the container, so its latency is the cold start or the `fleet-busy` wait ([execution.md](execution.md) item 14); then `exec` and `exec-cpu` per iteration. More than `SANDBOX_LOAD_MAX_THREADS` (25, the fleet's `max_instances` when written) needs `--override`. Sandboxes are not released explicitly; the Worker destroys them after their idle window. **`--seed-from repo:<slug>` is `load:seeded`**: one operator `GET /status` on the resident names the snapshot handle (`--seed-ref <branch>` rides along as the thread's ref), every thread calls `POST /seed` before its first command ([execution.md](execution.md) item 25) — recorded as `seed`, with the Worker's own step timings as `seed-restore`, `seed-deps` and `seed-fixup`, and each restore's two phases as `seed-checkout-download` / `seed-checkout-extract` and `seed-deps-download` / `seed-deps-extract` when the Worker reports them — and a refused seed ends its thread under the Worker's token. The receipt's checks add the D4 gate: `seed` p95 ≤ 90 s, zero `seed-missing` / `seed-failed` / `seed-unconfigured`; the result is written as `seeded-<runId>`. A resident with no snapshot is a refusal of the run, never a cold fallback: a seeded load measures the seed.
12. **`/healthz.process`.** The bot samples `process.memoryUsage()` and a `monitorEventLoopDelay` histogram (`startProcessMetrics`): `{rssMb, heapUsedMb, eventLoopLagP99Ms}`, the lag being the p99 over the window since the previous read (the histogram resets on each read, so consecutive polls read consecutive windows). Always present on the live `/healthz`; the harness reads it, and it is the only off-box view of the bot process under load.
13. **`load:pi` runs the five representative coding tasks on pi's harness.** For each task the driver puts the checkout on a branch it names (`load-pi/<task>-<runId>`, as the ship pipeline owns its children's branch), starts one `pi --mode rpc` in the checkout with every discovery off (`--no-extensions --no-skills --no-prompt-templates --no-themes`, a config directory of its own beside the receipt — `load-results/pi-<runId>-agent`, with `defaultProjectTrust: never`, kept after the run because pi's session files there are the run's own record — so neither the operator's `~/.pi/agent` nor a `.pi/` in the checkout is read) and exactly one extension loaded by path, pi's built-in tools allowlisted (`read, bash, edit, write, grep, find, ls`), and a session directory so the session file exists; then it sends `get_state` and the task's prompt and reads the stream until pi settles (`agent_settled`), the budget aborts it (`abort`, then a grace, then stdin closed), pi refuses the prompt, or the stream ends. The record per task: wall time, turns (assistant messages), pi's automatic retries, tokens and cost summed from pi's per-message `usage` (pi's catalog rates, an estimate), every tool call with its one-line summary, outcome, whether the extension's hook saw it and the refusal preview's verdict (item 14), the PR-shaped outcome — a `submit_pr_description` object that passes `parsePrDescription`, with the problems when it does not — the final text, the errors, a count per event kind, and the event kinds with no home on the run stream (`PI_EVENT_HOME`: each type pi documents maps to a `RunEvent` type or span name, or to `null`; an unknown type is reported as `unknown:<type>`). Each call is judged against the gate the hook stands for once the stream has said what became of it: `vetted` when the hook saw it before it ran; `rejected-by-pi` when pi answered the call by itself, before the hook and without running the tool — pi validates the arguments against the tool's schema before its `tool_call` hook fires (pi-agent-core `prepareToolCall`), and answers a call whose arguments fail, whose tool is not on its list, or whose assistant message the output token limit cut, with `tool_execution_start`, an error `tool_execution_end` in its own words and no hook (`piAnsweredWithoutRunning` reads those words; the record carries pi's reason as `piRejection`); `bypassed` when the hook never saw it and pi did not say it never ran — it ran, or was still open when the stream ended. The receipt's checks: every task settled, every task PR-shaped, every call pi ran also seen by the hook — none `bypassed`; the calls pi answered by itself are listed with pi's reason and never fail the check, since nothing ran. **The model key is read from the environment variable `--key-env` names (default: the variable pi itself reads for `--provider`), never from a file; without it the command refuses to start and prints exactly that variable's name.** The child's environment is an allowlist — `PATH`, `HOME`, the key under pi's own variable, pi's config directory, and the switches that keep pi off the network for everything but the model — and the key is never on the command line. pi runs in the checkout, not where the operator typed the command, and looks a relative path up there: every path the driver hands it — the config directory, the session directory, the extension — is absolute, whichever directory the driver ran from (a relative config directory is looked up in the checkout, where no models.json is, and pi knows no custom provider). Through the proxy the model's entry carries what pi's catalog says of the Claude family it fronts — `reasoning: true`, the 1M window, the 64k output ceiling — so the arm thinks at the same level and compacts at the same point as the direct arm; a bare custom entry pi runs with thinking forced off. On the Anthropic shape the entry also says which thinking payload the model takes — `compat.forceAdaptiveThinking`, from the production harness's `takesAdaptiveThinking` ([harness-pi.md](harness-pi.md) item 4): a Claude model from the 4.6 generation on takes adaptive thinking (`thinking.type: "adaptive"` plus `output_config.effort`) and the 5 family refuses the legacy budget with a 400, a model before 4.6 refuses adaptive and keeps the budget — because pi's built-in catalog says that per model and a model behind the proxy is not in it: without the flag pi sends the budget and a Claude 5 model answers 400 on its first thinking turn, every task settling in one turn with no tokens. The completions shape carries no such switch. A task pi left before its first turn (`exited`, no turn) has no stream to explain it: the receipt's notes carry pi's stderr for that task — redacted, folded onto one line, its first 300 characters — so the reason is on the receipt and not only in the JSON. Every string the record carries passes `redactSecrets`. `--print-prompt --task <name>` prints the task's prompt (with a branch of its own) and exits without starting pi or needing a key: the same words go to today's coding agent through `npm run cli -- ask` for the other arm of the comparison.
14. **The extension and the refusal preview.** The extension (`piExtension.ts`) has no imports so pi's own loader runs it as written: it registers `submit_pr_description` and `submit_verdict` as the bot's own definitions — the native table's description and JSON Schema field for field, transcribed and held equal by test, so a verdict requires `head` exactly as the relay's does ([harness-pi.md](harness-pi.md) item 11); pi validates the call against that schema without TypeBox — and a `tool_call` hook that observes and never blocks. Its one channel back is pi's `notify` UI request, which RPC mode writes to stdout as an `extension_ui_request` prefixed `switchboard-pi `, so a notice rides the same stream as pi's events and pairs with them by `toolCallId`; a dialog request (`select`, `confirm`, `input`, `editor`) is answered `cancelled` so no extension can hang an unattended run. The refusal preview (the coding preset's tool rules, `src/core/harness/pi/toolRules.ts`) stands in for the tool-level gate the authorization spec still lists as a gap and is not the policy table: each pi tool maps to a capability-profile bundle (`bash` → `shell`; `read`/`grep`/`find`/`ls` → `files`; `write`/`edit` → `write-files`; `submit_pr_description` → `pr`; `submit_verdict` → `verdict`); a bundle outside the coding preset's reach (`verdict`, or an unknown tool) is `outside-profile`; a `bash` that pushes to a remote other than `origin` or to a branch other than the run's (`HEAD` is the run's branch, since the driver checked it out), that merges or approves a pull request by CLI or API, that reads the executor's credential store, dumps the whole environment (`env`/`printenv` alone, `export -p`, `declare -p`, a bare `set`, `/proc/*/environ`, `process.env` whole — never `env VAR=x cmd` or one variable) or expands a credential-named variable, is `refused` with the rule named; a file tool whose path resolves outside the checkout, or names the credential file, is `refused`; everything else is `allowed`.
15. **The scripted provider streams, and speaks pi's tool names.** A `stream: true` request (pi's client always streams) is answered as `text/event-stream`: per step, one chunk carrying the whole call or text as a delta, one carrying the finish reason, one usage-only chunk with no choices, then `data: [DONE]`; a request without `stream` is answered as before. The `pi-coding` profile is the coding mix in pi's vocabulary (`read`, `bash`, `bash`, `write`) and always ends by submitting a description that passes `parsePrDescription` before its text — with pi the terminal tool reaches the driver and never GitHub, so there is no side effect to opt out of. `npm run load -- provider --profile pi-coding` plus `npm run load -- pi --provider scripted --model any --base-url http://127.0.0.1:8089 --key-env <any set variable>` is the dry run: a real pi process, the whole protocol, no model spend.
16. **A refusal's token is recovered from the error a client threw, never counted by message text.** `reasonOf` (`src/load/reasons.ts`) scans the message for one of the named tokens the Workers fold into their errors — `mirror-busy`, `user-pool-exhausted`, `disk-pressure`, `fleet-busy`, `runtime-replaced`, `not-onboarded`, `needs-ref`, `not-attached`, `rate-limited`, `seed-missing`, `seed-failed`, `seed-unconfigured` — wherever the token sits in the message; when no token is present, message fallbacks recover `fleet-busy` from the sandbox capacity error, `not-onboarded` from the resident's 404 answer, and `rate-limited` from an HTTP 429 or a "rate limit" phrase, checked before the timeout rule so a throttled request that also mentions a timeout counts as rate limiting. A timeout-shaped error (`TimeoutError`, "timed out", "timeout") is `timeout`; anything else is `unknown` — never a message fragment.
17. **`load:route` scores the request router against the requests people already typed** ([routing-and-config.md](routing-and-config.md) item 21; [record 0026](../../decisions/0026-capability-profiles-and-request-routing.md) asks for under 5 percent error before slice two). It pages the run store newest-first (`--since <date>`; `--limit N` labelled requests, default 200) and reads each record (`labelledRequests`): a run is a labelled example when a person chose its preset — `run_meta.agentSource` `directive`, typed for that message (the confusion table, record 0026's read-only-to-write clause and every bar are the directive labels' alone: `typedLabels`), or `sticky`, the thread's earlier preset carried onto a later message — the thread's choice, not the message's, so a sticky label is replayed and reported apart with its agreement and its own read-only-to-write count and never enters the table or the clause (the replay that moved the write door to `ship` scored directive labels 246/249 and sticky ones 30/51; the sticky misses were follow-ups such as "in one short paragraph, say what this thread changed" labelled `ship`) — or, for a record from before that stamp, on a preset other than `--default-agent` (default `general`), `unstamped`: the requester may have typed it, the thread may have carried it, or a channel or user scope's `agent` may have set it, and the record cannot say which (its `input` is directive-stripped), so these are replayed and reported apart — their count and how often the router agreed — and never enter the table or its bar; a stampless run on the default is unlabelled; never a run the router chose (its `route` event — the router is not graded against itself), a spawned or coordinator child, a schedule's run, an unknown preset, an empty text. The label is the preset the run ran on; the text is the record's `input` with every directive token hidden (`stripDirectiveTokens`), so the router sees exactly what a plain message would have been. Each request goes through the dispatcher's own `route` over `providerRouteModel` on `--provider`/`--model`, the provider a one-block table on pi's model library exactly as production builds the router's ([harness-pi.md](harness-pi.md) item 13), so the score is the deployed path's (the key from the environment as for pi; `--concurrency` at a time, 4 by default; the thread's earlier directives are not on a record and so none; the allowlist is every routable preset), and the receipt (`load-results/route-<runId>.md` and `.json`) is the per-preset confusion table with accuracy (`confusionTable`, `renderConfusion`), the misroutes (run id, label, routed, reason, the text), record 0026's read-only-to-write clause as a line of its own (`readToWriteRoutes`: every request whose label's identity is `none` or `read` — `general`, `research`, `review`, `explore` — that the router sent to a `write` preset, `coding` or `ship`; a compound is not one, its parts meeting the clause as children), the sticky and unstamped lines, the label sources and the skipped counts. **Historical write labels map onto the table's write preset** (`mapHistoricalLabels`, `tableWritePreset`): a label whose preset is not in the offered table but shares its `write` identity with the table's write preset — `coding`, once routable, after `ship` took its seat — scores as that preset (the requester asked for a write run; the table's write door moved under them), and the count of mapped labels is printed beside the table; a read label (`review`) answered with the write preset still scores as a misroute. The verdict's rows (`routeChecks`): accuracy at or above 95 percent over the directive labels, every one of them answered, read-only-to-write routes among them exactly 0 — a row that fails the verdict by itself, without anyone reading the table — and the three compound rows below. **The compound half**, on the same run of the command and under the same prompt — the compound form offered under `--max-parts` (default `spawn.maxChildren`'s 3), as production offers it to a requester who may run the conductor, so a labelled single the router splits is a misroute in the table: the checked-in set (`src/load/routeCompoundFixtures.ts`: twenty compound requests written in the house's voice with the presets a right split names, seven of them with a `ship` part carrying `collapsesTo: "ship"`, the write preset the whole request routes to since a write ask is never a part ([record 0034](../../decisions/0034-one-agent-per-unit-a-run-continues-a-transcript.md); [routing-and-config.md](routing-and-config.md) item 21), and five decoys — one ask with several steps that reads as compound, among them a read-only chain whose steps reach the web and then a repository, the split a fast model is most tempted by) is replayed (`replayCompound`) and scored (`compoundScore`): a compound to split is detected when the answer is the conductor with parts; a compound with a write part is collapsed when the answer is that preset, single, whether the router answered it outright as the prompt asks or the parse collapsed a compound answer that named it (the conductor with read parts, another single or no route is a miss, and its parts never enter the parts arithmetic); a decoy must stay a single route; and the parts are matched to the expected presets as multisets (an undetected compound matches none of its parts; a detected one with extra or wrong parts is a miss). The checks are detection on at least 90 percent of the compounds to split, every compound with a write part collapsed onto it (its own row, `n/m`, apart from the read-only-to-write clause: that clause is over the labelled singles alone, and a collapse never enters it, being a write label) and no decoy split, the row the compound wording is held to: the prompt says what is NOT compound once, in one place ([routing-and-config.md](routing-and-config.md) item 21), and a change to that wording is proven against this row on the live model before it lands, since a second rule paragraph once moved the row from 0 to 1 of 5 with every other row green, and the row stayed a coin flip under wordings that only defined independence until the paragraph counted what the person wants back first (a fixtures-only run, `--limit 0`, is the cheap probe: the compound and imperative sets alone, the history rows empty); the part-preset accuracy is printed beside them with every miss (id, kind, expected (`ship single (a write part among review+ship)` for a collapsing one), answered, reason, text). The history's `conductor` requests — every labelled request whose requester typed `agent:conductor`, left out of the singles table since the conductor is never a single route — are replayed the same way and scored on detection alone (their parts are not on the record), their count printed honestly, `no conductor request in the window` when there is none. **The imperative half**, on the same run and under the same prompt: the checked-in set (`src/load/routeImperativeFixtures.ts`: twenty-five imperatives expecting `ship`, the table's write preset — twenty terse ones, an order to change code or repair a failure with no file, cause or repository named, "looks like the ci failed, fix it" among them verbatim, the one real coding misroute the replay at the flip found; three spec-shaped ones, longer, on a named repository, saying how something should behave and asking for it to be done with no "fix" or "implement" anywhere, among them verbatim except the repository the production ask ("I need you to do this for me and send me screenshots … *On the `<name>` repo:* the topology screen should show …") that routed to `explore`; two whose task is in a linked conversation, carrying `references: 1` — the count the route stage puts on the router's user turn ([routing-and-config.md](routing-and-config.md) item 21), which the replay hands to `route()` the same way (`RouteFacts`) — among them verbatim except the repository and the permalink the production ask "in `<name>` ship `<link>` - this, (read the whole thread)" that routed to `general`; eight read-only decoys — five about the same failures ("check whether ci is red", "list the failing tests") expecting `research` or `general`, a question about the repository in the spec-shaped voice ("does the topology screen show … today? change nothing"), an ask only a sandbox answers ("how long does `npm run typecheck` take … time it once", expecting `explore`) and a read-only ask about a linked thread ("what did we decide in `<link>`? summarize it", `references: 1`), each expecting read-only presets alone; six review-shaped asks naming a pull request expecting `review`, one of them a pull request URL with a note about the request's own history — "(retry at head …: the run died)", the one read-to-write misroute the production replay found once `ship` held the write seat, on a neutral repository) is replayed (`replayImperative`) and scored (`imperativeScore`): an answer counts as a hit when it is one of the example's expected presets, and a look-alike (a decoy or a review-shaped ask) that reaches a write preset (`identity: write`) is counted apart. The checks are the imperatives reaching the table's write preset (`ship`, the bar's label derived from the table and never typed) on at least 90 percent of the set and look-alikes reaching a write preset exactly 0; each kind's hits are printed beside them with every miss (id, kind, expected, routed, reason, text). The set exists because the history has almost no such requests: the router's one real coding misroute at the flip was one, so the case is scored on every run of the command. **The command half** ([record 0036](../../decisions/0036-one-front-door-the-router-offers-every-command-and-ship.md) unit 3), on the same run: the checked-in set (`src/load/routeCommandFixtures.ts`: a fixture of each kind per command the router is offered — a happy path with every required argument bound as a person would say it, a paraphrase, and a decoy that names the command's subject without asking for what the command does — plus any further decoys a production miss pinned verbatim (`help.show` carries two); the `repo.test` and `repo.build` sets include a `threadRepo` form, the repository the thread names reaching the router's user turn as production puts it there; the conformance suite fences every offered command to at least one fixture of each kind — [command-registry.md](command-registry.md) item 25) is replayed (`replayCommands`) over `route()` with the full-capability catalogue's menu (`routableCommands` over a bare `CommandRegistry` on `ALL_CAPABILITIES`) and scored (`commandScore`): a fixture hits when the router called its command (a wrong command is a miss), its bound input compared to the expected one after `parseInput` on both sides, so a coerced number equals its string (a right command with a wrong post-parse input is an input miss); a decoy bound to ANY command is a miss unless its `allow` list names the called command. The replay binds and parses only — nothing is ever invoked; the registry carries no deps. Two rows in the verdict: the command named right on every fixture and no decoy bound (bar 1.0) and the bound inputs right after parse on at least 90 percent (bar 0.9); every miss is printed with the bound and the expected input. **The counters line** (`tallyingProvider`, `renderCounters`): every router call of the whole replay rides a tallying decorator on the provider that sums `inputTokens`, `cacheReadTokens` and `cacheWriteTokens` and counts the answers that carried two tool calls — refused by `providerRouteModel` (the route is one call) — and the receipt prints the mean of each counter per call and the two-call count, so the cost, the prompt caching (nonzero cache reads from the second call on) and the refusals are on every receipt. **The verifier** ([record 0044](../../decisions/0044-a-routed-write-is-confirmed-in-proportion-to-its-blast-radius.md), the verifier), under `--verify` alone and on the same run of the command half: every bind whose command's blast radius is `write` or `destructive` (`verifierAsked`: `blastRadius` off the BOUND command — what would run — so a read bind, an exec bind and an example that bound nothing are never asked) gets one more call through the same `RouteModel` and the same tallying provider (`verifyBind`). The prompt (`verifierPrompt` in `src/core/dispatch/route.ts`, a pure builder nothing in production calls) says in its system half that the model checks a binding and does not make one — it never routes, rebinds or rewrites — and in its user half carries the sentence, quoted as the router quotes it, and the bound chat form (`chatInvocation`, the line the person would type), and asks one question — does this line do what the person asked — answered by a forced call to the `verify` tool with `agrees` and a one-line `reason` (`parseVerifierAnswer`; a call that fails, calls another tool or answers prose is a disagreement with the failure as its reason, never a silent agreement). Two counters over the verified binds (`verifyCommands`, `verifierScore`): **write misbinds removed** — a verified bind `commandScore` marks wrong (a wrong command, a right command with the wrong post-parse input, or a decoy bound to a write outside its `allow`) that the verifier rejected — and **correct binds rejected** — a verified bind it marks right that the verifier rejected; printed beside the command rows as `verifier: removed <n> of <m> write misbinds · rejected <k> of <j> correct write binds` with the two ratios and every rejected bind with the line it was shown and its reason (`renderVerifier`). The record's bar — at least half the write misbinds removed under one rejected correct bind in twenty — is named on the line and never judged: no verdict row; the production decision is the maintainer's, taken off these two numbers. Without the flag nothing changes, and with it the replay is still parse-only: the verifier invokes nothing. The one command besides pi that spends model tokens — one small call per request, two on a verified bind; the tests run it with a scripted decision.

18. **`load:pi --suite review` runs the review tasks on pi's harness under the read identity, and posts nothing.** The tasks (`piReviewTasks.ts`) are merged pull requests of the repository the checkout clones — three to five shapes a review is routinely handed — each carrying its number, its head at merge, its head branch and its title, and never the repository's name: the checkout's `origin` names it (`originSlug`), the receipt renders each pull request's URL from that, and a checkout whose origin does not hold a pinned head refuses to start. The suite is repeatable because GitHub keeps `refs/pull/<n>/head` after a merge. For each task the driver fetches that ref beside the base branch into a ref of its own, detaches the checkout at it and refuses to start when `HEAD` is not the pinned head — the resident attaches a review's worktree at the PR head the same way, and a review of the wrong head is the one thing the post-step never posts; then it writes pi's `SYSTEM.md` — the registry's resident review prompt composed by the run loop's own `makeSystemComposer` with the REVIEW TARGET block naming the task's pull request, head and base and the checkout as the worktree, the read identity's harness note (the five read tools, no `edit`, no `write`, `submit_verdict` the one relay), and a driver note naming the relays this driver has no bot to serve (`diff_digest`, `update_status`, `web_fetch`, the skill tools) — and starts pi with the read identity's allowlist (`PI_REVIEW_TOOLS`: pi's tools less `edit` and `write`, plus `submit_verdict`; no `submit_pr_description`), the same extension, the same budget rules with 25 minutes as the default, and the prompt a person would type (the pull request by URL). The extension's `submit_verdict` — the native definition, so the model is held to naming `head` — records the verdict on the stream and the driver keeps it in the receipt in place of the post: nothing reaches GitHub; the driver note says the head is held against the reviewed one as the post-step's guard holds it. Each call is previewed against the tool rules under `identity: read` (item 14's rules with the read reach: `edit` and `write` outside the profile, any push refused). The score is the post-step's judgement without the post: the verdict parsed by the same parser (`parseVerdictInput`), its head held against the pinned one by the same guard (`checkReviewedHead`), the body the post-step would have posted rendered by the same `buildReviewPostBody` — its first line on the receipt — and the read-only facts: no write tool ran (a write pi refused before the hook is listed and does not fail the row; one that ran does), the checkout's tree clean and its `HEAD` still the pinned head after the task. The receipt's checks: every task settled, every task's verdict in the house shape naming the reviewed head, every call pi ran seen by the hook, no write tool ran, the checkout untouched, no credential persisted; the notes carry one row per task with the verdict, its finding count, the head check and the write calls. Both arms run as for coding — a built-in provider with its own key, or `--through-proxy` with a run bearer. The dry run is `npm run load -- provider --profile pi-review` plus `--suite review --provider scripted …`: the `pi-review` profile reads the head and the diff with pi's `bash` and submits an `approve` whose `head` is a placeholder the scripted provider resolves off the REVIEW TARGET block in the request (`REVIEW_HEAD_PLACEHOLDER`), the way a model reads it; a request without the block leaves the placeholder and the parser drops it.
19. **`load:door` counts the door's hand-backs and the pastes that followed** ([routing-and-config.md](routing-and-config.md) item 21; [record 0044](../../decisions/0044-a-routed-write-is-confirmed-in-proportion-to-its-blast-radius.md): the counts before anything is built, the evidence its first open question turns on). `npm run load -- door [--since <date>]` pages the run store's finished command runs — `listRuns` with agent `command`, `visibleTo: all`, the list's own cursor, at most 50 pages of 200 ([run-history.md](run-history.md) item 20) — through the one runs service over a bare registry (this process drives no runs), reads each run's events, and counts a run whose `route` event carries `outcome: hand_back` under the UTC day it finished and the command it bound, and a run carrying `outcome: pasted` under its hand-back's day and command by `handBackRunId` — whatever day the paste landed, since the question is whether that hand-back was pasted; a paste whose hand-back is not among the runs read (before `--since`, or gone from the store) is counted apart as unmatched; a routed read (a `route` with no outcome) and a typed inline run (no `route`) are read and left out. It prints the totals with the paste-through rate — `pastes / hand-backs`, a dash over none and never a division error — then each day with its commands under it, and a last line when the store could not be read, the counts being the live registry's alone and the exit code non-zero. It invokes nothing and spends no model tokens; it writes no receipt file: a count, not a load test.

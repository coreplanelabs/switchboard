# Model proxy: a run's bearer buys model calls through the bot, and no container ever holds a key

The credential boundary ([record 0016](../../decisions/0016-long-lived-process-not-serverless.md)): no Worker and no execution container holds a model key; the bot process does. A harness that runs inside an execution container and calls the provider itself ([record 0032](../../decisions/0032-pi-is-the-harness-the-native-loop-retires.md)) must therefore believe it holds a key while holding a token the bot minted for that run alone. The **model proxy** is that seam: two routes on the bot's HTTP server shaped like the two provider APIs a harness speaks natively, a **run bearer** minted per run and presented as the API key, and a **meter** that records every proxied call as the run's own `model.turn` span with the attrs the native runner sets — so the run page, the friction analyzer and the costs page keep one vocabulary and never learn the turn happened in another process. Its first client is the pi harness ([harness-pi.md](harness-pi.md)): a run whose preset is on pi hands pi the bearer as its provider key; every other run is unchanged.

## Behavior

1. **Two routes, the shapes a harness speaks natively.** `POST /v1/messages` is Anthropic-shaped and `POST /v1/chat/completions` OpenAI-shaped — the same two words the `providers:` block uses for a provider's `type` (`anthropic`, `openai-compatible`), so a run's route is its provider's type and nothing is ever translated between shapes: a run whose provider speaks the other shape is refused `400 wrong_shape` naming the path it should have used. The shim Worker forwards both paths to the container the way it forwards `/ingress` — it answers neither itself, reads nothing, and its route table names them with the one word `model-proxy` — and the Access application does not cover them; the run bearer is the whole door, decided in the bot. Transparent means: the proxy touches exactly two fields of the body (item 4) and re-serializes the rest as it came — `cache_control` markers, tool definitions and `tool_choice`, `thinking`, `output_config.effort`, `stop_sequences`, `metadata`, `stream` all reach the provider byte-for-byte — and hands the provider's answer back with its status, `content-type` and request id, a streamed answer chunk for chunk in order.
2. **The run bearer.** One is minted the moment a run's executor is provisioned (the dispatch's attach, `mintRunBearer`), bound to the run's id and pinned to the resolved `<provider>/<model>`, the preset's `maxTokens` and `maxTurns`, expiring at the run's effective budget plus `BEARER_MARGIN_MS` (five minutes, so the write-up a budget exhaustion asks for still has a credential). The token is `sbr_<runId>.<secret>` — the run named in the clear, 32 random bytes as the secret — so the proxy tells an unknown run from a wrong secret without a second lookup, and secrets compare in constant time. It is **revoked** the moment the run is reported finished (`RunEnding.finished` runs `onFinished` before the seal) and again by the dispatch's outer finally for a run that never reached its loop; a revoked entry stays until its expiry so a late call is answered `revoked`, then is swept. The store is in-process: a bot restart drops every bearer with the runs that held them, and the generation that resumes a run mints its own. A second mint for the same run replaces the first — except that a pi which outlived the bot still holds the bearer the previous generation revealed to it ([harness-pi.md](harness-pi.md) item 8): the run's harness facts carry that bearer's secret hash (`bearerHashOf`, SHA-256 hex — the store keeps hashes, never secrets, and a hash buys no call), and the generation that re-attaches adopts it onto the run's fresh entry (`adopt`) so pi's calls verify under this generation's grant and turn counter beside the new bearer; a row without a hash cannot make that pi's calls verify, so the harness ends it and restarts pi with the new bearer instead. Without a store (the CLI, tests) nothing is minted and the run is byte-identical to before. The token returns to the caller alone: never logged, never on the record, never in a file. **Rotation.** A process relaunched under a living bot — a replaced container, the ceiling of [record 0038](../../decisions/0038-the-harness-is-a-contract-pi-is-its-one-implementation.md)'s survival clause over [harness-pi.md](harness-pi.md) item 16's floor — gets a new secret on the run's own entry (`rotate`), never a second mint: the turns spent, the expiry and the span stay exactly what they were, where `mint` would reset them and hand each relaunch a fresh budget. The order is for a bot death: the new hash joins the entry and is handed to the caller's write of the run's row BEFORE every earlier hash — the mint's, an operator's, an adopted one — is dropped, so a generation that dies between the two steps leaves a row naming the secret the relaunch was minted and never the orphan's; a row write that throws propagates with both secrets verifying and nothing dropped. The write is issued synchronously inside `rotate` (the run's `saveFacts`, queued on the ledger's write-through, which flushes in order): what the store orders is that write's place in the queue, so no facts write may land between the callback and `rotate`'s return. A re-attach adopts and never rotates: a live process cannot be handed a new secret. `rotate` refuses by name the runs `issue` mints nothing for — unknown, ended, expired — and hands the row nothing then; `grantOf` counts the secrets that buy the run's calls (`bearers`): the mint's, one more per `issue` and `adopt`, exactly one once a rotation completes.
3. **The door, from the headers alone, in order.** A path that is not one of the two is `404`; a non-POST `405`; no bearer `401 missing_bearer` (the bearer rides `Authorization: Bearer <bearer>`, the OpenAI shape, or `x-api-key: <bearer>`, the Anthropic SDK's header — either is accepted on either route); a token that is not a run bearer `401 malformed_bearer`; a run this bot never minted `404 unknown_run`; the right run with a wrong secret `401 unknown_bearer`; a bearer past its expiry `403 expired`; one whose run ended `403 revoked`. The node adapter decides this before it reads a byte of the body and destroys a refused request. Past the door: a body over the cap (32 MB, the Messages API's own) is `413`; a body that is not a JSON object `400 invalid_body`. Every refusal is written in the route's shape so the client's SDK reads it as the provider's own error: `{ type: "error", error: { type: <code>, message } }` on the Anthropic route, `{ error: { type: <code>, message } }` on the OpenAI one. A refusal never echoes what the caller sent: an unknown path is refused without repeating it, and the wrong-shape message names the route hit from the proxy's own table.
4. **Pinning and the upstream.** `model` on the wire is the grant's bare model id whatever the body named; the output cap is the grant's `maxTokens` — as `max_tokens`, or on the OpenAI shape as `max_completion_tokens` when the body capped with that key (a stray `max_tokens` beside it is dropped, so no second cap survives). The upstream is the run's `providers:` entry: the Anthropic shape goes to `<baseUrl ?? https://api.anthropic.com>/v1/messages` with the real key as `x-api-key` and the client's `anthropic-version` (the SDK's default when the client sent none) and `anthropic-beta`; the OpenAI shape to `<baseUrl>/chat/completions` with `Authorization: Bearer <key>` when the entry names an `apiKeyEnv`, and no authorization header at all when it does not (a local endpoint). Only `accept`, `anthropic-version` and `anthropic-beta` are forwarded from the request; the run bearer's own headers never are. A provider the config does not name, or one without a `baseUrl` on the OpenAI shape, is `503 provider_unconfigured`; a key variable that is unset `503 provider_key_missing` naming the variable — both decided before a turn is spent. The key is revealed into the upstream request and nowhere else. The `providers:` block is read at each call, so a config reload reaches the proxy as it reaches the mint.
5. **The turn guard is enforced here, as a typed run event.** The grant's `maxTurns` is the preset's runaway guard — `runawayTurnCap(maxMinutes)`, six turns a minute over the wall clock ([harness-pi.md](harness-pi.md) item 15; 270 for a coding run) — not a budget a working run reaches. A turn is counted before the call is forwarded (so concurrent calls cannot overrun) and the call past it is refused `403 turn_budget_exhausted`, forwarding nothing and opening no span; the refusal publishes one `run_note` of kind `turn_budget_exhausted` on the run's stream naming the guard and the counts (`model proxy refused a call past the run's 270-turn guard (270 turns used)`; the response body says `the run is past its 270-turn guard (270 turns used)`) — the same kind the harness notes when it ends the run on the guard ([harness-pi.md](harness-pi.md) item 6), so the run page and the friction analyzer read one vocabulary. A `403` rather than a `429`: a rate-limit status is one an SDK retries, and this is a refusal. An upstream failure spends the turn. A run that ended between the door and the turn — its bearer verified a moment ago, the run revoked since — is `403 revoked` with no note: the store answers `ended`, never a zero-turn budget.
6. **The meter: one `model.turn` per proxied call, the loop's attrs.** Every forwarded call opens one `model.turn` span under the span the grant carries — the request root at the mint, the harness's `run.agent` once `reparent` moved it there ([harness-pi.md](harness-pi.md) item 5), so a proxied turn lands where the native loop's did — with `model` (the `<provider>/<model>` ref, as `run_meta` carries it) at start, and ends it with the attrs the native runner set: `stopReason` mapped as the deleted adapters mapped it (Anthropic `end_turn` and `stop_sequence` → `end_turn`, `tool_use`, `max_tokens`, anything else `other`; OpenAI `stop` → `end_turn`, `tool_calls` → `tool_use`, `length` → `max_tokens`), `inputTokens`, `outputTokens`, `cacheReadTokens` and `cacheWriteTokens` when the provider reported them (`usageFromAnthropic`, `usageFromOpenAI` in `src/core/modelProxy/usage.ts`), and `ttftMs` (the first chunk's arrival) on a streamed answer. A streamed answer is forwarded chunk for chunk as it arrives and the span ends only after the last chunk; the `SseMeter` reads the counts as the bytes pass — Anthropic's `message_start` carries the input and cache counts, `message_delta` the stop reason and the final output count; an OpenAI stream's `finish_reason` and its `usage` frame when the client asked for one (`stream_options.include_usage`) — a `data:` line may span chunks and CRLF framing is accepted. A buffered JSON answer is metered whole. An upstream status outside 2xx is forwarded verbatim (status, headers, body) and ends the span `error` with `httpStatus`; an upstream that cannot be reached is `502 upstream_unreachable`; a stream the upstream breaks ends the span `error` and errors the forwarded stream. The span's parent is the request root, so it streams onto the run's record through the same sink every setup span uses and is dropped, like any late span, once the run is sealed.
7. **What the proxy never says.** One log line per call — `[model-proxy] run=<id> turn=<n>/<max> <shape> → <status> in=<bytes> out=<bytes> <ms>ms` — and one per refusal naming the status, the code and the run id; never a body, a bearer, a secret or a key. The bearer store's verdicts carry a reason and a run id, never token material.
8. **The operator's probe bearer.** `POST /admin/model-proxy/bearer` with `{ "runId": "<id>" }` mints one more bearer on a live run's own entry — same expiry, same turn counter, same pinned model — and answers `201 { ok, runId, bearer, expiresAt, model, path, turns: { used, max } }`, the bearer written to that response once and never to a log (the line names the operator and the run). The door is the restart's and the crash's: an ingress bearer whose `http:<subject>` actor holds `deploy:write` — the operator who may stop the bot may mint a probe for one of its runs — `401` without a bearer, `403` without the grant naming it, `503` without a token map, `405` for a non-POST, all from the headers. A run this bot never minted is `404 unknown_run`; a run that ended or whose bearer expired `409 run_ended`; a body that is not `{ runId }` with a run id in the run-id alphabet `400`. Its calls are the run's: they spend its turns and land on its record as `model.turn` spans, and they stop at its end.
9. **The node adapter.** The door from the headers, then the call; a buffered answer is written whole; a streamed one has its headers flushed first and is written chunk by chunk under back-pressure, then ended; a caller that goes away mid-stream aborts the upstream call through the request's signal. Every response's content type is one of three literals chosen by kind — the provider's JSON or event stream as such, anything else as `text/plain` — with `X-Content-Type-Options: nosniff`, so nothing this route writes, a refusal or a provider's error page, is ever rendered by a browser as a document; the other forwarded headers ride as they came.
10. **Every run is the proxy's client.** The run's pi is handed the bearer as its provider key through the process environment ([harness-pi.md](harness-pi.md) item 4), and every model call it makes is one proxied turn here — pinned, guarded and metered as above; no code path in the bot calls a provider with the deployment's key for a run's turn. The bearer exists on every run — minted and revoked around each — and buys nothing unless presented.

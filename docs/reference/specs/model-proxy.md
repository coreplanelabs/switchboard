# Model proxy: a run's bearer buys model calls through the bot, and no container ever holds a key

The credential boundary ([record 0016](../../decisions/0016-long-lived-process-not-serverless.md)): no Worker and no execution container holds a model key; the bot process does. A harness that runs inside an execution container and calls the provider itself ([record 0032](../../decisions/0032-pi-is-the-harness-the-native-loop-retires.md)) must therefore believe it holds a key while holding a token the bot minted for that [run](../vocabulary.md#run) alone. The **model proxy** is that seam: three routes on the bot's HTTP server shaped like the three provider APIs a harness speaks natively, a **run bearer** minted per run and presented as the API key, and a **meter** that records every proxied call as the run's own `model.turn` span with the attrs the native runner sets — so the run page, the friction analyzer and the costs page keep one vocabulary and never learn the turn happened in another process. Its first client is the pi harness ([harness-pi.md](harness-pi.md)): a run whose preset is on pi hands pi the bearer as its provider key; every other run is unchanged.

## Behavior

1. **Three routes, the shapes a harness speaks natively.** `POST /v1/messages` is Anthropic-shaped (`anthropic-messages`), `POST /v1/chat/completions` Chat-Completions-shaped (`openai-chat`) and `POST /v1/responses` Responses-shaped (`openai-responses`) — the same words a `providers:` block's `wire` declares (item 11; the legacy `type` words load as their aliases), so a run's route is its provider's wire and nothing is ever translated between shapes: a run whose provider speaks another shape is refused `400 wrong_shape` naming the path it should have used. A preset on OpenCode with a Responses block is refused at dispatch by name (`resolveTarget`) until OpenCode's bundled `@ai-sdk/openai` is measured against the logging fake — the conformance matrix's declared `cannot` carries the same reason — so the Responses route's clients are pi's runs. The shim Worker forwards the three paths to the container the way it forwards `/ingress` — it answers none itself, reads nothing, and its route table names them with the one word `model-proxy` — and the Access application does not cover them; the run bearer is the whole door, decided in the bot. Transparent on successful calls means: the proxy touches exactly two fields of the request body (item 4) and re-serializes the rest as it came — `cache_control` markers, `tool_choice`, `thinking`, `output_config.effort`, `reasoning.effort`, `stop_sequences`, `metadata`, `stream` all reach the provider byte-for-byte; tool definitions do too except that per-wire schema shaping removes a construct measured as refused by that wire and records one `control_degraded` note per tool and keyword. The direct operator's `providerStructuredModel` → `PiAiProvider` Responses path applies that same pure shaper immediately before the adapter call; canonical tool definitions and other wires remain untouched — and the proxy hands a successful provider answer back with its status, `content-type` and request id, preserving every stream chunk in order while adding only the SSE keepalive comments item 6 names during silence; a failed answer follows item 12b and keeps only status, request id, typed cause and rendered sentence.
2. **The run bearer.** One is minted the moment a run's executor is provisioned (the dispatch's attach, `mintRunBearer`), bound to the run's id and pinned to the resolved `<provider>/<model>`, the preset's `maxTokens` and `maxTurns`, expiring provisionally at the provisioning allowance plus the run's effective lease plus the grace (`provisionalBearerExpiresAt`, [decision 0046](../../decisions/0046-a-budget-is-a-lease-carved-from-its-parent-and-one-module-proves-the-leases-fit.md)); the moment the harness starts the lease it moves the expiry to the lease's end plus the grace of one minute (`leaseStarted`, `bearerExpiresAt`, `ALLOWANCES.bearerGrace`) — the write-up and the post-step run inside the lease ([harness-pi.md](harness-pi.md) item 15), so a minute is all a late call needs, and the grace is measured from the lease, never from the attach. The token is `sbr_<runId>.<secret>` — the run named in the clear, 32 random bytes as the secret — so the proxy tells an unknown run from a wrong secret without a second lookup, and secrets compare in constant time. It is **revoked** the moment the run is reported finished (`RunEnding.finished` runs `onFinished` before the seal) and again by the dispatch's outer finally for a run that never reached its loop; a revoked entry stays until its expiry so a late call is answered `revoked`, then is swept. The store is in-process: a bot restart drops every bearer with the runs that held them, and the generation that resumes a run mints its own. A second mint for the same run replaces the first — except that a pi which outlived the bot still holds the bearer the previous generation revealed to it ([harness-pi.md](harness-pi.md) item 8): the run's harness facts carry that bearer's secret hash (`bearerHashOf`, SHA-256 hex — the store keeps hashes, never secrets, and a hash buys no call), and the generation that re-attaches adopts it onto the run's fresh entry (`adopt`) so pi's calls verify under this generation's grant and turn counter beside the new bearer; a row without a hash cannot make that pi's calls verify, so the harness ends it and restarts pi with the new bearer instead. Without a store (the CLI, tests) nothing is minted and the run is byte-identical to before. The token returns to the caller alone: never logged, never on the record, never in a file. **Rotation.** A process relaunched under a living bot — a replaced container, the ceiling of [record 0038](../../decisions/0038-the-harness-is-a-contract-pi-is-its-one-implementation.md)'s survival clause over [harness-pi.md](harness-pi.md) item 16's floor — gets a new secret on the run's own entry (`rotate`), never a second mint: the turns spent, the expiry and the span stay exactly what they were, where `mint` would reset them and hand each relaunch a fresh budget. The order is for a bot death: the new hash joins the entry and is handed to the caller's write of the run's row BEFORE every earlier hash — the mint's, an operator's, an adopted one — is dropped, so a generation that dies between the two steps leaves a row naming the secret the relaunch was minted and never the orphan's; a row write that throws propagates with both secrets verifying and nothing dropped. The write is issued synchronously inside `rotate` (the run's `saveFacts`, queued on the ledger's write-through, which flushes in order): what the store orders is that write's place in the queue, so no facts write may land between the callback and `rotate`'s return. A re-attach adopts and never rotates: a live process cannot be handed a new secret. `rotate` refuses by name the runs `issue` mints nothing for — unknown, ended, expired — and hands the row nothing then; `grantOf` counts the secrets that buy the run's calls (`bearers`): the mint's, one more per `issue` and `adopt`, exactly one once a rotation completes. The rotation's one caller is the run loop's relaunch (`prepareRelaunch`, [harness.md](harness.md) item 6): the row's facts — the new hash and the relaunch count — are written inside `record`, the harness is opened on the rotated bearer only after `rotate` returned, and a rotation refused by name refuses the relaunch, so no process ever starts on a secret the row does not name.
3. **The door, from the headers alone, in order.** A path that is not one of the three is `404`; a non-POST `405`; no bearer `401 missing_bearer` (the bearer rides `Authorization: Bearer <bearer>`, the OpenAI shapes' header, or `x-api-key: <bearer>`, the Anthropic SDK's — either is accepted on every route); a token that is not a run bearer `401 malformed_bearer`; a run this bot never minted `404 unknown_run`; the right run with a wrong secret `401 unknown_bearer`; a bearer past its expiry `403 expired`; one whose run ended `403 revoked`. The node adapter decides this before it reads a byte of the body and destroys a refused request. Past the door: a body over the cap (32 MB, the Messages API's own) is `413`; a body that is not a JSON object `400 invalid_body`. Every refusal is written in the route's shape so the client's SDK reads it as the provider's own error: `{ type: "error", error: { type: <code>, message } }` on the Anthropic route, `{ error: { type: <code>, message } }` on the two OpenAI ones. A refusal never echoes what the caller sent: an unknown path is refused without repeating it, and the wrong-shape message names the route hit from the proxy's own table.
4. **Pinning and the upstream.** `model` on the wire is the grant's bare model id whatever the body named; the output cap is the grant's `maxTokens` — as `max_tokens`, on the chat shape as `max_completion_tokens` when the body capped with that key (a stray `max_tokens` beside it is dropped, so no second cap survives), on the Responses shape as `max_output_tokens`, never below 16 (the API's own floor: a smaller pin would be refused upstream). The upstream is the run's `providers:` entry: the Anthropic shape goes to `<baseUrl ?? https://api.anthropic.com>/v1/messages` with the real key as `x-api-key` and the client's `anthropic-version` (the SDK's default when the client sent none) and `anthropic-beta`; the chat shape to `<baseUrl>/chat/completions` and the Responses shape to `<baseUrl>/responses`, each with `Authorization: Bearer <key>` when the entry names an `apiKeyEnv`, and no authorization header at all when it does not (a local endpoint). Only `accept`, `anthropic-version` and `anthropic-beta` are forwarded from the request; the run bearer's own headers never are. A provider the config does not name, or one without a `baseUrl` on an OpenAI shape, is a typed `permanent` 503; a key variable that is unset is a typed `key-absent` 503 — both decided before a turn is spent, logged under their internal proxy codes, and rendered through the one sentence without exposing configuration detail. The key is revealed into the upstream request and nowhere else. The `providers:` block is read at each call, so a config reload reaches the proxy as it reaches the mint.
5. **The turn guard is enforced here, as a typed run event.** The grant's `maxTurns` is the preset's runaway guard — `runawayTurnCap(maxMinutes)`, six turns a minute over the wall clock ([harness-pi.md](harness-pi.md) item 15; 540 for a coding run) — not a [budget](../vocabulary.md#budget) a working run reaches. A turn is counted before the call is forwarded (so concurrent calls cannot overrun) and the call past it is refused `403 turn_budget_exhausted`, forwarding nothing and opening no span; the refusal publishes one `run_note` of kind `turn_budget_exhausted` on the run's stream naming the guard and the counts (`model proxy refused a call past the run's 540-turn guard (540 turns used)`; the response body says `the run is past its 270-turn guard (270 turns used)`) — the same kind the harness notes when it ends the run on the guard ([harness-pi.md](harness-pi.md) item 6), so the run page and the friction analyzer read one vocabulary. A `403` rather than a `429`: a rate-limit status is one an SDK retries, and this is a refusal. An upstream failure spends the turn. A run that ended between the door and the turn — its bearer verified a moment ago, the run revoked since — is `403 revoked` with no note: the store answers `ended`, never a zero-turn budget.
6. **The meter: one `model.turn` per proxied call, the loop's attrs.** Every forwarded call opens one `model.turn` span under the span the grant carries — the request root at the mint, the harness's `run.agent` once `reparent` moved it there ([harness-pi.md](harness-pi.md) item 5), so a proxied turn lands where the native loop's did — with `model` (the `<provider>/<model>` ref, as `run_meta` carries it) and the tools the request offered at start — `tools`, their count; `toolNames`, sorted and comma-joined; `toolChoice`, the request's word as `auto` (the default when tools came), `none` (no tool came — whatever the choice said, an explicit `auto` included — or the request said so), `any` (the OpenAI dialects' `required`) or `tool` (a named tool — the chat shape's function object, the Responses shape's flat `{type: "function", name}`; the Responses tool table is flat too, its names read at the top like Anthropic's) — so a record says whether a write-up turn still carried the workspace tools ([harness-pi.md](harness-pi.md) item 15, [decision 0046](../../decisions/0046-a-budget-is-a-lease-carved-from-its-parent-and-one-module-proves-the-leases-fit.md)) and a call that never answers still says what it offered. **The harness's marks shape what goes upstream** (`shapeTools`, beside `pinRequest`; the record's amendment): the harness marks the run's bearer entry when it steers the write-up (`markLoopEnded`), and every request after it goes upstream with `tool_choice: none` — the model is shown its tools and may call none, so the checkpoint is a text turn, the cached tool and system prefix stand, and only the conversation's cached blocks are re-read for that turn; a [follow-up](../vocabulary.md#follow-up) turn on the session ([harness-pi.md](harness-pi.md) item 14) is marked for its duration with the tools it may call (`markTurn`, cleared by `clearTurn`): the request's tool list goes upstream trimmed to them with the choice left to the model (the description turn reads the [pull request](../vocabulary.md#pull-request) and the change and submits; the [verdict](../vocabulary.md#verdict) turn reads the head and submits), or, marked without a list, as it came (the re-review turn). Nothing is refused for the tools it carries; `toolChoice` on the span is the word that went upstream, `tools` and `toolNames` what the run offered. The marks live on the run's entry with its bearer, so a rotation or an adopt keeps them; and ends it with the attrs the native runner set: `stopReason` mapped as the deleted adapters mapped it (Anthropic `end_turn` and `stop_sequence` → `end_turn`, `tool_use`, `max_tokens`, anything else `other`; chat `stop` → `end_turn`, `tool_calls` → `tool_use`, `length` → `max_tokens`; the Responses shape has no finish reason, so its status is mapped — `completed` with a `function_call` item in the output → `tool_use`, `completed` otherwise → `end_turn`, `incomplete` at `max_output_tokens` → `max_tokens`, anything else `other`), `inputTokens`, `outputTokens`, `cacheReadTokens` and `cacheWriteTokens` when the provider reported them (`usageFromAnthropic`, `usageFromOpenAI`, `usageFromResponses` in `src/core/modelProxy/usage.ts` — the Responses usage shape is `input_tokens`, `output_tokens`, `input_tokens_details.cached_tokens` and `cache_write_tokens` as the cache counts, with `output_tokens_details.reasoning_tokens` riding inside the output count, never a fifth counter), and `ttftMs` (the first chunk's arrival) on a streamed answer. **The meter row** (record 0052): every `model.turn` also says who bills it and what it cost — `biller` (the block the call was forwarded through, the grant's provider name) and `vendor` (the card's, when the grant carries one) from the span's start, and at its end `usd`, `priceSource` and, on a BYOK turn, `feeUsd` (`priceTurn` in `src/core/modelPricing.ts`, over the operator's `costs.prices` and the card the grant carries). The precedence is `provider` > `operator` > `registry` > `none`: a provider-reported cost is stored as reported — the meter reads it beside the counters off the same usage object (`reportedCostOf`: OpenRouter's final chunk's `cost`, `is_byok` and `cost_details.upstream_inference_cost`; on BYOK `usd` is the fee plus the upstream cost with the fee beside as `feeUsd`; a BYOK chunk without the upstream charge keeps the fee as `feeUsd` beside the layer below that prices the tokens, never as `usd`) — else the operator's layer prices the counted tokens (`costs.prices` for the exact ref, [costs.md](costs.md) item 4b, or the block's own `models.<id>.price`), else the registry layer (the card's rate, its long-context tiers by pi's rule — the whole request re-rates at the highest tier whose `inputTokensAbove` the input side, input plus cache reads plus cache writes, exceeds — or the Anthropic family list, folded into this layer), else the turn is `none`: unpriced, never $0, and a stream broken before its final chunk is unmetered and `none`. A streamed answer preserves every provider chunk in order and the span ends only after the last one; while the provider is silent the proxy emits an SSE comment every `MODEL_STREAM_HEARTBEAT_MS` so the public container hop and pi's between-byte timer stay open through a reasoning pause — the comment is not a model event, is not metered and does not set TTFT; the `SseMeter` reads the counts as the provider bytes pass — Anthropic's `message_start` carries the input and cache counts, `message_delta` the stop reason and the final output count; a chat stream's `finish_reason` and its `usage` frame when the client asked for one (`stream_options.include_usage`); a Responses stream's closing `response.completed` / `response.incomplete` / `response.failed` event, which carries the whole response with its usage and status — a `data:` line may span chunks and CRLF framing is accepted. A buffered JSON answer is metered whole. An upstream status outside 2xx keeps its status and request-id header but its body is replaced by the typed cause plus renderer sentence, and ends the span `error` with `httpStatus`; an upstream that cannot be reached is a typed transient 502; a stream the upstream breaks ends the span `error` and errors the forwarded stream. The span's parent is the request root, so it streams onto the run's record through the same sink every setup span uses and is dropped, like any late span, once the run is sealed.
7. **What the proxy never says.** One log line per call — `[model-proxy] run=<id> turn=<n>/<max> <shape> → <status> in=<bytes> out=<bytes> <ms>ms` — and one per refusal naming the status, the code and the run id; never a body, a bearer, a secret or a key. The bearer store's verdicts carry a reason and a run id, never token material.
8. **The operator's probe bearer.** `POST /admin/model-proxy/bearer` with `{ "runId": "<id>" }` mints one more bearer on a live run's own entry — same expiry, same turn counter, same pinned model — and answers `201 { ok, runId, bearer, expiresAt, model, path, turns: { used, max } }`, the bearer written to that response once and never to a log (the line names the operator and the run). The door is the restart's and the crash's: an ingress bearer whose `http:<subject>` actor holds `deploy:write` — the operator who may stop the bot may mint a probe for one of its runs — `401` without a bearer, `403` without the grant naming it, `503` without a token map, `405` for a non-POST, all from the headers. A run this bot never minted is `404 unknown_run`; a run that ended or whose bearer expired `409 run_ended`; a body that is not `{ runId }` with a run id in the run-id alphabet `400`. Its calls are the run's: they spend its turns and land on its record as `model.turn` spans, and they stop at its end.
9. **The node adapter.** The door from the headers, then the call; a buffered answer is written whole; a streamed one has its headers flushed first and is written chunk by chunk under back-pressure, then ended; a caller that goes away mid-stream aborts the upstream call through the request's signal. Every response's content type is one of three literals chosen by kind — the provider's JSON or event stream as such, anything else as `text/plain` — with `X-Content-Type-Options: nosniff`, so nothing this route writes, a refusal or a provider's error page, is ever rendered by a browser as a document; the other forwarded headers ride as they came.
10. **Every run is the proxy's client.** The run's pi is handed the bearer as its provider key through the process environment ([harness-pi.md](harness-pi.md) item 4), and every model call it makes is one proxied turn here — pinned, guarded and metered as above; no code path in the bot calls a provider with the deployment's key for a run's turn. The bearer exists on every run — minted and revoked around each — and buys nothing unless presented.
11. **The card: one description of `<block>/<model>` per run, decided before the first call** ([record 0052](../../decisions/0052-a-run-resolves-one-model-card-and-every-control-is-decided-against-it-before-the-first-call.md); `src/core/modelCard.ts`, `src/core/modelRegistry.ts`, `src/core/installedModelRegistry.ts`). The `providers:` block declares what the card is resolved from (`src/core/provider.ts`): `wire` — `anthropic-messages`, `openai-chat` or `openai-responses` — with the legacy `type` (`anthropic`, `openai-compatible`) loading as its alias for one release, a block declaring both refused by name; `vendor` — a name, or `model` for an aggregator whose vendor is the model id's first segment; `catalog` — the pi registry file the block's cards are read from, defaulting to the block's own name when such a file exists and `none` for no catalog; `models.<id>` — the operator's override (`levels`, `capField`, `window`, `inputs`, `cache`, `price`, and `answers` — the answer shapes the card takes, `tool` and/or `text`, read by the intake gate's load-time check, [routing-and-config.md](routing-and-config.md) item 27); `passthrough` — extra body fields merged into every request, never a control. `vendorOf` is the one vendor parse beside `parseModelRef` (`catalog` never enters it: a block named unlike its catalog still serves the vendor the declaration or the id names), and the validator refuses a malformed declaration by name (`validateProviders`: a `catalog` the installed library does not ship, a `vendor: model` block whose ids carry no prefix, a `models.<id>.levels` word outside our tiers or `null`). `resolveModelCard` layers the operator's override over the registry card over the wire's structural defaults — the cap field each wire spells the cap with (`max_tokens`, `max_completion_tokens`, `max_output_tokens`), pi's 128000 window when no layer names one, the vendor-keyed cache table — carrying per field the layer that named it; the registry is the installed `@earendil-works/pi-ai`'s `providers/data/*.json`, read once per process, a card looked up under the block's wire first and then under any wire, our `openai-chat` spelled pi's `openai-completions`. `decideControls` then answers **native**, **degraded** or **refused** for each control the request asks about: the effort tier (a tier the card names is native under the card's own wire word, whatever its spelling; a tier the card marks `null` is refused; `xhigh`/`max` a card does not name degrade to the highest named tier below, and only that fallback degrades; a card naming no levels sends the asked tier unvouched), the output cap and the window (always decided — every run sends one and compacts somewhere), images and documents (a document degrades to a text stub until a harness carries files), and the cache rule. The dispatcher resolves the card in `resolveTarget` where it checks the block, before any ack card or span: a refused control ends the run with the reply naming the model and what it takes (`Model "<ref>" refuses effort "max": <model> does not take effort "max"`, the refusal code `model_card_refused`), the same shape as `Unknown provider`, and never a call that fails mid-run; the card rides the record as `run_meta.card` and each degraded control publishes one `run_note` of kind `control_degraded` (`control`, `asked`, `applied`, `vouched`, `why`) before the first turn. 12a. **The provider level and the held turn (record 0064).** The proxy is the one place a provider's health is observed, so it reports the level to the plane through the optional `plane` seam (`ModelProxyDeps.plane`, wired in the bot process to the write-through's `planeLevel`/`planePark` — `POST /plane/level` with `{name: "provider", provider, side: up|down, cause?}` and `POST /plane/park`; the CLI's `ask` loopback has no ledger and wires none): a provider-down `ProviderFailure` cause — `transient`, `rate-limited` or `credit-or-quota-exhausted`, including a 402 carrying `limit_source` — gets ONE immediate retry in all, so a proxied call makes at most two upstream calls; a client abort is neither retried nor reported (the caller going away says nothing about the provider); a failure past the immediate retry is sanitized, reports the provider `down` with its typed cause and **parks the run** on `provider_up(provider)` (the park keyed `<provider>#<runId>`, so a second failing turn of the same run is the same wait), and one rendered sentence is relayed in the route's shape — never the provider payload or URL; a relayed success reports `up` — the handler dedupes to changes, so a healthy provider is not re-reported every turn, and the first success after a `down`, from ANY run, is what flips the condition. On the plane, the `up` writes one typed reissue message per parked live run into its durable inbox (sender `plane`) and offers a `steer` carrying the same message and durable sequence in that transaction, then deletes the park row. The state Worker pushes the committed offer through `/plane/effects`; the active generation atomically verifies the open effect and its durable ownership while renewing the lease before it puts the row into the live harness inbox, acknowledging `done` after delivery, `skipped` when that sequence already arrived, and `deferred` while draining or on a non-owner. Deferred offers ride the owner's heartbeat, sequence dedupe makes push/heartbeat/reclaim one release, and the durable row remains the restart fallback; a run whose provider never answers ends on its lease as today. **The harness's half** (`src/core/harness/pi/harness.ts`; [harness-pi.md](harness-pi.md) item 6): every provider-down typed cause from `classifyProviderFailure` (transient transport/5xx, rate limit, or credit/quota exhaustion) holds the failed turn; intentional tool-cut and wind-down aborts are classified first and keep their existing endings, while every other match leaves pi settled on the failed call while the loop keeps ticking its budgets and draining the inbox, and retries on growing backoff until the loop's retry window is spent. On a ledger-tracked run (`HarnessRun.providerPark`) the proxy's parked condition and the harness hold are the same recovery: the plane's reissue steer may release it before the local backoff; a run without the capability still has the local hold. The plane's reissue steer — the inbox row with sender `plane`, its text `reissueSteerSentence` read back whole by `isReissueSteerText` (`src/core/plane/decide.ts`) — is recognized as it drains whether or not the hold exists yet (the plane's `up` can beat the harness's read of pi's errored `message_end`) and **buffered, never steered into pi as a follow-up**: it releases the hold and **re-issues exactly that held turn once**, as a prompt under its own id like the retry ladder's (pi reads a steer only at a turn boundary that is not coming), sent only once pi has settled on the held turn — one prompt per release however many reissue rows the buffer carried, the rows recorded as `input` events and their seqs consumed on pi's echo like any follow-up's, and a refused release prompt keeps the hold for the next settle (a `harness_error` note names the refusal) rather than clearing it with no steer ever coming again; a follow-up drained beside them rides the usual steer and is read at the re-issued turn's boundary. A run without the capability keeps the ladder; a wind-down already begun owns the ending as before. Every post-loop `followUp()` turn — PR description, verdict, re-review and ordinary follow-up alike — applies the same hold, lease-bounded retry and provider-up release instead of throwing a park-capable failure when that turn settles.

12b. **One typed provider-failure seam for every model call.** `ProviderFailure.cause` is the closed set `transient | rate-limited | credit-or-quota-exhausted | key-absent | key-invalid | model-unknown | request-rejected | permanent`. `classifyProviderFailure` alone reads a wire status, structured body or adapter transport error; mandatory provider facts win before untrusted body signals (402 → `credit-or-quota-exhausted`, 429 → `rate-limited`, 5xx/network → `transient`), and a body's `cause` field is ignored unless the model proxy's `provider_failure` envelope carries its response-specific HMAC marker and the pi bridge verifies that marker out of band; merely passing through the bearer-authenticated proxy does not authenticate provider-controlled content from a successful stream. The proxy signs the typed cause, safe sentence and any schema-rejection evidence it classified (one offered tool plus one keyword the provider named); a provider stream cannot forge or alter that marker, so an unmarked or tampered `provider_failure` shape is classified from its status and ordinary untrusted signals rather than its claimed cause. The proxy, pi harness, intake gate and memory reflection consume the cause rather than matching provider prose. The conformance matrix declares the disposition beside every cause: `transient`, `rate-limited` and `credit-or-quota-exhausted` **park** only where a live run lease can recover them; `key-absent`, `key-invalid`, `model-unknown`, `request-rejected` and `permanent` **end** the request. A one-shot CLI `ask` has no lease, so a door-level provider refusal prints the safe refusal and exits 1. `renderProviderFailure` maps each cause to one calm sentence for each disposition surface: only `parked` promises that kept work will continue under the live lease; `ended` names the cause and says the request did not start on no-lease intake and operator doors. A missing configured key remains a typed `key-absent` failure whose thrown/operator diagnostic and proxy log name the provider and variable (`Provider "<name>": <VARIABLE> is not set`), while requester surfaces receive only the calm sentence; neither form includes provider payload or URL. A structured-answer wrapper is transparent to this seam: `providerFailureOf` unwraps a nested typed cause before any fallback classification, so a malformed answer followed by a 402 remains credit/quota exhaustion. The proxy replaces every failed provider body with that cause, sentence and opaque authentication marker before the answer crosses into a harness, retaining a provider URL only as `operatorUrl` for a later admin surface. The intake gate stores the typed cause and posts the no-lease sentence once instead of silently dropping the reply. The operator stores and renders the same no-lease typed provider refusal instead of converting a failed call to `non_decision` and falling through to `general`; the 06:36Z OpenAI schema 400 is the `request-rejected` fixture. Reflection logs the rendered cause and writes nothing. No requester renderer receives the raw payload, so no user surface can print JSON, a provider URL or a recovery instruction.

12. **`providers check` and the registry drift gate** ([record 0052](../../decisions/0052-a-run-resolves-one-model-card-and-every-control-is-decided-against-it-before-the-first-call.md); `src/core/commands/providers.ts`, `scripts/registry-drift.ts`). The card's live half: `providers.check`, a typed command on every surface (action `providers:read` — a browser session's read baseline, a grant everywhere else; gated on no capability), reads the provider's own `GET <baseUrl>/models/<vendor>/<model>/endpoints` for each AGGREGATOR model the configuration names — a block declaring `vendor: model`, the refs from `configuredModelRefs` (the defaults' per-agent models and every block's `models.<id>` override key) — through the deps' injectable fetch, never a global one. `compareCardToEndpoints` is the pure comparison over the card the dispatcher would resolve (item 11) and the endpoint's facts (`endpointsFromJson`: `architecture.input_modalities`, each endpoint's `context_length` and `supported_parameters`): it reports where the two disagree, each drift with the `models.<id>` override that would pin the endpoint's fact — a window differing from the card's (a wire default is called unvouched) pins `window: <n>`; a modality list contradicting or unvouched by the card pins `inputs: {image: …}`; a parameter list without the card's cap field pins the wires' spelling it does list (`capField: max_tokens`); a `reasoning` parameter against a card naming no levels is reported as "levels not stated" — the endpoints API lists parameter names, never effort values — with the pin naming the wire's own words for the tiers pi's rule would otherwise refuse, confirmed against the vendor's documentation before pinning; a card naming levels against a parameter list without `reasoning` pins the refusal. A failing endpoints read is that model's own error line, never the whole check's failure; a configuration naming no aggregator model answers that plainly. The drift gate is the same module's offline half: `scripts/registry-drift.ts` (`npm run check:registry-drift`, under `check:consistency`) runs `registryDrift` over the example config's refs and the installed pi registry, naming every model whose block reads a catalog the registry ships but whose card the registry no longer carries — a pi bump that drops a card fails `verify` by name instead of surfacing on a run; a block without a catalog has no registry to disagree with and is never drift.

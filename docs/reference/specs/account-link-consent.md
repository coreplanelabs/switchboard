# Account-link consent

The configured browser flow implements [the accepted account-operation contract](../../decisions/0104-account-operations-require-fresh-proof-and-preserve-native-ownership.md) with the [proof adapters and atomic directory](person-directory.md). That decision supersedes [the earlier proposed linking design](../../decisions/0081-account-linking-proves-both-identities-and-revocation-fences-their-use.md). The browser host registers the identity handler and the replacement app exposes it under Settings → Identities. Configuration, current human Access proof, the directory and the named Slack secret govern availability. The separate local fixture uses fictional identities and enables no live account operation.

## Behavior

1. **Missing proof or configuration cannot enable linking.** The low-level linking adapter remains disabled by default and returns 404 before reading credentials or touching a provider or directory. Its explicit local-fixture mode requires an exact HTTPS loopback origin. The production browser host constructs the identity runtime and routes authenticated identity requests to it. Binding operations require the configured HTTPS origin, current human Access proof, directory and named Slack secret; missing prerequisites remain unavailable. Signed-in account reads and protected notice acknowledgment can remain available when Slack setup is removed, as specified below. The separate Vite fixture uses made-up identities only, not real credentials or requests to Slack.
2. **The browser is bound, not a person selector.** A Secure, HttpOnly, SameSite=Lax, host-only cookie carries the opaque operation and independent browser secret. Lax permits the top-level OAuth return. The URL, form and JSON view never carry that secret, a person target or a credential. Same-origin POSTs also require a form token bound to the cookie and exact action; closed forms reject extra or duplicate fields. The callback instead uses the stored one-time state and authenticated browser.
3. **Consent is local and explicit.** After callback, a clean URL displays the verified Access issuer/subject/audience and signed Slack user/workspace identifiers, not email/name matches or a requested team hint. Only an explicit checkbox and protected final POST can call the atomic transaction. The server re-verifies the current signed Access session at callback, display, consent, cancellation, interruption and receipt read. The session may predate the challenge: freshness means a new operation-bound target proof and local consent, not a new identity-provider login or a token-issuance timestamp. The store enforces the original tuple/audience/browser, state/revision, unchanged or shortened deadline and current directory revisions. Refresh never extends the intent.
4. **Retries are not new links.** Callback replays never exchange a second code. An uncertain exchange stays claimed across reconstruction; an explicit protected interrupt makes it terminal without retrying credentials. Cancellation and expiry cannot link. Duplicate final POSTs and response-loss retries return the existing terminal outcome within the original result window, not another person, binding receipt or operation audit. A same-origin, cookie-bound restart starts a fresh verification after a terminal operation, including a committed link. It rotates to a new browser seed; the old cookie can still read its result during the original window. An expired result does not restore old proof or mutate the saved binding. Active operations cannot restart.
5. **No credential-bearing rendering.** The callback always returns a bodyless 303 to the clean consent address, including failures. Every adapter response carries no-store and a restrictive CSP. JSON, callbacks, redirects and refusals use no-referrer. Only the clean hosted HTML form with status 200 uses same-origin so local POSTs retain their actual Origin; cross-origin provider navigation still sends no referrer. Only allowlisted verified metadata enters views or the directory; provider errors and raw callback parameters are never reflected. There is no logger, run-event sink, credential cache or audit hook on the browser adapter. Edge/proxy query redaction is a separate deployment obligation, not a claim established by this handler or its isolated tests.
6. **Production forms and fixture isolation.** Settings → Identities uses the shared consent module, a typed identity seed and protected native forms served by the registered identity runtime. Its explicit props and form CSP do not grant account authority. The separate fixture entry supplies start, consent, exchanging, committed and refusal states in either theme, using fictional identities without granting cross-surface access.

## Configured host handler

`createIdentityRuntime` composes the existing two-account ceremony. It requires the current human Access account and a host authorization callback for writes. Service credentials, view-as and cross-site posts cannot bind accounts. Missing configuration, directory, Access application or named secret remains unavailable. The browser host mounts the handler for identity requests. The handler carries protected forms and pins the Slack provider in its form CSP; it persists no OAuth credentials.

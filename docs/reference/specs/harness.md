# The harness contract: six clauses the bot holds any model-loop process to, pi as its one implementation

[Record 0038](../../decisions/0038-the-harness-is-a-contract-pi-is-its-one-implementation.md) decided that a **harness** — a process that runs the model loop for one run, in the container the run's machine class provides — is held to six things and nothing else: it starts with the run's bearer and never a provider key (credential); every tool call it runs is decided by the bot (gate); Switchboard's tools are served to it and run by the bot (relay); every event it emits has a home on the run's record (record); it is driven as a seed, steers and prompts and is ended (conversation); and it leaves facts on the run's row so the bot, in this generation or the next, finds its process or rebuilds it from the record (survival). The seam is one interface, `Harness` (`src/core/harness/contract.ts`), and the run loop is handed an object of it and calls it — never a word it compares. pi is the one implementation ([harness-pi.md](harness-pi.md) holds pi's rows: the mechanics of each clause as pi meets them); a second harness enters as a conformance row before it enters an image.

## Behavior

1. **Credential.** A harness starts with the run's bearer and the proxy's URL as its only way to a model, revealed once into its process's environment and never a provider key, a command line or a file; every model call it makes goes through the model proxy, which pins the model and the caps and meters the turn on the run's page ([model-proxy.md](model-proxy.md)). The proxy serves two wire dialects, the Anthropic messages shape and the OpenAI-compatible chat-completions shape (`PROXY_PATHS`), and refuses any other path by name before a byte is forwarded; a harness whose model library speaks a third dialect is a change to record 0038, never a quiet route. pi's row: [harness-pi.md](harness-pi.md) item 4 (the environment as the channel for the bearer, `models.json` naming the proxy as the one provider).
2. **Gate.** The gate decides intent; the walls enforce effects. Every tool call a harness runs is decided by the bot, before it runs when it runs in the container and at execution when it runs in the bot: a relayed tool is allowed by name at the ask because the bot's own gates decide it when it runs; the harness's own shell and file tools are judged by `judgeToolCall` with the run's identity and the thread's rules, each decision `accept` or `decline` and never cached outside the bot, a refusal a `tool_refused` note the model reads the reason of. A call the record shows ran with no decision beside it fails the run closed, and so does a call whose decision was a reply the bot did not send (on a harness whose approval lives in its own server the model's shell can forge one, so the gate there is enforcement by detection and the forgery is the harness's honest cannot on its conformance row); a call the harness itself refused before running is a `harness_error` note, not a bypass. What the gate decides is the call; what bounds the effects of an approved call is not the gate: an approved shell command runs as the container user with everything the container holds, so the walls are the container, the proxy holding the credentials, the token's scope and branch protection. The read identity's walls exist (a read-only worktree and no write token; the gate's read rules restate them); the write identity's one-push-target rule and the harness process's own secrets are held by rules alone, the two gap rows below. pi's row: [harness-pi.md](harness-pi.md) item 7 (the extension's hook, the coverage check from the stream, `GateBypassed`).
3. **Relay.** Switchboard's tools — the preset's toolset less the workspace tools the harness has of its own — are served to the harness by the bot, registered under their own names, and run in the bot under the run's context and the bot's own gates; a call may outlive one request and is joined, never run twice, by its call id; a call in flight when the previous bot generation died is settled from the record. pi's row: [harness-pi.md](harness-pi.md) item 7 (the three harness routes, `RelayedCalls`).
4. **Record.** Every event kind a harness emits has a disposition onto the run stream — `mapped`, `structure`, `folded`, `impossible` or `note` (`Disposition`; a harness's table is its `dispositions` property) — in the vocabulary the record already speaks (`tool_call`, `tool_result`, `assistant`, `run_note`), and its finished turns are mirrored into the ledger's step records so a resume reads its rows as it reads any run's; a kind the table does not name is a `harness_error` note naming it, so a harness bump shows in the first run's record. pi's row: [harness-pi.md](harness-pi.md) items 5 and 8 (`PI_EVENT_DISPOSITION`, the bridge, the mirror).
5. **Conversation.** A harness is driven as a seed (the thread's earlier turns, then the request as the prompt), steers (a follow-up, the wrap-up warning, the forced write-up, a soft stop), prompts (the post-turns on the same session: the description turn, the verdict turn, the head-move re-review), and a hard stop that ends it; the budgets and the wind-downs are the loop's words on every harness; Switchboard's effort tier reaches it in the harness's own word (`Harness.effort`). pi's row: [harness-pi.md](harness-pi.md) items 6, 9, 14 and 15.
6. **Survival.** A harness leaves facts on the run's row (`HarnessFacts`, `state.harness`) — the process, where it was filed, the container it runs in, the bearer's hash, and the count of its relaunches — so the bot that comes back, in this generation or the next, asks the harness where that process is (`find`) before anything is probed or ended, re-attaches to it where it lives, and rebuilds it from the record where it does not: an `authored-session` harness (`Harness.history`; pi) accepts the ledger's transcript as its own history, so a rebuild is a rewrite of it; an `own-store` harness has only its private store, so a store that is gone closes the run `interrupted` and its request runs again; either rebuild reads the record, never the dead process. **The ceiling.** A container replaced under a living bot — the harness's typed verdict, `HarnessContainerReplacedError`, carrying the record as the harness holds it (`HarnessRecord`: the transcript it mirrored onto the ledger, this generation's copy of the rows a bot death reads back; every call of the last turn settled; the counters; the deadline) — relaunches the process from that record in the container the run holds (`prepareRelaunch`, `src/core/dispatch/relaunch.ts`, called by the run loop on the typed verdict; harness-neutral, the rebuild itself the harness's own `open` with the record as its resume and `HarnessResume.relaunch` set). In order: the bound read off the row's `relaunches` (`RELAUNCH_CEILING`, two — the third finding closes the run `interrupted` naming the bound, no fourth start; the count is written by the loop and carried unchanged by the harness, so it survives a bot generation); the workspace re-attached where the row says it is or refused by name (`reattachWorkspace`, [run-history.md](run-history.md) item 54, the executor the run holds from then on); the bearer rotated on the run's own meter with the row's facts written exactly once inside the rotation — the new hash, the count one higher ([model-proxy.md](model-proxy.md) item 2); then the harness's rebuild — the run's relay registration taken over with its relayed calls kept and awaited, nothing probed or ended at the row's pid, the process started on the record, one `resumed` note. A refusal by name — the ceiling, the worktree, a bearer that cannot be rotated, a row without facts, an `own-store` harness whose store went with the container — is an interruption like the floor's (`RelaunchRefusedError`): the loop forgets the run on the relay, says why in a second `sandbox_restarted` note after the harness's verdict (the floor's own kind; never `resumed`, since the run is not — the note starts at the why and does not restate the verdict), and closes the run `interrupted` for the dispatcher's restart from the request, the refusal `workspace_lost` for the worktree and `container_replaced` otherwise; a row write that throws inside the rotation fails the run with nothing relaunched and both secrets verifying. **The record across two deaths.** A process rebuilt from the record — after a bot death or a relaunch — starts on a session whose last turn settles every call that was in flight; that settlement turn is written onto the ledger too, as the results pending for the rebuilt process's first step (pi: `PiMirror.prime`; the write-through's own convention, the results since the last assistant turn are the next step's one user turn), so the ledger's next rows are `[user(settlements + the continue's echo), assistant]` from the seed index, the ledger's rows equal the session's and the harness's record of them, and the roll order every image-changing release has — the container rolls (a relaunch, rebuild one), the bot rolls minutes later (a resume from the ledger, rebuild two) — hands the model a `tool_result` for every `tool_use`. The conformance row `survival-rebuild-records-settlement` holds every harness to it. **The first gate** (the plan's execution note, the mid-run re-attach) passed in the fakes: the seam composes — a recorded binding re-attaches mid-run with no gate context and a process starts again in a replacement container from the ledger's rows. What the fakes cannot prove is the resident: a `reuse: true` re-attach onto a container the platform just rolled is proven only by the live row ([harness-pi.md](harness-pi.md) `16, live`), owed before stage A closes. The floor beneath the ceiling is [harness-pi.md](harness-pi.md) item 16 (the verdict and the settle-and-close), pi's relaunch [harness-pi.md](harness-pi.md) item 8; OpenCode's ceiling is its own: `driveOpenCode`'s container-gone read (`saysContainerReplaced` on the feed) throws the same typed verdict carrying the record built from its mirrored rows, nothing killed or removed in the container that answers now, and its rebuild is an import of that record — and a resume naming the container this run holds ends the row's still-answering server and its tailer before a fresh start on the record, with the full re-attach onto that server (its password the row's `bearerHash`, the tailer kept, the feed from the `logOffset`) the one named gap that remains.
7. **The seam: an object handed in, never a word compared.** The process wires its harnesses into `HarnessProcessDeps.harnesses`, the roster of item 8 (`src/index.ts`, `src/cli.ts`: `PiHarness` with the deployment's `pi.compaction` thresholds and `OpenCodeHarness` with its `opencode.compaction` thresholds, each behind its own object as its own settings, so every harness is handed the same `HarnessDeps`), and the run loop picks one and calls it through the seam's door, `openThroughSeam(harness, deps, run)`, for every run, the answer handed back with the process alive on its session (`HarnessSession`: `answer`, `followUp`, `end`) for the post-turns; on a `finish` plan, `find(facts, container)` and then `end(facts, container)` for the leftover process. The loop names no harness and compares no word — the source scan of [harness-pi.md](harness-pi.md) item 1 forbids `runPiHarnessOpen` in the run stage as it forbids the deleted loop. The object declares its `name` (the roster key and the discriminator of the facts it writes), its `history` word, its `dispositions` table, its `effort` map and the `builtinTools` a run of each identity holds. **The row's facts are read by the harness that wrote them.** `HarnessFacts` is a union keyed on `harness`: pi's `{ harness: "pi", pid, logOffset, sessionFile?, root?, bearerHash?, container?, relaunches }` and the second harness's `{ harness: "opencode", pid, port, logOffset, sessionID, root, bearerHash?, container?, relaunches }` — the feed's byte boundary as pi's log has one, the bearer's hash and the container optional as on pi's row (a bot-host container has no word, and a bearer without a secret no hash), a shape nothing in the tree writes yet, carried so the seam is read against two shapes. `harnessFactsOf` reads a row by the shape its `harness` names, a row without the key as pi's (the one harness that ever wrote one), each shape's known fields by type with a field of the wrong type dropped, `relaunches` as 0 when absent or malformed, and keeps every key it does not know, so a field a later build writes survives this build's rewrite of the row; a row missing a shape's required fields, or naming a harness this build does not know, is no facts. `find` answers one of four words: `alive-here` (the process answers in the container the run was handed), `another-container` (the row names another container: a pid here is a stranger's, nothing is probed or ended), `dead` (this container, the pid does not answer: the harness rebuilds from the record), `another-harness` (the facts were written by a harness other than the one asked, answered with no container command). A `finish` plan on `another-container` or `another-harness` ends nothing and says so in a `resumed` note (the another-container note names both words, the row's and the container this run was handed; the another-harness note names the row's word and the judge that disowned it). The loop picks a resumed row's harness by the row's own word (item 8), so it never hands the door a foreign row; the seam's door (`openThroughSeam`, what the run loop and every conformance driver open a run through) keeps the refusal as its defence for any other caller: another harness's facts are refused before the harness is asked anything (`factsBelongTo`, the seam's one comparison of a row's harness with the object's name) — a `harness_error` note on the record, then `HarnessMismatchError` naming both harnesses; pi's `open` keeps the same check as a defence for a caller that is not the seam — and the loop reads such an interruption exactly as it reads a replaced container: every interruption is a `HarnessInterruptedError` carrying the card's reason and the request's refusal token, so the loop and the dispatcher name no harness's own error class; the run closes `interrupted`, its card closes `🔁 … the row's harness facts are <found>'s, not <expected>'s; restarting from the request`, never `❌`, the workspace is released, and the dispatcher runs the request again as a new run with the refusal `harness_mismatch`. The relaunch count is the loop's: a harness writes 0 on a fresh run and carries the row's count unchanged through every save and every restart of its process within the run.
8. **The roster and the configuration word: one roster, one word, and the row's word wins.** The process wires every harness it can drive a run on into one roster (`HarnessRoster`, `src/core/harness/roster.ts`, built in `src/index.ts` and `src/cli.ts` and nowhere else — the source scan of [harness-pi.md](harness-pi.md) item 1 forbids a harness word or class in the agent registry and a harness class in the run stage), keyed by the name each object declares (`Harness.name`), and that name IS the configuration word: `harness: { <preset>: pi | opencode }` in `config.yaml` puts a preset's fresh runs on the object of that name. The roster's words are one list (`HARNESS_NAMES`, held by type to the facts' discriminator, so a facts shape without a word or a word without a shape fails to build), read in three places and spelt in none of them. The validator (`validateHarness`): a mapping of registered presets to those words loads; a preset the registry does not know fails by name; a value that is not a roster word — `codex`, `native` (the loop that no longer exists), a case slip, a non-string — fails naming the words that exist (`harness.coding: codex is not a harness; the harnesses are pi and opencode`); a non-mapping fails as `harness must be a mapping of preset to a harness name (pi or opencode)`. The loop's pick for a fresh run (`harnessForPreset`): the preset's word, else `DEFAULT_HARNESS`, pi — nothing defaults to OpenCode, and production configuration names no preset. A resumed row's judge: a row that carries facts is judged (`find`), ended (`end`) and resumed (`open` with the facts) by the harness its facts name, picked off the roster, whatever the preset's word says now — a preset flipped between generations never mismatches a run in flight; a run keeps the harness it started on. A row naming a harness this build does not know (a rollback under a newer build's row, a harness removed) is no facts (item 7), so the preset's harness rebuilds the run from the record — the survival clause working — and the record says so: item 7's rule for a process that is not this one's to judge is "named, not ended", so before the rebuild (or before a finish runs its post-steps) one `resumed` note reads `the row names the <word> harness, which this build does not know; its process (pid N in container C) was neither judged nor ended here; the run was rebuilt on <harness>`, the pid and container `unknown` when the row did not record them. `run_meta.harness` (item 10) is the word's pick for the fresh run it announces. Each harness's deployment settings ride behind its own object from its own block — `pi.compaction` into `PiHarness`, `opencode.compaction` (`buffer` and `keepTokens`, OpenCode's own words, positive integers in tokens; `validateOpenCode` refuses any other shape or key by name, pi's words included) into `OpenCodeHarness` — so the loop carries nothing harness-specific. `config/config.example.yaml` documents the `harness` block with both words and the `opencode` block, commented out; [put a preset on OpenCode](../../how-to/put-a-preset-on-opencode.md) is the how-to. **The word's precondition is proven at the loop:** before any preset's word may be `opencode`, the survival clause's ceiling (item 6) holds end to end on OpenCode through the run loop — `harness: { coding: opencode }` opens a coding run on the roster's OpenCode over the fake `serve` (`scriptOpenCodeServe`: the conformance driver's serve bound to a bare container, learning the run at its first request from the launch's environment, the relay registration and the written configuration), the container is replaced with a call in flight, the loop relaunches from the record in the replacement with the bearer rotated, the row carries `relaunches: 1` with the new container and hash, the record holds the `sandbox_restarted` and `resumed` notes and the call's replaced settlement, and the run completes on the continuation the replacement's store was imported for.
9. **The container seam is harness-neutral in fact, not only in name.** `HarnessContainer` (`src/core/harness/container.ts`) is what any harness's process needs of the container the run's machine class provides — `makeRoot`, `cwd`, `writeFile`, `start`, `writeLine`, `readLog`, `alive`, `identity`, `request`, `kill`, `tail`, `remove` — with three implementations: `ExecHarnessContainer` over the run's executor, one command per operation as the thread's user ([harness-pi.md](harness-pi.md) item 4); `BotHostHarnessContainer` on the bot host for a preset without a workspace (item 12); and the in-memory fake the tests drive. `makeRoot(wanted)` answers the root the container makes from the one the harness proposes (its predictable `/tmp/switchboard-<harness>-<runId>`): the exec container answers the proposal itself, the bot host a `mkdtemp` beside it. `start` takes the program (a plain word on the container's PATH; a shell fragment is refused by name), its arguments, the stdout filter (lines carrying a mark never reach the log; absent, every line lands) and the run directory's layout (`HarnessPaths`: the root and the directories the start makes at 700, the FIFO, the log, the error log, the pid file, the command directory) as inputs, and answers the pid — the wrapper's, the leader of the group the process runs in, which `kill` ends first — and, when the start named a port, the port: a number to hand the process, or `free` to pick one in the container before the command runs (node on the exec classes, the host's own `net` on the bot host), put in `PORT_ARG`'s place among the arguments and in the environment under `SWITCHBOARD_HARNESS_PORT`, said on the first line of the exec's answer with the pid on the last, for the row; the placeholder among the arguments with no port named is a harness bug, refused by name before anything is made or spawned, never handed to the program as the word `{port}`. pi's start is byte-identical to the script the seam wrote before these were inputs: `pi`, pi's `message_update` filter, pi's layout, no port. `request(paths, { method, port, path, headers?, secretHeaders?, body? })` reaches a server the process listens on over loopback inside the container: `curl -sS -i` over the executor on the exec classes — the method, the port and the path checked as the shell and HTTP would read them, curl's own `--max-time` under the executor's timeout so a slow server is curl's named failure and never the executor's killed-command word, the body from stdin through `printf` or, past the inline size, from a file under the run's command directory that the request's own command removes, no `Expect: 100-continue`, never `-f`, so a 4xx or 5xx is an answer parsed to its status, its lowercased headers and its body with an interim `1xx` skipped — and `fetch` on the bot host, bounded by the same figure as the exec class's commands (`OP_TIMEOUT_MS`). A header whose value is a secret (a server's per-run password as Basic auth) goes in `secretHeaders`: on the exec classes its name is in the command text and its value rides the exec's env channel (`-H "name: $SWITCHBOARD_REQUEST_H<n>"`), the road the bearer takes on a start, so the executors' command logs never carry it; on the bot host it is a header like any other, nothing being logged on that road. The exec's answer is read as an HTTP answer first: the server's body is anyone's text, so the executors' runtime word in it is that answer, never a container gone; only an answer that is no HTTP answer goes through the word and the exit-prefix checks. A server nothing answers on, or one that does not answer in time, is a named failure, and a container gone under the request is the typed error, as from every other operation. `identity()` rethrows the executor's typed word that the container is gone (`ExecSandboxRestartedError`, or the seam's own `HarnessContainerRuntimeReplacedError` for the word handed back as a command's text; `isContainerGone`) instead of answering no name; an empty, malformed or failed answer is still no name. The run loop's `finish` plan reads that word from `find` as nothing left to end — a `resumed` note says the container is gone under the finish — and runs the post-steps with the answer, never failing the run over a leftover. A failed command is a `HarnessContainerError` naming the operation.
10. **`run_meta` names the harness.** The run's meta event carries `harness: <Harness.name>` when the process drives runs with one, so a record can be told from another harness's on the run page and in `runs get`; a process that starts no run publishes no such field, and a record written before the seam has none. Additive: every consumer that knows the other fields keeps working.
11. **The conformance table: one table, every harness, no row without the record.** The six clauses and the parity rows are one table of scenarios (`SCENARIOS`, `src/core/harness/testing/scenarios.ts`), each a function of a `HarnessDriver` — start a run from a scripted model, read the run events, the ledger steps, the row's facts and what the container was asked, end — so pi's driver (`src/core/harness/pi/testing/driver.ts`: the real bridge, mirror, relay and gate over the fake container and the scripted double, opened through the seam's door, `openThroughSeam`, as the run loop opens every run) and any second harness's driver walk the same rows and no harness gets a table of its own; the drivers the tree has are one list (`harnessDrivers`) the suite and the matrix script both read. The rows: credential (the bearer in the process's environment and no provider key — the driver plants a sentinel under the bot's provider-key variables for the run, and no value of the process's environment may carry it — and neither events nor steps carry the bearer), gate (an allowed command and a refused push with its `tool_refused` note; a command run without asking fails the run closed), relay (a relayed tool served under its name, run in the bot, its side effect in the run's context), record (the record's vocabulary and one ledger step per assistant turn; an unknown event kind a `harness_error` note), conversation (the seed then the prompt; a follow-up steered as the next user turn; a hard stop), survival (the facts on the row and their round trip; another container's row neither probed nor ended; another harness's row refused), and parity (the tools offered equal the harness's own for the identity plus the relayed ones; identity `none` and `read` hide and refuse what they must). A row's check reads the record: the lint (`runRow`) records every property a check reads and refuses a row that read neither `events` nor `steps`, so a row that passes without looking at the record cannot enter the table. A row a harness cannot pass is a failure in the matrix, never a skip; a limit a harness declares (`HarnessDriver.cannot`, row id to reason) is asserted, not skipped: the suite's test for that row requires the run to fail as declared, so a declaration the harness has outgrown goes red, and the matrix prints it as its own cell with the reason beneath the table. The matrix (`renderHarnessConformanceMatrix`, printed by `npx tsx scripts/harness-conformance-matrix.ts`) is harness × row, a harness without a driver shown absent; it is what a PR that touches a harness carries.

dark: nothing starts it yet). **The layout** (`openCodeRunPaths`, `src/core/harness/opencode/process.ts`) is `/tmp/switchboard-oc-<runId>/`, directly under the sticky `/tmp` for pi's reason: `xdg/{data,config,cache,state}` (the four XDG roots, every global path OpenCode has), `opencode.json`, `plugins/switchboard/index.js`, the server's `serve.in`, `serve.log`, `serve.err` and `pid`, the tailer's `tailer.js`, `tailer.in`, `tailer.err` and `tailer.pid`, `feed.jsonl` and `cmd/`; the tailer is a second process through the same seam (`paths.tailer`) whose log is the feed, so its stdout lands where the harness reads. **The environment** (`openCodeLaunchEnv`) is exactly: the bearer under `SWITCHBOARD_RUN_BEARER` (the name the configuration interpolates), the bot's URL under `SWITCHBOARD_HARNESS_URL`, `SWITCHBOARD_RUN_ID`, the four `XDG_*_HOME` under the run (`HOME` is left the container user's, so the model's shell sees the same `~/.gitconfig` and the rest that pi's shell sees), `OPENCODE_CONFIG` the run's file with the project's own configuration disabled under both names the server reads (`OPENCODE_CONFIG_PROJECT_DISABLE=1`, `OPENCODE_DISABLE_PROJECT_CONFIG=1`; the first wins), `OPENCODE_DISABLE_MODELS_FETCH=1`, `OPENCODE_DISABLE_AUTOUPDATE=1`, `OPENCODE_DB=:memory:` (the store is a cache; the ledger is the record) and `OPENCODE_PASSWORD` — the bearer's hash (`openCodePassword`): per run and random because the bearer is, derivable by a later generation from the row's `bearerHash` alone, worth nothing at the proxy or the bot's door; a bearer of another shape gets a random password and no re-attach. Never a provider key, whatever the bot's process holds; the server keeps the password in its environment (only `--stdio` mode deletes it), so a reply to an ask the bot did not send is a bypass the gate's unit must read as such. **The configuration** (`openCodeConfig`, held against the pinned schema in the tests): `providers.switchboard` with `package` `aisdk:@ai-sdk/anthropic` or `aisdk:@ai-sdk/openai-compatible` by the run's dialect (both bundled in the binary; nothing is installed at runtime), `settings.baseURL` `<bot>/v1` (both providers hang their route — `/messages`, `/chat/completions` — under it, the proxy's two paths) and `settings.apiKey: "{env:SWITCHBOARD_RUN_BEARER}"` (interpolated at load; a provider with a key needs no credential-store entry), the model with a zero rate card and the run's output cap; `model` that model; `default_agent: "switchboard"`; `agents.switchboard` `mode: "primary"`, the composed prompt and the harness note as `system` (`openCodePromptNote`: OpenCode's tool names for the identity, `bash` mapped onto `shell`), and `permissions` in the order the evaluator needs — `{ action: "*", resource: "*", effect: "ask" }` FIRST, then the identity's denies (`openCodePermissionRules`), because OpenCode appends these after its base policy and judges by the LAST matching rule while `*` matches every action: a deny after the ask is the last word for its action and hides the tool, an ask after the denies would be the last word for everything and hide nothing. The denies: `question`, `subagent`, `execute` (CodeMode, many calls in one), `webfetch` and `websearch` (egress that is not the proxy) for every identity; `edit` besides for `read`; `read`, `edit`, `shell`, `glob`, `grep`, `skill` and `external_directory` besides for `none`. `agents.title.disabled: true`, or every session's first prompt spends one more model call — a proxy turn — on a title. `plugins: ["./plugins/switchboard"]`: a directory relative to the file (the loader resolves `./` against the document's directory and drops a configured plugin that is a file), whose `index.js` is a placeholder that loads and registers nothing until the relay lands. `update: "disable"`, `share: "disabled"`, `snapshots: false`, `lsp: false`, `formatter: false`; `compaction: { buffer, keep: { tokens } }` only when the deployment sets them. The file carries no secret. **The launch** (`launchOpenCode`): the root the container makes for the run (`makeRoot`), the three files, `opencode serve --hostname 127.0.0.1 --port <free>` through `HarnessContainer.start` on the seam's picked port with no stdout filter (a server started without `--port` scans upward from 4096, so the port is always passed). **Readiness**: `GET /api/health` with the password as Basic auth — the one scheme the server reads, the health behind it like every route — answering 200 `{ healthy: true, version: "2.0.3", pid }` within `OPENCODE_READY_MS` (30 s), polled every `OPENCODE_READY_POLL_MS` while nothing listens or the server says it is starting; a 401 is the password refused, another version is a binary this build does not drive, a body that is not the health shape is no health, a server that exited is its stderr tail, each an `OpenCodeNotReadyError` by name at once; then `GET /api/config` echoing the run's document with every clause-carrying key present (`configProblem`: the loader drops a mistyped value by key with a logged diagnostic and keeps the rest, so presence is the proof a key took); then `POST /api/plugin/await-activation` settling the plugin before the first session; then the tailer started with `node` on `tailer.js` (its log the feed, kept and never truncated: `HarnessStart.keepLog`, so a restarted tailer cannot wipe what a recorded offset points into), and readiness ends only when the feed carries the tailer's `connected` note, whose end is the feed offset the launch answers and the row's first `logOffset`; the tailer's pid rides the row's facts beside the server's, so a generation that comes back probes both and restarts only what is gone; the server's port under `SWITCHBOARD_HARNESS_PORT` (the seam's own variable) and its pid under `SWITCHBOARD_SERVE_PID`. The pid, the port and the root go on the row (`openCodeFacts`). A container gone under any probe is the typed error, rethrown as it is. **The tailer** (`tailerSource.ts`, plain CommonJS requiring only Node's modules) subscribes to `GET /api/event` (`data: <json>` blocks, a `: heartbeat` comment between), writes one record per event as it arrives, reconnects with backoff (250 ms doubling to 5 s) when the stream drops — it is volatile by contract — and at every `session.step.ended`, `session.step.failed` and `session.execution.succeeded`/`failed`/`interrupted`, and on every reconnect for every session it knows, appends two records from the store: the session's pending asks (`GET …/permission`, whole) and the messages that changed since its previous refill of that session (`GET …/message?order=asc&limit=200`, the cursor followed to the end, diffed by message id against the JSON it keeps), so the feed grows with the work and not with the session; it exits when the server's process is gone. **The feed's records** (`OpenCodeFeedRecord`, `client.ts`, one JSON object per line): `{ feed: "event", at, event }`, `{ feed: "permissions", at, sessionID, reason, data }`, `{ feed: "messages", at, sessionID, reason, data }`, `{ feed: "tailer", at, note, … }` (`started`, `connected`, `reconnected`, `stream closed`, a refill that failed); `reason` is the event type that caused the refill, or `reconnect`. **The client** (`client.ts`) is hand-derived from `@opencode/protocol@2.0.3` and `@opencode/schema@2.0.3`, each route and shape named with its source file and line, and imports nothing from them at runtime; `client.test.ts` builds the pinned groups and decodes samples a live server at the pin answered, so a bump that moves a route or a field fails there and not in a run. 13. **OpenCode as the contract's object** (the relay, conversation and survival clauses over the process item 12 built). `OpenCodeHarness` (`opencode/harness.ts`) is the second `Harness`, driven through the seam like pi's. **The relay** (`OPENCODE_PLUGIN_SOURCE`, `pluginSource.ts`) is a local plugin the launch writes into `plugins/switchboard/index.js` (no `bun install`; a configured local plugin must be a directory): at load it fetches `GET /harness/tools` and registers each relayed tool through the v2 `ctx.tool.transform` editor as a DIRECT tool (`options.codemode: false`, or the model's direct call answers "No tool named …"), and each call runs `POST /harness/authorize` then `POST /harness/tool` with the model's call id (`context.id`) — the `202 pending` re-asked and the 90-second waits exactly as pi's extension does, so the relay's idempotency by the call id holds and the bot gains no MCP endpoint. A plugin-registered relayed tool raises no `permission.asked` (proven against the real binary), so it is gated only by its `/harness/authorize` and runs in the bot; the bridge's bypass detection skips relayed tools by name. Skipping them is sound, not a new hole in the honest cannot: relayed tools are admitted by roster and never decided per call by the gate (`authorizeToolCall` allows any tool on the run's roster, refusing only during the write-up), and their effect happens only in the bot behind its walls — the token's scope, branch protection, `spawn_run`'s limits — never in the container, so a `session.tool.*` record under a relayed name carries no container effect for the four-effect rule to catch. The rule's job is the harness's own tools, whose effects run in the container; the gate over `permission.asked` (item 2) is those. **The conversation**: the thread's earlier turns are imported as an authored session (`openCodeImportBody`: one store message per seed `ChatMessage`, `POST /api/session/import` into the run's location), the request is a `prompt { delivery: "queue" }`, the follow-ups and the wind-down are `prompt { delivery: "steer" }` (drained beside `driveOpenCode`; the wind-down also refuses relayed tools at the door as pi's does — `LiveHarness.toolsBlocked` reads the bridge's write-up state through the connection — and a steer the server never took is handed back to the inbox for a fresh turn, never recorded as folded in), the hard stop is `interrupt`, and the post-turns are one more `prompt` on the same session; the effort tier would ride the model ref's `variant` but stage A declares no reasoning variants, so `effort` is OpenCode's default. **The survival word is authored-session**: a rebuild imports the record into a fresh store with each call in flight a completed/error tool content carrying the settlement note, and the mirror primes the settlement turn (`OpenCodeBridge.prime`) so the ledger's first step, the store's rows and the model's view agree — the record then rebuilds a transcript with a result for every call. `find` probes the recorded port (any answer, even the password-guarded 401, is `alive-here`); `end` kills the server and its tailer and removes the root. **The survival ceiling is OpenCode's own**: `driveOpenCode`'s container-gone read (`saysContainerReplaced` on the feed) settles the open call on the record (`closeOpenSpans` — a failed `tool_result` carrying the replaced note), builds the record as pi's is (the mirrored rows through `projectStore`, the last turn's calls settled), writes a `sandbox_restarted` note naming both containers' words, and throws `OpenCodeContainerReplacedError(message, said, was, now, record)` with nothing killed or removed in the container that answers now, so `prepareRelaunch` re-opens `open` with the record — the registration taken over with `registry.replace` (its relayed calls kept), one `relaunched after the container was replaced` note. **A resume naming this container** ends the row's server and its tailer before a fresh start on the record when it still answers (`serverAnswers`), one `resumed` note saying so; a row naming another container is the orphan, neither probed nor ended here; the full re-attach onto a still-answering server is a named gap. The identity's own tools are the record's words (`shell → bash`, `glob → find`), so a tool call lands under the same name the roster names across harnesses.

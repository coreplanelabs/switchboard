# The harness contract: six clauses the bot holds any model-loop process to, pi as its one implementation

[Record 0038](../../decisions/0038-the-harness-is-a-contract-pi-is-its-one-implementation.md) decided that a **harness** — a process that runs the model loop for one run, in the container the run's machine class provides — is held to six things and nothing else: it starts with the run's bearer and never a provider key (credential); every tool call it runs is decided by the bot (gate); Switchboard's tools are served to it and run by the bot (relay); every event it emits has a home on the run's record (record); it is driven as a seed, steers and prompts and is ended (conversation); and it leaves facts on the run's row so the bot, in this generation or the next, finds its process or rebuilds it from the record (survival). The seam is one interface, `Harness` (`src/core/harness/contract.ts`), and the run loop is handed an object of it and calls it — never a word it compares. pi is the one implementation ([harness-pi.md](harness-pi.md) holds pi's rows: the mechanics of each clause as pi meets them); a second harness enters as a conformance row before it enters an image.

## Behavior

1. **Credential.** A harness starts with the run's bearer and the proxy's URL as its only way to a model, revealed once into its process's environment and never a provider key, a command line or a file; every model call it makes goes through the model proxy, which pins the model and the caps and meters the turn on the run's page ([model-proxy.md](model-proxy.md)). The proxy serves two wire dialects, the Anthropic messages shape and the OpenAI-compatible chat-completions shape (`PROXY_PATHS`), and refuses any other path by name before a byte is forwarded; a harness whose model library speaks a third dialect is a change to record 0038, never a quiet route. pi's row: [harness-pi.md](harness-pi.md) item 4 (the environment as the channel for the bearer, `models.json` naming the proxy as the one provider).
2. **Gate.** Every tool call a harness runs is decided by the bot, before it runs when it runs in the container and at execution when it runs in the bot: a relayed tool is allowed by name at the ask because the bot's own gates decide it when it runs; the harness's own shell and file tools are judged by `judgeToolCall` with the run's identity and the thread's rules, each decision `accept` or `decline` and never cached outside the bot, a refusal a `tool_refused` note the model reads the reason of. A call the record shows ran with no decision beside it fails the run closed; a call the harness itself refused before running is a `harness_error` note, not a bypass. pi's row: [harness-pi.md](harness-pi.md) item 7 (the extension's hook, the coverage check from the stream, `GateBypassed`).
3. **Relay.** Switchboard's tools — the preset's toolset less the workspace tools the harness has of its own — are served to the harness by the bot, registered under their own names, and run in the bot under the run's context and the bot's own gates; a call may outlive one request and is joined, never run twice, by its call id; a call in flight when the previous bot generation died is settled from the record. pi's row: [harness-pi.md](harness-pi.md) item 7 (the three harness routes, `RelayedCalls`).
4. **Record.** Every event kind a harness emits has a disposition onto the run stream — `mapped`, `structure`, `folded`, `impossible` or `note` (`Disposition`; a harness's table is its `dispositions` property) — in the vocabulary the record already speaks (`tool_call`, `tool_result`, `assistant`, `run_note`), and its finished turns are mirrored into the ledger's step records so a resume reads its rows as it reads any run's; a kind the table does not name is a `harness_error` note naming it, so a harness bump shows in the first run's record. pi's row: [harness-pi.md](harness-pi.md) items 5 and 8 (`PI_EVENT_DISPOSITION`, the bridge, the mirror).
5. **Conversation.** A harness is driven as a seed (the thread's earlier turns, then the request as the prompt), steers (a follow-up, the wrap-up warning, the forced write-up, a soft stop), prompts (the post-turns on the same session: the description turn, the verdict turn, the head-move re-review), and a hard stop that ends it; the budgets and the wind-downs are the loop's words on every harness; Switchboard's effort tier reaches it in the harness's own word (`Harness.effort`). pi's row: [harness-pi.md](harness-pi.md) items 6, 9, 14 and 15.
6. **Survival.** A harness leaves facts on the run's row (`HarnessFacts`, `state.harness`) — the process, where it was filed, the container it runs in, the bearer's hash, and the count of its relaunches — so the bot that comes back, in this generation or the next, asks the harness where that process is (`find`) before anything is probed or ended, re-attaches to it where it lives, and rebuilds it from the record where it does not: an `authored-session` harness (`Harness.history`; pi) accepts the ledger's transcript as its own history, so a rebuild is a rewrite of it; an `own-store` harness has only its private store, so a store that is gone closes the run `interrupted` and its request runs again; either rebuild reads the record, never the dead process. The floor for a container replaced under a live run is [harness-pi.md](harness-pi.md) item 16 (the run closes `interrupted`, its request runs again); the relaunch in the new container with a rotated bearer is the ceiling record 0038 names and no unit has built. pi's row: [harness-pi.md](harness-pi.md) item 8.
7. **The seam: an object handed in, never a word compared.** The process wires one `Harness` into `HarnessProcessDeps.harness` (`src/index.ts`, `src/cli.ts`: `PiHarness`, with the deployment's `pi.compaction` thresholds behind it as its own settings, so every harness is handed the same `HarnessDeps`), and the run loop calls it through the seam's door, `openThroughSeam(harness, deps, run)`, for every run, the answer handed back with the process alive on its session (`HarnessSession`: `answer`, `followUp`, `end`) for the post-turns; on a `finish` plan, `find(facts, container)` and then `end(facts, container)` for the leftover process. The loop names no harness and compares no word — the source scan of [harness-pi.md](harness-pi.md) item 1 forbids `runPiHarnessOpen` in the run stage as it forbids the deleted loop. The object declares its `name` (the roster key and the discriminator of the facts it writes), its `history` word, its `dispositions` table, its `effort` map and the `builtinTools` a run of each identity holds. **The row's facts are read by the harness that wrote them.** `HarnessFacts` is a union keyed on `harness`: pi's `{ harness: "pi", pid, logOffset, sessionFile?, root?, bearerHash?, container?, relaunches }` and the second harness's `{ harness: "opencode", pid, port, logOffset, sessionID, root, bearerHash?, container?, relaunches }` — the feed's byte boundary as pi's log has one, the bearer's hash and the container optional as on pi's row (a bot-host container has no word, and a bearer without a secret no hash), a shape nothing in the tree writes yet, carried so the seam is read against two shapes. `harnessFactsOf` reads a row by the shape its `harness` names, a row without the key as pi's (the one harness that ever wrote one), each shape's known fields by type with a field of the wrong type dropped, `relaunches` as 0 when absent or malformed, and keeps every key it does not know, so a field a later build writes survives this build's rewrite of the row; a row missing a shape's required fields, or naming a harness this build does not know, is no facts. `find` answers one of four words: `alive-here` (the process answers in the container the run was handed), `another-container` (the row names another container: a pid here is a stranger's, nothing is probed or ended), `dead` (this container, the pid does not answer: the harness rebuilds from the record), `another-harness` (the facts were written by a harness other than the one asked, answered with no container command). A `finish` plan on `another-container` or `another-harness` ends nothing and says so in a `resumed` note (the another-container note names both words, the row's and the container this run was handed); on a resume mid-loop the seam's door (`openThroughSeam`, what the run loop and every conformance driver open a run through) refuses another harness's facts before the harness is asked anything (`factsBelongTo`, the seam's one comparison of a row's harness with the object's name) — a `harness_error` note on the record, then `HarnessMismatchError` naming both harnesses; pi's `open` keeps the same check as a defence for a caller that is not the seam — and reads it as an interruption exactly as it reads a replaced container: every interruption is a `HarnessInterruptedError` carrying the card's reason and the request's refusal token, so the loop and the dispatcher name no harness's own error class; the run closes `interrupted`, its card closes `🔁 … the row's harness facts are <found>'s, not <expected>'s; restarting from the request`, never `❌`, the workspace is released, and the dispatcher runs the request again as a new run with the refusal `harness_mismatch`. The relaunch count is the loop's: a harness writes 0 on a fresh run and carries the row's count unchanged through every save and every restart of its process within the run.
9. **The container seam is harness-neutral in fact, not only in name.** `HarnessContainer` (`src/core/harness/container.ts`) is what any harness's process needs of the container the run's machine class provides — `makeRoot`, `cwd`, `writeFile`, `start`, `writeLine`, `readLog`, `alive`, `identity`, `request`, `kill`, `tail`, `remove` — with three implementations: `ExecHarnessContainer` over the run's executor, one command per operation as the thread's user ([harness-pi.md](harness-pi.md) item 4); `BotHostHarnessContainer` on the bot host for a preset without a workspace (item 12); and the in-memory fake the tests drive. `makeRoot(wanted)` answers the root the container makes from the one the harness proposes (its predictable `/tmp/switchboard-<harness>-<runId>`): the exec container answers the proposal itself, the bot host a `mkdtemp` beside it. `start` takes the program (a plain word on the container's PATH; a shell fragment is refused by name), its arguments, the stdout filter (lines carrying a mark never reach the log; absent, every line lands) and the run directory's layout (`HarnessPaths`: the root and the directories the start makes at 700, the FIFO, the log, the error log, the pid file, the command directory) as inputs, and answers the pid — the wrapper's, the leader of the group the process runs in, which `kill` ends first — and, when the start named a port, the port: a number to hand the process, or `free` to pick one in the container before the command runs (node on the exec classes, the host's own `net` on the bot host), put in `PORT_ARG`'s place among the arguments and in the environment under `SWITCHBOARD_HARNESS_PORT`, said on the first line of the exec's answer with the pid on the last, for the row; the placeholder among the arguments with no port named is a harness bug, refused by name before anything is made or spawned, never handed to the program as the word `{port}`. pi's start is byte-identical to the script the seam wrote before these were inputs: `pi`, pi's `message_update` filter, pi's layout, no port. `request(paths, { method, port, path, headers?, secretHeaders?, body? })` reaches a server the process listens on over loopback inside the container: `curl -sS -i` over the executor on the exec classes — the method, the port and the path checked as the shell and HTTP would read them, curl's own `--max-time` under the executor's timeout so a slow server is curl's named failure and never the executor's killed-command word, the body from stdin through `printf` or, past the inline size, from a file under the run's command directory that the request's own command removes, no `Expect: 100-continue`, never `-f`, so a 4xx or 5xx is an answer parsed to its status, its lowercased headers and its body with an interim `1xx` skipped — and `fetch` on the bot host, bounded by the same figure as the exec class's commands (`OP_TIMEOUT_MS`). A header whose value is a secret (a server's per-run password as Basic auth) goes in `secretHeaders`: on the exec classes its name is in the command text and its value rides the exec's env channel (`-H "name: $SWITCHBOARD_REQUEST_H<n>"`), the road the bearer takes on a start, so the executors' command logs never carry it; on the bot host it is a header like any other, nothing being logged on that road. The exec's answer is read as an HTTP answer first: the server's body is anyone's text, so the executors' runtime word in it is that answer, never a container gone; only an answer that is no HTTP answer goes through the word and the exit-prefix checks. A server nothing answers on, or one that does not answer in time, is a named failure, and a container gone under the request is the typed error, as from every other operation. `identity()` rethrows the executor's typed word that the container is gone (`ExecSandboxRestartedError`, or the seam's own `HarnessContainerRuntimeReplacedError` for the word handed back as a command's text; `isContainerGone`) instead of answering no name; an empty, malformed or failed answer is still no name. The run loop's `finish` plan reads that word from `find` as nothing left to end — a `resumed` note says the container is gone under the finish — and runs the post-steps with the answer, never failing the run over a leftover. A failed command is a `HarnessContainerError` naming the operation.
10. **`run_meta` names the harness.** The run's meta event carries `harness: <Harness.name>` when the process drives runs with one, so a record can be told from another harness's on the run page and in `runs get`; a process that starts no run publishes no such field, and a record written before the seam has none. Additive: every consumer that knows the other fields keeps working.
11. **The conformance table: one table, every harness, no row without the record.** The six clauses and the parity rows are one table of scenarios (`SCENARIOS`, `src/core/harness/testing/scenarios.ts`), each a function of a `HarnessDriver` — start a run from a scripted model, read the run events, the ledger steps, the row's facts and what the container was asked, end — so pi's driver (`src/core/harness/pi/testing/driver.ts`: the real bridge, mirror, relay and gate over the fake container and the scripted double, opened through the seam's door, `openThroughSeam`, as the run loop opens every run) and any second harness's driver walk the same rows and no harness gets a table of its own; the drivers the tree has are one list (`harnessDrivers`) the suite and the matrix script both read. The rows: credential (the bearer in the process's environment and no provider key — the driver plants a sentinel under the bot's provider-key variables for the run, and no value of the process's environment may carry it — and neither events nor steps carry the bearer), gate (an allowed command and a refused push with its `tool_refused` note; a command run without asking fails the run closed), relay (a relayed tool served under its name, run in the bot, its side effect in the run's context), record (the record's vocabulary and one ledger step per assistant turn; an unknown event kind a `harness_error` note), conversation (the seed then the prompt; a follow-up steered as the next user turn; a hard stop), survival (the facts on the row and their round trip; another container's row neither probed nor ended; another harness's row refused), and parity (the tools offered equal the harness's own for the identity plus the relayed ones; identity `none` and `read` hide and refuse what they must). A row's check reads the record: the lint (`runRow`) records every property a check reads and refuses a row that read neither `events` nor `steps`, so a row that passes without looking at the record cannot enter the table. A row a harness cannot pass is a failure in the matrix, never a skip; a limit a harness declares (`HarnessDriver.cannot`, row id to reason) is asserted, not skipped: the suite's test for that row requires the run to fail as declared, so a declaration the harness has outgrown goes red, and the matrix prints it as its own cell with the reason beneath the table. The matrix (`renderHarnessConformanceMatrix`, printed by `npx tsx scripts/harness-conformance-matrix.ts`) is harness × row, a harness without a driver shown absent; it is what a PR that touches a harness carries.

# The harness contract: six clauses the bot holds any model-loop process to, pi as its one implementation

[Record 0038](../../decisions/0038-the-harness-is-a-contract-pi-is-its-one-implementation.md) decided that a **harness** — a process that runs the model loop for one run, in the container the run's machine class provides — is held to six things and nothing else: it starts with the run's bearer and never a provider key (credential); every tool call it runs is decided by the bot (gate); Switchboard's tools are served to it and run by the bot (relay); every event it emits has a home on the run's record (record); it is driven as a seed, steers and prompts and is ended (conversation); and it leaves facts on the run's row so the bot, in this generation or the next, finds its process or rebuilds it from the record (survival). The seam is one interface, `Harness` (`src/core/harness/contract.ts`), and the run loop is handed an object of it and calls it — never a word it compares. pi is the one implementation ([harness-pi.md](harness-pi.md) holds pi's rows: the mechanics of each clause as pi meets them); a second harness enters as a conformance row before it enters an image.

## Behavior

1. **Credential.** A harness starts with the run's bearer and the proxy's URL as its only way to a model, revealed once into its process's environment and never a provider key, a command line or a file; every model call it makes goes through the model proxy, which pins the model and the caps and meters the turn on the run's page ([model-proxy.md](model-proxy.md)). The proxy serves two wire dialects, the Anthropic messages shape and the OpenAI-compatible chat-completions shape (`PROXY_PATHS`), and refuses any other path by name before a byte is forwarded; a harness whose model library speaks a third dialect is a change to record 0038, never a quiet route. pi's row: [harness-pi.md](harness-pi.md) item 4 (the environment as the channel for the bearer, `models.json` naming the proxy as the one provider).
2. **Gate.** The gate decides intent; the walls enforce effects. Every tool call a harness runs is decided by the bot, before it runs when it runs in the container and at execution when it runs in the bot: a relayed tool is allowed by name at the ask because the bot's own gates decide it when it runs; the harness's own shell and file tools are judged by `judgeToolCall` with the run's identity and the thread's rules, each decision `accept` or `decline` and never cached outside the bot, a refusal a `tool_refused` note the model reads the reason of. A call the record shows ran with no decision beside it fails the run closed, and so does a call whose decision was a reply the bot did not send (on a harness whose approval lives in its own server the model's shell can forge one, so the gate there is enforcement by detection and the forgery is the harness's honest cannot on its conformance row); a call the harness itself refused before running is a `harness_error` note, not a bypass. What the gate decides is the call; what bounds the effects of an approved call is not the gate: an approved shell command runs as the container user with everything the container holds, so the walls are the container, the proxy holding the credentials, the token's scope and branch protection. The read identity's walls exist (a read-only worktree and no write token; the gate's read rules restate them); the write identity's one-push-target rule and the harness process's own secrets are held by rules alone, the two gap rows below. pi's row: [harness-pi.md](harness-pi.md) item 7 (the extension's hook, the coverage check from the stream, `GateBypassed`).
3. **Relay.** Switchboard's tools — the preset's toolset less the workspace tools the harness has of its own — are served to the harness by the bot, registered under their own names, and run in the bot under the run's context and the bot's own gates; a call may outlive one request and is joined, never run twice, by its call id; a call in flight when the previous bot generation died is settled from the record. pi's row: [harness-pi.md](harness-pi.md) item 7 (the three harness routes, `RelayedCalls`).
4. **Record.** Every event kind a harness emits has a disposition onto the run stream — `mapped`, `structure`, `folded`, `impossible` or `note` (`Disposition`; a harness's table is its `dispositions` property) — in the vocabulary the record already speaks (`tool_call`, `tool_result`, `assistant`, `run_note`), and its finished turns are mirrored into the ledger's step records so a resume reads its rows as it reads any run's; a kind the table does not name is a `harness_error` note naming it, so a harness bump shows in the first run's record. pi's row: [harness-pi.md](harness-pi.md) items 5 and 8 (`PI_EVENT_DISPOSITION`, the bridge, the mirror).
5. **Conversation.** A harness is driven as a seed (the thread's earlier turns, then the request as the prompt), steers (a follow-up, the wrap-up warning, the forced write-up, a soft stop), prompts (the post-turns on the same session: the description turn, the verdict turn, the head-move re-review), and a hard stop that ends it; the budgets and the wind-downs are the loop's words on every harness — and the wind-down owns the ending on every harness: a model call that fails once the run is winding down (the finale bound's own abort of a call in flight included) is a `harness_error` note, never the run's failure, and the run closes with the wind-down's answer, which names the failed call where the write-up would have been (`windDownFailureNote`, the `writeUpFailed` clause of `timeBudgetAnswer`, `turnGuardAnswer` and `softStopAnswer` in `src/core/harness/windDown.ts`); the budget note says what the run was at when the clock ran out — the open tool calls by name, the model call under way, or the budget alone (`doingNow` on each bridge, `MODEL_CALL_IN_FLIGHT`). An operator's soft stop is honoured on every harness: the write-up steered (`SOFT_STOP_INSTRUCTION`) under a `stopped` note in mode `soft`, every tool refused meanwhile, the answer under the ⏹ label (`softStopAnswer`). The write-up is bounded on every harness (`loopClock.finaleMs`, the `writeUp` allowance of `src/core/budgets.ts`, three minutes): past the bound the harness aborts the call in flight (pi's `abort`, OpenCode's `interrupt`), says so on the card (`finaleTimedOutNote`) and closes by the wind-down's answer without waiting on a settle the aborted turn may never send — the process ended by the caller as after any loop — so a model call that never answers ends within the finale bound whatever the wind-down was, never as a failed run and never as a replaced container; where the abort itself is why no write-up came and the harness cannot read the aborted call's own words, `finaleAbortReason` stands in as the failed call's words on the `harness_error` note and in the answer's `writeUpFailed` clause. Switchboard's effort tier reaches it in the harness's own word (`Harness.effort`). pi's row: [harness-pi.md](harness-pi.md) items 6, 9, 14 and 15.
6. **Survival.** A harness leaves facts on the run's row (`HarnessFacts`, `state.harness`) — the process, where it was filed, the container it runs in, the bearer's hash, and the count of its relaunches — so the bot that comes back, in this generation or the next, asks the harness where that process is (`find`) before anything is probed or ended, re-attaches to it where it lives, and rebuilds it from the record where it does not: an `authored-session` harness (`Harness.history`; pi) accepts the ledger's transcript as its own history, so a rebuild is a rewrite of it; an `own-store` harness has only its private store, so a store that is gone closes the run `interrupted` and its request runs again; either rebuild reads the record, never the dead process. **The ceiling.** A container replaced under a living bot — the harness's typed verdict, `HarnessContainerReplacedError`, carrying the record as the harness holds it (`HarnessRecord`: the transcript it mirrored onto the ledger, this generation's copy of the rows a bot death reads back; every call of the last turn settled; the counters; the deadline) — relaunches the process from that record in the container the run holds (`prepareRelaunch`, `src/core/dispatch/relaunch.ts`, called by the run loop on the typed verdict; harness-neutral, the rebuild itself the harness's own `open` with the record as its resume and `HarnessResume.relaunch` set). In order: the bound read off the row's `relaunches` (`RELAUNCH_CEILING`, two — the third finding closes the run `interrupted` naming the bound, no fourth start; the count is written by the loop and carried unchanged by the harness, so it survives a bot generation); the workspace re-attached where the row says it is or refused by name (`reattachWorkspace`, [run-history.md](run-history.md) item 54, the executor the run holds from then on); the bearer rotated on the run's own meter with the row's facts written exactly once inside the rotation — the new hash, the count one higher ([model-proxy.md](model-proxy.md) item 2); then the harness's rebuild — the run's relay registration taken over with its relayed calls kept and awaited, nothing probed or ended at the row's pid, the process started on the record, one `resumed` note. A refusal by name — the ceiling, the worktree, a bearer that cannot be rotated, a row without facts, an `own-store` harness whose store went with the container — is an interruption like the floor's (`RelaunchRefusedError`): the loop forgets the run on the relay, says why in a second `sandbox_restarted` note after the harness's verdict (the floor's own kind; never `resumed`, since the run is not — the note starts at the why and does not restate the verdict), and closes the run `interrupted` for the dispatcher's restart from the request, the refusal `workspace_lost` for the worktree and `container_replaced` otherwise; a row write that throws inside the rotation fails the run with nothing relaunched and both secrets verifying. **The record across two deaths.** A process rebuilt from the record — after a bot death or a relaunch — starts on a session whose last turn settles every call that was in flight; that settlement turn is written onto the ledger too, as the results pending for the rebuilt process's first step (pi: `PiMirror.prime`; the write-through's own convention, the results since the last assistant turn are the next step's one user turn), so the ledger's next rows are `[user(settlements + the continue's echo), assistant]` from the seed index, the ledger's rows equal the session's and the harness's record of them, and the roll order every image-changing release has — the container rolls (a relaunch, rebuild one), the bot rolls minutes later (a resume from the ledger, rebuild two) — hands the model a `tool_result` for every `tool_use`. The conformance row `survival-rebuild-records-settlement` holds every harness to it. **The first gate** (the plan's execution note, the mid-run re-attach) passed in the fakes: the seam composes — a recorded binding re-attaches mid-run with no gate context and a process starts again in a replacement container from the ledger's rows. What the fakes cannot prove is the resident: a `reuse: true` re-attach onto a container the platform just rolled is proven only by the live row ([harness-pi.md](harness-pi.md) `16, live`), owed before stage A closes. The floor beneath the ceiling is [harness-pi.md](harness-pi.md) item 16 (the verdict and the settle-and-close), pi's relaunch [harness-pi.md](harness-pi.md) item 8; OpenCode's ceiling is its own: `driveOpenCode`'s container-gone read (`saysContainerReplaced` on the feed) throws the same typed verdict carrying the record built from its mirrored rows, nothing killed or removed in the container that answers now, and its rebuild is an import of that record — and a resume naming the container this run holds re-attaches onto the row's still-answering server (its password the row's `bearerHash`, the tailer kept or restarted over the same feed, the feed read from the `logOffset`, the pending asks decided through the gate; item 13), ending it before a fresh start on the record only when the re-attach itself cannot be done. **One more command before the crash judgement.** The floor's condition is the executor's word on a failing container command, and the platform's rollout has a window that misses it: the container's processes are killed first while `exec` still answers, so the alive probe finds the process gone before any command has failed with the word, and a harness that judged by the word alone read the process's own death where the container had in fact been replaced. So a process found dead WITHOUT the word — pi's loop once its transport ends unsettled, `driveOpenCode` once the feed ends — takes exactly one more container command, `identity`, before it judges (`replacedVerdict`, the container seam): that command failing with the word is the executor's word, and the verdict is replaced as it would have been had the word come on the read (`said` the word, `condition` tagged `word`); that command answering another word for the container than the one recorded when the process started is the verdict too, by the changed identity — a renamed container with a dead process is a replaced one; the boot id corroborates wherever the word can come and decides only here, where none can — with `condition` tagged `identity`, `said` nothing, and the `sandbox_restarted` note saying `identityChangedCondition()`'s sentence, `the changed identity was the condition: …`, in the executor's words' place; anything else — the same word, no word on either side, a command that failed for another reason — leaves the crash judgement standing, the failure it always was, with nothing named by the container. The condition is a tag (`ReplacedCondition`, `word | identity`) every verdict carries, so a reader of the error or of the record compares it and never parses a sentence, and `said` is present exactly when the tag is `word` — the invariant the class refuses at construction. The conformance rows `survival-dead-without-word-then-word`, `survival-dead-without-word-then-renamed` and `survival-dead-without-word-then-same` hold every harness to all three, the last the negative half: a wordless death in the same container is not a replacement. **The third failure shape: a command that fails on its transport with no word.** The platform's replacement has a second window the word misses: it kills the container under the process's command, and the read's transport dies with it — the resident client's `resident /exec: Peer closed WebSocket: 1006 WebSocket disconnected without sending Close frame.`, the binding's `The container is not running, consider calling start()`, a connection reset — before any word can come, so a harness that judged that a plain failure lost the run where the container had in fact been replaced. A container command that fails so (`saysTransportLost`, the container seam: a failure whose text names the container's transport or the container down, `CONTAINER_DOWN_WORDING`, or the seam's typed down answer; never the word, never a control file lost, never a command that failed as a command, and never an infra failure that says nothing of the container — the executors' `ExecInfraError` is the shape by its words, not by its type, so a probe that could not reach the container anyway is never spent) takes the same one more command (`replacedVerdict`), and the same three answers decide: the word on it, or a changed identity, is the replaced verdict as above — the condition tagged `word` or `identity`, the `sandbox_restarted` note, the record, nothing killed or removed, the relaunch from the record; the recorded identity leaves the failure standing, NAMED as the transport error it was (the run fails with that error, a `harness_error` note saying the one more command named no replacement), never a crash judgement of the harness's own. **The one more command survives the restore window.** After the platform's replacement the resident rebuilt its container in about a minute, and until then the one more command itself answers that the container is not running: that answer is a wait, never the judgement. `identity` throws it as `HarnessContainerDownError` — the container down under the question with no word, and, under the one more command alone, any infra failure that reached no container (the Worker's 502, its `not-serviceable` refusal while the isolate rolls: the very window the command must survive), while outside that command such a failure names nothing (`identityOrNothing`, what a launch and `find` read the row's word through) — and `replacedVerdict` re-sends the command after the executor's own backoff (`PROBE_WAIT_BACKOFF_MS`, 5 s, 10 s, then 15 s) until the container answers — the word, a changed identity or the same word then decide as ever — or the wait reaches the executor's own bound on a container's start (`PROBE_WAIT_MAX_MS`, five minutes) and runs out, deciding nothing; both constants are the start gate's ([execution.md](execution.md) item 23), the same rule: a starting container is a wait the executor re-sends through, not a verdict. The bound is wall-clock time from the wait's start, read on the harness's own clock between re-sends (`ProbeWait.now`; no clock of the seam's), so a command that itself hangs to its timeout is counted and one such command may overshoot the bound by at most its own timeout, never by the count of attempts. The wait observes the run: its hard-stop signal (`RunControl.hardSignal`, `ProbeWait.signal`) ends the wait at once, in the middle of a pause, and the run's deadline (`ProbeWait.deadline`) ends it before a re-send that would pass it — each said in the note, neither a verdict, and the run then ends as the stop or the failure it was. The harness's own sleep drives the wait, and the record says the wait began and how long the container took to answer, or why it ended. The conformance rows `survival-transport-lost-then-word`, `survival-transport-lost-then-renamed`, `survival-transport-lost-then-same`, `survival-transport-lost-down-then-same` and `survival-transport-lost-wait-stopped` hold every harness to all five.
7. **The seam: an object handed in, never a word compared.** The process wires its harnesses into `HarnessProcessDeps.harnesses`, the roster of item 8 (`src/index.ts`, `src/cli.ts`: `PiHarness` with the deployment's `pi.compaction` thresholds and `OpenCodeHarness` with its `opencode.compaction` thresholds, each behind its own object as its own settings, so every harness is handed the same `HarnessDeps`), and the run loop picks one and calls it through the seam's door, `openThroughSeam(harness, deps, run)`, for every run, the answer handed back with the process alive on its session (`HarnessSession`: `answer`, `followUp`, `end`) for the post-turns; on a `finish` plan, `find(facts, container)` and then `end(facts, container)` for the leftover process. The loop names no harness and compares no word — the source scan of [harness-pi.md](harness-pi.md) item 1 forbids `runPiHarnessOpen` in the run stage as it forbids the deleted loop. The object declares its `name` (the roster key and the discriminator of the facts it writes), its `history` word, its `dispositions` table, its `effort` map and the `builtinTools` a run of each identity holds. **The row's facts are read by the harness that wrote them.** `HarnessFacts` is a union keyed on `harness`: pi's `{ harness: "pi", pid, logOffset, sessionFile?, root?, bearerHash?, container?, relaunches }` and the second harness's `{ harness: "opencode", pid, port, logOffset, sessionID, root, bearerHash?, container?, relaunches }` — the feed's byte boundary as pi's log has one, the bearer's hash and the container optional as on pi's row (a bot-host container has no word, and a bearer without a secret no hash), a shape nothing in the tree writes yet, carried so the seam is read against two shapes. `harnessFactsOf` reads a row by the shape its `harness` names, a row without the key as pi's (the one harness that ever wrote one), each shape's known fields by type with a field of the wrong type dropped, `relaunches` as 0 when absent or malformed, and keeps every key it does not know, so a field a later build writes survives this build's rewrite of the row; a row missing a shape's required fields, or naming a harness this build does not know, is no facts. `find` answers one of four words: `alive-here` (the process answers in the container the run was handed), `another-container` (the row names another container: a pid here is a stranger's, nothing is probed or ended), `dead` (this container, the pid does not answer: the harness rebuilds from the record), `another-harness` (the facts were written by a harness other than the one asked, answered with no container command). A `finish` plan on `another-container` or `another-harness` ends nothing and says so in a `resumed` note (the another-container note names both words, the row's and the container this run was handed; the another-harness note names the row's word and the judge that disowned it).

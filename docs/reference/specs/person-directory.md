# Person directory

The directory is a foundation for [verified cross-surface identity](../../decisions/0079-a-person-outlives-the-surfaces-they-use.md), not an ingress cutover. It supplies a relationship, never grants or an authorization decision. Existing email linking, actors, ownership, run events and startup are unchanged. Linking ceremonies and request attribution remain separate implementation stages.

- **Code**: `src/core/identity/contract.ts`, `src/core/identity/engine.ts`, `src/core/identity/memory.ts`, `src/core/identity/sqlite.ts`.
- **Tests**: `src/core/identity/directory.test.ts`.

## Behavior

1. **Identity is not email.** A directory mints opaque `person:<uuid>` ids independently of surface ids. An external identity is the exact `(issuer, tenant, subject)` tuple, with explicit `null` tenant for issuers without a tenant. Case and punctuation are significant; no email/name lookup or normalization exists. Only a trusted caller that has authenticated the issuer, subject, audience and tenant may supply this tuple. Neither the directory nor its proof metadata verifies a credential.
2. **Trusted writes, not a link API.** `change` is an internal persistence contract, not an exposed tool or route. Its caller must authorize the operation and verify control of both human identities, or authorize separately audited recovery, before calling it. Creating a person alone confers no relationship. Link requires an existing person, an expected revision and closed proof metadata. Service delegation and link/recovery ceremonies are not implemented here. No production caller is wired to this seam.
3. **One identity, one person.** Link creates revision 1 from expected revision 0, or refreshes an active binding at its current revision. Conflicting people cannot both win. An identity is never reassigned to a different person, even after revocation. Recovery only reactivates the same person's revoked binding, requires administrator-recovery proof and cannot merge people or their histories. Every accepted mutation increments the revision once. A stale revision cannot undo a newer mutation; retries with the old revision return `stale` without a second receipt.
4. **Revocation is retained.** Revoke changes an active binding to a tombstone rather than deleting it. Ordinary link cannot resurrect it, even with the current revision. Resolve returns `bound`, `unknown`, `revoked`, `conflict`, `invalid` or `unavailable`; only `bound` carries a person claim. Every read consults current storage, without a positive cache. A read begun after committed revocation observes the tombstone. Admission and stream fencing across asynchronous work remain the future caller's responsibility.
5. **Atomic durable facts.** In-memory and transactional SQLite implementations use the same transition rules. SQLite persists persons, binding revisions and attributable link/revoke/recovery receipts. Reading the current binding, testing the revision, writing it and appending its receipt occur in one synchronous transaction. A failure rolls back both writes. Reopening the same database retains person ids and revoked state. The SQLite implementation accepts a node-free storage interface compatible with Durable Object SQL storage; it is not wired to a Worker or an ephemeral bot filesystem. Tests use real file-backed SQLite, not a simulated database.
6. **Fail closed.** An absent or failing directory yields `unavailable`, never an in-memory or email fallback. Invalid persisted bindings, including mismatched identity keys or missing people, resolve as `conflict` without a person claim. Storage errors do not leak their message. Inputs and stored proof shapes reject extra fields. Proof method and integer version are retained alongside the binding state and revision; no token, raw email or free-text proof payload is accepted. The run-attribution projection contains only the opaque person id, binding revision and proof method/version. It emits nothing for revoked/invalid bindings and does not itself emit a run event.

## Validation criteria

Each contract case runs against both implementations; SQLite cases use independent connections to one real database. In-memory storage is deliberately process-local and makes no restart-durability claim.

| Criterion | Evidence |
| --- | --- |
| Opaque persons and two independently authenticated subjects can bind to one person | `[unit]` `src/core/identity/directory.test.ts::person directory contract::*::binds two authenticated subjects to one opaque person` |
| Issuer, tenant and exact subject isolate identities, including delimiter collisions | `[unit]` `src/core/identity/directory.test.ts::person directory contract::*::isolates issuer tenant and exact subject tuples` |
| Concurrent conflicting links have exactly one winner and one receipt, including independent SQLite writer processes forced to contend on a held write lock | `[unit]` `src/core/identity/directory.test.ts::person directory contract::*::commits only one person for concurrent links of one subject`, `src/core/identity/directory.test.ts::SQLite person directory::arbitrates independent processes contending for one identity` |
| Current-revision refresh advances once; callers cannot mutate stored bindings or receipts through returned objects | `[unit]` `src/core/identity/directory.test.ts::person directory contract::*::refreshes at the current revision without exposing mutable stored objects` |
| Email collision neither resolves another subject nor supplies proof | `[unit]` `src/core/identity/directory.test.ts::person directory contract::*::email collision grants no person claim` |
| Revoke is visible to another reader; stale writes, retries and ordinary relinks cannot restore it | `[unit]` `src/core/identity/directory.test.ts::person directory contract::*::fences stale writes and refuses ordinary resurrection after revoke` |
| Recovery requires its proof and same person, preserves attributable history and advances revision | `[unit]` `src/core/identity/directory.test.ts::person directory contract::*::recovers only the revoked person with administrator recovery proof` |
| Proof metadata persists without tokens/email; run attribution excludes external subjects | `[unit]` `src/core/identity/directory.test.ts::person directory contract::*::persists closed proof metadata and projects only safe run attribution` |
| Missing people, malformed inputs and unsafe revisions never write | `[unit]` `src/core/identity/directory.test.ts::person directory contract::*::rejects invalid writes without receipts` |
| Reopened SQLite preserves the person, proof, revision, receipts and revocation | `[unit]` `src/core/identity/directory.test.ts::SQLite person directory::preserves binding and revocation across database reopen` |
| SQLite rolls back the binding when receipt persistence fails | `[unit]` `src/core/identity/directory.test.ts::SQLite person directory::rolls back the binding if its receipt cannot commit` |
| Corrupt durable data supplies no person claim | `[unit]` `src/core/identity/directory.test.ts::SQLite person directory::refuses corrupt or mismatched durable bindings` |
| Missing and unavailable directories never fall back to a person claim or leak errors | `[unit]` `src/core/identity/directory.test.ts::directory resolution::fails closed without a directory or when storage fails` |

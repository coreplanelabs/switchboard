# Agent: ship

The coding → review → fix loop to LGTM as one pipeline, run by the plan runner: `agent:ship` hands a request — a task, a plan's units, or a ship pull request to resume — to a Workflow coordinator in the bot's shim Worker, which runs each unit's pipeline as child `dispatch()` runs in a thread of the unit's own, gets the pull request reviewed, hands the findings back, and repeats until the review approves; on a plan branch it merges, elsewhere a person does. One dispatch hands off, one card follows the plan, one run record carries its story; every side effect (branch create, PR open/edit, review post, board comment, merge) is executed by the bot process from typed artifacts. There is one ship implementation: the runner. No round loop lives in the bot process.

## Behavior

1. **A directive, never a registry command.** `agent:ship in <owner>/<repo>: <task>` resolves through `parseDirectives`/`AGENTS["ship"]` (`machine: "repo-resident"`, `toolset: "full"`) and forks inside `dispatch()` after agent resolution — a `CommandRegistry` handler may never start an agent run (AGENTS.md invariant 3). Slack and CLI only: HTTP `/ingress` and the MCP dispatch tool refuse `agent:ship` with a pointer to the run page — the runner posts its card and opens each unit's thread through the requesting thread's channel, which a single-shot adapter has none of. Thread follow-ups are sticky like every agent.
2. **Compound permission gate.** Running ship requires `canRunAgent` for `ship` AND `coding` AND `review`, plus the repo allowlist for the target repo; the ship branch forks after the dispatcher's repo gate so `canUseRepo` always runs. Every child the runner spawns is an ordinary `dispatch()` run authorized again as the requesting user by the authorize stage ([http-ingress.md](http-ingress.md) item 9), so the compound gate refuses the whole pipeline up front rather than letting a unit fail at its first spawn; it grants nothing the children's own gates would not. The refusal names the missing grant.
3. **Ship owns the pipeline branch.** The resident binds one ref per thread at first attach and ignores later hints ([resident-repos.md](resident-repos.md) item 16); a thread bound to the base branch would hand every review round the base tree. Ship names the branch itself (`shipBranchName`: the task's slug and a hash of the thread key, so a re-issued task reuses its own deterministic branch; a plan unit's is `plan/<plan-id>/<unit-slug>`, item 15), and the runner's `branch` step creates it on origin from the pull request's base through the GitHub REST API BEFORE round 0's spawn (`createBranchRef`: the base tip's sha → `refs/heads/<branch>`; a 422 already-exists is success) — the resident refuses to bind a ref origin does not have — and every child is dispatched `on branch <ref>` so its thread binds to it at attach. A creation failure (or an unknown base) ends the unit with the reason before any round starts. A coding child's attach must land on the pipeline branch — the resident's one-ref-per-thread binding refuses a thread bound elsewhere before any model call, naming both refs — and a review child attaches at the pinned head (the extracted attach-head guard, [agent-review.md](agent-review.md) item 8).
4. **Round 0 = the PR gate end to end.** The coding child implements, pushes, and submits its `PrDescription`; its post-step is the coding PR post-step ([pr-description.md](pr-description.md) item 5) against the base the runner's tag names (`CoordinatorTag.base`, since the child's thread binds the head branch itself), so the pull request is opened from typed artifacts and the runner's `pr-check` after the round reads `{repo, prNumber, headSha}` from what heads the branch. Round-0 terminals other than "PR opened" — clarifying question, budget write-up, no description, unproven push — end the unit with a report naming the terminal and the child's final words leading; ship never retries a child round. The question passthrough keeps the thread alive: the user answers and re-issues.
5. **Review rounds run on a pinned head, in the unit's review thread.** The review child is an ordinary review run given the pull request and the head to pin (`buildShipReviewTurn`; a re-review round carries the previous round's findings and the dispositions the coding run recorded against them, matched by the runner with an id the review never issued named as dropped, item 6). It runs in the unit's **review thread**: opened once per unit beside the unit's thread by `unit-start` (or by the first review spawn of a row written before the field existed) and written on the unit row (`reviewThread`, [run-history.md](run-history.md) item 50; the lead names the unit, the requester and the branch), so the review child's worktree is readonly and its own and no round wipes the coding thread's ([record 0034](../../decisions/0034-one-agent-per-unit-a-run-continues-a-transcript.md)); a run live in the unit thread does not hold the review thread, and one live in the review thread answers the spawn `busy`. The head is pinned before its attach (readonly), the run submits the structured verdict with findings, the reviewed-head gate + repush-void machinery apply unchanged, and the review posts pinned to the head it read. A verdict always covers the full diff against base — the `re-review-delta` skill narrows *reading*, never verdict scope. **No verdict = abort**: a review child whose record carries no `submit_verdict` (budget, refusal, stop) ends the unit with a report naming that terminal — it is never converted into a `request_changes` the reviewer did not make.
6. **Findings and dispositions are typed artifacts.** `ReviewVerdict.findings[]`: `{ id, severity: blocking|major|minor|nit, file, line?, title }`, validated fail-closed per finding; `buildReviewPostBody` renders them under the verdict line, and the body starts with the exact `LGTM:` token only for `approve` — an `approve` carrying a `blocking` finding is downgraded to `request_changes` in `parseVerdictInput`, so the auto-approve workflow can never fire over a self-declared blocking defect. The findings step's coding run records one disposition per finding through `submit_dispositions` (`fixed|declined` + note). Dispositions are kept per round: finding ids are only unique within one review round, so a later round reusing an id for a new finding inherits nothing, while a finding carried forward unchanged (same id, severity, file, title) keeps its recorded disposition. The tool records what the run submits, always: every dispatched run has the sink, the tool holds no list of the review's ids, and the last set rides the run record ([run-history.md](run-history.md) item 2), where the runner's `read-record` reads it. The match is the runner's (`matchDispositions`, `src/core/ship/coordinator.ts`): when the machine reads the record and when the spawn route composes the re-review turn, the dispositions naming the round's finding ids are kept and one naming an id the review never issued is dropped, with a note to the re-review (`Dispositions naming no finding of the previous round (dropped): …`), so the state, the cap report and the reviewer agree on what was answered. A context without the sink (outside the run loop: a unit test's, a CLI's) is told that no run is recording, never a false "recorded" ack.
7. **The findings step: the review's findings are a message into the unit thread, and the coding session there addresses everything and repushes** ([record 0034](../../decisions/0034-one-agent-per-unit-a-run-continues-a-transcript.md)). After a verdict that requests changes the runner enters `findings` (item 15), never a `fix` child briefed from the review: the bot dispatches the review's findings into the unit thread as the requester with the coordinator's tag through the spawn route (a `findings` brief naming the review run, [http-ingress.md](http-ingress.md) item 9), the directive `agent:coding` explicit in the message's text so a person's `agent:review` detour in the thread or a lost store never routes the findings elsewhere. The message is what the requester would paste: every finding verbatim with its id, the review's own words, and the ask (a disposition per finding through `submit_dispositions`, the description resubmitted, the branch pushed, never a merge or an approve; the `address-review-findings` skill carries the craft); it carries no contract and no finding-id tag. The run resolves `coding` by directive and starts as any coding run in that thread does, so on a harness that keeps the thread's coding session the agent that wrote the code answers its review with the reasons it had, and on a native coding preset the run seeds from the channel with the findings as the request. A run live in the unit thread at that moment is a person's (the runner awaited its own child's end): the spawn is refused `coordinator_thread_live` ([thread-admission.md](thread-admission.md) item 8) and answered `busy`, the step waits and asks again under the unit's wall clock, and a busy answer that reaches the reserve ends the unit `wall_clock_cap` with no coding run started (item 8). Every severity including nits gets a disposition, commits are squashed coherent, the description is resubmitted (the bot re-renders and edits the PR at the new head), and the branch repushed. A coding round — round 0 or a findings step — that pushed the pipeline branch onto an open PR without resubmitting gets the same bounded description turn a plain coding run gets ([pr-description.md](pr-description.md) item 5), while its workspace is still attached, before its post-step; only a turn that still submits nothing leaves the post-step's warning. The post-step's note reaches the unit's thread like any coding run's, and a findings step that opened a NEW PR (the old one closed out from under the pipeline) is adopted at the round's `pr-check` for every later round and report. A findings step that ends with the branch still at the previously reviewed head repushed nothing — the unit aborts with that reason instead of burning a review round on the same diff, with ONE exception: a round that declined EVERY finding on the record changes no code on purpose, and the re-review still runs over the same head to verify those arguments and possibly concede (the decline path's designed resolution — `maxRounds` still bounds a decline stalemate). Rounds are strictly serial — the runner waits on each child's `run-finished` event and confirms its record before the next spawn (item 15) — and an operator stop of a child ends the unit as a stop naming the mode; the stop is honored between outcomes, never over one: a review verdict that already posted settles first — an approve that posted is merge-ready, stop or no stop, and a stopped report names a posted changes-requested review.
8. **Caps are ceilings, honestly reported.** The pipeline's wall clock is the ship run's effective profile ([routing-and-config.md](routing-and-config.md) items 2 and 4): the ship preset's declared budget — `ship.maxMinutes`, one number the profile and `resolveShipCaps` both read, the registry's 120 by default — as a boundary on the path or the request's `budget:` directive clipped it (`caps.maxMinutes` is `profile.minutes`; `maxRounds` stays the config block's), handed to the runner on the instance record as each unit's clock. The card names the clip before the fork like any run's (`budget 10 min (channel boundary; preset asks 120)`), and the ship run's ledger row and record carry the profile under the preset's name. The child rounds run under that profile: each attaches on its own preset's class and identity — within the parent's, which the gate judged once before the fork, because `coding` and `review` declare ship's class and an identity at or under ship's `write` — and is spawned with its budget clipped to the unit's remaining time (never under the two minutes a spawn accepts); a round starts only when the reservation check passes (`SHIP_ROUND_RESERVE_MS`). Worst-case rounds exceed the 120-min default by design (three full worst-case rounds ≈ 255 min): the wall clock, not `maxRounds`, ends most worst-case pipelines, while typical rounds run far below their ceilings. A cap report distinguishes **declined** findings (disposition recorded) from **unaddressed** ones (no disposition), computed against the LAST review round's findings with only the dispositions recorded for them — a carried-forward finding keeps its disposition, a reused id inherits nothing.
9. **LGTM → merge-ready; the merge is the runner's on a plan branch only.** Merge-ready stands on the POSTED approval: the review child's post-step returns a typed outcome the runner reads back (`reviewPosted`), and an approving verdict whose post failed or was refused by the reviewed-head guard ends the unit with an honest report naming the reason — the PR carries no approving review; re-issue ship in the thread with the PR URL to retry (item 10). On a posted `approve` of a task string's ship branch the unit ends `merge_ready` and reports: PR link, rounds used, declined findings, and the pending human merge as the remaining gate. When the instance's `merge` field says `runner` (the hand-off writes it: `runner` for a seeded plan, `person` for a task — item 16) the approve is followed by the runner's `merge` step under the `plan:merge` grant ([http-ingress.md](http-ingress.md) item 9; [authorization.md](authorization.md) item 2): a squash at exactly the approved head, only with the bot's LGTM standing at that sha and every check green, refused by reason otherwise — the release pull request is never merged by the runner, an instance whose field says `person` or carries none waits for a person naming the field, and, as defense in depth, so does a unit whose branch is not `plan/<its plan's id>/…`, the refusal naming the field and the branch. Ship's bot-process GitHub writes are exactly the branch create, the PR open/edit, the pinned review post, the board comments, and that one guarded squash; the coding prompts + fix skill carry never-merge/never-approve. Because the approving verdict's `LGTM:` line triggers the auto-approve workflow in a repository that has opted in, ship refuses a target repo with auto-merge enabled up front.
10. **Entry checks make restarts safe.** Ship never opens a duplicate PR (open-or-edit by head branch; a re-issued plan finds its unit's pull request at the pre-check, item 15). A ship invocation **resumes at review** — skipping round 0 — only when ALL hold: a user turn names the PR (the thread→PR inference reads user turns only), it is open, authored by this bot's own GitHub identity (the App's bot user — `resolveGithubIdentity`, resolved from GitHub once per process and matched by login AND immutable id; the code names no bot), same-repo head, and the invocation carries no new task text. An identity that cannot be resolved refuses fail-closed: an open PR's authorship cannot be judged. A PR reference binds the entry checks only when the invocation carries no other task text (a resume request) or the PR is ship's own; a PR number quoted as evidence inside new task text does not bind — it stays in the task as context and round 0 starts from the repo's default branch (or a user-named `on <ref>`), never from the quoted PR's head branch. This holds even when the cited PR's facts cannot be fetched: a PR named in the CURRENT message (`repoContext.prFromMessage`) beside new task text falls through to round 0 rather than refusing on the transient failure, and the round-0 base drops any PR-derived ref (`repoContext.refFromPr`, flagged at the resolver) so the failed fetch cannot leak the stranger's head branch. Kept fail-closed on a fetch failure: an INHERITED thread PR (not in-message), and a BARE in-message reference with no task text (a resume attempt must verify the PR first). A new task over ship's own still-open thread PR is refused naming the PR; a bare reference to a human-authored PR is refused as not ship's to drive. A resume is handed to the runner like every request (item 16): the one task unit's row carries `resume` — the pull request, its head and url — and the machine opens that unit at its first review round with no pre-check, no branch and no round 0 (`openUnitPipeline`'s `resume`), on the pull request's own head branch and base; the review child pins the head and the approve ends `merge_ready` for a person, as item 9 has it. No pipeline state lives in the bot process — the runner's is the Workflow's, durable across bot deaths (item 15) — so a bot death under a pipeline interrupts a **child**: the next generation closes that run `interrupted` and tells its thread ([run-history item 36](run-history.md)), the runner reads the record and ends the unit with the same note (`shipInterruptedNote`): the PR it had opened, if any, and the exact re-issue that continues the loop — `agent:ship` with only the PR URL (this item's resume-at-review), or with the task when no PR existed (round 0 again on the same deterministic branch; a plan is re-issued as its next attempt, item 16). Nothing restarts a pipeline unattended (the ship-restart plan's D1, which the runner keeps).
11. **Resident-only in practice; the children are ordinary runs.** The coding and review presets are `repo-resident` ([execution.md](execution.md) item 18), so a target repository that is not onboarded is refused at each child's authorize stage (`repo_not_onboarded`) — the spawn answers `refused` and the unit ends with the gate's name, never a per-round cold clone the requester did not ask for; a resident that is onboarded but cannot attach falls back exactly as a plain coding or review run does ([execution.md](execution.md) item 8), with the fallback named on the child's card. Each round attaches its own executor with the child agent's toolset (readonly review attach / writable coding attach — the mode-switch wipe is the accepted cost, bounded by clipped budgets).
12. **Rounds are legible.** Every round boundary the machine reports (`CoordinatorNote`, item 15) reaches the bot's `round` route: the unit's row records it (the `ship_round` vocabulary — index, agent, outcome; [run-history.md](run-history.md) item 50), the card is redrawn with the orchestrator-owned round header (`shipRoundHeader`: `Round 0 — coding`, `Round 1 — review`, `Round 1 — fix`; a fix round shares its review round's index), and the runner's `finish` writes the parent's record with one typed `ship_round` event per boundary in order and the plan's summary as its answer ([http-ingress.md](http-ingress.md) item 9). Every child is a run of its own with its own record, `model.turn` spans and cost, tagged with the instance and its step (`parentInstanceId`, `idempotencyKey`; [run-history.md](run-history.md) item 48) — per-round cost is the child run's, read from its record, and the parent's card is the runner's to redraw, never a child's to erase. `ship` joins `NO_REFLECT_AGENTS`: the parent's report is per-PR findings ephemera. Endings are truthful: the unit's ending kind distinguishes merged / merge-ready / aborted / capped / stopped / no verdict / interrupted / refused (item 15), the plan's summary lists each unit's, and the card closes ✅ only for a plan whose every unit is merged or merge-ready — anything else closes ⚠️ over the units' endings.
13. **The child contract is a typed object the pipeline renders, never one the child assembles** (`src/core/ship/contract.ts`): what a coding child is handed for a plan unit, and what the review child checks the diff against — the unit's own text, the spec rows it names, the repository's agent rules and the guards it may not weaken, because the instructions handed to a worker decide the outcome and the plan already knows more than a task string carries. `contractFromPlan({ planMarkdown, unitId, readSpec })` is pure — the plan and the specs arrive as text, nothing reads a disk or the network — and builds `{ unit, specRows, agentRules, guards, rebase }`: the unit is its `### U<n>.` heading to the next `###`/`##` heading, verbatim (a closing thematic break dropped), with the plan's bullet keys (Goal, Requirements, Dependencies, Files, Approach, Test scenarios, Verification) parsed whole; the spec rows are the items the section names as `<spec>.md item(s) <n>…` — path-prefixed, backticked, linked or bare, comma/and lists and ranges, a parenthetical after the number, and a bare `spec item <n>` attributed to the nearest preceding spec named in the section (to nothing when another file such as `AGENTS.md` is nearer) — each once, in order, resolved to the spec's numbered item verbatim plus the validation-table rows whose criterion names that item (a leading `<n>:`, `item <n>`, a list, a range) with their proof bindings; a spec that is not readable or has no such item is said in the render, never invented. The agent rules are the text the caller read (`AGENTS.md`, else `CLAUDE.md`, else none); the guards are `specs:check`, `specs:coverage --test-guard`, `hygiene:check`, `decisions:check` and `check:pr-title`, one line each on what they refuse; a unit the plan lacks throws naming the units it has. `contractFromTask(task)` is the compatibility path: a task string is a plan of one unit — the task as its whole section — with no spec rows, so the ship directive on a task string keeps working unchanged. `renderContract(contract, { maxChars })` renders one block under `## Contract` with the fixed sub-headings `### First instruction` (rebase the unit's branch onto the merged parent, both named when known; a conflict ends the unit), `### Unit <id> — <title>` (the section's body verbatim), `### Spec rows`, `### Agent rules` (with its source file) and `### Guards`, in that order and to the same bytes for the same object. Over the budget (`DEFAULT_CONTRACT_MAX_CHARS`, the one both children render with, until real renders fix the number) it cuts in a fixed order — the unit's Approach text first, then the agent rules, then the spec items' behavior text (their proof rows stay), then the proof rows (the rows' names stay) — never spec rows before Approach, each cut leaving a placeholder saying where to read the dropped text, and a closing line saying what was dropped; a part that is not there is not reported dropped; the unit's other bullets (its test scenarios above all), the rows' names and the guards are never cut, and the render reports its length and whether it is still over. The runner's spawn route composes the contract bot-side from the plan at the base ref (`contractFor`, [http-ingress.md](http-ingress.md) item 9) and hands it to the child as `DispatchOptions.contract`: the dispatcher appends the rendered block to a coding child's FIRST user turn as its own text part after the request's text (`withContractInFirstUserTurn`; the description turn sees the same turn), and renders the same object into a review child's system prompt right after the REVIEW TARGET block ([agent-review.md](agent-review.md) item 17), so both children hold one object rather than two readings of a tree that may differ; a run without a contract runs exactly as before. `contract render --plan <path> --unit U<n> [--root <path>] [--branch <name>] [--onto <ref>] [--max-chars n]` ([command-registry.md](command-registry.md) Catalogue; CLI-only under `contract:read`, because it reads host paths the caller names) renders a unit by hand for a person: it reads the plan, the specs it names under the repository root the plan path implies (`docs/plans/<file>` → the directory above `docs`, else the plan's own directory, else `--root`) and the rules file, prints the block followed by a receipt line with the measured length, the budget and what was dropped, refuses a missing plan as `not_found` and an unknown unit as `invalid_input` naming the plan's units, and renders an unreadable spec as not found rather than failing. Two questions the design record leaves open are answered conservatively until decided: a unit naming no spec rows receives none (not the covering specs' rows by path), and a child reports a follow-up in its handoff (item 14) rather than proposing a unit.
14. **The handoff is data the parent posts, never prose a person copies** (`src/core/ship/handoff.ts`; [agent-coding.md](agent-coding.md) item 9): what a coding child hands back beside its description when it ran for a plan unit — `{ deviations: [{ from, to, why }], followUps: [{ what, where }], unproven: [{ criterion, why }] }` — so a deviation from the unit reaches the unit's board issue without a person writing it there. The module is pure and dependency-light (the run record's node-free contract imports its type and shape check, so nothing in it may pull in zod or a Node built-in): `parseHandoff` validates a tool call (the three lists present, each at most `HANDOFF_MAX_ITEMS` entries, every field a non-empty string of at most `HANDOFF_MAX_FIELD_CHARS` once trimmed, unknown keys dropped; a refusal is a string naming the path); `isHandoffShape` is the structural check a stored record runs — shape only, no bounds, because redaction may lengthen a stored string; `redactHandoff` puts every string leaf through the redaction seam; `renderHandoffComment` renders the board-issue comment — the unit id and the pull request in its first line, each non-empty list under its own heading, an empty list omitted with its heading, then the ledger rows in a fenced block a person pastes into the plan's follow-ups ledger while the plan is `proposed`, and nothing at all for an entirely empty handoff, the same bytes for the same object; `renderHandoffLedgerRows` renders one row per entry in the ledger's exact three-column shape (`HANDOFF_LEDGER_HEADER`), the source naming the unit's handoff and its pull request, the disposition `open` until a person decides, cells escaped so a pipe or a newline cannot break a row. A coding child takes the handoff through the same `ToolContext` sink as the description (the last call wins; an affirmed empty handoff is three empty lists, distinguishable from none) and it rides the child's run record, redacted by the one record assembly ([run-history.md](run-history.md) item 2), where the runner's `read-record` sees that one exists. The parent posts it at the unit's end: the runner's `unit-end` step names the last coding child (`codingRunId`, the machine's `lastCodingRunId`), and the bot's route — when the unit's row names a board issue (the open issue titled by the unit id, found at `unit-start`) — reads that child's record, a run of this instance and no other, and appends the rendered handoff under the ending's report in the one comment it leaves there, through the bot's own GitHub identity; an empty handoff, a run outside the instance, a run the history lacks or a record without one leaves the comment as the report alone, a failed comment never fails the step, and a task-string unit (no issue) posts nowhere while the child's record still has the handoff. The plan's own follow-ups ledger is amended by a person at review points, each row `open` until decided: no bot path writes a plan record, and a plan's body freezes once accepted.
15. **The plan runner's state machine is pure over the coordinator's step returns** (`src/core/ship/coordinator.ts`; [record 0031](../../decisions/0031-the-coordinator-runs-a-plan-not-a-pull-request.md); the coordinator itself is [http-ingress.md](http-ingress.md) item 9). The ship coordinator — a Workflow instance in the bot's shim Worker — has no model turn and holds no credential: it asks the bot for one step at a time and feeds the answer back, and everything it decides is a pure function here. Nothing in the module reads a clock (every bot answer carries `at`, the machine's only time) or carries a task's text or a thread's contents (a spawn's `brief` names the unit and the run ids whose records the bot reads to compose the child's turn). Two machines. **The plan graph and its cursor.** `parsePlanGraph(planMarkdown, planId)` is every `### U<n>.` unit in the plan's order with the unit ids its Dependencies bullet names (lists and `U<a> to U<b>` ranges, itself excluded), its slug (`u<n>-` and at most 24 characters of its title) and its head branch `plan/<plan-id>/<unit-slug>`; the plan id is the plan file's name without its extension (`planIdOf`: lowercase letters, digits and hyphens, or a throw naming the path), `parsePlanBranch` reads a branch back and answers undefined for every other shape — the line the merge grant draws — and `planInstanceId` names the plan and, from the second, its attempt (`plan-<plan-id>`, `plan-<plan-id>-<n>`; the suffix never trims into the name), so a second runner for one attempt meets the engine's duplicate-id refusal and a re-issue gets the next id; `parseShipPlanRequest` reads `plan <path>.md [units U<n>, U<m>]` and nothing else, so a task string stays a task string. `openPlanCursor(graph, selected?)` puts the selected units (every unit when none are named) in play in the plan's order and refuses an unknown unit naming the plan's units and a dependency cycle; `readyUnits` are the pending units whose in-play dependencies are done — a dependency outside the selection is the requester's assertion that it is done; `startUnit` refuses a unit outside the selection, one already started or settled and one not ready, each by name; `settleUnit(…, "done")` frees the dependents and `settleUnit(…, "failed")` — any ending but a merge: a conflict, a cap, a stop, a refused merge — blocks them transitively and leaves every other ready unit in play; `cursorFinished` when nothing is pending or running. **The unit pipeline.** `openUnitPipeline(input, at)` over `{ unit: { id, branch }, repo, base, caps, childMinutes, merge: runner | person, resume? }` — a `resume` (item 10: the pull request of ship's own the requester named, its head and url) opens the pipeline at its first review round with the pull request adopted and no pre-check, branch or round 0; `nextAction(state)` names the step the machine is at — `pr-check` first (`<unit>/pr-check`: what already heads the branch), `branch` (the head branch from the base), `spawn` (the preset, the round, the child's budget, the brief), `wait` (`run-finished-<runId>` with a timeout of one chunk), `read-record`, `pr-check` again after round 0 and every findings step, `merge`, `sleep`, `end` — under a step name `<unit>/<round>/<kind>` (`<unit>/0/coding`, `<unit>/1/review`, `<unit>/1/findings`; the waits, reads and busy waits numbered under it, `<unit>/pr-check`, `<unit>/branch`, `<unit>/merge/<n>`), so a spawn's idempotency key is unique across a plan's units and never carries a colon; `applyReturn(state, ret)` is the transition, and an answer for any step but the one the machine is at — a duplicate `run finished`, a replayed spawn — changes nothing, so every return is safe to apply twice. The rounds follow items 3 to 9 over the returns: first the pre-check — a pull request already merged heading the unit's branch (a person's merge, or an earlier attempt's that died after it: what a re-issued plan meets) ends the unit `merged` at once with `by: other`, no branch created and no child spawned, so the cursor marks it done and its dependents run; `none` or `open` proceeds — an open pull request is round 0's to rebase and re-describe, adopted at the round's own pr-check, never here; then the branch, then round 0 as a coding child briefed with the unit's contract and the rebase onto the base; a `spawned` or `alreadySpawned` answer starts the round's wait — one child, never a second — sliced: each wait is one chunk of five minutes (`WAIT_CHUNK_MS`) with a `read-record` between the chunks, the slices summing to exactly the child's budget plus five minutes (the last the remainder) and, past that, an overdue child asked about every chunk, never in a zero-length wait — so an event the engine never delivered costs a chunk, not the budget; the budget being the preset's own clipped to the pipeline's remaining wall clock (item 8's clip, never under the two minutes a spawn accepts); a `busy` answer waits a chunk for the live run's end and asks again, or ends at the wall-clock cap when the clock ran out meanwhile; a `refused` answer ends the unit with the authorize stage's own name and a `failed` one as an abort; every wait — an event or a timeout alike — is confirmed by `read-record`: a run still live waits again under the next step name and advances nothing, `interrupted` ends the unit with the ship-restart note of item 10, a finished coding child is followed by `pr-check` — no pull request heading the branch is the round-0 terminal at round 0 and an abort after a findings step; a merged one and no open one (the merge landed during the round: a person's, or an earlier attempt's the child found nothing left to ship for) ends the unit `merged` with `by: other` the same way, the round noted `completed`; the open pull request's number and head are adopted, so one closed and reopened under the pipeline is followed — and a findings step whose head is the one the review read aborts unless every finding of that review was declined on the record (item 7); a review round is briefed with the pull request, the head to pin and, from the second round, the previous review's run and the coding run that answered its findings (`prior.codingRunId`), and its verdict settles the round: none is the no-verdict abort (item 5), `request_changes` the findings step (item 7: a `findings` brief naming the review run, spawned as the coding preset under the review round's index, the dispositions its run recorded matched to the round's ids by `matchDispositions` when its record is read, item 6) — or the round cap when the rounds are spent, the wall-clock cap when the reservation fails (item 8) — and `approve` merge-ready, unless the approval did not post, an honest abort (item 9); a stopped child ends the unit as an operator stop naming the mode, honored around a posted verdict and never over one (item 7); a failed child aborts the unit. Under `merge: runner` an approve is followed by the `merge` step at the approved head — `merged` ends the unit `merged` with `by: runner`, `pending` polls every five minutes for at most an hour under `<unit>/merge/<n>`, `refused` ends it `merge_refused` naming the reason, and an approve with no known head to merge at is `merge_refused` too, never a person's merge-ready; under `merge: person` the unit ends `merge_ready` and a person merges, as item 9 has it. Every transition reports the round boundaries the card and the run stream take (`CoordinatorNote`: `started`, `pr_opened`, `approve`, `request_changes`, `no_verdict`, `aborted`, `stopped` — item 12's vocabulary, drawn by `shipRoundHeader`) and the ending; `renderUnitReport(state)` renders the thread's report in the pipeline's own words — merge-ready with the verdict and the declined findings, the cap with its declined/unaddressed split, the stop, the abort, the interrupted note — plus the merge's (`merged` — the runner's under `plan:merge`, or `by: other`: already merged, naming the merge commit and when GitHub merged it and never that the runner merged; `merge_refused`) and the refusal's. The Workflow that drives this machine (`driver.ts`: the machine's steps under its names, one retry policy, every wait confirmed by `read-record`, a task row's `resume` read into the machine's input, the last coding child named on the unit's end) and the bot routes it asks are [http-ingress.md](http-ingress.md) item 9; what hands a request to them is item 16. The merge is item 9's `merge` step under `plan:merge` ([authorization.md](authorization.md) item 2): `merge` on `UnitPipelineInput` comes from the plan route — the instance's field, read `person` when the answer lacks it — never from the branch's name, so a plan's unit is merged by the runner once the review approved at its head and the checks are green, and ship on a task string still never merges.
16. **Every `agent:ship` request hands to the plan runner** (`src/core/coordinator/handOff.ts`, `src/core/dispatch/ship.ts`; [record 0031](../../decisions/0031-the-coordinator-runs-a-plan-not-a-pull-request.md); the runner itself is [http-ingress.md](http-ingress.md) item 9). There is no switch: the `ship` config block holds `maxRounds` and `maxMinutes` and refuses any other key at load by name (`validateShip`) — `ship.coordinator`, the key that once chose between the runner and an in-process loop, with a line saying the runner is the one implementation and pointing at the [migration notes](../migrations.md). The branch runs the preflight (item 2's compound gate, item 3's branch name, item 10's entry checks), registers the run record and card, and hands the request to the runner: the request names a plan (`plan <path>.md [units U<n>, …]`, `parseShipPlanRequest` over the directive-stripped text) or a task; a plan is read at the pull request's base ref through the App (`GithubApi.readFile`), parsed with item 15's `parsePlanGraph` and narrowed by item 15's cursor to the selected units in the plan's order, and a task is a plan of one unit, `task`, on the ship branch of item 3 in the requesting thread — a resume at review (item 10) is that one unit with the pull request on its row (`CoordinatorUnit.resume`), on the pull request's own head branch and base. The bot writes the instance record — the requester, channel and thread, the card's handle, the caps as the profile gate clipped them (item 8: the rounds cap from the block, the wall clock the profile's minutes), the run id, the card's label and `merge`, who merges the units' pull requests (`runner` for a seeded plan, `person` for a task, whatever the request's words say — item 9's door checks it; [run-history.md](run-history.md) item 49) — under the plan's id (`planInstanceId`, `plan-<plan-id>`; a task's under `ship-<run id>`), then one unit row per selected unit with its branch and the dependencies the plan states ([run-history.md](run-history.md) item 50), then asks its own shim for the Workflow instance: `POST <PUBLIC_BASE_URL>/admin/coordinator/instances` with the `coordinator` bearer of the token map the bot holds (`createInstanceViaShim`; the answer read by `readCreateInstanceAnswer`, the reverse of the shim's `createInstanceResponse`). The run then ends `completed` with where the plan runs as its answer and reply — the instance, the plan and its units in dependency order (a task: its branch in this thread; a resume: that the review loop resumes at its next review round with no coding round first), that each unit runs in a thread of its own in the channel under the requester's grants, that the card follows the plan and its summary lands in the requesting thread — and the card closes ✅; the runner's steps call back into the bot from there, and its `finish` writes the plan's story under the same run id ([http-ingress.md](http-ingress.md) item 9). Every refusal is a reply and an `aborted` hand-off (the card closes ⚠️; the run record still says `completed`, because the request was answered), never a throw, and nothing is created on one: no base branch known; a plan file the repository lacks at the base, naming the path, the ref and GitHub's words; a plan file whose name is not a plan id; a plan with no unit headings; a unit the plan lacks or a dependency cycle, in the cursor's words; a process without a durable instance store (`NullCoordinatorInstanceStore` — run history not on the state Worker); the shim's `duplicate_instance` for an id the state Worker had no record of; the shim's `create_failed`, a shim that could not be reached, `PUBLIC_BASE_URL` unset or a token map without a single `coordinator` entry, each by reason — **a deployment without the runner's prerequisites is told which one is missing and runs ship no other way**. The records are written before the create. **A plan runs by attempts**: no record under `plan-<plan-id>` is a first attempt; a record there is an earlier attempt's, and the shim's status of the latest attempt (`GET /admin/coordinator/instances/<id>`, the highest suffix with a record) decides before anything is written — still running (`queued`, `running`, `paused`, `waiting`, `waitingForPause`) refuses the request naming the instance and its status, and its rows, a live runner's threads, rounds, pull requests and endings, are never touched; no such instance (the leftover of a create that failed after the records were written) is replaced with this request's record and rows under the same id and attempt (`replace`, [run-history.md](run-history.md) item 49), the units earlier attempts merged skipped there too, and the reply says so; ended (`complete`, `errored`, `terminated`) is resumed as the next attempt under `plan-<plan-id>-<n>` with `attempt` on the record, rerunning only the units the earlier attempts did not merge (a `merged` ending on any attempt's row), each dependency kept on the row as the plan states it so a merged one counts as done, the reply naming what is left and what was merged; every named unit merged already is a refusal; a status the bot does not read as ended, a shim that could not say, and a `duplicate_instance` for an id the state Worker had no record of (a store wiped or restored) are refusals a person decides, nothing written. Thread follow-ups steer the runner's children like any run ([thread-admission.md](thread-admission.md) item 2): a reply in a unit's thread reaches the child in flight there; the requesting thread's own run is over once the hand-off answered.

## Roadmap (gaps)

- `[gap]` Ship over HTTP/MCP — the hand-off itself is short, but the runner posts its card and opens each unit's thread through the requesting thread's channel, which a single-shot adapter has none of; a job-shaped ingress (accept, return the run link, the runner reporting somewhere the caller can read) remains the gap.

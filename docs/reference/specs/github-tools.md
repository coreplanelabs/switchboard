# GitHub tools: repo and PR reads, Actions triage + issue writes from any agent

Every [agent](../vocabulary.md#agent) with a tool loop can read the org's repositories and read/write their issues through Switchboard's own GitHub App credential — over the REST API from the bot process, with no workspace — so a plain mention answers "open an issue on the switchboard app" and "how does our resident system work?" instead of bouncing the user to a directive, and the research agent never again reports our private repo as "inaccessible" after a public-web 404. A pasted GitHub Actions URL is triaged the same way: "why did this [run](../vocabulary.md#run) fail?" is answered from the run, its jobs and the failed job's log, with no shell.

- **Code**: `src/core/dispatch/executionGithubContext.ts` (same-run native source proof and current capability), `src/core/dispatch/reviewHistoryRestore.ts` (recorded history proof and separate freshness checks), `src/core/dispatch/githubReadContext.ts` (per-call requester-scoped GitHub source receipts), `src/core/references/sourceResultContext.ts` (stored result byte verification), `src/core/references/githubAccessDiagnostic.ts` (closed execution read failure facts), `src/execution/githubReadSource.ts` (closed native task snapshots), `src/core/resumeLaunch.ts` (original snapshot recovery), `src/execution/githubApi.ts` (the `GithubApi` seam; `RestGithubApi` — REST + the one GraphQL `deleteIssue` mutation, read-scoped token for reads and write-scoped for writes; `InMemoryGithubApi`), `src/tools/github.ts` (the thirteen `github_*` tools, `GithubCapability`, `GITHUB_READ_TOOLS` / `GITHUB_ISSUE_WRITE_TOOLS`), `src/tools/runnableTool.ts` (`ToolContext.github`), `src/tools/toolsets.ts` (`TOOLSETS` incl. the `assistant` set), `src/agents/registry.ts` (`general` on `assistant`, prompts), `src/core/dispatch/repositoryBriefs.ts` (authorized connected repository metadata and source briefs), `src/core/dispatch/contextAccess.ts` (saved-context revalidation), `src/core/dispatch/runLoop.ts` (verified request capability), `src/core/dispatcher.ts` (operator and reply rechecks), `src/core/dispatch/run.ts` (`githubCapabilityFor` — the per-run capability with the requesting user's `canUseRepo` gate; injected into every tool context, ship children included), `src/execution/githubApp.ts` (`issues:read`, `pull_requests:read` and `actions:read` in the read-scoped permission set).

## Behavior

1. **The seam, two implementations** (invariant 2/5): `GithubApi` covers `listRepos` (the installation's repositories), `isPublicRepo` (current public visibility for one exact repository), `readFile` / `listTree` / `searchCode` (repo reads at any ref), `listIssues` / `getIssue` (issues, never [pull requests](../vocabulary.md#pull-request); `getIssue` includes up to 30 comments), `getPullRequest` (the PR title, body, state and head/base refs for context, never publication authority), `createIssue` / `updateIssue` / `commentIssue` / `deleteIssue`, and the Actions reads `getActionsRun` / `getActionsJob` / `getActionsJobLog` (item 9). `RestGithubApi` speaks `api.github.com` from the bot process — never `gh`, never a clone — and mints the App token per call class: **reads on the read-scoped token, writes on the write-scoped one**, so a read tool cannot write even under prompt injection. The read-scoped permission set gains `issues: read` for this (execution.md item 5). Every non-2xx is a `GithubApiError` carrying the HTTP status and GitHub's own message; a missing credential is a 401 before any request. Bodies over GitHub's 65536-char limit are clipped with a visible note; files are read as decoded UTF-8 (binary → a note, by default >200k chars → clipped unless a caller sets a larger `ReadFileOptions.maxChars`, >1 MB → re-read via the raw media type as a stream that is cancelled once the caller's clip is in hand, so a multi-MB blob costs the clip's memory, not its own). `listIssues` reads 100-row pages (at most 3) until `limit` issues are collected or the list ends — GitHub interleaves pull requests in that endpoint and they are dropped, so one page can hold fewer issues than rows. `deleteIssue` resolves the node id over REST and runs the GraphQL `deleteIssue` mutation; a `FORBIDDEN` / "not authorized" answer is a 403, a PR number is refused as not-an-issue. **Known limit:** GitHub grants issue deletion only to a repository admin's USER credential — an App installation gets "Viewer not authorized to delete" even with `issues: write` — so with the production credential `deleteIssue` always fails closed; the seam keeps the method because a `GH_TOKEN` of an admin (the non-App fallback) can delete. `InMemoryGithubApi` (repos with files + issues + pull requests + seeded Actions runs; unknown repo → 404 like GitHub; issues listed newest-updated first on a deterministic clock, as GitHub's `sort=updated&direction=desc` does) is the second implementation and the test double.
2. **Thirteen tools, reads vs writes.** Reads — `github_repos`, `github_file`, `github_tree`, `github_search_code`, `github_issue_list`, `github_issue_get`, `github_pull_get`, `github_actions_run`, `github_actions_job_log` — are `sideEffectFree` (the runner may run several from one turn concurrently). Writes — `github_issue_create`, `github_issue_update` (title/body/state/labels/assignees; closing is `state: closed`), `github_issue_comment`, `github_issue_delete` (permanent; the description tells the model to use it only on an explicit delete request, and that the App credential cannot delete — a 403 from GitHub becomes "issue deletion is not available to Switchboard's GitHub App credential … Nothing was changed. Offer to close it instead …") — run strictly in order. Every tool answers a string, never throws: no capability → "GitHub tools are not available in this context."; a malformed `repo`/`number`/missing field → a one-line correction naming the expectation; a 404 is worded as what it usually is ("the repo is outside the Switchboard GitHub App installation (github_repos lists the reachable ones), or the path/ref/number does not exist"); 401/403/timeouts each their own line. Successful writes report exactly what happened with the number and URL (`Opened owner/name#41: title\n<url>`) so the answer can quote it.
3. **Writes and main-agent reads use the resolved requester.** The dispatcher builds `GithubCapability.canWrite` from `config.canUseRepo(actor, repo)`. A refused issue write stops before the API call. The main agent reads public installation repositories allowed by the resolved actor. It also reads private repositories in a verified one-person Slack DM when that same requester has a stored GitHub login and id, and GitHub currently returns that id with read, write, or admin permission on the installed repository. Legacy login-only bindings, missing proof, error, shared channel, relay, and stale permission all refuse private reads. The same capability gates the catalog, every tool read, stored-result reuse, and reply publication; code search stays within one approved repo. Other agents retain their installation-scoped read access.
4. **Enablement by toolset**: the reads join every toolset with a tool loop — `full` (coding), `readonly` (review), `web` (research), `explore` ([agent-explore.md](agent-explore.md) item 2), `assistant`, `conductor`, and `orchestrator` ([orchestration-plane.md](orchestration-plane.md) item 12); the issue writes join `assistant` and `full` only — the read-only review agent, the research agent and the explore agent never mutate GitHub. `none` stays empty.
5. **`general`: the assistant** ([agent-general.md](agent-general.md)): toolset `assistant` = the GitHub tools + `web_fetch` + `update_status` + authorized `recall` + own-session `notes` — no shell, no file writes, no `web_search`, no [verdict](../vocabulary.md#verdict)/PR submission — with a 60-minute [budget](../vocabulary.md#budget) for longer multi-source lookups and the turn guard derived from it. Its prompt names the tools, tells it to resolve a loosely-named repo with `github_repos` (or the [thread](../vocabulary.md#thread)) rather than asking, to read a repo before answering about it, to report exactly what a tool did and never claim an unperformed action, and to redirect code changes / PR reviews / web research to `agent:coding` / `agent:review` / `agent:research`. It still declares no `resources` — the tools are REST in the bot process, so a general ask never provisions a workspace (agent-general item 4).
6. **`research` reads repos too** ([web-tools.md](web-tools.md) item 5): its toolset gains the reads (not the writes) and its prompt names them, tells it to read a github.com URL of ours with `github_file`/`github_tree` (web_fetch cannot see private repos), and forbids concluding a repo is inaccessible from a public-web 404.
7. **Requires the App installation to cover the repo** (execution.md item 5): a repo outside `repository_selection: "selected"` 404s on every call — the tool wording says so and points at `github_repos`. The App needs Contents (read for the read tools), Issues (read + write), Actions (read, for item 9), Metadata; the installation grants `issues: write` and `contents: write` over the repos it covers.
8. **Every call is measured** ([tracing.md](tracing.md) item 23). The `github_*` tools see the REST client as a view under their own call's span, so each request is a `github.rest` span naming its route word (never the repo, path or query) and each token mint a `github.token_mint` span; the run's timeline counts them inside the tool call, and the log carries them.
9. **Actions triage: two more reads.** `github_actions_run` takes the URL a person pastes (`github.com/<owner>/<repo>/actions/runs/<id>`, with or without `/job/<id>` or `/attempts/<n>`) or `repo` + a run id, and renders the run (workflow, run number and attempt, conclusion and status, event, branch, short sha, title, start and span, workflow file) and every job — what went wrong first, then what is still running, then what passed — with its conclusion, duration and id and, for a job that did not succeed, its non-success steps and its URL; it ends by naming the job to read next. `github_actions_job_log` takes a job URL or `repo` + a job id and renders the job's steps with their conclusions and durations, every `##[error]` line (30 at most), and the last `lines` lines of the log (default 200, at most 2000) or, with `match`, only the lines containing that text. The log is remote text: ANSI is stripped and secrets are redacted before anything reads it, and GitHub's per-line timestamp is dropped. Behind them `GithubApi` gains `getActionsRun` (the run plus its jobs, 100-row pages, at most 3), `getActionsJob` and `getActionsJobLog`. The log endpoint answers a 302 to a signed URL on a blob host; the client follows it by hand **without the App credential** (the URL is its own credential) and reads the body as a tail window of `ACTIONS_LOG_MAX_CHARS` (2 M) characters — a multi-MB log costs the cap's memory and keeps its end, where a failed job's failure is; `complete: false` and a note in the answer say the head was dropped. A run URL handed to the log tool, an id without a repo, a repo that contradicts the URL and a non-numeric id each get a one-line correction; a 404 is worded as items 2 and 7 word it. The read-scoped token already carries `actions: read`. **Known limits:** the latest attempt only (an `/attempts/<n>` URL reads the run's current attempt); the combined job log, never the per-step files of the run's log archive; a live job's log is what GitHub has so far, and the answer says so.

10. **Repository briefs reuse connected-repository reads.** The operator's brief loader uses the same `GithubApi` installation listing, tree and file reads. Installation listing follows every page; it never silently drops repositories after a fixed page count. It lists only repositories the resolved requester may use, and checks that permission again before each brief read. Every authorized connected repository contributes its description and default branch; a bounded selection, prioritizing established thread repositories and request relevance, also contributes README, repository guidance and package identity. Selection limits enrichment, never repository eligibility: the model can read any authorized catalog entry. Source paths, blob SHAs, truncation and observation time travel with each brief. Missing files or an unavailable individual repository preserve the other context; an unavailable catalog is explicit. Repository text is quoted, redacted untrusted context and cannot grant permission or become an instruction. Briefs refresh from the existing read seam each request; concurrent reads within that request share their result.

Same-run specialist reads use version 2 of the existing context envelope and source-result receipt. Their references bind the original acknowledged run admission, tool input, call and exact result bytes. Only the current live owner can validate those references against its delivered canonical session and fresh native read capability. Message, main-agent and other-run readers receive no scope. Each original repository must remain installed or have current explicit public visibility for the same repository name through the read-scoped metadata API. Private, internal, unknown and mismatched metadata never proves public access. The original read family must still succeed after that check. When public visibility replaces installation membership, its current result after the standard delivery cap must match the original result hash. A different public result cannot authorize retained private bytes; changed public results remain unproved. Global code search also proves current contents access to every originally exposed repository. Unknown tool families remain unproved. This preserves installation-scoped private specialist policy; it adds no requester grant.

## Validation criteria

## Native identities in read metadata

The existing `GithubApi.listRepos` and `getPullRequest` results retain native GitHub IDs when the source supplies them. A PR object ID stays separate from its repository-local number. Head and base repository IDs stay separate, including a fork. An explicit null head repository stays null; it cannot borrow the base repository ID. Repository names remain display/source metadata and do not define native identity.

Older or seeded metadata without IDs remains readable, with those fields absent. A supplied malformed, non-positive or unsafe numeric ID is refused; it is never coerced or replaced with a name, PR number or generated value. Both REST and in-memory implementations preserve this contract. Existing token permissions, request paths and user-facing tool formatting stay unchanged. These IDs are scoped to the GitHub client/source; they do not prove current access, freshness, source custody or a valid task match.

Repository and PR read metadata also retain the credential's non-secret `source`: host, App ID and installation ID. The existing mint cache captures this source with the token; later configuration changes cannot relabel an older token. Each response retains its own source through concurrent reads, pagination and traced client views. Static or injected opaque tokens have no installation source. Invalid configured IDs leave source identity unknown; malformed supplied numeric source metadata is refused. A branch tip can override the PR head only when both reads have the same known source, or both sources remain unknown under the existing legacy policy. The source describes the read credential, not the installation membership of a fork or a grant of current access.

This extends read metadata only. Canonical source/context matching, native-ID backfill and access checks still need the shared intake integration. A future native matcher must hold missing identity instead of guessing from a name. No source producer, inbox delivery or ownership change is enabled.

## Saved native task source context

A complete PR read can add `githubSource` to the existing `RepoContext` and `LiveRunMeta`. The snapshot keeps the read credential's host/App/installation, the native base repository and PR IDs, the PR number, separate nullable fork identity, and observed head/base refs and SHA. Explicit, accepted and inherited PR resolution use the same projection. Partial metadata and opaque credential identity stay absent. No name supplies a missing native ID.

The existing reservation and execution claim save the snapshot with the run. Promotion preserves a carried row's original snapshot. The existing JSON stores retain it through reclaim; resume restores it only for the same PR number. The private main conversation still omits repository metadata. These are source observations, not execution targets, source-access grants or instructions. Ref strings remain source data and do not authorize a checkout. A future matcher must validate the canonical row, original orchestrator link and current source/access before routing to the orchestrator.

This cut does not index or match source events, route to workers, backfill legacy rows, persist private main context, or retain the snapshot in finished public run summaries. Those paths remain unqualified. A missing or invalid source snapshot gives future matching no native proof.

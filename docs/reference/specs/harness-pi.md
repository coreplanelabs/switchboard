# The pi harness: a preset's runs driven by pi in the run's own container, on the run's own record

[Record 0032](../../decisions/0032-pi-is-the-harness-the-native-loop-retires.md) decides that pi (`@earendil-works/pi-coding-agent`) replaces the native turn loop one preset at a time. This is the harness that replacement runs on: pi in `--mode rpc` inside the run's execution container, started as the thread's user (or, for a preset without a workspace, as a child of the bot itself, item 12) with the run's model-proxy bearer as its only key, driven by the bot over pi's line protocol, every event it emits bridged onto the run's own stream in the native loop's vocabulary, our tools and the coding preset's tool rules as its extension, the transcript mirrored onto the run ledger so a bot restart continues the run. Which preset runs on it is a property of the preset a deployment overrides (`harness:`), so the series can move one preset at a time and a deployment can move — or move back — one early; today every preset declares `native`, and a deployment that sets nothing runs exactly as before.

## Behavior

1. **The harness is a preset property a deployment overrides.** `AgentDef.harness` is `native` (the in-process loop, `src/runner.ts`) or `pi`; every preset declares `native` today, `coding` explicitly, the one the series moves first. A deployment's top-level `harness:` block names a harness per preset (`harness: { coding: pi }`) and wins over the declaration; `effectiveHarness(agent, block)` is the one question the run stage asks. The block is validated at load: a preset the registry does not know, or a value that is neither harness, fails by name, and a non-mapping fails too — a setting that silently read as "nothing changed" while the operator believed a preset had moved would be the worst kind of quiet. A preset with a workspace runs pi in the run's container; a preset without one runs it as a child of the bot (item 12); the registry declares neither kind on pi.
2. **The seam is one branch in the run loop, and everything around it is shared.** `runLoop` asks `effectiveHarness` once; on `pi` it hands the run to `runPiHarness` in place of `runAgent` with the same tool context, the same event and progress sinks, the same control, inbox and ledger step hook, the same `run.agent` parent span and the same resume plan — and the rules the gate (item 7) judges pi's own tools by, which follow the thread the way the post-step's pull-request target does: when the thread came from a pull request or a coordinator's spawn, the thread is bound at the run's own branch (a fix round repushes the PR's head; a unit child is dispatched at its unit branch), so that branch is the one push target and the base its pull request targets is protected; otherwise the binding is that base, protected, and the run pushes a branch of its own making. Admission, resolution, the gates, the workspace attach, the bearer mint and the prompt before it, and the reviewed-head settle, the workspace observation, the description turn, the coding PR post-step, the answer's publish, the finish and the release after it are the same code: the post-step sees the same branch and pull-request facts because it reads them off the same stream (`trackPushedBranch` over the bridge's `tool_call.command`) and the same workspace. A preset on pi in a process without the harness deps, without `PUBLIC_BASE_URL` (the container reaches the proxy and the routes through it; for a preset without a workspace the missing name is `PORT`, item 12) or without a minted bearer fails the run naming exactly what is missing; without the block every run is the native loop byte for byte and pi is never started.
3. **pi lives in every image, pinned and proven.** Each execution image installs `@earendil-works/pi-coding-agent` globally with its own Node 24 at one exact version, read by the pin parser like pnpm's and playwright's; the layer proves at build time that the `pi` on PATH answers the pin and that its help names RPC mode, and the resident image proves it once more as `worker1`, the way a run's pi is started. The bot image installs the same layer in its runtime stage, as root before the switch to the bot's user, on the Node it already builds from, for the presets without a workspace, whose pi is a child of the bot (item 12), and the pin is held equal across the three images. Installing it is dark — nothing in an image starts pi.
4. **The process: pi as the thread's user, the bearer as its only key, through the container seam.** A run's pi has one directory of its own outside the checkout, directly under `/tmp`: `/tmp/switchboard-pi-<runId>` (`piRunPaths`; the same layout under any root is `piRunPathsAt`, how a re-attach reaches the root a row recorded, item 8), made at mode 700 by whichever OS user runs the run's commands (the umask before the mkdir in every script that creates it: the `mkdtemp` shape). `/tmp` is sticky (mode 1777), so every run's root is a sibling under a parent any user may create in and only the owner may remove from, and nothing about the root depends on knowing which user that is. There is no parent between `/tmp` and the root in any case, shared or per user: the resident runs each thread's commands as its own pool user and `mkdir -p` gives a parent it creates to its caller, so a parent shared by every run would belong to whichever user ran first and every other user's run would fail at its own mkdir before a model turn, a shared parent made 1777 would not repair a container where the owned one already stands, and a parent per user would only move that ownership to the runs that know their user. The directory holds pi's config directory with `settings.json` that never trusts the checkout — and carries the deployment's compaction thresholds when the config's `pi.compaction` block sets them (`reserveTokens`, `keepRecentTokens`, pi's own names in tokens: pi compacts when the context passes the model's window less the reserve and keeps about the recent tokens named; unset, pi's defaults stand and the file is byte-identical to before the block existed; a receipt or a test of the compaction path sets a reserve near the window so a short run compacts, production leaves it unset; positive integers only, any other shape or key refused at load by name) — `models.json`, `SYSTEM.md` and `sessions/`, the extension, the FIFO, the log, the error log and the pid file. `models.json` names one provider — the bot's model proxy on the wire shape the run's provider speaks (`anthropic-messages` at the bot's base, `openai-completions` under `<base>/v1`) — with `apiKey: "$SWITCHBOARD_RUN_BEARER"`, a zero rate card, because pi's own cost is never what a page shows: the proxy meters, and — on the Anthropic shape — the thinking payload the model takes as pi's `compat.forceAdaptiveThinking` (`takesAdaptiveThinking`): a Claude model from the 4.6 generation on takes adaptive thinking (`thinking.type: "adaptive"` plus `output_config.effort`) and the 5 family refuses the legacy budget (`thinking.type: "enabled"` plus `budget_tokens`) with a 400; a model before 4.6 refuses adaptive and keeps the budget. pi's built-in Anthropic catalog says this per model and sends the budget for a model it does not know; the proxy's model is not in that catalog, so the harness says it — the generation is the id's first version number (`claude-fable-5` is 5, `claude-sonnet-4-5-20250929` 4.5: a date is never a minor), and an id with none is taken for the current generation. The completions shape carries no such switch. pi starts detached (`setsid -f`) with `--mode rpc`, every discovery off (`--no-extensions --no-skills --no-prompt-templates --no-themes`), the extension by explicit path, `--tools` allowlisting pi's own workspace tools (`read`, `bash`, `edit`, `write`, `grep`, `find`, `ls`) plus the relayed ones, the proxy's provider and the run's model with the effort tier as pi's thinking level (the five tiers are pi's levels by name; no tier leaves pi's default), and a session directory — or `--session <file>` when pi has turns to start from: the thread's earlier turns (item 9) or a resume's mirrored transcript (item 8). Its stdin is a FIFO the wrapper holds open read-write on a spare descriptor, so pi never sees an end of file while it lives; its stdout goes through a line-buffered filter that drops `message_update` deltas into a log the harness polls; its stderr into its own file; the wrapper's pid, the group leader, is recorded. **The environment is the channel for the bearer**: the run bearer, the bot's URL, the run id, `PI_CODING_AGENT_DIR` and pi's offline switches ride `ExecOptions.env` — the exec's own env option on every executor (the local child gets the public environment plus these and never the host's secrets; the resident and the sandbox send them as the body's `env`, the resident Worker reading the map through the one validated reader and handing it to the exec's env option under its own injected variables) — never a command line, never a file, never a model key, Slack token or GitHub App credential. Every operation is one command over the run's own `Executor` as the thread's user — a file written in `printf` chunks under `umask 077`, a line fed to the FIFO (a long one through a file), the log read from a byte offset as one-line base64 so the bytes survive the text channel exactly, `kill -0` for liveness, the container's identity read (`identity`: the kernel's boot id from `/proc/sys/kernel/random/boot_id`, one word or nothing; a container that cannot name itself judges nothing by it), the group then the leader killed, the run's directory removed as one tree — and a command the executor reports failed is a named `PiContainerError`, never a silent empty. Once the run is over — settled, stopped or failed — the harness ends pi and then removes the run's directory, best-effort like the kill: nothing reads its log, session or FIFO again (a later run in the thread seeds from the record, item 9; a resume that finds pi alive, item 8, belongs to a generation whose run never ended). `makeRoot` is the seam's answer to where a fresh run's files go: the exec container answers this predictable root, which its scripts make; the bot host makes a root of its own (item 12); the harness files nothing before it has the answer and records it on the row (item 8), so the way back never has to guess it. The in-memory `FakePiContainer` is the seam's second implementation (it answers the predictable root too); the bot host's `BotHostPiContainer` (item 12) the third.
5. **The bridge: pi's events become the native loop's, and the proxy meters the turns.** Every event kind pi's protocol documents has a disposition (`PI_EVENT_DISPOSITION`, held to the same set of kinds as the spike's home table): `tool_execution_start` opens a `tool.<name>` span under `run.agent` and announces the `tool_call` inside it (the same one-line summary the loop writes, bash's full command beside it, capped and redacted); `tool_execution_end` emits the `tool_result` with the loop's `ok`, bash's `exitCode` read from pi's `Command exited with code N` trailer (or the executors' `exit N:` prefix), the summary and the capped output, and ends the span with `callId`, `ok`, `exitCode`; the model's text beside its tool calls is `assistant`, a text-only turn is the answer candidate, a turn whose every call is `update_status` is bookkeeping — not counted against the guard, its text held until the next turn decides ([run-loop.md](run-loop.md) item 15); `💭 thought for …` is said at each assistant message's end; `compaction_end` is a `compacted` note with the token counts and any summarization retries folded in; `extension_error`, a dialog request (answered `cancelled`, since no one is watching), an event kind this build does not know and a kind the harness turns off at start (`auto_retry_*`, `bash_execution_update`) are `harness_error` notes naming what happened; `message_update` and `tool_execution_update` are folded into the final records; `response`, the agent and turn boundaries and `queue_update` are structure. The model turns are not the bridge's: every call pi makes goes through the model proxy, which spends the run's turn guard and closes one `model.turn` span with the runner's attrs — and the harness re-parents the run's grant from the request root to its `run.agent` (`RunBearerStore.reparent`), so a proxied turn lands where the loop's would. The proof of sameness is the loop itself: the same turn through `runAgent` on a scripted provider and through the bridge on the equivalent pi stream yields equal `tool_call`, `tool_result` and `assistant` events.
6. **The wind-downs are the loop's, in the loop's words.** The harness counts pi's turns for the guard and keeps the deadline; it steers the wrap-up warning once as the deadline nears (`wrapUpInstruction`, a `wrap_up` note), steers the session's notepad after every `compaction_end` that carried a summary (`compactionSteer`, [session-log.md](session-log.md) item 10: the notes as they stand, or that they are empty and how to keep them, and that `recall` reaches every earlier turn — never during the write-up, after a hard stop or while a re-attach catches up on history; a notepad read that fails there costs the steer its notes and never the run), and at the deadline or the turn guard it steers the loop's forced write-up instruction (`timeBudgetInstruction`, `turnGuardInstruction` with the pace) with every tool refused meanwhile through the gate (item 7) — the model reads the refusal's reason — and answers with the loop's label (`⚠️ _Hit the N-minute budget…_`, `⚠️ _Stopped after N model turns in M — that pace looks like a loop…_`) around the text pi settled on, or the loop's reason alone when none came; the write-up is bounded like the native finale (three minutes, then `abort`). A soft stop steers `SOFT_STOP_INSTRUCTION` the same way and answers `⏹ _Stopped early by an operator (soft stop)…_`; a hard stop sends `abort`, ends pi, closes the open tool spans as errors and answers the one-line `⛔` abort message with no write-up. The notes are the loop's kinds (`wrap_up`, `time_budget_exhausted`, `turn_budget_exhausted`, `stopped` with its mode), so the friction analyzer reads one vocabulary. A thread follow-up ([thread-admission.md](thread-admission.md) item 2) is steered into pi as the loop's follow-up prompt, its images along, recorded as the same `input` event and `follow_up` note, its ledger seq folded into the next step record. A follow-up that carries staged files ([execution.md](execution.md) item 20) is staged before its steer is sent — the same hook the native loop awaits, bound by the run loop only when the deployment configures a store: each file is copied into the store and pulled into the container's workspace over the run's executor, the `in` event recorded, and the steer's text ends with the attachments line, so pi never reads a name it cannot open; steers go out in the order their follow-ups were drained, one batch's staging awaited before the next is sent; a hook that throws still steers the person's words with a line saying the files could not be staged. Without a store the steer is sent as it always was. Auto-retry is turned off at start: a model call that fails ends the turn with pi's error, and the run fails with it — except while catching up after a restart (item 8). pi's own death before settling fails the run with the tail of its stderr; a prompt pi refuses fails it by reason.
7. **The extension and the gate: our tools registered into pi, every tool call decided in the bot.** Before pi starts, the harness writes its extension into the run's directory (`PI_EXTENSION_SOURCE`, plain JavaScript that imports nothing: pi's own loader runs it as written). At load the extension fetches the run's relayed tool definitions from the bot (`GET /harness/tools`) and registers each as a pi tool with the bot's JSON Schema, so `update_status`, `submit_pr_description`, `submit_handoff`, `submit_dispositions`, `attach_file`, `diff_digest`, `web_fetch`, the skill tools, the GitHub tools, the session tools `recall` and `notes` ([session-log.md](session-log.md) item 10) and any bridged MCP tool exist under their own names — the preset's toolset less the workspace tools pi has of its own (`relayedTools`) — and the composed system prompt gains one last note mapping the native workspace tool names onto pi's. A relayed tool's call posts to `POST /harness/tool` and runs in the bot with the run's own tool context — the same `RunnableTool`, the executor, the requester's GitHub gate, the dispatcher's recorders — under the `tool.<name>` span the bridge opened, its result in pi's content shape (images as image blocks, a document as its descriptor), a failure as an error result the model reads. Its `tool_call` hook asks `POST /harness/authorize` before every tool executes, pi's own included: a relayed tool is allowed (it runs under the bot's own gates); pi's own tools are judged by the coding preset's tool rules (`judgeToolCall`: `origin` alone as a remote; the run's branch as the one push target when the run was given one, else any branch but the protected ones — the base its pull request would target; never a merge or an approval; never the executor's credential store, an environment dump or a credential-named variable; paths inside the checkout; a tool outside the preset's reach); during a write-up every tool is refused. A refusal is a `tool_refused` note on the run and the reason the model reads. **The gate's coverage is checked from the stream.** The authorize route tells the harness the gate saw each call (`LiveHarness.gateSaw`, whatever the answer; the bridge keeps the ids), and pi's `tool_call` hook fires only after pi's own argument validation (pi-agent-core `prepareToolCall`), so a `tool_execution_end` the gate never saw is one of two things. A call pi answered by itself — its arguments failed the tool's schema, its tool is not on pi's list, or its assistant message was cut by the output token limit; pi announces it, ends it with an error result in its own words and never fires the hook (`piAnsweredWithoutRunning` reads those words) — never ran: it is a `harness_error` note naming pi's reason and refuses nothing. So did a call the extension blocked by itself, without a verdict — refused at the door by a 4xx before the route reached the gate, or a bot that did not answer for the wait — whose end carries the extension's own reason (`authorization refused at the door: …`, `authorization unavailable: …`): a `harness_error` note naming it. Every other such end is a tool that ran unvetted: a `harness_error` note names the call, pi is aborted and the run fails closed on it (`the gate was bypassed: pi ran <tool> (call <id>) without asking the bot`), its `run.agent` span ending in error. Calls that started while the harness was catching up on a re-attach (item 8) are not judged — the generation that died vetted them. The hook blocks at once on a refusal at the door — a 4xx: the bearer wrong, expired or revoked, the run not on the harness — since nothing later changes it, and keeps asking a bot it cannot reach or that is failing (a network error, a 5xx) every two seconds, blocking the call by itself after 90 seconds, naming why. The three routes are the model proxy's door: the run bearer names its run and verifies against the store before a byte of the body is read (no bearer or a malformed one 401, an unknown run 404, a wrong secret 401, an expired or revoked one 403), a run not on the harness is 404, the body is capped and must be JSON, and a bearer buys nothing else. The shim forwards the paths blind under the one route word `harness`. **A relayed call may outlive one request.** The conductor's `await_runs` waits for minutes and `send_to_run` may wait on a child's admission, so `POST /harness/tool` holds a request for at most the relay's window (`RELAY_POLL_WINDOW_MS`, 30 s) and then answers `202 { pending: true, toolCallId }`; the extension asks again with the same call id, at once after a window and no sooner than a second after a bot that answered early, until the answer lands. The bot runs each call once: the run's relayed calls are kept by call id beside its registration (`RelayedCalls`), a request for a call already running joins it, an answered call keeps its answer until the run ends so an ask retried after a lost response reads the same one, and a `spawn_run` asked twice spawns once. The window sits under every timeout on the path: the extension gives up on one request after 60 s of its own (`AbortSignal.timeout` beside pi's abort signal), pi's fetch on the headers after 300 s, and the bot's server bounds only a request's arrival (its header timeouts, 60 s and 300 s, which a body that arrives whole never nears), never a response. A bot the extension cannot reach or that fails mid-wait (a network error, a timed-out request, a 5xx) is asked again every two seconds and the call fails after 90 s naming the tool; a 4xx at the door fails it at once; pi's abort ends the asking. When the run ends, a relayed call still running is told to stop through its context's signal and the calls go with the registration. A tool that answers within the window (every relayed tool but the conductor's waits) is answered in one request exactly as before. The rules judged here are the same ones the spike previewed; the policy table's own tool-level rows remain the authorization spec's open gap.
8. **The mirror and the way back.** pi's finished messages become the ledger's transcript in the runner's vocabulary: an assistant turn (its text and tool calls; thinking dropped) is one step record with its calls in flight, written before the tools' results land, exactly as `runAgent`'s step report; the results since, and any steer's text, are the one user turn the next step carries; the prompt pi echoes is the seed already on the ledger and is not written twice. The row's state gains the harness facts (`harness: { pid, logOffset, root, sessionFile, bearerHash, container }`): the pid, the run's root (the directory pi was filed under, item 4) and the container's identity (`PiContainer.identity`, item 4) from the first save, right after pi starts; the offset refreshed at each turn's end; the session file once `get_state` names it. A bot restart hands a pi run off like a native one ([run-history.md](run-history.md) item 39 reads no harness): pi keeps running in the container, and the ledger's resume plan reaches the harness like any run's. Before any pid is probed, the container this run was handed names itself and the row's word is compared: a row naming ANOTHER container is "pi is elsewhere", never "pi is dead": that pid here is a stranger's, so it is neither probed nor ended, nothing of the orphan is removed here (its root is not here), the `resumed` note names the orphan by pid and container, and pi restarts on the mirrored transcript in this container; a row without a container, or a container that cannot name itself, is judged by the pid alone as before, and a re-attach records the container it found. (The dispatcher's resume never changes backend, [run-history.md](run-history.md) item 54, so the case is a container replaced under the same thread key: a recycled sandbox, a pid reused.) When the container's pi still lives (its pid answers) and the row names its root, the harness re-attaches at that root: it reads the log from the recorded offset and feeds the FIFO there, whatever root this build would file a fresh run under, so a build that moves the directory cannot lose the runs in flight across its deploy; it treats a model call that failed and pi's settling on it while the bot was away as facts of the death (a `harness_error` note, not a failure — and not a turn: the errored message writes no row and takes no index, so the log stays whole for the next reclaim; [session-log.md](session-log.md) item 2), and asks pi to continue on the same session — having adopted the bearer that pi holds onto this generation's proxy by the hash its facts carry (`bearerHash`; [model-proxy.md](model-proxy.md) item 2); a row whose facts carry no hash names a pi whose calls no proxy here can honour, so that pi is ended by pid and restarted on the mirrored transcript like one the row named no root for, the `resumed` note saying why. A live pi whose row names no root (written before the root was recorded) cannot be found: it is ended by its pid and the run goes on as after a death. When pi died, or no facts landed, the harness writes a session file rebuilt from the mirrored transcript (pi's version-3 format, one linear branch, every call in flight at the kill answered with the restart note and never re-run — its effects are the container's) and starts pi on `--session <file>` under this build's own root, removing a dead pi's recorded root when it is another. The session file's header names the directory this pi runs in as the container answers it for the root just made (`PiContainer.cwd`): the thread's checkout on an execution container, where the executor runs every command; the run's own root on the bot host (item 12). It is never a constant: pi exits at once on a stored working directory that does not exist where it runs, and the bot host has no checkout path and a new root in each generation. The seed session (item 9) names its directory the same way. Both paths say so in a `resumed` note, the ended pi's naming why. pi's compaction is a row of that transcript too ([session-log.md](session-log.md) item 6): a `compaction_end` whose result carries the summary hands the bridge the entry — the summary, `tokensBefore`, pi's `firstKeptEntryId` — and the mirror writes it as its own step, the results pending since the last assistant turn as the user turn they would have been and the entry as the row after them, nothing in flight; the rebuilt session file renders each such row as pi's `compaction` entry where it sat, so the restarted pi's window is the summary and the turns after it rather than the raw turns compacted again. A compaction that failed, was aborted or carried no summary writes no row — the `compacted` or `harness_error` note alone. A pi run handed off after its final answer (the mirror wrote the text-only turn as a step with nothing in flight) is a `finish` plan ([run-history.md](run-history.md) item 37): no pi starts, the pi the previous generation left is ended at the pid and root its facts name, only in the container the facts name (a leftover pi elsewhere is named in a `resumed` note, not ended here), and the post-steps run with the answer.
9. **The seed rule: the session is the thread so far, the prompt is the one new turn.** The dispatcher's seed is the thread's history first and the request as the last user turn (`buildMessages` in `src/core/dispatch/messages.ts`, merged into the alternation providers require, so the request is one user turn). `splitSeed` reads it in that shape: the last user turn is the prompt pi is sent (`promptOf`: its text parts joined, its images as pi's image blocks, a document named in the text since pi's prompt carries none), and every turn before it is the session pi starts on — written into the container as a session file by the same `piSessionFile` the way back (item 8) uses, so an earlier assistant turn's tool calls and their results are pi's own `toolCall` blocks and `toolResult` entries, and an earlier document is named in a text block — and pi starts on `--session <file>` as a resume does. A seed of one turn — a fresh mention, a coordinator's unit thread whose lead is the bot's — writes no session file and starts pi on the bare session directory, byte for byte as before the rule; the mirror's index still counts from the whole seed, already on the ledger, and no `resumed` note is said. Without the rule a run in a thread with earlier user turns prompted pi with the thread's oldest turn and never showed it the request. The seed the dispatcher hands over is no longer always the thread's history: a follow-up on a pi preset whose thread has a session log of that agent starts from the log's tail within the seed budget, the lines a person wrote since the previous run ended and the request ([session-log.md](session-log.md) item 9) — the same shape, so `splitSeed` reads it unchanged: the request is still the last user turn and everything before it the session file, tool calls and results from the log included.

10. **The review preset on the harness: the read identity's allowlist, framing and gate, and a verdict that reaches GitHub exactly as the native loop's does.** `harness: { review: pi }` moves the review preset (`effectiveHarness` is already per preset; the block names any preset the registry knows). A review runs where it runs today — the resident's read-only worktree attached by identity `read`, no write token in the tree, the mirror as its origin — and the harness reads that identity once (`AgentDef.identity`) for three things. **The allowlist**: pi's `--tools` carries pi's own tools less `edit` and `write` for a read identity (`piBuiltinToolsFor`: `read`, `bash`, `grep`, `find`, `ls`) plus the relayed ones — the `readonly` toolset less the workspace tools: `update_status`, `submit_verdict`, `web_fetch`, `diff_digest`, the skill tools, the GitHub reads — so pi never has a write tool to call, before the gate ever sees a call. **The framing**: the composed system prompt is the dispatcher's — the registry's review prompt (the resident variant, the REVIEW TARGET block, the contract, the skills) as `makeSystemComposer` renders it, never a copy — and the harness note last names the five read tools, says the run has no `edit` and no `write` and is read-only, and maps `read_file` onto `read` alone. **The gate**: the rules the gate judges pi's own tools by carry the run's identity, folded in by the harness beside the thread's branch facts, and the reach is the identity's (`reachFor`): a write run's is the coding preset's; a run without an identity's is empty (item 12); a read run's holds no `write-files`, `github-write` or `pr` bundle, so `edit`, `write` and a `submit_pr_description` are `outside-profile`; its shell never pushes — `git push` in any form is refused `read-only` — and never writes to GitHub by CLI or API (`gh pr comment|edit|…`, `gh api` with a write method or a field, curl at `api.github.com` with a write method or a body), while every read of both stays allowed; a merge or an approval is refused before that as it is for every run. Each refusal is a `tool_refused` note. **The verdict path**: `submit_verdict` is a relayed tool, so pi's call is the native tool's own call (`tool.run(input, ctx)` in the bot with the run's tool context, `onVerdict` included): the verdict the run holds, the acknowledgement the model reads and the parser's refusal of a malformed one are the native loop's, and everything after the loop is the same code — the reviewed-head settle, `runReviewPostStep` behind the reviewed-head guard, the `LGTM:` first line built by code for an approve and `Changes requested:` otherwise, a comment and never an approval or a merge, the `review_posted` event or the `review_not_posted` note, the `reviewPost` fact on the record. Without the block, or with `harness: { review: native }`, a review is the native loop byte for byte and pi never starts. **Not yet on the harness**: a substantive head move mid-review (item 12 of [agent-review.md](agent-review.md)) still runs its one more turn through `runAgent` — the harness has returned and ended pi by the time the settle classifies the move — so on a deployment with `review: pi` that turn alone is native, with the bot's key and the native `bash`/`read_file`; making it a `prompt` on the same pi session, as record 0032 says, needs the session to outlive the harness's return and is the next pull request of this unit, with the deletions of the native read-only path.
12. **A preset without a workspace runs pi as a child of the bot.** The general, research and conductor presets run on machine class `none`: no container is provisioned and the run's executor is the null one, so there is nothing to exec a container command through. `harness: { general: pi }` (or `research`, or `conductor`) moves such a preset onto the harness all the same. The run loop reads the run's machine class once and, for `none`, drives pi through the seam's third implementation, `BotHostPiContainer` (`piContainerFor` picks it; every other class keeps `ExecPiContainer` over the run's executor). Its operations are `node:fs` and `node:child_process` on the bot host: the run's root made by the container itself (`makeRoot`: `mkdtemp` beside the predictable root, on its name as the prefix, exclusive and 700 in one call, with a suffix nobody can guess, recorded on the row's facts by item 8 so the way back finds it), its files created 600 and never replaced (a path already present is refused, never followed or truncated), pi spawned in that directory as its own group leader with `--mode rpc` and the same arguments, its stdin a pipe from the bot, its stdout through the same `message_update` filter into the same log the transport polls, its stderr into its own file, the pid recorded; a kill is TERM to the group, a second's grace, then KILL while the leader still stands (once it has gone the group id could name a reused pid, so nothing more is sent); `remove` takes the root down as one tree. The two files are the bot host's disk: a write that fails there is handled, never an unhandled stream error in the bot process, and it ends pi, so the harness finds it dead and fails the run with the error log's tail rather than waiting on a log nothing lands in; a pi spawned but not tracked (the pid file could not be written) is ended before `start` fails by name. The child's environment is PATH, HOME and what the launch names (the bearer, the URL, the run id, pi's config directory and the offline switches), and never another variable of the bot process, which holds every secret the deployment has. **The bot is what pi reaches**: `SWITCHBOARD_HARNESS_URL` and models.json's provider point at this process's own HTTP server over loopback (`http://127.0.0.1:<PORT>`, `HarnessDeps.loopbackUrl`), where the model proxy and the three harness routes already listen, and never at `PUBLIC_BASE_URL` through the shim; a process without `PORT` fails such a run by name, as one without `PUBLIC_BASE_URL` fails a container preset's. **No shell and no files**: a run whose identity is `none` holds none of pi's own tools: `piBuiltinToolsFor` gives it nothing, so `--tools` is the relayed tools alone and pi never has a `read`, `bash`, `grep`, `find`, `ls`, `edit` or `write` to call; its reach for pi's own tools is empty (`reachFor`: `NONE_REACH`), so a built-in tool such a pi asks the gate for all the same (a pi that grew a tool, a stale allowlist) is refused by name (`<tool> is the <bundle> bundle: a run without a workspace (identity none) has none of pi's own tools`) with a `tool_refused` note, before any rule about what the call does is consulted; the harness note in SYSTEM.md says the run has no workspace and none of pi's own tools, names the relayed ones and maps no native name onto one. Every tool the run has is a relayed one (for general, the `assistant` toolset's `web_fetch`, `update_status`, the GitHub reads and the issue writes), running in the bot as the requesting user under the bot's own gates, as on every run (item 7). The bridge, the mirror, the wind-downs and the record are unchanged: a general run on pi replays like a native one. **A restart**: a bot-host pi is a child of one bot generation, and a fresh generation cannot reach its predecessor's child (its stdin was that process's pipe), so `alive` answers no for a pid this container did not start (and the bot host names no container, so nothing is judged by identity there) and the ledger's resume restarts pi on the mirrored transcript (item 8), the path a container's pi that died with its container takes; the session it restarts on names the root this generation made as its working directory (`cwd` answers the run's own root, where `start` spawns pi), never the checkout the run loop names, which this host does not have and pi would refuse; pi in RPC mode exits on its stdin's end of file, so a bot death takes its pi with it. The bot image carries pi at the pin for this (item 3). **Research and the conductor take the same path** under `harness: { research: pi }` and `harness: { conductor: pi }`: the container asked for by the `none` class, the loopback URL, none of pi's own tools, the preset's toolset relayed and nothing else: for research the `web` toolset's `web_fetch`, `web_search`, `update_status` and the GitHub reads, each the native tool run in the bot under its own gates (a `web_fetch` of an internal address is refused by the tool's URL guard without a fetch, and that refusal is what pi reads); for the conductor the `conductor` toolset's `spawn_run`, `send_to_run`, `await_runs`, `list_runs` and `get_run_status` beside `web_fetch`, `update_status` and the GitHub reads, its waits carried by the relay's pending answer (item 7) and its spawn seeding the child from the run's session log ([agent-conductor.md](agent-conductor.md) item 3). Nothing changes for a deployment that sets no key: the registry's general, research and conductor declare no harness, so they run the native loop byte for byte, and a block moving another preset leaves them there.
11. **A verdict names its head because the served definition requires it; the relay neither refuses nor supplies one.** The `submit_verdict` a review's pi is served is the native tool's definition field for field — the description that says to run `git rev-parse HEAD` in the checkout reviewed and pass its output, the schema whose `required` names `head` beside `verdict` and `summary` — and pi validates every call against the schema it was served before the extension runs it, so a verdict naming no head is a schema error the model reads and answers, and never reaches the relay. The relay adds nothing to a verdict and removes nothing from it: a relayed call is the native tool's own (item 10), so a verdict without a head is accepted exactly as the native call accepts it — the run's `onVerdict` receives what the parser yields, head absent — and the reviewed-head guard decides afterwards. The relay never stamps the run's pinned head into a verdict: the settle reads the worktree's own `HEAD` first (`observed`), and the model's `head` is the guard's fallback for a workspace whose `HEAD` could not be read — a head written from the run's expectation would pass exactly the check that exists to catch a review of another commit. A driver with no bot that serves an extension of its own registers the same two definitions verbatim ([load-harness.md](load-harness.md) item 14); one that serves a `submit_verdict` without `head` gets verdicts naming none, since a model follows the schema it is given.

# The pi harness: a preset's runs driven by pi in the run's own container, on the run's own record

[Record 0032](../../decisions/0032-pi-is-the-harness-the-native-loop-retires.md) decided that pi (`@earendil-works/pi-coding-agent`) replaces the native turn loop one preset at a time; the series is complete, and the loop, both provider adapters and the native tool table are deleted (the source scan in `src/core/harness/oneHarness.test.ts` keeps them gone, item 1). This is the one harness every run is driven by: pi in `--mode rpc` inside the run's execution container, started as the thread's user (or, for a preset without a workspace, as a child of the bot itself, item 12) with the run's model-proxy bearer as its only key, driven by the bot over pi's line protocol, every event it emits bridged onto the run's own stream in the vocabulary the native loop wrote, our tools and the coding preset's tool rules as its extension, the transcript mirrored onto the run ledger so a bot restart continues the run, the run's budgets and wind-downs kept by the harness itself (items 6 and 15). A deployment has nothing to set: the `harness:` block that moved the presets one at a time is a retired key (item 1).

## Behavior

1. **One harness; the `harness:` key is retired.** Every preset's runs are driven by pi — there is no other loop in the tree, and `AgentDef` has no harness field. The deployment's top-level `harness:` block, which moved the presets onto pi one at a time during record 0032's series, selects nothing now and is validated as a retired key at load: a mapping of registered presets to `pi` loads unchanged, so a `config.yaml` written during the series still starts; `native` names a loop that no longer exists and fails the load by name (`harness.<preset> must be pi — the native loop is deleted and every preset runs on pi; remove the harness block`), as does any other value, a preset the registry does not know, or a non-mapping (`harness must be a mapping of preset to pi (a retired key; remove it)`) — a setting that read as "this preset runs the native loop" while nothing did would be the worst kind of quiet. The source scan (`src/core/harness/oneHarness.test.ts`) fails the build the day any of it comes back: `src/runner.ts`, `src/providers/`, `src/tools/workspace.ts` or `src/core/harness/select.ts` present; a module under `src/` importing one of them or calling `runAgent`, `ProviderRegistry`, an adapter, `ExecHealthTracker` or `effectiveHarness` by name; a `runAgent` or `effectiveHarness` reference or a harness comparison in the run stage; a preset declaring a harness or the registry exporting a table of them; a workspace tool of pi's own in the toolset table; `run-loop.md` back in the specs index. A preset with a workspace runs pi in the run's container; a preset without one runs it as a child of the bot (item 12).
2. **The run stage hands every run to the harness, and everything around it is shared.** `runLoop` hands the run to `runPiHarnessOpen` (item 14's open form) with the tool context, the event and progress sinks, the control, the inbox and the ledger step hook, the `run.agent` parent span and the resume plan — and the rules the gate (item 7) judges pi's own tools by, which follow the thread the way the post-step's pull-request target does: when the thread came from a pull request or a coordinator's spawn, the thread is bound at the run's own branch (a fix round repushes the PR's head; a unit child is dispatched at its unit branch), so that branch is the one push target and the base its pull request targets is protected; otherwise the binding is that base, protected, and the run pushes a branch of its own making. Admission, resolution, the gates, the workspace attach, the bearer mint and the prompt before it, and the reviewed-head settle, the workspace observation, the description turn, the coding PR post-step, the answer's publish, the finish and the release after it are one code path for every preset — the settle's re-review and the description turn reaching their one more model turn through item 14's seam: the post-step sees the same branch and pull-request facts because it reads them off the same stream (`trackPushedBranch` over the bridge's `tool_call.command`) and the same workspace. No run starts without pi: a process without the harness deps, without `PUBLIC_BASE_URL` (the container reaches the proxy and the routes through it; for a preset without a workspace the missing name is `PORT`, item 12) or without a minted bearer fails the run naming exactly what is missing. The CLI's one-shot `ask` is such a process: it opens its own loopback HTTP server for the length of the run — the model proxy and the three harness routes, nothing else (`askLoopbackServer`, `src/cli.ts`) — so the run's pi reaches it over `127.0.0.1` whether it runs as a child of the process or in the local workspace, and closes it once the run's record has settled.
3. **pi lives in every image, pinned and proven.** Each execution image installs `@earendil-works/pi-coding-agent` globally with its own Node 24 at one exact version, read by the pin parser like pnpm's and playwright's; the layer proves at build time that the `pi` on PATH answers the pin and that its help names RPC mode, and the resident image proves it once more as `worker1`, the way a run's pi is started. The bot image installs the same layer in its runtime stage, as root before the switch to the bot's user, on the Node it already builds from, for the presets without a workspace, whose pi is a child of the bot (item 12), and the pin is held equal across the three images and the bot's own `@earendil-works/pi-ai` dependency (item 13), so pi's library in the process and the pi in the images move together. Outside the images pi comes from the process's PATH — the CLI's `ask` on a developer's machine, the test that spawns it (`src/cli.ask.test.ts`) on a CI runner — so `@earendil-works/pi-coding-agent` is a devDependency at the same exact pin, and `npm test`, `npm run` and `npx` put its `node_modules/.bin/pi` first; a machine without npm's PATH needs pi installed at the pin. Nothing in an image starts pi; the harness does, once per run.
4. **The process: pi as the thread's user, the bearer as its only key, through the container seam.** A run's pi has one directory of its own outside the checkout, directly under `/tmp`: `/tmp/switchboard-pi-<runId>` (`piRunPaths`; the same layout under any root is `piRunPathsAt`, how a re-attach reaches the root a row recorded, item 8), made at mode 700 by whichever OS user runs the run's commands (the umask before the mkdir in every script that creates it: the `mkdtemp` shape). `/tmp` is sticky (mode 1777), so every run's root is a sibling under a parent any user may create in and only the owner may remove from, and nothing about the root depends on knowing which user that is. There is no parent between `/tmp` and the root in any case, shared or per user: the resident runs each thread's commands as its own pool user and `mkdir -p` gives a parent it creates to its caller, so a parent shared by every run would belong to whichever user ran first and every other user's run would fail at its own mkdir before a model turn, a shared parent made 1777 would not repair a container where the owned one already stands, and a parent per user would only move that ownership to the runs that know their user. The directory holds pi's config directory with `settings.json` that never trusts the checkout — and carries the deployment's compaction thresholds when the config's `pi.compaction` block sets them (`reserveTokens`, `keepRecentTokens`, pi's own names in tokens: pi compacts when the context passes the model's window less the reserve and keeps about the recent tokens named; unset, pi's defaults stand and the file is byte-identical to before the block existed; a receipt or a test of the compaction path sets a reserve near the window so a short run compacts, production leaves it unset; positive integers only, any other shape or key refused at load by name) — `models.json`, `SYSTEM.md` and `sessions/`, the extension, the FIFO, the log, the error log and the pid file. `models.json` names one provider — the bot's model proxy on the wire shape the run's provider speaks (`anthropic-messages` at the bot's base, `openai-completions` under `<base>/v1`) — with `apiKey: "$SWITCHBOARD_RUN_BEARER"`, a zero rate card, because pi's own cost is never what a page shows: the proxy meters, and — on the Anthropic shape — the thinking payload the model takes as pi's `compat.forceAdaptiveThinking` (`takesAdaptiveThinking`): a Claude model from the 4.6 generation on takes adaptive thinking (`thinking.type: "adaptive"` plus `output_config.effort`) and the 5 family refuses the legacy budget (`thinking.type: "enabled"` plus `budget_tokens`) with a 400; a model before 4.6 refuses adaptive and keeps the budget. pi's built-in Anthropic catalog says this per model and sends the budget for a model it does not know; the proxy's model is not in that catalog, so the harness says it — the generation is the id's first version number (`claude-fable-5` is 5, `claude-sonnet-4-5-20250929` 4.5: a date is never a minor), and an id with none is taken for the current generation. The completions shape carries no such switch. pi starts detached (`setsid -f`) with `--mode rpc`, every discovery off (`--no-extensions --no-skills --no-prompt-templates --no-themes`), the extension by explicit path, `--tools` allowlisting pi's own workspace tools (`read`, `bash`, `edit`, `write`, `grep`, `find`, `ls`) plus the relayed ones, the proxy's provider and the run's model with the effort tier as pi's thinking level (the five tiers are pi's levels by name; no tier leaves pi's default), and a session directory — or `--session <file>` when pi has turns to start from: the thread's earlier turns (item 9) or a resume's mirrored transcript (item 8). Its stdin is a FIFO the wrapper holds open read-write on a spare descriptor, so pi never sees an end of file while it lives; its stdout goes through a line-buffered filter that drops `message_update` deltas into a log the harness polls; its stderr into its own file; the wrapper's pid, the group leader, is recorded. **The environment is the channel for the bearer**: the run bearer, the bot's URL, the run id, `PI_CODING_AGENT_DIR` and pi's offline switches ride `ExecOptions.env` — the exec's own env option on every executor (the local child gets the public environment plus these and never the host's secrets; the resident and the sandbox send them as the body's `env`, the resident Worker reading the map through the one validated reader and handing it to the exec's env option under its own injected variables) — never a command line, never a file, never a model key, Slack token or GitHub App credential. Every operation is one command over the run's own `Executor` as the thread's user — a file written in `printf` chunks under `umask 077`, a line fed to the FIFO (a long one through a file), the log read from a byte offset as one-line base64 so the bytes survive the text channel exactly, `kill -0` for liveness, the container's identity read (`identity`: the kernel's boot id from `/proc/sys/kernel/random/boot_id`, one word or nothing; a container that cannot name itself judges nothing by it), the group then the leader killed, the run's directory removed as one tree — and a command the executor reports failed is a named `PiContainerError`, never a silent empty. Once the run is over — settled, stopped or failed — the harness ends pi and then removes the run's directory, best-effort like the kill: nothing reads its log, session or FIFO again (a later run in the thread seeds from the record, item 9; a resume that finds pi alive, item 8, belongs to a generation whose run never ended). `makeRoot` is the seam's answer to where a fresh run's files go: the exec container answers this predictable root, which its scripts make; the bot host makes a root of its own (item 12); the harness files nothing before it has the answer and records it on the row (item 8), so the way back never has to guess it. The in-memory `FakePiContainer` is the seam's second implementation (it answers the predictable root too); the bot host's `BotHostPiContainer` (item 12) the third.
5. **The bridge: pi's events become the run's, in the vocabulary the native loop wrote, and the proxy meters the turns.** Every event kind pi's protocol documents has a disposition (`PI_EVENT_DISPOSITION`, held to the same set of kinds as the spike's home table): `tool_execution_start` opens a `tool.<name>` span under `run.agent` and announces the `tool_call` inside it (the same one-line summary the loop writes, bash's full command beside it, capped and redacted); `tool_execution_end` emits the `tool_result` with the loop's `ok` — pi's `isError`, or, for a relayed tool that declares `failsInText` (`RunnableTool`; the harness hands the bridge the declaring names as `textFailing`), a result text opening `error:` read as the deleted native runner read it (`toolTextFailed`, [run-visibility.md](run-visibility.md) item 5), while a relay of someone else's bytes (`read_file`, `web_fetch`, the skill and GitHub reads) is never judged by its content — bash's `exitCode` read from pi's `Command exited with code N` trailer (or the executors' `exit N:` prefix), the summary and the capped output, and ends the span with `callId`, `ok`, `exitCode`; the model's text beside its tool calls is `assistant`, a text-only turn is the answer candidate, a turn whose every call is `update_status` is bookkeeping — not counted against the guard, its text held until the next turn decides (the guard, item 15, is not spent by it); `💭 thought for …` is said at each assistant message's end; `compaction_end` is a `compacted` note with the token counts and any summarization retries folded in; `extension_error`, a dialog request (answered `cancelled`, since no one is watching), an event kind this build does not know and a kind the harness turns off at start (`auto_retry_*`, `bash_execution_update`) are `harness_error` notes naming what happened; `message_update` and `tool_execution_update` are folded into the final records; `response`, the agent and turn boundaries and `queue_update` are structure. The model turns are not the bridge's: every call pi makes goes through the model proxy, which spends the run's turn guard and closes one `model.turn` span with the runner's attrs as the proxy knows them ([model-proxy.md](model-proxy.md) item 6: `model`, `stopReason`, the four token counts, `ttftMs`) and never the stream timings only the deleted native runner's observer wrote (`blocks`, `thinkingMs`, `textMs`; [live-view.md](live-view.md) item 15), so a record from before the deletion is told from one since by their presence — and the harness re-parents the run's grant from the request root to its `run.agent` (`RunBearerStore.reparent`), so a proxied turn lands where the loop's would. The vocabulary is held as a literal: the `tool_call`, `tool_result` and `assistant` events the native loop emitted for one turn — compared equal against a scripted provider while both loops stood — are what the bridge must still emit for the equivalent pi stream (`src/core/harness/pi/bridge.test.ts`). **What the native loop did around a turn that pi does its own way, and what went with it.** pi runs a turn's tool calls as it chooses (the loop ran consecutive side-effect-free calls concurrently, mutating ones alone in order); pi's own adapters place the prompt-cache markers and replay thinking (the loop's Anthropic adapter set four `cache_control` breakpoints, a per-agent TTL and clamped `effort` per model — `AgentDef.cacheTtl` stays on the def for the router's and reflection's requests and is not read by the harness); the loop's fail-fast on a wedged sandbox (`ExecHealthTracker`: two consecutive `ExecInfraError`s with no success between ended the run with a diagnostic) and its `fleet_busy` retry text are gone — the harness's container operations and the relayed tools read an `ExecInfraError` as the failure of that one operation, named, a `PiContainerError` when it is pi's own file or process, and the container is provisioned before pi starts; its stuck-loop guard is the gap below, and its rolling-container settlement is item 16's floor — the run ends for a restart from its request instead of going on. The note kinds `sandbox_dead`, `fleet_busy` and `stuck_loop` stay on `RunNoteKind` so a record from before the deletion still reads, and no loop writes them; `sandbox_restarted` is the harness's own again, said of a container replaced under a live run (item 16).
6. **The wind-downs, in the loop's words** (`src/core/harness/pi/windDown.ts`)**.** The harness counts pi's turns for the guard and keeps the deadline (the budgets, item 15); it steers the wrap-up warning once as the deadline nears (`wrapUpInstruction`, a `wrap_up` note), steers the session's notepad after every `compaction_end` that carried a summary (`compactionSteer`, [session-log.md](session-log.md) item 10: the notes as they stand, or that they are empty and how to keep them, and that `recall` reaches every earlier turn — never during the write-up, after a hard stop or while a re-attach catches up on history; a notepad read that fails there costs the steer its notes and never the run), and at the deadline or the turn guard it steers the loop's forced write-up instruction (`timeBudgetInstruction`, `turnGuardInstruction` with the pace) with every tool refused meanwhile through the gate (item 7) — the model reads the refusal's reason — and answers with the loop's label (`⚠️ _Hit the N-minute budget…_`, `⚠️ _Stopped after N model turns in M — that pace looks like a loop…_`) around the text pi settled on, or the loop's reason alone when none came; the write-up is bounded (`FINALE_TIMEOUT_MS`, three minutes, then `abort`). A soft stop steers `SOFT_STOP_INSTRUCTION` the same way and answers `⏹ _Stopped early by an operator (soft stop)…_`; a hard stop sends `abort`, ends pi, closes the open tool spans as errors and answers the one-line `⛔` abort message with no write-up; past the loop the run stage releases the workspace with `always` whatever the preset (a resident `/detach force`), runs no memory reflection and posts no review — there are no findings to distill or post ([live-view.md](live-view.md) item 10 has the route). The notes are the loop's kinds (`wrap_up`, `time_budget_exhausted`, `turn_budget_exhausted`, `stopped` with its mode), so the friction analyzer reads one vocabulary. A thread follow-up ([thread-admission.md](thread-admission.md) item 2) is steered into pi as the loop's follow-up prompt, its images along, recorded as the same `input` event and `follow_up` note, its ledger seq folded into the next step record. A follow-up that carries staged files ([execution.md](execution.md) item 20) is staged before its steer is sent — the hook the run loop binds only when the deployment configures a store: each file is copied into the store and pulled into the container's workspace over the run's executor, the `in` event recorded, and the steer's text ends with the attachments line, so pi never reads a name it cannot open; steers go out in the order their follow-ups were drained, one batch's staging awaited before the next is sent; a hook that throws still steers the person's words with a line saying the files could not be staged. Without a store the steer is sent as it always was. Auto-retry is turned off at start: a model call that fails ends the turn with pi's error, and the run fails with it — except while catching up after a restart (item 8). A call the provider refused under its usage policy is the failure by name: pi maps the wire's refusal to an error and keeps the wire's own stop reason beside it (`rawStopReason` — the Messages API's `refusal` and `sensitive`, the Chat Completions `content_filter`; `POLICY_REFUSAL_STOP_REASONS`, a closed set of words, the explanation's text never read), the bridge says so beside the provider error (`policyRefusal`), and the harness never retries it (the same words are refused again), publishes a `policy_refusal` note carrying the provider's explanation for the run page, and ends the run with `ModelPolicyRefusedError` — whose message is the one sentence the thread reads, `⚠️ the model refused this request under its usage policy — rephrase it and the thread continues`, with the run link and none of the provider's words — so the record says `failure: policy_refusal` ([run-history.md](run-history.md) item 57) and the session's next seed leaves the refused request out ([session-log.md](session-log.md) item 9); a follow-up turn on the session (item 14) refused the same way ends the same way. pi's own death before settling fails the run with the tail of its stderr; a prompt pi refuses fails it by reason.
7. **The extension and the gate: our tools registered into pi, every tool call decided in the bot.** Before pi starts, the harness writes its extension into the run's directory (`PI_EXTENSION_SOURCE`, plain JavaScript that imports nothing: pi's own loader runs it as written). At load the extension fetches the run's relayed tool definitions from the bot (`GET /harness/tools`) and registers each as a pi tool with the bot's JSON Schema, so `update_status`, `submit_pr_description`, `submit_handoff`, `submit_dispositions`, `attach_file`, `diff_digest`, `web_fetch`, the skill tools, the GitHub tools, the session tools `recall` and `notes` ([session-log.md](session-log.md) item 10) and any bridged MCP tool exist under their own names — the preset's toolset less the workspace tools pi has of its own (`relayedTools`) — and the composed system prompt gains one last note mapping the native workspace tool names onto pi's. A relayed tool's call posts to `POST /harness/tool` and runs in the bot with the run's own tool context — the same `RunnableTool`, the executor, the requester's GitHub gate, the dispatcher's recorders — under the `tool.<name>` span the bridge opened, its result in pi's content shape (images as image blocks, a document as its descriptor), a failure as an error result the model reads. Its `tool_call` hook asks `POST /harness/authorize` before every tool executes, pi's own included: a relayed tool is allowed (it runs under the bot's own gates); pi's own tools are judged by the coding preset's tool rules (`judgeToolCall`: `origin` alone as a remote; the run's branch as the one push target when the run was given one, else any branch but the protected ones — the base its pull request would target; never a merge or an approval; never the executor's credential store, an environment dump or a credential-named variable; paths inside the checkout; a tool outside the preset's reach); during a write-up every tool is refused. A refusal is a `tool_refused` note on the run and the reason the model reads. **The gate's coverage is checked from the stream.** The authorize route tells the harness the gate saw each call (`LiveHarness.gateSaw`, whatever the answer; the bridge keeps the ids), and pi's `tool_call` hook fires only after pi's own argument validation (pi-agent-core `prepareToolCall`), so a `tool_execution_end` the gate never saw is one of two things. A call pi answered by itself — its arguments failed the tool's schema, its tool is not on pi's list, or its assistant message was cut by the output token limit; pi announces it, ends it with an error result in its own words and never fires the hook (`piAnsweredWithoutRunning` reads those words) — never ran: it is a `harness_error` note naming pi's reason and refuses nothing. So did a call the extension blocked by itself, without a verdict — refused at the door by a 4xx before the route reached the gate, or a bot that did not answer for the wait — whose end carries the extension's own reason (`authorization refused at the door: …`, `authorization unavailable: …`): a `harness_error` note naming it. Every other such end is a tool that ran unvetted: a `harness_error` note names the call, pi is aborted and the run fails closed on it (`the gate was bypassed: pi ran <tool> (call <id>) without asking the bot`), its `run.agent` span ending in error. Calls that started while the harness was catching up on a re-attach (item 8) are not judged — the generation that died vetted them. The hook blocks at once on a refusal at the door — a 4xx: the bearer wrong, expired or revoked, the run not on the harness — since nothing later changes it, and keeps asking a bot it cannot reach or that is failing (a network error, a 5xx) every two seconds, blocking the call by itself after 90 seconds, naming why. The three routes are the model proxy's door: the run bearer names its run and verifies against the store before a byte of the body is read (no bearer or a malformed one 401, an unknown run 404, a wrong secret 401, an expired or revoked one 403), a run not on the harness is 404, the body is capped and must be JSON, and a bearer buys nothing else. The shim forwards the paths blind under the one route word `harness`. **A relayed call may outlive one request.** The conductor's `await_runs` waits for minutes and `send_to_run` may wait on a child's admission, so `POST /harness/tool` holds a request for at most the relay's window (`RELAY_POLL_WINDOW_MS`, 30 s) and then answers `202 { pending: true, toolCallId }`; the extension asks again with the same call id, at once after a window and no sooner than a second after a bot that answered early, until the answer lands. The bot runs each call once: the run's relayed calls are kept by call id beside its registration (`RelayedCalls`), a request for a call already running joins it, an answered call keeps its answer until the run ends so an ask retried after a lost response reads the same one, and a `spawn_run` asked twice spawns once. A call the run's row says was in flight when the previous bot generation died is settled on the registration, before anything is awaited (`RelayedCalls.settle`, item 8): the re-attached pi's extension, whose first request died with that generation, asks again with the same call id and reads the restart note (`isError`, the words the rebuilt session file carries for the same call) — the tool never runs a second time; a call the row does not know runs as before, and a call already running keeps its own answer. The window sits under every timeout on the path: the extension gives up on one request after 60 s of its own (`AbortSignal.timeout` beside pi's abort signal), pi's fetch on the headers after 300 s, and the bot's server bounds only a request's arrival (its header timeouts, 60 s and 300 s, which a body that arrives whole never nears), never a response. A bot the extension cannot reach or that fails mid-wait (a network error, a timed-out request, a 5xx) is asked again every two seconds and the call fails after 90 s without an answer, counted from the bot's last one, naming the tool; a 4xx at the door fails it at once; pi's abort ends the asking. When the run ends, a relayed call still running is told to stop through its context's signal and the calls go with the registration. A tool that answers within the window (every relayed tool but the conductor's waits) is answered in one request exactly as before. **The door during a generation's boot.** The routes answer from the moment the bot's HTTP server listens, which comes before the ledger reclaim, the Slack handshake and the resumes (`src/index.ts`), and a run is on the registry only once its resume has reached the harness (`HarnessRegistry.register` in `runPiHarnessOpen`, after the resume's admission, workspace re-attach and bearer mint), its previous bearer adopted right after (item 8). A request from a surviving pi that lands in between names a run this process does not know yet — `unknown_run` before this generation minted the run's entry, `unknown_bearer` between the mint and the adoption, `run_not_on_harness` before the registration — and the extension takes a 4xx as final, so the door does not answer one. It reads this generation's takeover of the ledger's live runs (`LedgerTakeover`, `src/core/runLedger/takeover.ts`: fed by every reclaim outcome, at boot and on each sweep pass, and by the launcher when a resume's dispatch is over or the run was closed instead). A request with one of those three refusals while the boot reclaim has not yet listed the ledger is **held** — the response waits for the listing, up to `DOOR_HOLD_MS` (`HANDOFF_BUDGET_MS` + 4 s = 10 s: the budget the previous generation had to hand its runs off, as long again to take them, under the extension's 60 s on one request) — and judged again once it lands. Then a run the ledger lists as live and not yet resumed here (handed to the launcher and not yet ended, or held by another generation until the sweep takes it), or any such bearer while the listing has still not arrived, is answered **retryably**: `POST /harness/tool` gets `202 { pending: true, reason }` — a pending answer, which the relay asks again with the same call id and which refreshes its 90 s wait, so a resume longer than the wait still lands — and the other two routes `503 { error: reason }` with `Retry-After: 2` (the hook's own cadence; its 90 s from the first ask stand), `reason` being `run_resuming` or `reclaim_pending`; the body is never read for a held answer, as for a refusal, and the log line says `held (<reason>) run=<id>`. The re-ask then lands on the re-registered run and reads the answer settled for it (item 8). A bearer no resume can make good — malformed, expired, revoked — is final whatever the boot is doing; once the reclaim has listed the ledger a bearer no live row names is `401`/`404` as before, and a run's resume ending (its dispatch settled, or the launcher closed it) returns the store's verdict on its bearer. The rules judged here are the same ones the spike previewed; the policy table's own tool-level rows remain the authorization spec's open gap.
8. **The mirror and the way back.** pi's finished messages become the ledger's transcript in the runner's vocabulary: an assistant turn (its text and tool calls; thinking dropped) is one step record with its calls in flight, written before the tools' results land, exactly as `runAgent`'s step report; the results since, and any steer's text, are the one user turn the next step carries; the prompt pi echoes on a fresh start is the seed already on the ledger and is not written twice. The row's state gains the harness facts (`harness: { pid, logOffset, root, sessionFile, bearerHash, container }`): the pid, the run's root (the directory pi was filed under, item 4) and the container's identity (`PiContainer.identity`, item 4) from the first save, right after pi starts; the session file once `get_state` names it; and the log offset, the byte the next generation reads pi's log from. **What the saved offset names**: the boundary after the last record whose effect the ledger holds — the assistant turn the mirror wrote as a step, the compaction it wrote as a row — saved right after each such write. Never where the transport's chunked reads had reached (the transport keeps the two apart: `offset` is the read position, `consumedOffset` the boundary after the record last handed out), and never at a turn's end: pi writes a call's `toolResult` before the turn's `turn_end`, so an offset taken there already sits past a result the mirror still holds in memory for the next step's user turn, and a bot that died during the model call after it took the result with it — the ledger then showed an assistant turn with a call followed by the next assistant turn, no user turn between them. Whatever pi wrote after the saved boundary died with the bot's memory and is read again. A bot restart hands a pi run off like a native one ([run-history.md](run-history.md) item 39 reads no harness): pi keeps running in the container, and the ledger's resume plan reaches the harness like any run's. Before any pid is probed, the container this run was handed names itself and the row's word is compared: a row naming ANOTHER container is "pi is elsewhere", never "pi is dead": that pid here is a stranger's, so it is neither probed nor ended, nothing of the orphan is removed here (its root is not here), the `resumed` note names the orphan by pid and container, and pi restarts on the mirrored transcript in this container; a row without a container, or a container that cannot name itself, is judged by the pid alone as before, and a re-attach records the container it found. (The dispatcher's resume never changes backend, [run-history.md](run-history.md) item 54, so the case is a container replaced under the same thread key: a recycled sandbox, a pid reused.) When the container's pi still lives (its pid answers) and the row names its root, the harness re-attaches at that root: it reads the log again from the recorded offset and feeds the FIFO there, whatever root this build would file a fresh run under, so a build that moves the directory cannot lose the runs in flight across its deploy. **The re-read is idempotent.** The results and steers the dead generation read but never wrote land as the next step's user turn — a call still running at the death ends on the restart note the relay answers the extension's re-ask with (below), and that note is the result the mirror writes. The last row the dead generation did write — an assistant turn, or the compaction that closed the transcript — read again because the row's offset is saved after the ledger's write, and a death between the two leaves it one row behind, is known to the mirror by sight (`ledgerTailOf`: the compaction whose `before` is the message count, else the last message when an assistant's) and spends no second index: the first row the mirror is about to write is compared with it, once (a message with no parts is still no turn). The index a resumed mirror starts at counts every row the transcript holds, compaction rows included, since the ledger writes a step's rows from that index. The answers pi gave the dead generation's own commands are not taken for answers to this generation's: every generation's command ids carry the moment it began and a nonce (`prompt:<ms>-<nonce>`, so two generations begun in one millisecond share none), and the catch-up ends at this generation's prompt answer and no earlier. A steer's text read again is not mistaken for the seed's echo: only a fresh start's prompt is the seed, and its echo is the first user message after this generation's prompt is answered; a continue prompt's echo — this generation's or a dead one's — is a user turn like a steer's text, since the model was told it. The stream's tool events for a call read again are said again: they narrate, where the ledger's rows are the transcript and are written once. The harness treats a model call that failed and pi's settling on it while the bot was away as facts of the death (a `harness_error` note, not a failure — and not a turn: the errored message writes no row and takes no index, so the log stays whole for the next reclaim; [session-log.md](session-log.md) item 2), and asks pi to continue on the same session with a `prompt` queued as a steer (`streamingBehavior: "steer"`): the pi found alive may be inside a tool call — its extension waiting on the relay for the answer the dead generation never sent — and pi refuses a plain prompt while its loop runs (`Agent is already processing`), a refusal that failed the run and ended pi with the call still open; queued, the continue lands after the call as the next user turn, and an idle pi (a model call failed while the bot was away, the loop ended) takes the same command as the prompt it is. The row cannot tell the two shapes apart — the last step's calls in flight name both, since their results ride the next step's user turn — so pi decides; the calls in flight are settled on the relay before anything is awaited (item 7), so the extension's re-ask reads the restart note and runs nothing. All of this having adopted the bearer that pi holds onto this generation's proxy by the hash its facts carry (`bearerHash`; [model-proxy.md](model-proxy.md) item 2); a row whose facts carry no hash names a pi whose calls no proxy here can honour, so that pi is ended by pid and restarted on the mirrored transcript like one the row named no root for, the `resumed` note saying why. A live pi whose row names no root (written before the root was recorded) cannot be found: it is ended by its pid and the run goes on as after a death. When pi died, or no facts landed, the harness writes a session file rebuilt from the mirrored transcript (pi's version-3 format, one linear branch, every call in flight at the kill answered with the restart note and never re-run — its effects are the container's) and starts pi on `--session <file>` under this build's own root, removing a dead pi's recorded root when it is another. The session file's header names the directory this pi runs in as the container answers it for the root just made (`PiContainer.cwd`): the thread's checkout on an execution container, where the executor runs every command; the run's own root on the bot host (item 12). It is never a constant: pi exits at once on a stored working directory that does not exist where it runs, and the bot host has no checkout path and a new root in each generation. The seed session (item 9) names its directory the same way. Both paths say so in a `resumed` note, the ended pi's naming why. pi's compaction is a row of that transcript too ([session-log.md](session-log.md) item 6): a `compaction_end` whose result carries the summary hands the bridge the entry — the summary, `tokensBefore`, pi's `firstKeptEntryId` — and the mirror writes it as its own step, the results pending since the last assistant turn as the user turn they would have been and the entry as the row after them, nothing in flight; the rebuilt session file renders each such row as pi's `compaction` entry where it sat, so the restarted pi's window is the summary and the turns after it rather than the raw turns compacted again. A compaction that failed, was aborted or carried no summary writes no row — the `compacted` or `harness_error` note alone. A pi run handed off after its final answer (the mirror wrote the text-only turn as a step with nothing in flight) is a `finish` plan ([run-history.md](run-history.md) item 37): no pi starts, the pi the previous generation left is ended at the pid and root its facts name, only in the container the facts name (a leftover pi elsewhere is named in a `resumed` note, not ended here), and the post-steps run with the answer.
9. **The seed rule: the session is the thread so far, the prompt is the one new turn.** The dispatcher's seed is the thread's history first and the request as the last user turn (`buildMessages` in `src/core/dispatch/messages.ts`, merged into the alternation providers require, so the request is one user turn). `splitSeed` reads it in that shape: the last user turn is the prompt pi is sent (`promptOf`: its text parts joined with a blank line into pi's one prompt string — so a request turn built of more than one text part reaches pi whole, the ship pipeline's unit contract among them, which enters the coding child's first user turn as its own text part after the request's text (`withContractInFirstUserTurn`, `src/core/ship/codingChild.ts`; [agent-ship.md](agent-ship.md) item 13) — its images as pi's image blocks, a document named in the text since pi's prompt carries none), and every turn before it is the session pi starts on — written into the container as a session file by the same `piSessionFile` the way back (item 8) uses, so an earlier assistant turn's tool calls and their results are pi's own `toolCall` blocks and `toolResult` entries, and an earlier document is named in a text block — and pi starts on `--session <file>` as a resume does. A seed of one turn — a fresh mention, a coordinator's unit thread whose lead is the bot's — writes no session file and starts pi on the bare session directory, byte for byte as before the rule; the mirror's index still counts from the whole seed, already on the ledger, and no `resumed` note is said. Without the rule a run in a thread with earlier user turns prompted pi with the thread's oldest turn and never showed it the request. The seed the dispatcher hands over is not always the thread's history: a follow-up whose thread has a session log of its agent starts from the log's tail within the seed budget, the lines a person wrote since the previous run ended and the request ([session-log.md](session-log.md) item 9) — the same shape, so `splitSeed` reads it unchanged: the request is still the last user turn and everything before it the session file, tool calls and results from the log included.

10. **The review preset on the harness: the read identity's allowlist, framing and gate, and a verdict that reaches GitHub exactly as the native loop's did.** A review runs where it always ran — the resident's read-only worktree attached by identity `read`, no write token in the tree, the mirror as its origin — and the harness reads that identity once (`AgentDef.identity`) for three things. **The allowlist**: pi's `--tools` carries pi's own tools less `edit` and `write` for a read identity (`piBuiltinToolsFor`: `read`, `bash`, `grep`, `find`, `ls`) plus the relayed ones — the `readonly` toolset less the workspace tools: `update_status`, `submit_verdict`, `web_fetch`, `diff_digest`, the skill tools, the GitHub reads — so pi never has a write tool to call, before the gate ever sees a call. **The framing**: the composed system prompt is the dispatcher's — the registry's review prompt (the resident variant, the REVIEW TARGET block, the contract, the skills) as `makeSystemComposer` renders it, never a copy — and the harness note last names the five read tools, says the run has no `edit` and no `write` and is read-only, and maps `read_file` onto `read` alone. **The gate**: the rules the gate judges pi's own tools by carry the run's identity, folded in by the harness beside the thread's branch facts, and the reach is the identity's (`reachFor`): a write run's is the coding preset's; a run without an identity's is empty (item 12); a read run's holds no `write-files`, `github-write` or `pr` bundle, so `edit`, `write` and a `submit_pr_description` are `outside-profile`; its shell never pushes — `git push` in any form is refused `read-only` — and never writes to GitHub by CLI or API (`gh pr comment|edit|…`, `gh api` with a write method or a field, curl at `api.github.com` with a write method or a body), while every read of both stays allowed; a merge or an approval is refused before that as it is for every run. Each refusal is a `tool_refused` note. **The verdict path**: `submit_verdict` is a relayed tool, so pi's call is the native tool's own call (`tool.run(input, ctx)` in the bot with the run's tool context, `onVerdict` included): the verdict the run holds, the acknowledgement the model reads and the parser's refusal of a malformed one are the tool's own, and everything after the loop is the same code — the reviewed-head settle, `runReviewPostStep` behind the reviewed-head guard, the `LGTM:` first line built by code for an approve and `Changes requested:` otherwise, a comment and never an approval or a merge, the `review_posted` event or the `review_not_posted` note, the `reviewPost` fact on the record. **The head-move re-review is on the harness too**: a substantive head move mid-review (item 12 of [agent-review.md](agent-review.md)) is one more `prompt` on the same pi session through the harness's open form (item 14).
12. **A preset without a workspace runs pi as a child of the bot.** The general, research and conductor presets run on machine class `none`: no container is provisioned and the run's executor is the null one, so there is nothing to exec a container command through. Such a preset runs on the harness all the same. The run loop reads the run's machine class once and, for `none`, drives pi through the seam's third implementation, `BotHostPiContainer` (`piContainerFor` picks it; every other class keeps `ExecPiContainer` over the run's executor). Its operations are `node:fs` and `node:child_process` on the bot host: the run's root made by the container itself (`makeRoot`: `mkdtemp` beside the predictable root, on its name as the prefix, exclusive and 700 in one call, with a suffix nobody can guess, recorded on the row's facts by item 8 so the way back finds it), its files created 600 and never replaced (a path already present is refused, never followed or truncated), pi spawned in that directory as its own group leader with `--mode rpc` and the same arguments, its stdin a pipe from the bot, its stdout through the same `message_update` filter into the same log the transport polls, its stderr into its own file, the pid recorded; a kill is TERM to the group, a second's grace, then KILL while the leader still stands (once it has gone the group id could name a reused pid, so nothing more is sent); `remove` takes the root down as one tree. The two files are the bot host's disk: a write that fails there is handled, never an unhandled stream error in the bot process, and it ends pi, so the harness finds it dead and fails the run with the error log's tail rather than waiting on a log nothing lands in; a pi spawned but not tracked (the pid file could not be written) is ended before `start` fails by name. The child's environment is PATH, HOME and what the launch names (the bearer, the URL, the run id, pi's config directory and the offline switches), and never another variable of the bot process, which holds every secret the deployment has. **The bot is what pi reaches**: `SWITCHBOARD_HARNESS_URL` and models.json's provider point at this process's own HTTP server over loopback (`http://127.0.0.1:<PORT>`, `HarnessDeps.loopbackUrl`), where the model proxy and the three harness routes already listen, and never at `PUBLIC_BASE_URL` through the shim; a process without `PORT` fails such a run by name, as one without `PUBLIC_BASE_URL` fails a container preset's. **No shell and no files**: a run whose identity is `none` holds none of pi's own tools: `piBuiltinToolsFor` gives it nothing, so `--tools` is the relayed tools alone and pi never has a `read`, `bash`, `grep`, `find`, `ls`, `edit` or `write` to call; its reach for pi's own tools is empty (`reachFor`: `NONE_REACH`), so a built-in tool such a pi asks the gate for all the same (a pi that grew a tool, a stale allowlist) is refused by name (`<tool> is the <bundle> bundle: a run without a workspace (identity none) has none of pi's own tools`) with a `tool_refused` note, before any rule about what the call does is consulted; the harness note in SYSTEM.md says the run has no workspace and none of pi's own tools, names the relayed ones and maps no native name onto one. Every tool the run has is a relayed one (for general, the `assistant` toolset's `web_fetch`, `update_status`, the GitHub reads and the issue writes), running in the bot as the requesting user under the bot's own gates, as on every run (item 7). The bridge, the mirror, the wind-downs and the record are unchanged: a general run replays like any run's. **A restart**: a bot-host pi is a child of one bot generation, and a fresh generation cannot reach its predecessor's child (its stdin was that process's pipe), so `alive` answers no for a pid this container did not start (and the bot host names no container, so nothing is judged by identity there) and the ledger's resume restarts pi on the mirrored transcript (item 8), the path a container's pi that died with its container takes; the session it restarts on names the root this generation made as its working directory (`cwd` answers the run's own root, where `start` spawns pi), never the checkout the run loop names, which this host does not have and pi would refuse; pi in RPC mode exits on its stdin's end of file, so a bot death takes its pi with it. A bot death is also the only way a bot-host pi is lost mid-run: the container replaced under a live run (item 16) is the exec container's case alone — the bot host names no container and its `node:fs` and `node:child_process` operations never say the runtime was replaced — so a bot-host pi found not alive before the run settled is the same-container failure of item 16, and `BotHostPiContainer` carries nothing for the replaced case. The bot image carries pi at the pin for this (item 3). **Research and the conductor take the same path**: the container asked for by the `none` class, the loopback URL, none of pi's own tools, the preset's toolset relayed and nothing else: for research the `web` toolset's `web_fetch`, `web_search`, `update_status` and the GitHub reads, each the native tool run in the bot under its own gates (a `web_fetch` of an internal address is refused by the tool's URL guard without a fetch, and that refusal is what pi reads); for the conductor the `conductor` toolset's `spawn_run`, `send_to_run`, `await_runs`, `list_runs` and `get_run_status` beside `web_fetch`, `update_status` and the GitHub reads, its waits carried by the relay's pending answer (item 7) and its spawn seeding the child from the run's session log ([agent-conductor.md](agent-conductor.md) item 3).
11. **A verdict names its head because the served definition requires it; the relay neither refuses nor supplies one.** The `submit_verdict` a review's pi is served is the native tool's definition field for field — the description that says to run `git rev-parse HEAD` in the checkout reviewed and pass its output, the schema whose `required` names `head` beside `verdict` and `summary` — and pi validates every call against the schema it was served before the extension runs it, so a verdict naming no head is a schema error the model reads and answers, and never reaches the relay. The relay adds nothing to a verdict and removes nothing from it: a relayed call is the native tool's own (item 10), so a verdict without a head is accepted exactly as the native call accepts it — the run's `onVerdict` receives what the parser yields, head absent — and the reviewed-head guard decides afterwards. The relay never stamps the run's pinned head into a verdict: the settle reads the worktree's own `HEAD` first (`observed`), and the model's `head` is the guard's fallback for a workspace whose `HEAD` could not be read — a head written from the run's expectation would pass exactly the check that exists to catch a review of another commit. A driver with no bot that serves an extension of its own registers the same two definitions verbatim ([load-harness.md](load-harness.md) item 14); one that serves a `submit_verdict` without `head` gets verdicts naming none, since a model follows the schema it is given.

13. **pi's model library is the bot's provider layer for the calls made outside a run loop.** Two model calls are not a run's turn: the request router's one completion ([routing-and-config.md](routing-and-config.md) item 21) and memory reflection's one extractor call ([memory.md](memory.md) item 12). Both go through `@earendil-works/pi-ai` — pi's own adapters, the code a run's pi drives through the model proxy — as a library inside the bot with the deployment's key; the native adapters those two calls once went through are deleted with the loop ([record 0032](../../decisions/0032-pi-is-the-harness-the-native-loop-retires.md)'s series). The table `config.yaml` names is built on it as `PiAiProviders` (`src/core/harness/piAi.ts`): one provider per block in config order, the words the deleted `ProviderRegistry` used for an unknown name and for an `openai-compatible` block without a `baseUrl`; the dispatcher carries it as `CoreDeps.completions`, and `routing.model`, `defaults.models.general` and `memory.model` resolve through it by the same `<provider>/<model>` ref. Each block is one pi API — `anthropic` speaks `anthropic-messages` at pi's Anthropic host, `openai-compatible` speaks `openai-completions` at the block's base URL with its trailing slash stripped (`piApiFor`, the mapping `piModelsJson` writes for a run) — and each request is one pi model named after the block, with the request's output cap as its own, no thinking and a zero rate card (the price is never read; usage is the four counters). The request keeps the completion vocabulary: `PiAiProvider.complete` takes the `CompletionRequest` the callers already build and answers a `CompletionResult` — the system prompt and every turn in pi's shape (`toPiContext`: a user turn's tool results lead as tool-result messages named after the calls they answer, a document part becomes the compatible adapter's text note, thinking rides with its signature), the tools with their JSON Schema as pi's parameters, and the forced tool call in each API's own spelling (`piStreamOptions`: Anthropic's `tool_choice: {type: "tool", name}`, Chat Completions' `{type: "function", function: {name}}`) — so the router's tool-form contract is unchanged and `routing: { answer: text }` still sends no tool. The key is read at call time from the block's `apiKeyEnv` (the SDK's own `ANTHROPIC_API_KEY` for an `anthropic` block that names none) through the process's secrets and revealed into pi's request options alone; an unset variable fails before any request, naming it (`Provider "<name>": <VAR> is not set`); a keyless `openai-compatible` block — a local server — sends no authorization header at all. pi's final message comes back as the result (`fromPiMessage`): text, tool calls and thinking in order, `stop`/`toolUse`/`length` as `end_turn`/`tool_use`/`max_tokens` (the last is what the router refuses by name), the usage's `input`/`output`/`cacheRead`/`cacheWrite` as the four counters; an `error` or an `aborted` stop is a thrown error naming the provider and the model with pi's message, so `route()` records `router failed: …` and `reflect()` warns `reflection failed: …` as they did for a native adapter's throw, and the request's `AbortSignal` reaches the wire. What pi does on its own on this path that the compatible adapter did not: prompt-cache markers on the system prompt, the tools and the last user turn (the request's `cacheTtl` as pi's retention; both prompts are static per deployment, so a route or a reflection reads the cache from its second call on), and its OpenRouter compatibility rules for a block at `openrouter.ai`. Nothing is recorded that was not before: neither call opens a `model.turn` span or puts usage on a record — the router's call sits under the request's `dispatch.route` span, reflection is a background pass off the run's trace — and `CompletionRequest.effort` and `observer` are not carried, since neither caller sets them. The library is pinned in `package.json` at exactly the pi pin the three images hold (item 3), so one version moves everywhere at once; the offline replay (`load:route`, [load-harness.md](load-harness.md) item 17) builds the router's model on the same table, so its score is the score of the path production runs. **A run's own model calls never touch this table**: pi calls the model proxy ([model-proxy.md](model-proxy.md)), which forwards the two wire shapes — `anthropic-messages` and `openai-completions` — with the deployment's key and meters each answer's usage (`usageFromAnthropic`, `usageFromOpenAI` in `src/core/modelProxy/usage.ts`, the readers the adapters once held); and `resolveTarget` checks the resolved model ref's provider against the config's `providers` before any card (`Unknown provider "<name>". Configured providers: …`), so a ref naming a provider the config lacks is refused at resolution and not at pi's first model call, minutes in.
14. **The session outlives the loop for the run stage's post-turns: one more `prompt`, never a second process and never the native loop.** Three turns can run after a loop returns and before the answer lands — the coding preset's description turn ([pr-description.md](pr-description.md) item 5), the review's verdict turn ([agent-review.md](agent-review.md) item 5) and the review's head-move re-review ([agent-review.md](agent-review.md) item 12) — each one more `prompt` on the run's own pi session. The run loop takes the harness's open form, `runPiHarnessOpen`, which hands the loop's answer back with pi alive and idle on its session — the transport still polling, the run still registered on the relay, the root in place — together with a follow-up entry (`PiFollowUpTurn`) and the session's end (`OpenPiSession`); `runPiHarness`, the closed form, is that loop with the end at once. The loop hands the entry to `runDescriptionTurn`, `runVerdictTurn` and `settleReviewedHead` as `followUp` on their turn specs, and ends pi after each has had its say — before the coding post-step and before the workspace pi runs in is released; on a throw, before the release too. A follow-up turn sends the caller's user turn — `descriptionFollowUp`, `verdictFollowUp` or `rereviewFollowUp` — as a `prompt` under a command id of its own, reads pi's records off the same transport through the same bridge, and answers with pi's reply once it settles, labelled as the loop labels a write-up. The relayed tools read the turn's tool context for its duration — the registry entry's `toolContext` is the turn's, then the run's again — so the hook the caller overrides (the description's capture, the verdict turn's and the re-review's own verdict capture) is the one fed, and `remainingMs` is the turn's. Its budget is its own, never the run's remainder: the description turn's clip (8 turns, 5 minutes) or the review preset's; past either, the same write-up steer with every tool refused (`toolsBlocked`), the same `time_budget_exhausted` or `turn_budget_exhausted` note and the same label on the answer; the loop's stops with them — a soft stop steers the soft-stop write-up with every tool refused, says `stopped` (soft) and labels the answer ⏹, exactly as the loop does, a hard stop is `abort`, `HARD_STOP_MESSAGE` and the `stopped` note, and the finale bound closes a write-up that overruns. Its spans: a `run.agent` opened under the caller's span (`run.description_turn`, `run.verdict_turn`, `run.settle_reviewed_head`), the proxy's turns re-parented to it and the bridge's `tool.<name>` spans under it, ended when the turn ends — `error` when the turn threw, was hard-stopped or bypassed the gate, `ok` otherwise, and the loop's own `run.agent` likewise ends `error` when the loop threw; the loop's `run.agent` ends when the loop settles, before any follow-up. Its rows are not mirrored: the ledger's transcript is the loop's — a kill mid-turn resumes from it ([pr-description.md](pr-description.md) item 5) — so nothing the turn says is a step, the row's offset stands, and the next run in the thread seeds from the same log either way; the inbox is not drained during a follow-up turn and no compaction steer follows one. Failure handling is the caller's: a prompt pi refuses, a model call that fails, a pi that exits mid-turn or a gate bypass (its `harness_error` note and `abort` as in the loop) throws — the description turn logs it and reports nothing submitted, the re-review fails the run; a follow-up asked of a session already ended throws naming it and sends nothing. pi's system prompt is the session's — pi reads `SYSTEM.md` once, at load, and its RPC has no command to change it — so the re-review does not recompose the REVIEW TARGET block: the follow-up text alone names the new head, the moved worktree and the fresh `submit_verdict` it wants. **A `finish` plan has no session** (item 8: the previous generation's loop had answered and its pi is ended here), so a post-turn a resumed run still owes is not run, and neither caller starts a second pi (a fresh session would carry none of the run's context, and the record already says what the run did). The description turn publishes its `description_turn` note saying there is no session to ask on — the loop answered before a restart — and submits nothing, so the post-step's note says the description was not resubmitted ([pr-description.md](pr-description.md) item 5's warning); a substantive head move the settle finds is not re-reviewed: no worktree move, a `head_moved` note saying the session is gone and that the verdict stands for the head it reviewed, and the post gate pins it there ([agent-review.md](agent-review.md) item 10).

15. **Budgets: the wall clock is the budget, the turn cap the runaway guard derived from it.** Each preset defines `maxMinutes`, the hard deadline the harness keeps (item 6). Its `maxTurns` is not set by hand: every preset that runs the loop derives it as `runawayTurnCap(maxMinutes)` = `maxMinutes × RUNAWAY_TURNS_PER_MINUTE`, with `RUNAWAY_TURNS_PER_MINUTE = 6` (`src/agents/registry.ts`, `loopBudget`) — a model turn every ten seconds, sustained for the whole budget, is a loop, not work (a busy run takes 20–40 s a turn), so the cap is never a number a working run reaches, and a run that reaches it first was pacing like a loop. Derived caps: coding 270 in 45 min, review 150 in 25, research 48 in 8, general 30 in 5, explore and conductor 720 in 120; `ship` keeps `maxTurns: 1` because its def never runs the loop. When a boundary or a `budget:` directive clips a run's minutes below the preset's ([routing-and-config.md](routing-and-config.md) item 2), `budgetedAgent` re-derives `maxTurns` from the clipped minutes with the same helper, so the six-per-minute guard holds for the budget the run actually has (coding clipped to 10 minutes runs with 60 turns). The guard is spent where the calls are made — the model proxy counts a turn before it forwards the call and refuses the one past the cap ([model-proxy.md](model-proxy.md) item 5) — and the harness reads the same count off pi's turns (item 6); an `update_status`-only turn does not count against it ([item 5's bookkeeping rule](#behavior)). **Wrap-up warning**: once, as the deadline nears (≤ 3 min or 25 % left), the model is steered how long remains and to consolidate rather than explore (`wrapUpInstruction`, a `wrap_up` note). **Forced write-up**: at the deadline or the turn guard the model gets one more turn with every tool refused (item 7) to report findings so far and what a follow-up should do, told which of the two ended the run (`timeBudgetInstruction`, `turnGuardInstruction` with the pace). The answer is prefixed `⚠️ Hit the <N>-minute budget before finishing — findings so far:` at the deadline, and `⚠️ Stopped after <N> model turns in <M> minutes — that pace looks like a loop; findings so far:` when the guard fires — the turns counted and the minutes elapsed, never the word budget, because the cap is not one (`timeBudgetAnswer`, `turnGuardAnswer`); an empty write-up still produces a user-facing message that says the same reason; the `run_note` kinds are `time_budget_exhausted` and `turn_budget_exhausted` (the friction analyzer and the model proxy share them); the write-up is bounded (`FINALE_TIMEOUT_MS`, three minutes). A resumed run whose loop had ended under one of these before the restart wears the same label, read back from its notes (`answerUnderEnding` in the run loop; [run-history.md](run-history.md) item 37). **Current wall clocks**: general 5 min · research 8 · review 25 · coding 45 · explore 120 · conductor 120 · ship 120 (the pipeline's, [agent-ship.md](agent-ship.md)); each turn guard is six times the minutes. Changing a wall clock is a feature change — update this item and the registry together; the guard follows.

16. **A container replaced under a live run ends the run `interrupted`, and its request runs again as a new run — the floor of record 0038's survival clause.** The resident's rolling-container pause ([resident-repos.md](resident-repos.md) item 65) replaces the container under a live run — every image-changing release does it twice, at our deploy's restart and at the platform's own roll a few minutes later — and the harness drives pi *inside* that container, so pi and the tool it was running are gone with the old container's disk while the run's record is whole on the ledger. **The condition is the executor's word**, on any container command under the loop — the log read, the `alive` probe, a line into the FIFO (a failed write surfaces at the next read, the transport's order): the command failed with the executors' word for a replaced runtime (`saysContainerReplaced`), **typed first**: the resident client's `ExecSandboxRestartedError`, its one word for every answer that says the container under the thread is gone — the container exited inside a rollout and the executor re-attached to the replacement before the command ran ([resident-repos.md](resident-repos.md) item 65); a deploy swapped the runtime under the command in flight (`runtime-replaced`, item 43); the preflight found the container disk recycled since the last attach (`worktree-missing`, item 27) — the last two thrown **at once, before any recovery**, because pi's own tools run inside the container and never through the bot, so the roll usually lands between two of the harness's polls and reaches the seam only as the next poll's `worktree-missing`, and because the recovery the client used to make first — a re-attach that blocks through the restore, or is refused `image-stale`/`not-serviceable` while the replacement reconciles — stood in for the verdict on 1.230.0 (run `5b7e3b50`, the floor's failed live receipt: the harness read `pi exited before the run settled` or the attach's refusal, said nothing, and the run was not dispatched again); and the seam's `PiContainerRuntimeReplacedError`, an executor that handed the word back as a command's *text* (`stdoutOf` raises it rather than let `alive` read it as `dead` or the log read decode it as bytes). Then the words themselves, `runtime-replaced` or `runtime-unreachable` (the sandbox's word for a runtime nothing answered, [execution.md](execution.md) item 9), anywhere in a failure's text — behind the executors' `exit N:` prefix and newline, the seam's wrap, or the resident client's own sentence — since the seam's commands print a pid, a boot id, `alive`/`dead`, base64 or nothing and never the word, so a failure carrying it is the executor's; a failure without any of that is the failure it was. The container's name is corroboration, never the condition: the container this run was handed names itself again (`identity`, item 4) and both words go on the note beside the recorded one (`facts.container`, item 8) — the word is the kernel's boot id, which a container replaced on the same kernel keeps, so a match proves nothing and a change is not needed. Then, in order: every call still open on the bridge is settled on the record with the restart note said of the container (`replacedCallNote`: the tool ran in the container and its result died with it, so it is never re-run from here; its `tool.<name>` span ends in error), a `run_note` of kind `sandbox_restarted` says `the container running pi was replaced (<old identity> → <new identity>; the executor said: <its words>); the run restarts from its request`, and the loop throws `PiContainerReplacedError` (`said`, `was`, `now`) after the relay has forgotten the run. Nothing is killed and nothing removed: the executor reaches the replacement now, where a pid is a stranger's and the run's root never was, whatever the container answers for its name. The run loop reads the error as an interruption, never a failure: the registry and the record finish `interrupted` — the one status a replaced container has, so this floor and the unscheduled relaunch ceiling share it for one root cause — the workspace is released, the card closes `🔁 <label> · container replaced under the run; restarting from the request · <elapsed>` and never `❌`, and the dispatcher, in place of the failure reply, hands the request to the restart a refused workspace re-attach takes ([run-history.md](run-history.md) item 54: `prepareRestartTurn`, the follow-ups the run never consumed appended, dispatched as a new run once the thread is free); the request's own outcome is the refusal's shape, `container_replaced`, as `workspace_lost` is item 54's. A pi found dead without the executor's word died where it ran: the failure it always was — `pi exited before the run settled` with the error log's tail, pi ended and its root removed — naming the container's word when it changed by then (`(the container names itself <now> now; pi's was <was>)`), so the record can be read, and judging nothing by it. **What this is not**: a relaunch of pi in the replacement container on the mirrored transcript with a rotated bearer, which would keep the run and cost it one model call — the survival clause's ceiling, with its credential fence and its bound on relaunches — is an unscheduled option recorded in [record 0038](../../decisions/0038-the-harness-is-a-contract-pi-is-its-one-implementation.md)'s third amendment; ending the run `interrupted` and dispatching the request again is the behaviour: this item is the settle-and-close floor that record names, and a run that meets a roll starts its request over.
- `[gap]` **No stuck-loop guard.** The native loop counted consecutive identical failures per call signature (`callSignature`, `src/core/runFriction.ts`): a one-line nudge on the third, the forced write-up on the sixth with a `stuck_loop` note and the label `⚠️ Stopped after the same call failed 6 times identically — findings so far:`. The harness has none: a model re-issuing the same failing call runs until the wall clock or the turn guard (item 15) ends it. The bridge sees every `tool_execution_end` with its outcome, so the same count fits there, the nudge a steer at the next turn boundary and the write-up the one the budgets use; the tracker item that owns it is named in [record 0032](../../decisions/0032-pi-is-the-harness-the-native-loop-retires.md)'s series status.

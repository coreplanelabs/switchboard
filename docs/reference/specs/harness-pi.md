# The pi harness: a preset's runs driven by pi in the run's own container, on the run's own record

[Record 0032](../../decisions/0032-pi-is-the-harness-the-native-loop-retires.md) decides that pi (`@earendil-works/pi-coding-agent`) replaces the native turn loop one preset at a time. This is the harness that replacement runs on: pi in `--mode rpc` inside the run's execution container, started as the thread's user with the run's model-proxy bearer as its only key, driven by the bot over pi's line protocol, every event it emits bridged onto the run's own stream in the native loop's vocabulary, our tools and the coding preset's tool rules as its extension, the transcript mirrored onto the run ledger so a bot restart continues the run. Which preset runs on it is a property of the preset a deployment overrides (`harness:`), so the series can move one preset at a time and a deployment can move — or move back — one early; today every preset declares `native`, and a deployment that sets nothing runs exactly as before.

## Behavior

1. **The harness is a preset property a deployment overrides.** `AgentDef.harness` is `native` (the in-process loop, `src/runner.ts`) or `pi`; every preset declares `native` today, `coding` explicitly, the one the series moves first. A deployment's top-level `harness:` block names a harness per preset (`harness: { coding: pi }`) and wins over the declaration; `effectiveHarness(agent, block)` is the one question the run stage asks. The block is validated at load: a preset the registry does not know, or a value that is neither harness, fails by name, and a non-mapping fails too — a setting that silently read as "nothing changed" while the operator believed a preset had moved would be the worst kind of quiet. Only a preset with a workspace can run on pi (pi is a process in the run's container); the registry declares none of the workspace-less presets on pi.
2. **The seam is one branch in the run loop, and everything around it is shared.** `runLoop` asks `effectiveHarness` once; on `pi` it hands the run to `runPiHarness` in place of `runAgent` with the same tool context, the same event and progress sinks, the same control, inbox and ledger step hook, the same `run.agent` parent span and the same resume plan — and the rules the gate (item 7) judges pi's own tools by, which follow the thread the way the post-step's pull-request target does: when the thread came from a pull request or a coordinator's spawn, the thread is bound at the run's own branch (a fix round repushes the PR's head; a unit child is dispatched at its unit branch), so that branch is the one push target and the base its pull request targets is protected; otherwise the binding is that base, protected, and the run pushes a branch of its own making. Admission, resolution, the gates, the workspace attach, the bearer mint and the prompt before it, and the reviewed-head settle, the workspace observation, the description turn, the coding PR post-step, the answer's publish, the finish and the release after it are the same code: the post-step sees the same branch and pull-request facts because it reads them off the same stream (`trackPushedBranch` over the bridge's `tool_call.command`) and the same workspace. A preset on pi in a process without the harness deps, without `PUBLIC_BASE_URL` (the container reaches the proxy and the routes through it) or without a minted bearer fails the run naming exactly what is missing; without the block every run is the native loop byte for byte and pi is never started.
3. **pi lives in both execution images, pinned and proven.** Each execution image installs `@earendil-works/pi-coding-agent` globally with its own Node 24 at one exact version, read by the pin parser like pnpm's and playwright's and held equal across the two images; the layer proves at build time that the `pi` on PATH answers the pin and that its help names RPC mode, and the resident image proves it once more as `worker1`, the way a run's pi is started. The bot image never carries pi: the harness runs where the run's tools run. Installing it is dark — nothing in an image starts pi.
4. **The process: pi as the thread's user, the bearer as its only key, through the container seam.** A run's pi has one directory of its own outside the checkout, under a root of the thread user's own: `/tmp/switchboard-pi-<user>/<runId>` when the run knows the OS user its executor runs commands as (the resident's pool user, carried on the attach answer as `ResidentBinding.user` and handed to the harness by the run loop), `/tmp/switchboard-pi/<runId>` on an executor with one user (the local host, the sandbox). The users' roots are siblings directly under `/tmp` (mode 1777) with nothing between them for one user to own: the resident runs each thread's commands as its own pool user and `mkdir -p` gives a parent it creates to its caller at 755, so one root shared by every run would belong to whichever user ran first and every other user's run would fail at its own mkdir before a model turn; a shared parent made 1777 would not repair a container where the 755 one already stands, which is why the root is per user rather than the parent shared. The directory holds pi's config directory with `settings.json` that never trusts the checkout, `models.json`, `SYSTEM.md` and `sessions/`, the extension, the FIFO, the log, the error log and the pid file. `models.json` names one provider — the bot's model proxy on the wire shape the run's provider speaks (`anthropic-messages` at the bot's base, `openai-completions` under `<base>/v1`) — with `apiKey: "$SWITCHBOARD_RUN_BEARER"`, a zero rate card, because pi's own cost is never what a page shows: the proxy meters, and — on the Anthropic shape — the thinking payload the model takes as pi's `compat.forceAdaptiveThinking` (`takesAdaptiveThinking`): a Claude model from the 4.6 generation on takes adaptive thinking (`thinking.type: "adaptive"` plus `output_config.effort`) and the 5 family refuses the legacy budget (`thinking.type: "enabled"` plus `budget_tokens`) with a 400; a model before 4.6 refuses adaptive and keeps the budget. pi's built-in Anthropic catalog says this per model and sends the budget for a model it does not know; the proxy's model is not in that catalog, so the harness says it — the generation is the id's first version number (`claude-fable-5` is 5, `claude-sonnet-4-5-20250929` 4.5: a date is never a minor), and an id with none is taken for the current generation. The completions shape carries no such switch. pi starts detached (`setsid -f`) with `--mode rpc`, every discovery off (`--no-extensions --no-skills --no-prompt-templates --no-themes`), the extension by explicit path, `--tools` allowlisting pi's own workspace tools (`read`, `bash`, `edit`, `write`, `grep`, `find`, `ls`) plus the relayed ones, the proxy's provider and the run's model with the effort tier as pi's thinking level (the five tiers are pi's levels by name; no tier leaves pi's default), and a session directory — or `--session <file>` when pi has turns to start from: the thread's earlier turns (item 9) or a resume's mirrored transcript (item 8). Its stdin is a FIFO the wrapper holds open read-write on a spare descriptor, so pi never sees an end of file while it lives; its stdout goes through a line-buffered filter that drops `message_update` deltas into a log the harness polls; its stderr into its own file; the wrapper's pid, the group leader, is recorded. **The environment is the channel for the bearer**: the run bearer, the bot's URL, the run id, `PI_CODING_AGENT_DIR` and pi's offline switches ride `ExecOptions.env` — the exec's own env option on every executor (the local child gets the public environment plus these and never the host's secrets; the resident and the sandbox send them as the body's `env`, the resident Worker reading the map through the one validated reader and handing it to the exec's env option under its own injected variables) — never a command line, never a file, never a model key, Slack token or GitHub App credential. Every operation is one command over the run's own `Executor` as the thread's user — a file written in `printf` chunks under `umask 077`, a line fed to the FIFO (a long one through a file), the log read from a byte offset as one-line base64 so the bytes survive the text channel exactly, `kill -0` for liveness, the group then the leader killed — and a command the executor reports failed is a named `PiContainerError`, never a silent empty. The in-memory `FakePiContainer` is the seam's second implementation.
5. **The bridge: pi's events become the native loop's, and the proxy meters the turns.** Every event kind pi's protocol documents has a disposition (`PI_EVENT_DISPOSITION`, held to the same set of kinds as the spike's home table): `tool_execution_start` opens a `tool.<name>` span under `run.agent` and announces the `tool_call` inside it (the same one-line summary the loop writes, bash's full command beside it, capped and redacted); `tool_execution_end` emits the `tool_result` with the loop's `ok`, bash's `exitCode` read from pi's `Command exited with code N` trailer (or the executors' `exit N:` prefix), the summary and the capped output, and ends the span with `callId`, `ok`, `exitCode`; the model's text beside its tool calls is `assistant`, a text-only turn is the answer candidate, a turn whose every call is `update_status` is bookkeeping — not counted against the guard, its text held until the next turn decides ([run-loop.md](run-loop.md) item 15); `💭 thought for …` is said at each assistant message's end; `compaction_end` is a `compacted` note with the token counts and any summarization retries folded in; `extension_error`, a dialog request (answered `cancelled`, since no one is watching), an event kind this build does not know and a kind the harness turns off at start (`auto_retry_*`, `bash_execution_update`) are `harness_error` notes naming what happened; `message_update` and `tool_execution_update` are folded into the final records; `response`, the agent and turn boundaries and `queue_update` are structure. The model turns are not the bridge's: every call pi makes goes through the model proxy, which spends the run's turn guard and closes one `model.turn` span with the runner's attrs — and the harness re-parents the run's grant from the request root to its `run.agent` (`RunBearerStore.reparent`), so a proxied turn lands where the loop's would. The proof of sameness is the loop itself: the same turn through `runAgent` on a scripted provider and through the bridge on the equivalent pi stream yields equal `tool_call`, `tool_result` and `assistant` events.
6. **The wind-downs are the loop's, in the loop's words.** The harness counts pi's turns for the guard and keeps the deadline; it steers the wrap-up warning once as the deadline nears (`wrapUpInstruction`, a `wrap_up` note), and at the deadline or the turn guard it steers the loop's forced write-up instruction (`timeBudgetInstruction`, `turnGuardInstruction` with the pace) with every tool refused meanwhile through the gate (item 7) — the model reads the refusal's reason — and answers with the loop's label (`⚠️ _Hit the N-minute budget…_`, `⚠️ _Stopped after N model turns in M — that pace looks like a loop…_`) around the text pi settled on, or the loop's reason alone when none came; the write-up is bounded like the native finale (three minutes, then `abort`). A soft stop steers `SOFT_STOP_INSTRUCTION` the same way and answers `⏹ _Stopped early by an operator (soft stop)…_`; a hard stop sends `abort`, ends pi, closes the open tool spans as errors and answers the one-line `⛔` abort message with no write-up. The notes are the loop's kinds (`wrap_up`, `time_budget_exhausted`, `turn_budget_exhausted`, `stopped` with its mode), so the friction analyzer reads one vocabulary. A thread follow-up ([thread-admission.md](thread-admission.md) item 2) is steered into pi as the loop's follow-up prompt, its images along, recorded as the same `input` event and `follow_up` note, its ledger seq folded into the next step record. Auto-retry is turned off at start: a model call that fails ends the turn with pi's error, and the run fails with it — except while catching up after a restart (item 8). pi's own death before settling fails the run with the tail of its stderr; a prompt pi refuses fails it by reason.
7. **The extension and the gate: our tools registered into pi, every tool call decided in the bot.** Before pi starts, the harness writes its extension into the run's directory (`PI_EXTENSION_SOURCE`, plain JavaScript that imports nothing: pi's own loader runs it as written). At load the extension fetches the run's relayed tool definitions from the bot (`GET /harness/tools`) and registers each as a pi tool with the bot's JSON Schema, so `update_status`, `submit_pr_description`, `submit_handoff`, `submit_dispositions`, `attach_file`, `diff_digest`, `web_fetch`, the skill tools, the GitHub tools and any bridged MCP tool exist under their own names — the preset's toolset less the workspace tools pi has of its own (`relayedTools`) — and the composed system prompt gains one last note mapping the native workspace tool names onto pi's. A relayed tool's call posts to `POST /harness/tool` and runs in the bot with the run's own tool context — the same `RunnableTool`, the executor, the requester's GitHub gate, the dispatcher's recorders — under the `tool.<name>` span the bridge opened, its result in pi's content shape (images as image blocks, a document as its descriptor), a failure as an error result the model reads. Its `tool_call` hook asks `POST /harness/authorize` before every tool executes, pi's own included: a relayed tool is allowed (it runs under the bot's own gates); pi's own tools are judged by the coding preset's tool rules (`judgeToolCall`: `origin` alone as a remote; the run's branch as the one push target when the run was given one, else any branch but the protected ones — the base its pull request would target; never a merge or an approval; never the executor's credential store, an environment dump or a credential-named variable; paths inside the checkout; a tool outside the preset's reach); during a write-up every tool is refused. A refusal is a `tool_refused` note on the run and the reason the model reads. **The gate's coverage is checked from the stream.** The authorize route tells the harness the gate saw each call (`LiveHarness.gateSaw`, whatever the answer; the bridge keeps the ids), and pi's `tool_call` hook fires only after pi's own argument validation (pi-agent-core `prepareToolCall`), so a `tool_execution_end` the gate never saw is one of two things. A call pi answered by itself — its arguments failed the tool's schema, its tool is not on pi's list, or its assistant message was cut by the output token limit; pi announces it, ends it with an error result in its own words and never fires the hook (`piAnsweredWithoutRunning` reads those words) — never ran: it is a `harness_error` note naming pi's reason and refuses nothing. So did a call the extension blocked by itself, without a verdict — refused at the door by a 4xx before the route reached the gate, or a bot that did not answer for the wait — whose end carries the extension's own reason (`authorization refused at the door: …`, `authorization unavailable: …`): a `harness_error` note naming it. Every other such end is a tool that ran unvetted: a `harness_error` note names the call, pi is aborted and the run fails closed on it (`the gate was bypassed: pi ran <tool> (call <id>) without asking the bot`), its `run.agent` span ending in error. Calls that started while the harness was catching up on a re-attach (item 8) are not judged — the generation that died vetted them. The hook blocks at once on a refusal at the door — a 4xx: the bearer wrong, expired or revoked, the run not on the harness — since nothing later changes it, and keeps asking a bot it cannot reach or that is failing (a network error, a 5xx) every two seconds, blocking the call by itself after 90 seconds, naming why. The three routes are the model proxy's door: the run bearer names its run and verifies against the store before a byte of the body is read (no bearer or a malformed one 401, an unknown run 404, a wrong secret 401, an expired or revoked one 403), a run not on the harness is 404, the body is capped and must be JSON, and a bearer buys nothing else. The shim forwards the paths blind under the one route word `harness`. The rules judged here are the same ones the spike previewed; the policy table's own tool-level rows remain the authorization spec's open gap.
8. **The mirror and the way back.** pi's finished messages become the ledger's transcript in the runner's vocabulary: an assistant turn (its text and tool calls; thinking dropped) is one step record with its calls in flight, written before the tools' results land, exactly as `runAgent`'s step report; the results since, and any steer's text, are the one user turn the next step carries; the prompt pi echoes is the seed already on the ledger and is not written twice. The row's state gains the harness facts (`harness: { pid, logOffset, sessionFile }`), refreshed at each turn's end. After a bot restart the ledger's resume plan reaches the harness like any run's: when the container's pi still lives (its pid answers), the harness re-attaches — reads the log from the recorded offset, treats a model call that failed and pi's settling on it while the bot was away as facts of the death (a `harness_error` note, not a failure), and asks pi to continue on the same session; when pi died, or no facts landed, it writes a session file rebuilt from the mirrored transcript (pi's version-3 format, one linear branch, every call in flight at the kill answered with the restart note and never re-run — its effects are the container's) and starts pi on `--session <file>`. Both paths say so in a `resumed` note. pi's compaction is a row of that transcript too ([session-log.md](session-log.md) item 6): a `compaction_end` whose result carries the summary hands the bridge the entry — the summary, `tokensBefore`, pi's `firstKeptEntryId` — and the mirror writes it as its own step, the results pending since the last assistant turn as the user turn they would have been and the entry as the row after them, nothing in flight; the rebuilt session file renders each such row as pi's `compaction` entry where it sat, so the restarted pi's window is the summary and the turns after it rather than the raw turns compacted again. A compaction that failed, was aborted or carried no summary writes no row — the `compacted` or `harness_error` note alone.
9. **The seed rule: the session is the thread so far, the prompt is the one new turn.** The dispatcher's seed is the thread's history first and the request as the last user turn (`buildMessages` in `src/core/dispatch/messages.ts`, merged into the alternation providers require, so the request is one user turn). `splitSeed` reads it in that shape: the last user turn is the prompt pi is sent (`promptOf`: its text parts joined, its images as pi's image blocks, a document named in the text since pi's prompt carries none), and every turn before it is the session pi starts on — written into the container as a session file by the same `piSessionFile` the way back (item 8) uses, so an earlier assistant turn's tool calls and their results are pi's own `toolCall` blocks and `toolResult` entries, and an earlier document is named in a text block — and pi starts on `--session <file>` as a resume does. A seed of one turn — a fresh mention, a coordinator's unit thread whose lead is the bot's — writes no session file and starts pi on the bare session directory, byte for byte as before the rule; the mirror's index still counts from the whole seed, already on the ledger, and no `resumed` note is said. Without the rule a run in a thread with earlier user turns prompted pi with the thread's oldest turn and never showed it the request. The seed the dispatcher hands over is no longer always the thread's history: a follow-up on a pi preset whose thread has a session log of that agent starts from the log's tail within the seed budget, the lines a person wrote since the previous run ended and the request ([session-log.md](session-log.md) item 9) — the same shape, so `splitSeed` reads it unchanged: the request is still the last user turn and everything before it the session file, tool calls and results from the log included.

10. **The review preset on the harness: the read identity's allowlist, framing and gate, and a verdict that reaches GitHub exactly as the native loop's does.** `harness: { review: pi }` moves the review preset (`effectiveHarness` is already per preset; the block names any preset the registry knows). A review runs where it runs today — the resident's read-only worktree attached by identity `read`, no write token in the tree, the mirror as its origin — and the harness reads that identity once (`AgentDef.identity`) for three things. **The allowlist**: pi's `--tools` carries pi's own tools less `edit` and `write` for a read identity (`piBuiltinToolsFor`: `read`, `bash`, `grep`, `find`, `ls`) plus the relayed ones — the `readonly` toolset less the workspace tools: `update_status`, `submit_verdict`, `web_fetch`, `diff_digest`, the skill tools, the GitHub reads — so pi never has a write tool to call, before the gate ever sees a call. **The framing**: the composed system prompt is the dispatcher's — the registry's review prompt (the resident variant, the REVIEW TARGET block, the contract, the skills) as `makeSystemComposer` renders it, never a copy — and the harness note last names the five read tools, says the run has no `edit` and no `write` and is read-only, and maps `read_file` onto `read` alone. **The gate**: the rules the gate judges pi's own tools by carry the run's identity, folded in by the harness beside the thread's branch facts, and the reach is the identity's (`reachFor`): a write run's is the coding preset's; a read run's holds no `write-files`, `github-write` or `pr` bundle, so `edit`, `write` and a `submit_pr_description` are `outside-profile`; its shell never pushes — `git push` in any form is refused `read-only` — and never writes to GitHub by CLI or API (`gh pr comment|edit|…`, `gh api` with a write method or a field, curl at `api.github.com` with a write method or a body), while every read of both stays allowed; a merge or an approval is refused before that as it is for every run. Each refusal is a `tool_refused` note. **The verdict path**: `submit_verdict` is a relayed tool, so pi's call is the native tool's own call (`tool.run(input, ctx)` in the bot with the run's tool context, `onVerdict` included): the verdict the run holds, the acknowledgement the model reads and the parser's refusal of a malformed one are the native loop's, and everything after the loop is the same code — the reviewed-head settle, `runReviewPostStep` behind the reviewed-head guard, the `LGTM:` first line built by code for an approve and `Changes requested:` otherwise, a comment and never an approval or a merge, the `review_posted` event or the `review_not_posted` note, the `reviewPost` fact on the record. Without the block, or with `harness: { review: native }`, a review is the native loop byte for byte and pi never starts. **Not yet on the harness**: a substantive head move mid-review (item 12 of [agent-review.md](agent-review.md)) still runs its one more turn through `runAgent` — the harness has returned and ended pi by the time the settle classifies the move — so on a deployment with `review: pi` that turn alone is native, with the bot's key and the native `bash`/`read_file`; making it a `prompt` on the same pi session, as record 0032 says, needs the session to outlive the harness's return and is the next pull request of this unit, with the deletions of the native read-only path.
11. **A verdict names its head because the served definition requires it; the relay neither refuses nor supplies one.** The `submit_verdict` a review's pi is served is the native tool's definition field for field — the description that says to run `git rev-parse HEAD` in the checkout reviewed and pass its output, the schema whose `required` names `head` beside `verdict` and `summary` — and pi validates every call against the schema it was served before the extension runs it, so a verdict naming no head is a schema error the model reads and answers, and never reaches the relay. The relay adds nothing to a verdict and removes nothing from it: a relayed call is the native tool's own (item 10), so a verdict without a head is accepted exactly as the native call accepts it — the run's `onVerdict` receives what the parser yields, head absent — and the reviewed-head guard decides afterwards. The relay never stamps the run's pinned head into a verdict: the settle reads the worktree's own `HEAD` first (`observed`), and the model's `head` is the guard's fallback for a workspace whose `HEAD` could not be read — a head written from the run's expectation would pass exactly the check that exists to catch a review of another commit. A driver with no bot that serves an extension of its own registers the same two definitions verbatim ([load-harness.md](load-harness.md) item 14); one that serves a `submit_verdict` without `head` gets verdicts naming none, since a model follows the schema it is given.

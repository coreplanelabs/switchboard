# Agent: general

The default — the plain @-mention. An agent with a small, workspace-free toolset: it answers directly, reads the org's repositories and acts on their issues through Switchboard's GitHub credential, and reads a linked URL — so the everyday asks are answered here, and only code changes, PR reviews, and web research are handed to the other agents.

- **Code**: `src/agents/registry.ts` (`general`, `GENERAL_SYSTEM`), `src/tools/toolsets.ts` (the `assistant` toolset), `src/tools/github.ts`, default model in the deployed config (`config/config.example.yaml` documents the key)
- **Docs**: [The agents and their toolsets](../../explanation/agents-and-toolsets.md), [github-tools.md](github-tools.md)
- **Budgets**: 60 min / 16k tokens (the turn guard is derived: 360, six a minute — [harness-pi.md](harness-pi.md) item 15) · toolset `assistant`

## Behavior

1. Answers directly and concisely in Slack-friendly formatting — the length is the shared brevity rule's ([routing-and-config.md](routing-and-config.md) item 26): the answer first, nothing after it is complete. Its tools are the `assistant` toolset ([github-tools.md](github-tools.md) items 4–5): the GitHub reads (`github_repos`, `github_tree`, `github_file`, `github_search_code`, `github_issue_list`, `github_issue_get`, `github_pull_get`, `github_actions_run`, `github_actions_job_log`), the issue writes (`github_issue_create` / `update` / `comment` / `delete`), `web_fetch`, and `update_status` — no shell, no file writes, no `web_search`, no [verdict](../vocabulary.md#verdict) or PR submission.
2. Runs on the model resolved from config. Short questions can finish promptly; the declared hour-long ceiling lets a multi-source lookup continue without a five-minute cutoff, unless a request boundary clips the effective lease. The three-minute write-up allowance remains inside that lease ([harness-pi.md](harness-pi.md) item 15). If the source lookup's budget ends without a write-up, the final answer states that the requested findings are unverified instead of claiming a result or presenting the generic budget sentence as a completed answer; it names a same-conversation `continue` reply, without asking the person to repeat the question. A follow-up from the original requester reconstructs the original ask across successive budget-ended continuations, verifying each prior budget close and requester (including earlier thread pages), rather than trusting a prior source result; all new tool calls run under the follow-up requester's grant. An unreadable question fails closed, and a different sender cannot continue the previous requester's source lookup. An answer with partial findings remains labelled as partial. The ordinary-run outcome records the typed ending and raw write-up presence before fallback wording. The final card shows an absent or unknown answer separately from the unchanged source checklist; checked research steps never establish answer delivery. Same-requester continuation reads that durable budget ending, not words in the reply. A legacy budget close with no saved outcome fails closed. Research source lookups use the same boundary.
3. Never claims abilities it lacks and never fabricates: when a request needs a code change, a PR review, or web research it says so and points at the [agent](../vocabulary.md#agent) that can, **in the person's own words, never as a directive line to type** — the prompt says a plain message reaches those agents by itself ([routing-and-config.md](routing-and-config.md) item 21: a change routes to `ship`, the write door) and gives the plain-words form as the example ("in acme/api: fix the failing login test", "review `<PR URL>`"), and forbids handing back a command or an `agent:…` line. The redirect points at **asking in plain words right where the person is** — a [follow-up](../vocabulary.md#follow-up) in the same thread or anywhere in the channel: under the operator ([routing-and-config.md](routing-and-config.md) item 29, on by default) the door reads every message, thread replies included, and starts the right agent from the person's own words — so the prompt forbids telling the person to post a new top-level message, re-post, re-ask elsewhere or retype anything (issue 2046: that retype hand-back is the shape record 0069 retires — a write ask `general` cannot run is the door's to hand to the ship route with the [thread](../vocabulary.md#thread)'s words, never the person's to re-say). The prompt also forbids asserting a hand-off it cannot make — never "I'll hand this to the coding agent": `general` cannot start another agent's run, so it never says it will hand off, route, forward or start anything (interim until the operator of record 0057 binds before any agent runs). A general answer that ends in "run `agent:ship …`" is the router's miss turned into the person's chore, the shape the door exists to remove; the redirect names what was found and how to ask, not what to type. When it acts, it reports exactly what the tool did (issue number + URL) and never claims an action it did not perform. A loosely-named repo ("the switchboard app") is resolved with `github_repos` or the thread, not by asking. Deleting an issue happens only on an explicit delete request — closing is an update; and since GitHub grants deletion only to a repo admin's user credential, the App-backed delete reports its refusal and offers to close instead ([github-tools.md](github-tools.md) item 1). Regression pins: inventing a repo URL and telling the user to run git; bouncing "open an issue on the switchboard app" to `agent:coding` with "I have no tools for that".
4. **Runs on machine class `none`** (`AgentDef.machine`): a general ask never creates, reconnects, or touches a sandbox or workspace — even when remote execution (E2B/Cloudflare) is configured, and even when the sandbox credential is missing. The GitHub tools are REST calls in the bot process, not a workspace. See [execution.md](execution.md) behavior 7.
5. **Knows its own settings — and itself.** Like every agent, its system prompt carries the dispatcher's config block ([routing-and-config.md](routing-and-config.md) behavior 8) naming the agent/model that actually resolved and how users tune them, and the self-description block (behavior 11) saying what Switchboard is, which agents exist, how residents work, and where the source and specs live — so "what are your settings?" and "how does your resident system work?" are answered from fact, never with a confabulated "I'm stateless" or a public-web 404.
6. **Issue writes are permission-gated per repo** ([github-tools.md](github-tools.md) item 3): `restrict.repos` against the requesting user's `repos` grant, checked before any API call; a refusal is reported to the user, not retried.
7. **Runs on pi as a child of the bot.** Like every preset it runs on the pi harness ([harness-pi.md](harness-pi.md) item 1); having no workspace, its pi is a child of the bot itself: none of pi's own shell or file tools, the `assistant` toolset relayed and run in the bot as the requesting user, pi reaching the model proxy over loopback, the same record ([harness-pi.md](harness-pi.md) item 12).

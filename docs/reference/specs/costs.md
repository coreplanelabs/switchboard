# Costs dash: what a deployed group costs per day

`GET /costs` is an Access-gated, read-only page (plus a JSON twin) showing what a named group of deployed pieces costs per day on every meter Cloudflare bills a Workers deployment on, read live from the providers' own billing datasets and priced at list — and what share of the account's whole Cloudflare spend that is, so a deployer can tell this software's cost from everything else on their account. The first group is `switchboard` — the bot Worker + its container, the resident/sandbox/memory Workers and their containers — but the config is a map of groups so the same page serves other apps on the account later. LLM spend is layered in from the Anthropic Admin API when an Admin key and a per-group workspace are configured.

## Configuration

```yaml
costs:
  cloudflareAccountId: <32-hex>
  cloudflareAccountName: acme-infra            # optional: printed beside the account's share; else the id's first hex
  cloudflareTokenEnv: CF_ANALYTICS_TOKEN      # default
  anthropicAdminKeyEnv: ANTHROPIC_ADMIN_KEY   # default; optional feature
  groups:
    switchboard:
      label: Switchboard
      workers: [switchboard, switchboard-resident, switchboard-sandbox, switchboard-memory]   # the attribution root
      containerApps: { <application id>: bot, <application id>: resident, <application id>: sandbox }
      durableObjectNamespaces: { <namespace id>: bot DO }   # optional labels — a namespace hosted by a listed Worker is attributed anyway
      r2Buckets: { <bucket name>: label }                    # optional — a bucket named <worker>-cache (the template's name) is attributed anyway
      anthropicWorkspaceId: wrkspc_…          # optional
```

| Secret | Scope | Effect when absent |
|---|---|---|
| `CF_ANALYTICS_TOKEN` | Cloudflare API token, **Account → Account Analytics: Read** only, scoped to the one account | `/costs` answers 503 (feature off) |
| `ANTHROPIC_ADMIN_KEY` | Anthropic Admin API key (`sk-ant-admin…`) | LLM column absent; page says "LLM spend not configured" (never $0) |

Container application ids: `GET /accounts/{id}/containers/applications`; DO namespace ids: `GET /accounts/{id}/workers/durable_objects/namespaces`. A group's LLM spend is the cost report filtered to `anthropicWorkspaceId`; the bot's API key must live in that workspace for the attribution to be right (the org default workspace reports as `null` and is never attributed to a group).

## Behavior

1. **Pricing model is Cloudflare's.** vCPU bills on **active** seconds (`cpuTimeSec`); memory and disk bill on the **provisioned** size for every awake second (`allocatedMemory` / `allocatedDisk` byte-seconds). Durable Objects bill **duration** ($12.50 per million GB-s, metered as 128 MB × active wall-clock seconds) plus requests ($0.15/M). Duration comes from `durableObjectsPeriodicGroups.sum.duration`, which is already the billable GB-s per namespace — **not** from summed request wall time (`durableObjectsInvocationsAdaptiveGroups.wallTime`), which double-counts overlapping long requests (SSE streams, `exec`) and has been observed ~2× above billed (bot: 179k s summed vs 86k s active on one day). The other meters a Workers deployment is billed on are priced too, from their own datasets: SQLite rows read ($0.001/M) and written ($1.00/M) from the same `durableObjectsPeriodicGroups` rows; SQLite storage ($0.20/GB-month) from `durableObjectsSqlStorageGroups`; Worker requests ($0.30/M) and CPU time ($0.02 per million CPU-ms; the dataset reports microseconds) from `workersInvocationsAdaptive`; R2 storage ($0.015/GB-month) from `r2StorageAdaptiveGroups` (payload + metadata) and operations from `r2OperationsAdaptiveGroups` — class A $4.50/M (an action that mutates or lists: `Put*`, `Create*`, `Complete*`, `Upload*`, `List*`, `Copy*`), class B $0.36/M (`Get*`, `Head*`, `Usage*`), deletes and aborts free, an action not met before classed by its verb so it is priced rather than dropped; Workflows from `workflowsAdaptiveGroups` — steps ($0.80 per 100,000: the step endings, `STEP_SUCCESS` and `STEP_FAILURE`, summed per Workflow per day; `ATTEMPT_*` are the retries inside a step and `WORKFLOW_*` the instance's own lifecycle, neither a step on the bill) and persisted state ($0.20/GB-month on the day's peak bytes; no analytics dataset reports them, so the GraphQL source answers 0 there and the meter prices what it can see), while a Workflow's requests and CPU time bill at Workers rates onto the hosting Worker's own row and are never re-metered. A GB-month rate is prorated per day over the mean month (`DAYS_PER_MONTH` = 365.25 ÷ 12) on the day's peak bytes. Constants in `CLOUDFLARE_PRICES` (Cloudflare list prices; re-check against the pricing pages when they move); the page states them. Gross — plan fees and included allowances are not subtracted. Not priced: Workers Logs volume (no analytics dataset exposes it) and Access (free at this seat count); the page says so.
2. **Attribution is by Worker script, and the account is the denominator.** A group names its Workers; everything Cloudflare bills hangs off a script, so `attributionOf` derives the rest: a Durable Object namespace is attributed to the Worker that hosts it (the `durableObjectsInvocationsAdaptiveGroups` join of `namespaceId` → `scriptName`, any day in range), labelled by a `durableObjectNamespaces` entry when there is one and by its Worker's name otherwise — a listed namespace is attributed even when the range shows it no invocation; an R2 bucket is attributed when it carries exactly the name the deploy templates give a Worker's bucket (`<worker>-cache`, the resident template's `{{script}}-cache`) or is listed in `r2Buckets` — a prefix match would let a stranger's `switchboard-2-tfstate` inflate `switchboard`'s figure on a shared account; a Workflow when it carries exactly the name the resident template gives its refresh Workflow (`<worker>-refresh`) — the Workflows dataset names no script, so the name is the only join, and the Workflow's steps and state land in the hosting Worker's group; Worker requests and CPU by `scriptName`; container applications only by the configured `containerApps` map (no dataset ties an application to its Worker). A resource that appears after the config was written is therefore counted, not silently dropped, as long as it belongs to a named Worker. Every row in the account — attributed or not — is priced the same way into `account.cloudUsd`, so the page can say what share of the account's Cloudflare spend this group is; the report carries the `attribution` it used (Workers, namespaces, buckets, Workflows, apps) so a reader can check what was counted. LLM rows count only when `workspaceId` equals the group's `anthropicWorkspaceId`.
3. **One row per UTC day, zero-filled.** `resolveRange(?days)` gives 1–90 days (default 30, garbage → default) ending today; today is flagged `partialLastDay`. The averages use full days only: *Yesterday* = last full day, *7-day average* (absent, and said so, when the range has no full day). *Projected month* is two run-rates added and × 30.4: cloud from the last seven full days, LLM from the closed days that have LLM spend (from the first such day on, so a workspace younger than the range is not diluted by its leading zero days) — and while a rate has no full day to stand on, from the open day scaled to a full one by the fraction of the UTC day elapsed at the report's `generatedAt` (floored at one hour). The tile's second line names both rates and what each stands on. One 7-day rate over the totals would read an order of magnitude low on a young workspace, since model spend dwarfs the Cloudflare spend. A range with no full day (`?days=1`) leads with *Today so far* instead of an empty *Yesterday*. The range switcher is a pill row beside the group pills — `today · 7d · 30d · 90d` — not header small print; a shorter range costs fewer buckets, never more. The short preset is today in UTC, not a rolling 24 hours: both billing sources bucket by UTC day and the cost report offers nothing finer, so a rolling window would be a figure neither source can stand behind.
4. **LLM unavailable ≠ $0, and LLM is dollars, not a share.** With no Admin key (`NullLlmCostSource` → `null`) or no workspace on the group, `llmAvailable` is false and the page says "LLM spend not configured"; the totals then exclude LLM rather than reporting a fake zero. The *LLM spend* tile is the range's LLM dollars with yesterday's and the open day's figures beneath — a share of the total was retired because model spend runs an order of magnitude above the Cloudflare spend, so a percentage said nothing.
4a. **The open day is estimated, and says so.** The Anthropic cost report is the invoice and closes late: a day gets its bucket some hours after midnight UTC and the open day never has one (nor does the usage report at `bucket_width=1d`, read live against the API when this was written). So the Anthropic source prices every day after the cost report's last bucket from the **hourly** usage report — `GET /v1/organizations/usage_report/messages?bucket_width=1h&group_by[]=workspace_id&group_by[]=model&limit=24` for that day, paginated — summed per workspace × model and priced at `ANTHROPIC_PRICES` (list, per family: input, output, 5-minute and 1-hour cache writes, cache reads; a dated release id resolves to its family through `anthropicPriceOf`, and `claude-fable-5-1` is a different family from `claude-fable-5` because its cache reads bill differently). Such a row is `estimated: true`; the day carries `llmEstimated` and the page marks it (tile, table row, hover, a line under the chart). A model the table has no price for is not $0 in silence and does not fail the page: its tokens land in `unpricedTokens` / `llmUnpricedTokens` and the page says some tokens are outside the estimate. Closed days are never re-estimated: a cost-report bucket with no rows still closes its day. At most the trailing `MAX_ESTIMATED_DAYS` (three: today plus two days of report lag) are estimated, read concurrently — an older day with no bucket had no spend (a new workspace or organization), and a page load must never become one live usage read per day of a 90-day range. `ANTHROPIC_PRICES` is a copy of the pricing page; re-check it when the page moves.
5. **Sources are seams.** `CloudflareUsageSource` and `LlmCostSource` are interfaces; the real ones take an injectable `fetch`. The Cloudflare source POSTs one GraphQL query (`containersUsageAdaptiveGroups` + `durableObjectsPeriodicGroups` + `durableObjectsInvocationsAdaptiveGroups`, `date`-bucketed, exclusive end = start of the day after `to`) with the token only in `Authorization`; a non-200 **or** a GraphQL-level `errors` array (the API 200s on those) throws. The Anthropic source walks `GET /v1/organizations/cost_report?group_by[]=workspace_id&bucket_width=1d&limit=31` page by page (`next_page`) — with `ending_at` at the start of the open day when the range has one (the report never holds that day, and the API answers 400 to a range that begins there), so a range that is only the open day asks the cost report nothing and is estimated outright — converts cent-strings to dollars, and refuses a non-USD row — or a report still paginating past 20 pages — rather than mis-summing or returning a truncated total; then the usage report for the open days (item 4a), with the same page cap and the same status-by-name failure. No error message carries the credential.
6. **Live per request, nothing stored.** Every page/JSON load calls both sources; there is no cache and no persistence (AGENTS.md invariant 6 is moot — there is no state to lose).
7. **Routes.** `/costs` and `/costs.json` → the first configured group; `/costs/<group>` and `/costs/<group>.json`; group slugs are `[a-z0-9-]{1,40}`. GET-only (405 otherwise). Unknown group → 404. Not configured → 503 naming the config keys. Upstream failure → 502 with a capped reason, never a 500. JSON shape per day: `durableObjects` is DO **duration** cost keyed by namespace label; DO **request** cost is the sibling `doRequestsUsd` (not attributable to a namespace). A consumer wanting the full DO figure sums both — `totals.byResource.durableObjects` already does.
8. **Page.** The server serves the shared web shell with the report + group list as the `CostsSeed`; `web/src/pages/CostsPage.vue` (+ `CostChart.vue`, the pure math in `web/src/lib/costs.ts`) renders inline SVG stacked bars (one rect per day × component, and one transparent column per day that is the one hover target: pointing at it opens a tooltip panel — the day and its total on top, then one row per component that cost anything, largest first, the LLM estimate tagged `est.` — a fixed-width, non-wrapping panel that is a child of the chart's host rather than of its scroll box (so it never grows the card or shows scrollbars) and flips to the left of the pointer near the right edge and above it near the bottom; the whole breakdown is also the column's `aria-label`; the browser's native SVG `<title>` tooltip was retired because it appears late and is easy to miss; the segments carry no tooltip of their own since the column above them takes the pointer), a legend whose entries link to where each series is billed, a per-resource split whose rows link likewise, and a full table view newest first (the open day on top). The *Share of account* tile names the account (`costs.cloudflareAccountName`, else the id's first eight hex) and links it to the Cloudflare dashboard and its billing page; the footer links every attributed Worker to its metrics page and every bucket to its R2 page; the LLM series links to Anthropic's cost page. The report carries `account.id`, `account.name` and `generatedAt` for this. Hostile strings render as text (the seed island escapes every angle bracket, and the components never render raw markup); the same `WEB_HTML_HEADERS` (strict CSP, `X-Frame-Options: DENY`, `no-store`) as `/runs`. Series colors are the validated categorical set with dark-mode steps, assigned by first appearance, never re-ranked.
9. **Access gate.** `/costs*` sits in the same fail-closed Access branch as `/runs*` and `/residents*` in `src/index.ts`. The startup log states `GET /costs (<groups>; LLM on|off)` or the 503 reason.
10. **Cost by user, the data first.** Who spent what is a question the run history answers, not the billing sources: every record carries `usage` (its `model.turn` tokens per model, summed at finish) and the store answers `usageByUser` — per requester and UTC day of finish, a child billed to its parent's requester, wall-clock summed, older records priced from their stored events as they are asked about ([run-history.md](run-history.md) item 56). The requester is the **person**: a run an app relayed for them ([slack-channel.md](slack-channel.md) item 13) and a run their bound ingress token, MCP token or CLI sent ([authorization.md](authorization.md) item 15) carry their `slack:U…` as `userId`, so one person is one row whatever they came in through, and the **me** toggle claims all of it; a credential nobody bound (`http:cron`, an unbound bearer) stays its own row.
10a. **Cost by user, the page.** `?view=users` on a group's page opens the **By user** tab (the tiles and the chart stay as the group's context; the daily split and table step aside), and `/costs/<group>/users.json` is its twin; the range and group pills keep the tab, and the tab keeps the range. The report (`buildUserCostReport`, pure and unit-tested; the service only fetches its two inputs) is one row per requester over the range, largest total first: runs, **LLM** — the user's tokens per model at `ANTHROPIC_PRICES` (the provider prefix dropped from the span's model ref; cache writes at the 5-minute rate, since the spans record one cache-write count), a model the table has no price for reported as unpriced tokens on the row rather than $0 — **Cloud allocated** — each covered day's `cloudUsd` from the daily report split by the user's share of that day's run wall-clock, said to be an allocation, not a meter; a day with spend and no runs is unallocated, never invented onto anyone — the total, and its share of everything attributed. A filter narrows by name or id; **me** keeps the signed-in viewer's rows: the Access identity's email is matched against the Slack email of each user in the report (`resolveUserEmail`, one lookup per distinct Slack user, cached for the process), the matched ids ride in `viewer.userIds`, and the toggle is disabled with the reason when nothing matched. The lookup takes the platform-namespaced id (`slack:U…`), the same `slackEmailLookup` the MCP connect ticket uses (its first version passed the bare `U…` and matched nobody). The email read needs the `users:read.email` bot scope (in the manifest and `REQUIRED_BOT_SCOPES`, so `/healthz` names it when the installed app lacks it); without it nobody matches. The range is the history's, not the calendar's: `coverage.from` is the latest of the range's start, the store's oldest finish and its retention cutoff, the coverage line says where the data begins, that earlier days are past the retention window when the range was clamped, and how many runs are still being priced (`pending`, the backfill outstanding). One plain reconciliation line, over the covered days that have a workspace figure: LLM attributed against the group's own LLM figure (invoice or estimate) on those days, how many days that is, the unattributed remainder named for what it is (the router, review abridges, runs without a record, list-vs-invoice drift), then the days whose runs spent tokens against a zero figure — spend billed outside this workspace, the bot's key before it moved in — counted apart with their dollars and never subtracted into a negative remainder (a range with no figure at all says so instead of comparing; when the compared days themselves attribute more than the workspace shows — list above invoice, or a key that moved mid-day — the line says how much more in words, never a negative dollar), cloud allocated and cloud on days with no runs. With run history off the report is empty and the page says so. The by-user read rides the same request as the daily one, live and unstored (item 6), behind the same Access gate (item 9); an upstream failure is the same capped 502.

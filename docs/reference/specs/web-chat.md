# Web chat — the home page

`/threads` is a chat: a signed-in person types a plain request and watches the run it starts, with its route, its work and its reply, on the page. [Record 0043](../../decisions/0043-the-home-page-is-a-chat-the-browser-is-a-channel-and-a-turn-is-a-run.md) decides the shape: the browser is channel adapter #5 over `dispatch()`; a **conversation** is the runs of one `web:` thread, read from the run store and never stored twice; an **assistant turn** is the run itself, rendered by the run page's one view model over the same event stream; and the page's delight is motion over surfaces that already exist, under rules a test checks. This spec covers the page (the record's rollout PR 2, served over fixtures) and names the adapter's rows as `[gap]` until PR 3 lands them.

## Behavior

1. **Routes and the ways in.** `/threads` is a new conversation; `/threads/<conversation>` is one conversation; both render `HomePage.vue` from a `HomeSeed`, and the whole surface sits under the one prefix so the Access application covers it with one rule. `/` redirects to `/threads`. **Threads** is the first section of the site nav on every installation. Every page's header opens with the constant part, the mark and the word Switchboard as one link to `/threads`, and the page's own title beside it as a subordinate label; the product is always named, the page is what changes. The name is the system's own: a run is a unit of work, a thread a unit of context, and a thread on any channel is one; the rail lists the person's threads across channels (record 0043's amendment), a thread from another channel by its whole key, read-only (item 7). The runs page stays the operator surface: stop, kill, scheduled, costs and delivery never move here. `/threads*` sits behind the dashboard gate like every section (the Access application must list the `threads` prefix); `/` is not gated and answers `302` to `/threads`.
2. **The seed is the conversation's runs.** `HomeSeed.turns` is one `HomeTurnSeed` per run of the thread, oldest first: the run as every listing views it (`RunView`, a live row with its `token` as the index carries it), the request text (the `input` event), the reply text (the `answer` event) and the route it ran under (the `route` event). `conversations` is the rail's RECENT list: the viewer's own threads across every channel — the runs `ownedBy` the viewer's actor (their session and, when linked, their person) grouped by `threadKey`, the newest 20 threads, newest first — each titled by its first request's first line cut to 60 characters (`threadTitle`, from the oldest run that recorded an `input` — a run that died before publishing one is skipped; the oldest run's label only when no run has a request), the same line cut to 240 as its `excerpt` (what the row's tooltip says in full, `EXCERPT_MAX`), with its channel's platform as `surface`; a `web:` conversation of the viewer's own lane is linked by its conversation id, any other thread by its whole key. Bounded by the bot: nothing pages on this page; the runs page holds everything. `elsewhere` is set when the open thread is another channel's: its platform and, when a run recorded one, the thread's own link. `suggestions` are the empty state's chips (`suggestionsFor`): what Switchboard does well, grounded in the viewer's own runs — a review on the repository they last worked in (or a pull request by its link where GitHub is on), why their last run failed (or what it did), the agent and model a run here gets, an MCP server where MCP is on — and one that asks what it can do, last; every chip is a read or a request the front door hands back, never a change started blind, so a click is safe; `commands` are the `/` palette's rows, every command the registry exposes to chat and the viewer may run, in chat form with the command's own `describe` (record 0008); `retentionDays` bounds the conversation's life and the rail says so. The thread's **silent intake receipts** ([slack-channel.md](slack-channel.md) item 15; [run-history.md](run-history.md) item 59) ride the same list as `HomeReceiptTurnSeed` rows (`kind: "receipt"`, the verdict's `reason`, its `decidedAt`), interleaved among the runs by `decidedAt` (`interleaveReceipts`; a run's stamp is `receivedAt ?? startedAt`); an `addressed` receipt seeds nothing — its run is the turn. Only a thread the viewer may see — one with at least one readable run — is asked for its receipts, so a receipt never reveals a thread its runs would not (the foreign-thread `404` stands and the ledger is not read for it); `WebChatDeps.intake` is null when the run ledger is off, and a null or failing ledger seeds the runs alone. A receipt turn never enters the history a run reads (`historyOf` skips it — the message's text was never stored) and never opens a stream. A **hosted ship parent's** turn ([record 0060](../../decisions/0060-a-ship-pipeline-is-a-live-run-for-its-whole-life-and-runs-on-every-channel-that-can-open-a-thread.md); `RunView.hosted`) seeds and streams like any turn, but the composer never reads it as the thread's live run — it occupies no thread, its units run elsewhere — so `liveItem` skips it: with only a hosted turn live the control reads `send`, and a normal live turn beside it keeps `steer`/`stop` as ever.
3. **Sending.** Enter (not Shift+Enter) POSTs `{ text }` to `sendUrl` with same-origin credentials; a chip sends its words on click, no Enter. On send the person's turn is drawn at once, held back (`data-pending`) until the answer, and the mark in the header pulses once down its route. A `202 { runId, viewPath }` mounts an assistant turn on the run's own stream — and, when the page was opened at `/threads`, rewrites the address to `/threads/<conversation>` without a load or a history entry (`browser.replaceUrl`), so a reload finds the conversation that now exists: `viewPath` is `/runs/<id>?t=<token>`, and the page derives `/runs/<id>/events?t=…` and `/runs/<id>/stop?t=…` from it (`liveUrls`); anything else in the path is refused. A `200 { reply }` is one of three things (`classifyReply`): a **hand-back**, a reply beginning `HAND_BACK_PREFIX` (`To run this:`), fills the composer with the command, focused, with the hint `Enter runs it`, and paints no turn; a **steer acknowledgement** (`↪ Folded into …`) paints nothing, because the live turn's `input` event confirms the turn already drawn (item 5); any other reply is an **inline turn**, painted once and never stored. A failed send keeps the person's turn and says why under it (`not sent: <reason>`).
4. **A turn is a run.** `AssistantTurn.vue` owns one `createRunPageModel` (the run page's fold, live-view item 18) and attaches to the run's stream through the run page's own `attachRunStream` (`runStream.ts`: the seq dedupe, the named frames, the phases; nothing of the transport is the turn's own). Live, it draws: the receipt chip once the `route` event arrives (else the agent's chip from `run_meta`), the model's real name once known, the pending row while the model is silent and nothing runs (the run page's own `PendingTurnRow`: ∿, the model's badge, a verb from the shared list walked by the silence's length, the elapsed since the last stamped event, live-view item 18), the work open by default as the run page's own `StepBlock`s, and the reply whole when the `answer` lands. `finished` freezes the clock at the server's stamp (at the elapsed it shows, for a turn a `202` mounted without a server clock); `end` closes the stream and the turn becomes the finished shape in place. A stream the browser gives up on (`disconnected`) keeps the turn live for the conversation, so the composer stays `steer`: the clock freezes where the stream dropped and a row says so with the run's own page as the way on; nothing is drawn as over until `end` or a reload. Finished, closed, a turn is the receipt, the reply (or the record's outcome word when it made none), and one line of facts: the duration on the heat scale and `open run`; its work folds under it and reads the run's replay once, on first open, from `/runs/<id>/events`. The head's elapsed is the turn's one ticking number: the fold's summary is the step count alone. The relation reads both ways: a run's own page says `in thread ›` beside its Request, linking `/threads/<key>` (the seed's `threadKey`, whole — `web:<sub>:<id>` or `slack:C…:1712.34` — so a Slack run's page opens the thread read-only here), and a row on the runs index leads its `⋮` menu with **Open thread**, the source's own link after it as `Open in Slack`; a run whose registry row is gone has no key and no link (`threadHref` in `indexRow.ts`, the one spelling).
5. **A message during a live run.** The composer's control reads `steer` as soon as there is text, and the POST goes to the same route; the pipeline steers it (thread-admission item 1) and answers the acknowledgement, which the page ignores. The live turn's stream carries the `input` event the harness records when it drains the inbox; the page matches it to the newest unfolded person's turn with the same words (`matchSteer`) and stamps that turn `↪ folded in at <m:ss>`. One message, drawn once. The request's own `input` event is the turn the page drew and stamps nothing.
6. **One control, two states.** The send button is `send` while no run is live in the conversation (disabled only with an empty box), `stop` while one is and the box is empty (a soft stop, `POST <stopUrl>&mode=soft`), `steer` while one is and there is text. It is never disabled while a run is live; its icon crossfades between the three. The hint under the box names the state and is always laid out (its height is reserved; only its opacity changes), so nothing on the page shifts when it appears.
7. **The rail, the shortcuts and the empty state.** The rail is a column from `md` up and a sheet from the left on a phone; the header's panel button is its one control on both — from `md` up it hides and shows the column (`aria-expanded`, its label following the viewport across a resize), on a phone it opens the sheet. The column opens 18 rem wide and is the person's to size: a handle at its right edge (`role=separator`, in the gap) follows a drag between 14 and 28 rem (`RAIL_WIDTH`, `clampRailWidth`), the arrows step it one rem, Home and End are the band's edges, a double-click resets it, and the width never transitions — it follows the hand. The width and whether the column is hidden are the two things this browser remembers about the page (`RAIL_PREF`, `browser.readPref`/`writePref`; a blocked storage keeps nothing and the page still works); the sheet has neither the handle nor a memory, and where the pointer is a finger the handle is not drawn. It holds, in order: the **new-thread** control, the one solid control on the page, with its shortcut `⇧⌘O` in view (`⌃⇧O` where there is no ⌘); a **filter** field that narrows the recent rows by a fuzzy subsequence match (`filterRows`; Escape clears), reached by `⌘K` from anywhere on the page (a hidden column is shown again first; on a phone `⌘K` opens the sheet, then focuses); the RECENT rows — each a `RouterLink`: a conversation is an address whose seed the router loads in place ([live-view.md](live-view.md) item 31), like every section — each the title and a short distance (`compactAge`: `now`, `3m`, `1h`, `2d`, then the date as the runs index writes it), a live dot on one whose run is in flight, and an ink bar on the current one — and, once the pointer has rested on a row for 500 ms, a tooltip (`ThreadTip`, laying out `threadTip`'s facts): the first request's line in full (the seed's `excerpt`), the moment as a date and time, the channel (`Web` for the person's own lane; else the surface's name, led by the Slack mark for a Slack thread, and that it is read-only here), the run count, and `live` when a run is in flight. No row wears a tag: a thread from another channel is told apart on hover and on opening (the read-only line below), and the row's room is the title's; an **All runs** link to `/runs`; the retention sentence; and one sentence on how the two pages relate — *A thread is a conversation; each message you send is a run. Runs lists every run across everyone's threads* — with `Runs` the link, because the two words were never explained anywhere a reader stood. The rail's live dots are the **feed's**, not the seed's: the page opens `/runs?stream=1&mine=1` (live-view item 29's narrowed feed — every run of the viewer's in flight on any channel) and reads it through `railLive.ts` (`applyIndexEvent`, `liveRailRows`): until the feed has replayed, the seed's `live` flags stand; from then on a row's dot follows the feed, a run the seed did not count adds to the row's count and moves its distance, and a thread the seed did not list (started since the page loaded) gets a row on top titled by the run's label snippet until a reload reads its request. A reconnect replays the active set, so the map is cleared on the second open and a finish the page missed while away never stays lit. The rows are joined by thread key: a row's short id is a conversation of the viewer's lane (`HomeSeed.lane`, `web:<sub>`), a key with a colon is itself. The empty state hangs from the top at a capped offset (`clamp(1.5rem, 14vh, 9rem)`), so a tall screen never sinks it to the middle and a short one keeps it in reach; it lands in a choreography, each part 40 ms after the last: the mark (drawing its route, then floating), the greeting naming the person and the time of day (`greeting`, from the browser's local hour, following the clock), the line under it, the composer, the chips. The composer is focused on load. A thread from another channel (`elsewhere`) opens **read-only**: its turns draw, there is no composer, and a line at the foot names the channel and links to the thread — a reply belongs where the thread is; another person's `web:` lane (read by an all-channels holder) is named as theirs, with nowhere to reply. Where the pointer is a finger (`pointer: coarse`), every control on the page is at least 44 px tall: the chips, the rail's control, filter and rows, the palette's rows, the composer's control; the hover lifts are off there.
8. **The composer.** The box grows with its text to eight lines; its hairline brightens to ink on focus and a line of colour travels once around the ring and fades as it arrives, leaving the ink border (the `ring-sweep`: a rotating conic gradient running the data blue into the mark's green into white, masked to a 2 px ring with a soft glow, one second), on every focus and once as the empty state lands. The box and its ghost share one metrics class (`composer-text`), so the grey completion lands exactly after the caret. Its placeholder guides the hand by state (`placeholderFor`): what to ask while nothing is live, what the box does while a run is, nothing after a hand-back (the filled command is the guide). Enter sends and Shift+Enter breaks a line. `/` at the start of a message opens the **palette**, a level-aware completer over the seed's commands (`slashCompleter.ts`, one map built from the chat forms): `/` offers the groups, `/config ` the verbs of `config`, `/config set ` the command's arguments and options (`HomeCommandSeed.args`, `.options` — the same forms `help` prints); a word narrows its level by prefix first, else fuzzily on the word or its description; at every level the best match is **ghost text** after the caret, the rest of the word in grey, and Tab or → (with the caret at the end) accepts it and opens the next level on a space, the arrows changing which match is the ghost; once the words are a command the ghost is its remaining usage, shown and never accepted, and a word starting with `-` completes the options not yet used; Enter accepts a match and, once the words are a command, sends; Escape closes the palette until the next word; a word that settles on no group or verb closes it (the person is typing something else). The slash never reaches the bot: the page strips it from a message that names a command (`stripSlash`), and the bot reads `<group> <verb>` at the start of a message. A message with a second line or a slash mid-sentence is prose.
9. **Following the transcript.** New content scrolls the transcript only when the reader was already at the bottom (`shouldFollow`, 60 px of slack); otherwise a `↓ new` pill appears and a click jumps down. The tab title is the conversation's title, `(n)` ahead of it while runs of the viewer's are live — the feed's count (item 7), plus the open conversation's own run until the feed names it — and the favicon is the index's live dot while that count is above zero, so the Threads tab shows live whenever the Runs page would show one of the viewer's runs live, not only while the open conversation has one.
10. **Motion rules.** Every transition the page adds is opacity plus at most 8 px of translate along Y, between 120 and 200 ms, ease-out; under `prefers-reduced-motion` every move keeps its opacity and drops its travel. The vocabulary is four moves (`sb-rise`, `sb-fade`, `sb-move`, `sb-stagger`) and three named exceptions under a second, each off under reduced motion: the mark's route draw (`mark-draw`), the mark's pulse on a send (`mark-pulse`) and the composer's ring sweep (`ring-sweep`); the mark's idle float (`mark-idle`) moves it 1 px over 4.6 s. Nothing else on the page moves that the person did not cause, except the pending row's pulse and a clock's tick. The design system's own rules hold: chroma is data alone (the receipt chip in the preset's hue, a failed outcome, the heat ramp), the type ladder is the run page's three voices.
11. **The adapter** (`src/channels/web.ts`, record 0043). `POST /threads/<conversation>/send` sits behind the dashboard gate; a send must be same-origin (`originAllowed`, as `/api` writes are), JSON, under the ingress body cap, and into the session's **own lane**: the thread key is `web:<sub>:<conversation>` for a plain id, and a whole key from another channel is refused `403` (read here, answered there). The message is the gate's identity, never the request's: the browser session is the credential (`access:<sub>`), and when record 0042 linked it to its person the message names the **person** as `userId` (with their name) and the session as `authenticatedAs` — the shape a bound ingress token sends ([authorization.md](authorization.md) item 15, `requesterOf`) — else the session itself, named by its email; `channelId` is `web:<sub>` (`dm` in `visibilityOf`), `receivedAt` the adapter's clock, and `access` is a chat surface in `resolveChatActor` (the browser actor, whose baseline holds every group's read plus `memory:write` and `mcp:write`, item 9). The IO is the ingress IO's (`WebIO`: replies collected, `runStarted` raced against completion) with `history()` the thread's turns read from the run store as the person's and the agent's lines, stamped — the asking run left out, as every channel's history excludes the triggering message. A run created → `202 { runId, viewPath: /runs/<id>?t=<token>, threadKey }`, the token read from the registry after `runStarted` (a run gone from the registry first — discarded — is answered as a run-less request); no run → `200 { reply, run? }`. The seeds: `/threads` mints a 20-hex conversation id; `/threads/<id>` is `listRuns({ threadKey, status: "all", visibleTo: readableRuns(actor) })` for the newest 20 runs, oldest first, plus one `getRun(id, { include: "messages" })` each (`turnOf`: the first `input`, the last `answer`, the `route` event; a live run's token from the registry); another channel's thread the viewer may see nothing of is the same `404` an unknown run gives; the viewer's own empty conversation opens empty. The rail is item 2's, the palette `paletteCommands` (every chat-exposed command `authorize` admits the actor to, in `chatForm` with its `describe`), the chips `suggestionsFor`. The request's trace root is `channel: web`; the thread-key namespace `web` is a production namespace the binding purge refuses.
12. **A silent receipt is a read-not-answered turn** ([record 0058](../../decisions/0058-a-thread-reply-is-read-before-it-is-answered-intake-decides-whether-the-bot-was-addressed.md); the intake gate). A Slack thread the gate stayed silent in shows each `silent` receipt where the run would have been: one muted line (`SilentTurn.vue`) — the ◌ glyph, **Read, not answered**, the verdict's reason and the moment (`decidedAt`, exact on hover) — in order among the runs, so a person reading the thread here sees what the gate read and why it did not answer, never a blank gap. The line is not a run: it opens no stream, folds no work, carries no receipt chip, and the conversation's title still comes from the first person's turn. The message's own text is never shown — the gate stores only the receipt (run-history item 59), and the thread's channel holds the words.

# Web chat — the home page

`/threads` is a chat: a signed-in person types a plain request and watches the run it starts, with its route, its work and its reply, on the page. [Record 0043](../../decisions/0043-the-home-page-is-a-chat-the-browser-is-a-channel-and-a-turn-is-a-run.md) decides the shape: the browser is channel adapter #5 over `dispatch()`; a **conversation** is the runs of one `web:` thread, read from the run store and never stored twice; an **assistant turn** is the run itself, rendered by the run page's one view model over the same event stream; and the page's delight is motion over surfaces that already exist, under rules a test checks. This spec covers the page (the record's rollout PR 2, served over fixtures) and names the adapter's rows as `[gap]` until PR 3 lands them.

## Behavior

1. **Routes and the ways in.** `/threads` is a new conversation; `/threads/<conversation>` is one conversation; both render `HomePage.vue` from a `HomeSeed`, and the whole surface sits under the one prefix so the Access application covers it with one rule. `/` redirects to `/threads`. **Threads** is the first section of the site nav on every installation. Every page's header opens with the constant part, the mark and the word Switchboard as one link to `/threads`, and the page's own title beside it as a subordinate label; the product is always named, the page is what changes. The name is the system's own: a run is a unit of work, a thread a unit of context, and a thread on any channel is one; the rail lists the person's threads across channels (record 0043's amendment), a thread from another channel by its whole key, read-only (item 7). The runs page stays the operator surface: stop, kill, scheduled, costs and delivery never move here. `/threads*` sits behind the dashboard gate like every section (the Access application must list the `threads` prefix); `/` is not gated and answers `302` to `/threads`.
2. **The seed is the conversation's runs.** `HomeSeed.turns` is one `HomeTurnSeed` per run of the thread, oldest first: the run as every listing views it (`RunView`, a live row with its `token` as the index carries it), the request text (the `input` event), the reply text (the `answer` event) and the route it ran under (the `route` event). `conversations` is the rail's RECENT list: the viewer's own threads across every channel — the runs `ownedBy` the viewer's actor (their session and, when linked, their person) grouped by `threadKey`, the newest 20 threads, newest first — each titled by its first request's first line cut to 60 characters (`threadTitle`; the run's label when the read fails), with its channel's platform as `surface`; a `web:` conversation of the viewer's own lane is linked by its conversation id, any other thread by its whole key. Bounded by the bot: nothing pages on this page; the runs page holds everything. `elsewhere` is set when the open thread is another channel's: its platform and, when a run recorded one, the thread's own link. `suggestions` are the empty state's chips (`suggestionsFor`): what Switchboard does well, grounded in the viewer's own runs — a review on the repository they last worked in (or a pull request by its link where GitHub is on), why their last run failed (or what it did), the agent and model a run here gets, an MCP server where MCP is on — and one that asks what it can do, last; every chip is a read or a request the front door hands back, never a change started blind, so a click is safe; `commands` are the `/` palette's rows, every command the registry exposes to chat and the viewer may run, in chat form with the command's own `describe` (record 0008); `retentionDays` bounds the conversation's life and the rail says so.
3. **Sending.** Enter (not Shift+Enter) POSTs `{ text }` to `sendUrl` with same-origin credentials; a chip sends its words on click, no Enter. On send the person's turn is drawn at once, held back (`data-pending`) until the answer, and the mark in the header pulses once down its route. A `202 { runId, viewPath }` mounts an assistant turn on the run's own stream — and, when the page was opened at `/threads`, rewrites the address to `/threads/<conversation>` without a load or a history entry (`browser.replaceUrl`), so a reload finds the conversation that now exists: `viewPath` is `/runs/<id>?t=<token>`, and the page derives `/runs/<id>/events?t=…` and `/runs/<id>/stop?t=…` from it (`liveUrls`); anything else in the path is refused. A `200 { reply }` is one of three things (`classifyReply`): a **hand-back**, a reply beginning `HAND_BACK_PREFIX` (`To run this:`), fills the composer with the command, focused, with the hint `Enter runs it`, and paints no turn; a **steer acknowledgement** (`↪ Folded into …`) paints nothing, because the live turn's `input` event confirms the turn already drawn (item 5); any other reply is an **inline turn**, painted once and never stored. A failed send keeps the person's turn and says why under it (`not sent: <reason>`).
4. **A turn is a run.** `AssistantTurn.vue` owns one `createRunPageModel` (the run page's fold, live-view item 18) and attaches to the run's stream through the run page's own `attachRunStream` (`runStream.ts`: the seq dedupe, the named frames, the phases; nothing of the transport is the turn's own). Live, it draws: the receipt chip once the `route` event arrives (else the agent's chip from `run_meta`), the model's real name once known, the pending row while the model is silent and nothing runs (the run page's own `PendingTurnRow`: ∿, the model's badge, a verb from the shared list walked by the silence's length, the elapsed since the last stamped event, live-view item 18), the work open by default as the run page's own `StepBlock`s, and the reply whole when the `answer` lands. `finished` freezes the clock at the server's stamp (at the elapsed it shows, for a turn a `202` mounted without a server clock); `end` closes the stream and the turn becomes the finished shape in place. A stream the browser gives up on (`disconnected`) keeps the turn live for the conversation, so the composer stays `steer`: the clock freezes where the stream dropped and a row says so with the run's own page as the way on; nothing is drawn as over until `end` or a reload. Finished, closed, a turn is the receipt, the reply (or the record's outcome word when it made none), and one line of facts: the duration on the heat scale and `open run`; its work folds under it and reads the run's replay once, on first open, from `/runs/<id>/events`. The head's elapsed is the turn's one ticking number: the fold's summary is the step count alone.
5. **A message during a live run.** The composer's control reads `steer` as soon as there is text, and the POST goes to the same route; the pipeline steers it (thread-admission item 1) and answers the acknowledgement, which the page ignores. The live turn's stream carries the `input` event the harness records when it drains the inbox; the page matches it to the newest unfolded person's turn with the same words (`matchSteer`) and stamps that turn `↪ folded in at <m:ss>`. One message, drawn once. The request's own `input` event is the turn the page drew and stamps nothing.
6. **One control, two states.** The send button is `send` while no run is live in the conversation (disabled only with an empty box), `stop` while one is and the box is empty (a soft stop, `POST <stopUrl>&mode=soft`), `steer` while one is and there is text. It is never disabled while a run is live; its icon crossfades between the three. The hint under the box names the state and is always laid out (its height is reserved; only its opacity changes), so nothing on the page shifts when it appears.
7. **The rail, the shortcuts and the empty state.** The rail is a column from `md` up and a sheet from the left on a phone (the header's panel button opens it). It holds, in order: the **new-thread** control, the one solid control on the page, with its shortcut `⇧⌘O` in view (`⌃⇧O` where there is no ⌘); a **filter** field that narrows the recent rows by a fuzzy subsequence match (`filterRows`; Escape clears), reached by `⌘K` from anywhere on the page (on a phone `⌘K` opens the sheet, then focuses); the RECENT rows, each with its relative time, a live dot on one whose run is in flight, its surface's word label on a thread from another channel (`slack`, `http`: the channel id's prefix, as the runs index labels a requester), and an ink bar on the current one; an **All runs** link to `/runs`; and the retention sentence. The empty state lands in a choreography, each part 40 ms after the last: the mark (drawing its route, then floating), the greeting naming the person and the time of day (`greeting`, from the browser's local hour, following the clock), the line under it, the composer, the chips. The composer is focused on load. A thread from another channel (`elsewhere`) opens **read-only**: its turns draw, there is no composer, and a line at the foot names the channel and links to the thread — a reply belongs where the thread is; another person's `web:` lane (read by an all-channels holder) is named as theirs, with nowhere to reply. Where the pointer is a finger (`pointer: coarse`), every control on the page is at least 44 px tall: the chips, the rail's control, filter and rows, the palette's rows, the composer's control; the hover lifts are off there.
8. **The composer.** The box grows with its text to eight lines; its hairline brightens to ink on focus and a light sweeps once around the ring (the `ring-sweep`: a rotating conic gradient masked to the 1 px border, 700 ms), on every focus and once as the empty state lands. Its placeholder guides the hand by state (`placeholderFor`): what to ask while nothing is live, what the box does while a run is, nothing after a hand-back (the filled command is the guide). Enter sends and Shift+Enter breaks a line. `/` at the start of a message opens the **palette** (`slashQuery`): the seed's commands, each as `/<chat form>` with its description, narrowed by the fuzzy filter as the person types (`filterCommands`, chat form or description), the arrows moving the selection, Enter or Tab or a tap inserting the chat form and a space (`completeCommand`) so the arguments come next, Escape closing it; the slash never reaches the bot, which reads `<group> <verb>` at the start of a message. A message with a second line or a slash mid-sentence is prose.
9. **Following the transcript.** New content scrolls the transcript only when the reader was already at the bottom (`shouldFollow`, 60 px of slack); otherwise a `↓ new` pill appears and a click jumps down. The tab title is the conversation's title, `(1)` ahead of it while a run is live, and the favicon is the index's live dot.
10. **Motion rules.** Every transition the page adds is opacity plus at most 8 px of translate along Y, between 120 and 200 ms, ease-out; under `prefers-reduced-motion` every move keeps its opacity and drops its travel. The vocabulary is four moves (`sb-rise`, `sb-fade`, `sb-move`, `sb-stagger`) and three named exceptions under 700 ms, each off under reduced motion: the mark's route draw (`mark-draw`), the mark's pulse on a send (`mark-pulse`) and the composer's ring sweep (`ring-sweep`); the mark's idle float (`mark-idle`) moves it 1 px over 4.6 s. Nothing else on the page moves that the person did not cause, except the pending row's pulse and a clock's tick. The design system's own rules hold: chroma is data alone (the receipt chip in the preset's hue, a failed outcome, the heat ramp), the type ladder is the run page's three voices.
11. **The adapter** (`src/channels/web.ts`, record 0043). `POST /threads/<conversation>/send` sits behind the dashboard gate; a send must be same-origin (`originAllowed`, as `/api` writes are), JSON, under the ingress body cap, and into the session's **own lane**: the thread key is `web:<sub>:<conversation>` for a plain id, and a whole key from another channel is refused `403` (read here, answered there). The message is the gate's identity, never the request's: the browser session is the credential (`access:<sub>`), and when record 0042 linked it to its person the message names the **person** as `userId` (with their name) and the session as `authenticatedAs` — the shape a bound ingress token sends ([authorization.md](authorization.md) item 15, `requesterOf`) — else the session itself, named by its email; `channelId` is `web:<sub>` (`dm` in `visibilityOf`), `receivedAt` the adapter's clock, and `access` is a chat surface in `resolveChatActor` (the browser actor, whose baseline holds every group's read plus `memory:write` and `mcp:write`, item 9). The IO is the ingress IO's (`WebIO`: replies collected, `runStarted` raced against completion) with `history()` the thread's turns read from the run store as the person's and the agent's lines, stamped — the asking run left out, as every channel's history excludes the triggering message. A run created → `202 { runId, viewPath: /runs/<id>?t=<token>, threadKey }`, the token read from the registry after `runStarted` (a run gone from the registry first — discarded — is answered as a run-less request); no run → `200 { reply, run? }`. The seeds: `/threads` mints a 20-hex conversation id; `/threads/<id>` is `listRuns({ threadKey, status: "all", visibleTo: readableRuns(actor) })` for the newest 20 runs, oldest first, plus one `getRun(id, { include: "messages" })` each (`turnOf`: the first `input`, the last `answer`, the `route` event; a live run's token from the registry); another channel's thread the viewer may see nothing of is the same `404` an unknown run gives; the viewer's own empty conversation opens empty. The rail is item 2's, the palette `paletteCommands` (every chat-exposed command `authorize` admits the actor to, in `chatForm` with its `describe`), the chips `suggestionsFor`. The request's trace root is `channel: web`; the thread-key namespace `web` is a production namespace the binding purge refuses.

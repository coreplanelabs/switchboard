# Agent: explore

The long, read-only investigation: `agent:explore` clones a repository into a cold sandbox on a read-scoped credential, runs whatever the question needs — builds, test suites, pipelines, benchmarks — for up to two hours, searches the web beside it, and reports a claim table with the commands it ran and the numbers they produced. It never opens a pull request. It is the first preset on the `repo-cold` machine class ([record 0026](../../decisions/0026-capability-profiles-and-request-routing.md)): a request needing a shell, web search, a read credential and two hours runs without a new agent being written.

- **Code**: `src/agents/registry.ts` (`explore`, `EXPLORE_SYSTEM`), `src/tools/workspace.ts` (the `explore` toolset), `deploy/cloudflare-sandbox/worker.ts` (the exit-124 hint names `setsid -f`), `src/core/dispatch/resolve.ts` + `src/core/dispatch/authorize.ts` (the class's repository vet and refusals — [execution.md](execution.md) item 18), default model in the deployed config (`config/config.example.yaml` documents the key)
- **Docs**: [The agents and their toolsets](../../explanation/agents-and-toolsets.md), [execution.md](execution.md) items 2 and 18, [routing-and-config.md](routing-and-config.md) items 1–4 (directives, the effective profile, the profile gate)
- **Tests**: `src/agents/registry.test.ts` (the `explore agent` block), `src/tools/github.test.ts` + `src/tools/web.test.ts` (the toolset), `src/core/dispatcher.test.ts` (the `agent:explore` block), `src/execution/sandboxKeepalive.test.ts` (the sandbox Worker's hint)
- **Budgets**: 150 turns / 120 min / 64k tokens · toolset `explore` · machine `repo-cold` · identity `read` · cache TTL `1h`

## Behavior

1. **A preset, chosen by name.** `agent:explore` resolves through `parseDirectives`/`AGENTS["explore"]` like every directive and is sticky in its thread like every agent ([routing-and-config.md](routing-and-config.md) items 1 and 3); no router picks it yet. Its declared profile is machine `repo-cold`, identity `read`, 120 minutes — the two-hour budget no other preset holds — and the turn and token budgets are a runaway backstop and a per-call limit sized for a long loop of batched checks. The cache TTL is `1h`: a detached job polled across calls makes steps longer than the default cache entry lives. No built-in effort: the config layers decide, as for `coding`. Open to everyone unless `restrict.agents` names it; a self-serve MCP server never reaches it (`MCP_SELF_SERVE_AGENTS`, [mcp-tools.md](mcp-tools.md)), because it holds a shell.
2. **Reach: the `explore` toolset** — `bash`, `read_file`, `update_status`, `web_fetch`, `web_search`, `list_skills`/`use_skill` and the GitHub reads (`github_repos`, `github_tree`, `github_file`, `github_search_code`, `github_issue_list`, `github_issue_get`), and nothing that writes: no `write_file`, no `submit_*` (no verdict, description, dispositions or handoff), no issue writes. It is the one toolset beside `web` that holds `web_search` ([web-tools.md](web-tools.md) item 4). Read-only is a toolset-and-prompt contract; the wall is the identity.
3. **Machine `repo-cold`, identity `read`** ([execution.md](execution.md) items 5 and 18): every run is a fresh per-thread sandbox with the checkout, even when the repository has a serviceable resident — a two-hour, memory-hungry job shares no container with the reviews that depend on the resident — and the resident registry and Worker are never consulted, so an outage there can neither refuse nor delay it. A bare `owner/name` is vetted against GitHub with the run's own read-scoped credential (one `GET /repos/<owner>/<name>`; a repository the installation cannot see refuses as `repo_not_visible`, GitHub's silence as `repo_unverified`). The sandbox holds a read-scoped token, so the run can clone and read and can never push, whatever the caller holds; an investigation that must push is a second preset, never a directive. The prompt says so and tells the run to clone the repository itself (the cold sandbox pre-clones nothing).
4. **The deliverable is a claim table.** The prompt turns the request into claims — the explicit ones and the ones a careful engineer would check — and has each verified by running it: one row per claim with the exact command, the number or output it produced, and a verdict (holds / does not hold / could not check, with why). Numbers over adjectives; what was not reached is said. The final message leads with a one-line verdict, then the table (aligned rows in a code block, since Slack has no table markup), then what a follow-up should do.
5. **A job past the command cap is detached with `setsid -f`.** Every `/exec` runs under `timeout … bash -c`, whose process group is reaped when the command returns ([execution.md](execution.md) item 2), so a plain background job dies with the command that started it while a `setsid -f` job outlives it. The prompt names the per-command ceiling (`BASH_TIMEOUT_MAX_MS`, twenty minutes, the one constant in `src/execution/bashTimeout.ts`), the `timeoutMs` knob, and the detach-and-poll recipe (`setsid -f sh -c '<command> > /tmp/job.log 2>&1; echo $? > /tmp/job.exit'`, then `tail` the log on later calls); the sandbox Worker's exit-124 hint names the same tool and never `nohup`. Neither text names the tool that does not work.
6. **Never a pull request.** The prompt forbids opening a pull request, committing and pushing, and every PR or issue write; a change the investigation calls for is described in the write-up and handed to `agent:coding` by name. The toolset has no submission tool and the token cannot push, so the rule is held three times: prompt, toolset, identity.
7. **Knows its own settings — and itself.** Like every agent, its prompt carries the config block ([routing-and-config.md](routing-and-config.md) item 8) — the resolved agent, model and effort, its budget and what clipped it — and the About block (item 11), and it maintains the status card through `update_status`.

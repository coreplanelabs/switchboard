# Delivery indicators: how work reaches main, per week and per unit

`GET /delivery` is a gated, read-only page (plus a JSON twin) and `delivery report` its command twin on every surface: for one repository, the leading indicators of agent-run development computed from facts the system already keeps — GitHub's record of the merged pull requests (their reviews, pushes, workflow runs and the board issue each links) and the run history — grouped by Monday-start week and by unit (a board issue). Nothing is written to GitHub: its facts are read on an interval and kept as one snapshot per repository on the state Worker, every load serves that snapshot and says how old it is (`?fresh=1` on the page, `--fresh` on the command, read GitHub now), the run history joins live on every load, and the arithmetic is one pure function a recorded trunk pass pins.

## Configuration

```yaml
delivery:
  repos: [acme/api, acme/web]   # the page serves these; the first is its default
  reviewers: []                 # logins whose reviews are verdicts, beside the App's own identity
  agentLogins: []               # agents beyond the `[bot]` suffix
  agentCoauthors: [Claude]      # `Co-Authored-By:` names that mark a commit as an agent's
  snapshot:
    everyMinutes: 60            # minutes between two reads of a repository's facts (5–1440; default 60)
```

The page and the command need the `github` capability (the App triple or `GH_TOKEN`): every read is the App's read-scoped installation token. Without the block the command still answers `--repo owner/name`; the page answers 503 naming the block. A malformed block throws at startup. The snapshot lives on the state Worker whichever `*.worker` block names it (`runtimeOverrides.worker`, `runHistory.worker`, `schedules.worker` or `memory.worker`, the same `MEMORY_TOKEN` bearer — the snapshot is a cache and earns no block of its own); without one it is kept in memory, a restart loses it and the process says so at startup.

## Behavior

1. **Four indicators and the plain counts, one pure function.** `buildDeliveryReport` takes the merged pull requests' facts and the runs, and returns per-week rows, per-unit rows, per-pull-request rows and the totals, each carrying the same `DeliveryIndicators`: pull requests merged and how many were agent-authored (the author is a `[bot]` login or a configured agent login); **issue → merge** as the median and mean hours from the linked board issue's opening — or the pull request's own opening when none is linked — to the merge; **first-pass CI** as passed / known, where a pull request passes when every decisive pull-request-triggered workflow run (`pull_request` or `pull_request_target`; a `push`-triggered run on the branch is not the pull request's own check and is never judged) on its first head concluded `success` at attempt one, fails on any red run or any rerun, and is not counted when no such run exists; **review rounds** as the review agent's verdicts (reviews by a configured reviewer login — the App's own identity by default) per reviewed pull request, with the fix rounds (a verdict that followed a push since the previous verdict; a re-verdict with no push is a disposition, not a fix); **findings** by severity from the verdict bodies' `- [severity] F<n> …` lines (`blocking`, `major`, `minor`, `nit`, `fyi`; `blocker` reads as `blocking`; prose repeating a finding is not one), the blocking ones being the count the plan asks for, and the **no-human-edit share** — the findings on pull requests where every push after the first verdict was an agent's, over all findings; and the **agent runs** the history keys to the pull requests (count and minutes). A push is an agent's when its actor is a bot or configured agent login, or when a commit it carried names an agent co-author — the maintainer's own agent pushes under the maintainer's login, so the login alone would call every one of those human. The auto-approve identity's approvals are not verdicts.
2. **Weeks start on Monday, UTC, and every week in range has a row.** `weekStartOf` puts a merge in the week of its Monday; `weeksOf` lists every Monday from the week of `since` to the week of `until`, so a week with no merge is a row of zeros and nulls (median, share and per-PR ratios are `null` with nothing to divide), never an error. A pull request merged outside the range is left out. Rows come back in pull request number order; units in issue number order with the unlinked pull requests last under `(no issue)`.
3. **The range is `--weeks` or `--since`, ending today.** `resolveDeliveryRange`: `weeks` counts Monday-start weeks back from the current week (default 4, clamped 1..26); `since` (`YYYY-MM-DD`) names the first day instead and the week count follows from it; a malformed value is the default; a start after today is today. On the page, `?weeks=` and `?since=` are the same knobs; the command's `--since` decides when both are given.
4. **The facts come from four GitHub reads per repository, read-only.** `GithubDeliverySource`: the closed pull requests newest-touched first, pages of 100 until a row last touched before the range began (a row's update time is never before its merge time, so nothing merged in range can follow) or the page cap (`DEFAULT_MAX_PULL_PAGES`, 8 pages — the newest 800 closed pull requests; a capped read costs the pages plus about three calls per merged row, under half of an App installation's 5,000 calls an hour, and only a first read or `fresh` reaches it) — the report says `truncated` when the cap ended the read. An incremental read (`touched`, the snapshot's refresh of item 10) goes back to the instant it names instead of the range's start: the first row touched before it ends the listing, and a listed row whose update time the caller already holds (`known`) is not read again — its facts stand. Each fact carries the listing's `updatedAt`, which is what the next incremental read compares. Per merged pull request, its timeline (reviews with author, state, head and body; commits with their `Co-Authored-By:` trailers; force-pushes with their actor, which carry the co-authors of the commits the timeline now lists, since GitHub records nothing of what a force-push replaced), its head branch's workflow runs (head, trigger, conclusion, attempt — a retry shows in the attempt, which a check suite does not record), and the board issue its body links (a closing keyword — `closes`, `fixes`, `resolves` — or a `board item` reference, followed by `#<n>` or the issue's URL in the report's own repository; a bare mention or the board's parent is not a link, and neither is another repository's issue URL, since the issue is read from the report's repository where that number is some other issue) for its creation time. The first head is the earliest `pull_request` run's head, else the earliest review's, else the current head. A 404 on the issue or on Actions is an absent fact; any other non-2xx throws with the status and a redacted, capped body. Every parser is pure and tested on the API's recorded shapes. The fetch also says from when it is complete (`completeFrom`): the range's start when the listing was exhausted or reached older rows (the instant it went back to, on an incremental read), the oldest update it reached when the cap ended it — a pull request merged after that instant was updated after it, so it is among the rows read — which is what lets a snapshot answer a narrower range without a false `truncated` (item 10).
5. **The run history joins under the caller's own visibility.** The runs the report keys are the caller's finished runs of the repository since the range began — listed under `predicateFor(actor, "runs:read", "run")` exactly as the runs index decides, up to the list cap — and a run names its pull request through the `…/pull/<n>` in its label; a run of another repository or one naming no pull request adds nothing. A caller who may read no runs gets the pull requests' facts alone, never a refusal. The web handler asks the same question of the gate's identity.
6. **One service for the page and the command; a Null Object without GitHub.** `createDeliveryService` resolves the range, fetches through its `DeliverySource` (in production the snapshot source of item 10, handed `fresh` when asked), merges the identities (the config's under the process's — the App's login as a reviewer), builds the report and stamps it with `snapshotAt` — when the facts were read: the snapshot's time, or now for a live read; `repos()` are the configured repositories; `unavailable()` is undefined. `NullDeliveryService` (a process with no GitHub credential) has no repository, `unavailable()` says why, and refuses every report with the same reason. The page serves configured repositories only (an unknown one is 404); the command takes any `owner/name`.
7. **`delivery report` on every surface.** `delivery report [--repo owner/name] [--since YYYY-MM-DD] [--weeks n] [--fresh]`, action `delivery:read`, effect read, gated on the `github` capability (hidden everywhere without it — command-registry item 28); the browser baseline holds every group's read, so a signed-in viewer runs it, a chat user needs the grant, a `dispatch`-only token is refused. The bare form takes the first configured repository and is `invalid_input` naming `--repo` when none is configured; a repository that is not `owner/name` is `invalid_input`; the Null Object and an upstream failure are `unavailable` with the reason; `--fresh` reads GitHub now and refreshes the snapshot (item 10). The JSON is the report, `snapshotAt` in it; the text (`render`) opens with the repository, the range and `as of <day> <hh:mm> UTC, <age>` (`just now`, `n minutes ago`, `n hours ago`, `n days ago`), then one block per week — merged, issue → merge, first-pass CI, review rounds, findings with the no-human-edit share, agent runs — then the units, in single-spaced lines chat carries as they are.
8. **Routes.** `/delivery` and `/delivery.json` → the first configured repository; `/delivery/<owner>/<name>` and `/delivery/<owner>/<name>.json`; each segment is word characters, dots and dashes, never dots alone. GET-only (405 otherwise). No GitHub credential → 503 with the Null Object's reason; no repository configured → 503 naming `delivery.repos`; unknown repository → 404; upstream failure → 502 with a capped reason, never a 500. `?weeks=`, `?since=` and `?fresh=1` pass to the service; the handler asks the service on every request and the service answers from the snapshot (item 10), so a page load costs no GitHub read unless it says `fresh`. The JSON twin is exactly the seed's report, `snapshotAt` in it, served `no-store` — the freshness is the snapshot's, not the HTTP cache's.
9. **Page.** The shared web shell with the report and the repository list as the `DeliverySeed`; `web/src/pages/DeliveryPage.vue` in the costs page's shape and tokens: the six tiles over the range (merged, issue → merge, first-pass CI, review rounds, no human edit, blocking caught), a table by week and a table by unit (issue and pull request links to GitHub), the range switch and the repository switcher, and in the footer — always in view — `As of <Mon d, hh:mm UTC>, <age>` with a `read GitHub now` link that keeps the page's own query and adds `fresh=1` (the age ticks by the minute while the page is open), then the method one click away with the identities judged by and the JSON twin named; hostile strings render as text (the seed island escapes every angle bracket; the components never render raw markup); the same hardened headers as `/runs`. The site nav lists Delivery when `github` is on ([live-view.md](live-view.md) item 18).
10. **The snapshot: one window of facts per repository, refreshed incrementally on an interval, served to every request that fits.** The `DeliverySource` the service reads in production is `SnapshottingDeliverySource`, a Decorator over `GithubDeliverySource` (`deliveryFromConfig`): per repository it keeps one `DeliverySnapshot` — the pull requests' facts over the widest range the page offers (`SNAPSHOT_WEEKS` = 13 Monday-start weeks ending today), each row with GitHub's update time, `snapshotAt` (when the last read began), `truncated` and `completeFrom` — in memory and on a `DeliverySnapshotStore`. A request whose range starts inside the snapshot's window is served from it: `buildDeliveryReport` filters the facts to the range as it always did (so the report is the one a live read at `snapshotAt` would have given), `truncated` is whether the range starts before `completeFrom`, and the report carries the snapshot's `snapshotAt` and `completeFrom`. A range reaching further back than the window (`--since` earlier than 13 weeks ago) is a live read over that range, stamped now, and leaves the snapshot alone. With no snapshot yet — the first boot of an installation, a repository just configured — the first request reads the newest rows of the window once (up to the source's page cap, item 4), stores them and is served from them; requests arriving meanwhile share that one read. **A refresh is incremental** (`refresh`): it lists the rows touched since the previous read began, less `REFRESH_OVERLAP_MS` (ten minutes — room for a listing that lags or a clock that skews), hands the source the update times the snapshot holds so a row that has not moved is not read again (item 4), and merges the result into the snapshot — so the hourly cost follows the repository's activity (one listing call per hundred touched rows and about three per row that moved), not the window. `fresh` reads the newest rows of the window whole again — the same read as the first — and merges those in. **The merge** (`mergeSnapshot`, pure, the same for a first read, a refresh and `fresh`): the read's rows replace theirs by number, the rest survive, and rows merged before the window's start are dropped; the snapshot is complete from the earlier of the two `completeFrom` instants when the read reached back to the previous read's time (they overlap), from the read's own reach when it stopped short of it (a gap it cannot vouch for — a capped listing after a long outage), and never before the window's start; `truncated` is whether that instant is after the window's start. So a capped first read fills in by accretion as the weeks pass and heals once the window's start moves past its `completeFrom`, and `fresh` never discards a row its capped read did not reach. **The store** is the `DeliveryDO` on the state Worker (`WorkerDeliverySnapshotStore`, `POST /delivery/get {repo}` → `{snapshot | null}`, `POST /delivery/put {snapshot}` → `{ok, prs}`, `POST /delivery/merge {patch}` → `{ok, prs}` or 404, the same bearer as memory and run history): one row per pull request under a meta row per repository, read back in pull request number order — a busy repository's window is many MB of review bodies and workflow runs, which is why it is rows and not one document. A first read is written whole (`put`: one transaction replacing the repository's rows); a refresh is written as its patch (`merge`: the rows re-read replace theirs by number, the numbers that aged out go, the meta is replaced, one transaction), so the hourly write is the change, not the window; a merge into a repository the Worker holds no snapshot for is refused (404 — a partial snapshot would claim a completeness it lacks), the client answers false, and the bot writes the snapshot whole instead. The Worker validates both shapes (`isDeliverySnapshot`, `isDeliverySnapshotPatch`, shared by relative import), refuses a repository that is not `owner/name` and a pull request whose facts exceed a fraction of the row limit (413), and fences the request body at its own ceiling. `InMemoryDeliverySnapshotStore` is the second implementation and the process's fallback without a state Worker. The store is read once per process per repository (memory answers after that) and written on every refresh. **The refresh loop** is the bot's own timer (`startRefreshLoop`, started in `src/index.ts` for the configured repositories; the CLI starts none and reads — on a first or `--fresh` read, writes — the same store): a tick a minute, unref'd, runs once at start and then refreshes each repository whose snapshot is missing or older than `delivery.snapshot.everyMinutes` (default 60, bounds 5–1440), one repository at a time — so a stale snapshot after a restart is refreshed at once and a young one is left alone, and no repository is read more often than the interval. It is not a schedule-registry entry: the interval is config, the Worker crons are static, and a refresh is a cache write, not a run. **Failures degrade, never refuse**: a store that cannot be read is an absent snapshot (a warning, then a read that computes and stores); a store that refuses a write is a warning — the snapshot in memory still serves and the next refresh writes again, whole when the store holds nothing to patch; a GitHub read that fails during a refresh is a warning and the snapshot keeps serving with its age growing until a tick succeeds; a GitHub read that fails with no snapshot to fall back on is the upstream failure of items 7 and 8.

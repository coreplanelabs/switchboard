# Delivery indicators: how work reaches main, per week and per unit

`GET /delivery` is a gated, read-only page (plus a JSON twin) and `delivery report` its command twin on every surface: for one repository, the leading indicators of agent-run development computed from facts the system already keeps — GitHub's record of the merged pull requests (their reviews, pushes, workflow runs and the board issue each links) and the run history — grouped by Monday-start week and by unit (a board issue). Nothing is written anywhere: every load is a live read, and the arithmetic is one pure function a recorded trunk pass pins.

## Configuration

```yaml
delivery:
  repos: [acme/api, acme/web]   # the page serves these; the first is its default
  reviewers: []                 # logins whose reviews are verdicts, beside the App's own identity
  agentLogins: []               # agents beyond the `[bot]` suffix
  agentCoauthors: [Claude]      # `Co-Authored-By:` names that mark a commit as an agent's
```

The page and the command need the `github` capability (the App triple or `GH_TOKEN`): every read is the App's read-scoped installation token. Without the block the command still answers `--repo owner/name`; the page answers 503 naming the block. A malformed block throws at startup.

## Behavior

1. **Four indicators and the plain counts, one pure function.** `buildDeliveryReport` takes the merged pull requests' facts and the runs, and returns per-week rows, per-unit rows, per-pull-request rows and the totals, each carrying the same `DeliveryIndicators`: pull requests merged and how many were agent-authored (the author is a `[bot]` login or a configured agent login); **issue → merge** as the median and mean hours from the linked board issue's opening — or the pull request's own opening when none is linked — to the merge; **first-pass CI** as passed / known, where a pull request passes when every decisive pull-request-triggered workflow run (`pull_request` or `pull_request_target`; a `push`-triggered run on the branch is not the pull request's own check and is never judged) on its first head concluded `success` at attempt one, fails on any red run or any rerun, and is not counted when no such run exists; **review rounds** as the review agent's verdicts (reviews by a configured reviewer login — the App's own identity by default) per reviewed pull request, with the fix rounds (a verdict that followed a push since the previous verdict; a re-verdict with no push is a disposition, not a fix); **findings** by severity from the verdict bodies' `- [severity] F<n> …` lines (`blocking`, `major`, `minor`, `nit`, `fyi`; `blocker` reads as `blocking`; prose repeating a finding is not one), the blocking ones being the count the plan asks for, and the **no-human-edit share** — the findings on pull requests where every push after the first verdict was an agent's, over all findings; and the **agent runs** the history keys to the pull requests (count and minutes). A push is an agent's when its actor is a bot or configured agent login, or when a commit it carried names an agent co-author — the maintainer's own agent pushes under the maintainer's login, so the login alone would call every one of those human. The auto-approve identity's approvals are not verdicts.
2. **Weeks start on Monday, UTC, and every week in range has a row.** `weekStartOf` puts a merge in the week of its Monday; `weeksOf` lists every Monday from the week of `since` to the week of `until`, so a week with no merge is a row of zeros and nulls (median, share and per-PR ratios are `null` with nothing to divide), never an error. A pull request merged outside the range is left out. Rows come back in pull request number order; units in issue number order with the unlinked pull requests last under `(no issue)`.
3. **The range is `--weeks` or `--since`, ending today.** `resolveDeliveryRange`: `weeks` counts Monday-start weeks back from the current week (default 4, clamped 1..26); `since` (`YYYY-MM-DD`) names the first day instead and the week count follows from it; a malformed value is the default; a start after today is today. On the page, `?weeks=` and `?since=` are the same knobs; the command's `--since` decides when both are given.
4. **The facts come from four GitHub reads per repository, read-only.** `GithubDeliverySource`: the closed pull requests newest-touched first, pages of 100 until a row last touched before the range began (a row's update time is never before its merge time, so nothing merged in range can follow) or the page cap (default 3 pages) — the report says `truncated` when the cap ended the read; per merged pull request, its timeline (reviews with author, state, head and body; commits with their `Co-Authored-By:` trailers; force-pushes with their actor, which carry the co-authors of the commits the timeline now lists, since GitHub records nothing of what a force-push replaced), its head branch's workflow runs (head, trigger, conclusion, attempt — a retry shows in the attempt, which a check suite does not record), and the board issue its body links (a closing keyword — `closes`, `fixes`, `resolves` — or a `board item` reference, followed by `#<n>` or the issue's URL in the report's own repository; a bare mention or the board's parent is not a link, and neither is another repository's issue URL, since the issue is read from the report's repository where that number is some other issue) for its creation time. The first head is the earliest `pull_request` run's head, else the earliest review's, else the current head. A 404 on the issue or on Actions is an absent fact; any other non-2xx throws with the status and a redacted, capped body. Every parser is pure and tested on the API's recorded shapes.
5. **The run history joins under the caller's own visibility.** The runs the report keys are the caller's finished runs of the repository since the range began — listed under `predicateFor(actor, "runs:read", "run")` exactly as the runs index decides, up to the list cap — and a run names its pull request through the `…/pull/<n>` in its label; a run of another repository or one naming no pull request adds nothing. A caller who may read no runs gets the pull requests' facts alone, never a refusal. The web handler asks the same question of the gate's identity.
6. **One service for the page and the command; a Null Object without GitHub.** `createDeliveryService` resolves the range, fetches, merges the identities (the config's under the process's — the App's login as a reviewer) and builds the report; `repos()` are the configured repositories; `unavailable()` is undefined. `NullDeliveryService` (a process with no GitHub credential) has no repository, `unavailable()` says why, and refuses every report with the same reason. The page serves configured repositories only (an unknown one is 404); the command takes any `owner/name`.
7. **`delivery report` on every surface.** `delivery report [--repo owner/name] [--since YYYY-MM-DD] [--weeks n]`, action `delivery:read`, effect read, gated on the `github` capability (hidden everywhere without it — command-registry item 28); the browser baseline holds every group's read, so a signed-in viewer runs it, a chat user needs the grant, a `dispatch`-only token is refused. The bare form takes the first configured repository and is `invalid_input` naming `--repo` when none is configured; a repository that is not `owner/name` is `invalid_input`; the Null Object and an upstream failure are `unavailable` with the reason. The JSON is the report; the text (`render`) is one block per week — merged, issue → merge, first-pass CI, review rounds, findings with the no-human-edit share, agent runs — then the units, in single-spaced lines chat carries as they are.
8. **Routes.** `/delivery` and `/delivery.json` → the first configured repository; `/delivery/<owner>/<name>` and `/delivery/<owner>/<name>.json`; each segment is word characters, dots and dashes, never dots alone. GET-only (405 otherwise). No GitHub credential → 503 with the Null Object's reason; no repository configured → 503 naming `delivery.repos`; unknown repository → 404; upstream failure → 502 with a capped reason, never a 500. Live per request, nothing stored.
9. **Page.** The shared web shell with the report and the repository list as the `DeliverySeed`; `web/src/pages/DeliveryPage.vue` in the costs page's shape and tokens: the six tiles over the range (merged, issue → merge, first-pass CI, review rounds, no human edit, blocking caught), a table by week and a table by unit (issue and pull request links to GitHub), the range switch and the repository switcher, the method one click away in the footer with the identities judged by, and the JSON twin named; hostile strings render as text (the seed island escapes every angle bracket; the components never render raw markup); the same hardened headers as `/runs`. The site nav lists Delivery when `github` is on ([live-view.md](live-view.md) item 18).

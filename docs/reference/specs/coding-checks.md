# Coding checks

Every coding workspace receives the same task-directed validation guidance. The agent reads repository instructions, scripts and CI and chooses a bounded check relevant to the task. Where a trusted checkout binding, typed executor and durable ledger are available, `run_check` records execution. The default requires no repository-specific test command. Environment preparation and its ownership/recovery guards remain separate; the older [startup smoke policy](first-coding-test.md) is compatibility behavior, not automatically a task baseline.

## Behavior

1. **Select with context.** Before intended code changes, the agent inspects the task, relevant `AGENTS.md`, package scripts and CI to identify the cheapest useful baseline. A monorepo task selects the relevant package or test, never a whole-suite default. The existing checks-by-cost rule and remaining run budget apply. Reusable repository instructions are useful input; they are not an additional central configuration requirement.
2. **Prefer recorded execution when supported.** `run_check` takes `purpose: baseline | verification`, `command` and optional `timeoutMs`. The runner supplies the bound executor, run identity and workspace; model arguments cannot select another run or supply a result. The command uses the existing sandbox authority and execution budget. The tool does not grant publication, installation, network or external-write authority. Its command passes the shared shell-command restrictions as well as the current harness lifecycle gate; its own timeout is clipped by the existing command-budget policy.
3. **Record facts.** Before executing the check, the runner observes the checkout path, head and working-tree fingerprint; this is an observation, not an immutable snapshot. The existing run ledger records the tool-call identity and pending intent before execution, then the typed outcome before returning a receipt. If authorization, budget or a stop prevents dispatch after intent is saved, `not_started` records that fact; it is not an unknown execution or a completed command. Exit status, bounded/redacted output and available execution provenance come from the executor. Output is untrusted evidence. A successful process exit does not prove that assertions ran, that the selected check was relevant, or that the repository is healthy. A nonzero process exit likewise does not distinguish a failing assertion from missing setup by itself.
4. **Keep history.** A completed baseline records the pre-command workspace observation and subsequent process result. This is not a stable-tree or effective-command-directory attestation: another operation may change the checkout between observations, and the command itself can change directories or files. Later edits do not invalidate or erase that historical observation, and an exact duplicate call returns its saved result instead of executing again. A new verification uses a new call identity. Reusing an identity with different submitted arguments is refused, including switching between an omitted timeout and an explicit default timeout. A known `not_started` operation can be attempted under a new call identity after the refusal is resolved. A pending or unknown operation is not automatically replayed, and a new call identity cannot retry the same unknown command. New Resident checks persist distinct metadata and selected-command request identities before each dispatch. A retained preflight result is saved before parsing its workspace observation; unresolved preflight identity cannot start the selected command or certify scratch custody closure. A read-only lookup can recover the original saved result immediately after transport loss or when the same check identity is inspected later within its current owner and run budget. A retained metadata result can be inspected but cannot start the selected command: its saved head/fingerprint does not prove the current checkout at that path. Terminal runs can use `runs.check` to inspect retained canonical check evidence without resuming. `runs.settlecheck` can retire exactly one unresolved alias only from an existing original native-ended proof; it never dispatches or signals native work. The lookup requires the original owner, thread, command and workspace incarnation; it never dispatches the command. Missing, pending, interrupted and legacy evidence stays held. This does not grant a stopped run permission to resume, cancel native work or recover a historical check without its saved identity. This rule is not a semantic detector for differently spelled commands.
5. **State the limits.** The agent is instructed to establish the baseline before intended edits. This is a workflow expectation, not a read-only phase or a structural guarantee: arbitrary commands can write, and neither the purpose label nor a shell parser proves command semantics. A verification receipt is not a publication-gate receipt, approval, or permission to publish.
6. **Report capability limits honestly.** The universal prompt does not imply universal receipt support. A cold path cloned by the model may lack a trusted checkout binding, and an executor without typed `execResult` cannot produce this receipt. An initially absent or untracked ledger refuses before metadata or command execution and explicitly reports that the command did not start. A later durable-write failure remains a persistence failure. Existing pending or unknown operations take precedence over missing capabilities after resume and remain unresolved. If a non-mutating capability refusal establishes that the requested command did not start, the agent may use ordinary permitted shell tools and report their actual output without claiming a typed check receipt. Policy refusal, an unknown outcome or persistence failure never licenses that fallback or an automatic replay. If the evidence does not establish that the command did not start, preserve the uncertainty.
7. **Use judgment when a baseline is unavailable.** For a documentation-only change, select a relevant documentation check when one exists. If no useful bounded baseline exists, report that fact and its reason; do not run an unrelated command merely to fill a receipt. Missing dependencies or tools remain environment limitations, not passing tests. The final validation states what actually ran, what failed, and what remains unverified.

8. **Refresh the phase notes.** A verification may include a complete `checkpoint` with the current phase, goal, decisions, rejected approaches, reported completed work, unproven work and next step. The model-visible schema permits checkpoints only with `purpose: verification`; both purposes remain valid without a checkpoint. Invalid, oversized or baseline checkpoints also refuse at runtime before execution. Only a new recorded verification with a known zero exit replaces the existing notepad through its owner-fenced, source-preserving write. Reported work remains explicitly model-reported; the saved check identity, head, working-tree fingerprint and command hash record process evidence separately. The checkout observation precedes the command and cannot attest an unchanged tree or assertion coverage. A check replay never replaces newer notes. Failed, unknown, stopped or fenced paths keep the preceding notes. Lost note-write acknowledgement is reported as unknown without re-executing the recorded check; the agent must reconcile notes before refreshing them. Ordinary `notes` writes remain compatible. Both harnesses use this shared tool capability.

9. **Reserve recorded checks for execution evidence.** Each run retains at most 32 check receipts and 4,000 characters per output stream. A full receipt ledger refuses before metadata or command dispatch. Each refusal publishes a bounded, redacted `harness_error` run note under its original call ID before it returns. The tool reports that the command did not start and permits other tools and saved-result replay to continue; existing unknown operations and persistence failures still stop recovery. A completed result with truncated output explicitly states that its evidence is partial. Source reading uses `review_read` or `read`. When a request requires shell-based source collection, save the large read-only output once under `$TMPDIR` and page it with `read`, rather than spending check receipts on small shell slices. A missing or incomplete read never supplies review coverage.

## Evaluation procedure

Use an authorized test installation and disposable fixtures, with normal coding requests rather than an explicitly supplied test command. Keep run identifiers, deployed version, fixture heads, commands and results in the operator's evidence store, not this spec. Do not create production events solely to fill a receipt.

1. Submit a small change in one package of a fixture monorepo with two independently testable packages. Inspect its transcript and receipts: the agent read local instructions/scripts, selected the relevant package's bounded test, and observed its baseline before the first intended source edit. A test in the unrelated package or a whole-suite default fails this selection criterion. The transcript proves this observed ordering only; it does not establish a universal pre-edit security boundary.
2. Submit a documentation-only change in a fixture with a documented documentation check, then in one without a useful bounded check. The first should use the documented check. The second should name the unavailable baseline and still report appropriate validation for its actual change, without fabricating a passing test.
3. In separate fixtures, use a runnable test with a failing assertion and a missing required tool or dependency. Inspect the actual command evidence and the agent's explanation. Neither condition may be described as clean; a generic nonzero exit alone must not be called an assertion failure.
4. Confirm a later verification has a distinct call identity and names its own result. The earlier baseline remains history. Publication still requires the existing ownership, exact-tree checks and review rules.
5. On a supported installation, confirm typed receipts; on a path without a trusted checkout or typed executor, confirm the agent describes ordinary shell evidence without inventing a receipt. A command-policy refusal or ambiguous earlier operation must not trigger a shell fallback.
6. Exercise duplicate delivery and an interrupted response in the test harness. Confirm exact completed replay executes once and pending/unknown replay executes zero additional commands. Authoritative operation reconciliation is not implemented by this tool; retain the unresolved operation, and never substitute a model-written file.

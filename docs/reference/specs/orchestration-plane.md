# Orchestration plane

Switchboard can say **what is happening**: every live and recently ended run, every ship unit and every tracked pull request, each with its owner and its health, as one table read from the stores that already exist. The table is the first surface of the orchestration plane (record 0064, `docs/decisions/0064-the-plane-owns-every-runs-state-a-refusal-becomes-a-queue-position-an-ending-is-judged-by-the-ledger-that-saw-it-and-a-release-is-a-quiet-window-a-person-closes.md`, which merges beside this [unit](../vocabulary.md#unit)): the read-only projection the plane's later units (the queue, the windows, the watches and their moves) grow beside. Nothing in this feature decides, writes or steers.

**Pure table, thin reads (locked design).** One node-free module says what the rows mean, `src/core/plane/table.ts`, so the command's text, the page and the tests agree on every word; the service reads and hands the facts over. A health flag is derived from a fact the row already carries and never from a clock the plane owns: the stall facts are the [runs](../vocabulary.md#run) index's ([live-view.md](live-view.md) item 32), the [pull request](../vocabulary.md#pull-request) facts are the merge door's ([agent-ship.md](agent-ship.md) item 9), a unit's ending is the coordinator's row ([run-history.md](run-history.md) item 50).

## Behavior

1. **Runs and their health.** The table lists every run live in this process or on the ledger under another generation, then every run finished within the recent window (one hour by default), each under the viewer's `runs:read` predicate, exactly the rows `runs list` would show. A row's owner is its requester, with the name the adapter resolved when it did, or the generation driving it when the row is live under another container. Its health flags come from the pace facts the live summary carries: `bound-exceeded` when the in-flight call ran past the bound it declared, `stalled` when no tool call landed for a whole pace window, `no-signal` for a row live under another generation, which carries no pace fact and is never read as stalled; a finished row reads `provisional`, `interrupted` or `failed` from its record, or nothing. Live rows sort first, stalled ahead of healthy, then rows with a flag, then the recently ended, newest first within each band.
2. **Pull requests and their health.** Every pull request a unit row or a run's record names is read once through the merge door's own GitHub reads (the facts, the checks at the head, the reviews), up to a bound (20 by default, the units' first), and judged in the merge door's order: `approved` when a review approves the head, `dirty` when GitHub reports a conflict with the base, `red` when a check at the head failed else `pending` when one is still running, `mistitled` when the title fails the repository's title rule, `merged` or `closed` for a closed one, and `unknown` alone when GitHub could not be read or the process holds no GitHub credential. A pull request is owned by the unit whose row names it, else by the run that opened it, else by a person.
3. **Units and the owner gap.** Every instance a listed run belongs to contributes its unit rows, under the same predicate the unit page applies, with the instance's facts beside them. A unit with no ending is `live` while a run of it is live and `waiting` otherwise; an ending record 0051 idles on reads `idle`; `merged` and `merge-ready` read as they are, and a merge-ready unit whose pull request is still open is also an `owner-gap`, the state record 0064 names; a pull request the plane could not read, on GitHub or past the read cap, leans open, so a read failure never hides the gap. A coordinator child is joined to its unit through the spawn's idempotency key, else through the unit whose [thread](../vocabulary.md#thread) it runs in.
4. **`plane show`.** One typed registry command, action `runs:read`, effect read, on every surface by derivation (`plane show` in chat and on the CLI, `GET /api/plane.show`, the `plane_show` MCP tool), answering the table as JSON and rendering it as three sections, aligned columns for a terminal and bullets for chat, each section saying `(none)` when empty; a row's health prints in the user's words — the `owner-gap` flag reads `unmerged` beside `merge-ready` (record 0066, "The collapse"), and the flags join as a phrase, never the raw flag join. The router is offered it with its three fixtures.
5. **The panel.** `GET /plane` serves the shared web shell with the table as its seed and `GET /plane.json` answers the same table, one view in two encodings (record 0056), Access-gated beside `/runs` and `/costs`; a viewer the gate resolved to nobody sees nothing, a table that cannot be built is a 502 with the reason, never a 500. The page paints the three sections with the same words and links each run as the runs index does: a live run of this process through its capability token, every other run tokenless. **Plane** is a nav section beside Runs, always present because its rows are run facts under the same predicate.
6. **The decider.** One pure, node-free function says what the plane does: `decide(state, event) → { state, effects, writes }` (`src/core/plane/decide.ts`), over a closed event union (`ask`, `sealed`, `withdraw`, `window`, `level`, `observation`, `reask`) and a closed effect union (`admit`, `probe`), never throwing — an event about a run or thread the state does not know is a no-op. An ask on a free thread proceeds: state unchanged, no writes, no effects (`planeAskWordOf` reads `proceed`). An ask on a live thread queues with a `thread_free` condition and a position counted among the thread's waiting rows. A seal flips the condition and the queue walk admits oldest first, re-evaluating after each admission — the admitted run's thread is live again, so a second row on the same thread keeps waiting. A withdraw marks the waiting row `withdrawn`, and a withdrawn row is never admitted. Effects carry stable ids derived from the run (`admit:<runId>`), so a duplicate offer after a roll is the same effect. The ledger object applies it inside ONE `transactionSync` (`planeApply`): the state read from its own tables, the decider's writes and the offered effects committed together or not at all.
7. **The tables and the answers' effects.** The ledger object holds the plane's six tables from this unit on — `plane_queue(run_id, requester, thread_key, stage, request_json, conditions_json, position_at, queued_at, state)`, `plane_reservations(kind, key, run_id, at)`, `plane_windows(kind, key, phase, opened_at, reason_json)`, `plane_findings(id, watch, subject, timeline_json, filed_at)`, `plane_effects(id, body_json, offered_at, acked_at)` and `plane_levels(resident, name, side, reported_at, generation)` — so an earlier bot and a later Worker agree on the schema; only the queue and the effects are written yet. The endings unit adds the seventh, `plane_endings(run_id, kind, cause, at)` ([run-history.md](run-history.md) item 33). Every answer the object gives the bot's heartbeat and reclaim-sweep calls carries `effects: PlaneEffect[]` — the unacknowledged offers, oldest first, at most 32 — always present, empty until a unit writes one; the client reads a field-less answer from an older Worker as none offered. The bot acknowledges each effect by id on `POST /plane/ack`: `done` and `skipped` close the offer, `deferred` leaves it riding the next answer; an unknown id is a no-op, never an error. The write-through acks everything it receives `deferred` today — nothing executes an effect until the transport unit lands.
8. **Shadow.** `plane.admission: off | shadow | on` is the plane's gate ([routing-and-config.md](routing-and-config.md) item 31; default `off` — `planeAdmissionOf`). Under `shadow` the dispatch's admission stage posts its own outcome per dispatch to `POST /plane/outcome`, fire and forget through the write-through (`planeOutcome` — a failed or missing route is one warning, never a wait or a throw): `proceeded` for a claim, `refused:thread-live` for every thread-in-flight refusal, `refused:allowlist` for the [agent](../vocabulary.md#agent) gate's; a steer, a supersede and a redispatch are not asks for a new run and post nothing, and the executor's `fell_cold:<token>` arrives with the resident unit. The object judges the same ask with the decider inside one transaction and logs the decider's word beside the bot's; nothing runs — and nothing queues — from the decider under shadow, and a disagreement (a `proceeded` the decider would queue, a thread-live refusal it would admit) bumps a per-condition counter in `meta` (`plane_disagreements`) for the later `plane disagreements` line; a pair the decider does not model yet is logged uncounted. `off` posts nothing.
9. **The resident conditions (record 0064, "The queue").** Each resident computes two levels — `seat` (the worker-user pool, threads and ops both: `above` exactly when no user is free, the next attach's `user-pool-exhausted`) and `memory` (the gate's soft side, [resident-repos.md](resident-repos.md) item 70) — in a pure module (`deploy/cloudflare-resident/levels.ts`), stamped with its generation (the container's boot id where memoized, else the DO incarnation). Every `/attach`, `/exec` and `/status` answer carries the `levels` document; a crossing lands in a per-name outbox re-offered on every answer until a newer crossing supersedes it, and a boot or a replaced runtime re-states both names. The registry posts the fleet drain the same way (`name: "drain"` on `/drain`, `/undrain` and its answers): the set posts `above` and arms ONE alarm at the record's `until`, a clear posts `below`, and the alarm posts `below` for a drain nobody lifted. The bot forwards a post to `POST /plane/level`; on the object, `seat` and `memory` land as level events — a `below` side walks the queue — and `drain` as the `resident-drain` window's open and lift. A resident-stage ask (`stage: "resident"`, the resident named) queues on a level reported `above`, holds no reservation (its thread is already this run's), and proceeds — for the bot to fall cold — when the resident is `unknown` (`residentSideOf`: no report, or one from another generation); a `restartOf` ask passes the windows and the memory line. A refusal-by-name the bot meets at attach or exec (`POST /plane/observe`: `user-pool-exhausted` → seat, the gate's `memory-pressure` → memory, `draining` → the drain window, `runtime-unreachable`/`runtime-replaced` → seat) re-enters an admitted run's queue row `waiting` at its old position and writes the level `above` — the refusal is evidence. While a waiting row waits on a resident that has said nothing within the re-ask cadence (`plane.reaskMinutes`, default 2, stored from the admit post's `reaskMs`; `PLANE.reaskMinutes` in `src/core/budgets.ts`), the object's alarm — pulled forward to the cadence, never pushed back — emits one `probe(resident)` effect per resident (`probe:<resident>`: at most one open per resident, re-offered after an ack), which the heartbeat loop answers by probing `/status` and forwarding the levels; a probe is never deferred by a drain and a process without the seam skips it. `plane.coldFallback` (default false — `planeColdFallbackOf`) is the rollback lever: write presets fall cold instead of queueing. The bot's stage-three ask and its forwarding are the executor's half, still to land: `[gap]` a coding ask on a resident above a line queues at stage three, a read preset falls cold, and the bot forwards levels and refusals.

10. **The moves and the findings (record 0064, "Endings and the watches").** A **watch** is a named predicate over the plane's state, evaluated only at the events that can change it; a **move** is its mechanical recovery, one pure step of the decider; a **finding** is filed when no move applies. The decider's event union grows `pr_tracked` (a tracked pull request's title, judged against the title rule by the caller — the decider is node-free and holds no vocabulary), `child_sealed` (a child's seal with its pushed branch, pull request and runner-liveness facts), `approval` (the merge door's read: the head and its `mergeableState`) and `runner_status` (the engine's status with the unfinished units and the attempt); the effect union grows the moves — `retitle` (`unit_title`: a failing title, id `retitle:<repo>#<number>`), `pr_open` (`orphaned_child`: a pushed branch with no pull request and no live runner, id `pr_open:<repo>#<branch>`), `rebase_round` (`dirty_at_approval`: briefed `REBASE_ROUND_BRIEF`, "rebase onto the base and push", keyed by the approved head — the reviewed-head gate voids the approval and re-review follows), and `reissue` (`runner_gone`: `errored` or `terminated` with units unfinished, or the hosting deadline passed on an instance not `waiting`, keyed by the attempt number). Every id is derived from the event, so a fact read twice offers the same effect once; a move whose precondition no longer holds when the bot executes it is acknowledged `skipped`, and the write-through defers every move effect until its executor lands. The runner's own open takes the same title rule at open (the recover pr-check titles by the head commit's subject when it passes, [agent-ship.md](agent-ship.md) item 10), and `plane stop <instance>` is the `runner_stop` move as one destructive command ([agent-ship.md](agent-ship.md) item 16). A finding (`src/core/plane/findings.ts`) carries the watch and the timeline of events that fired it, deduplicated by watch and subject (`mergePlaneFindings` — two findings on one subject are ONE, timelines merged and bounded); the bot dispatches a research-tier run over the timeline inside the untrusted fence (`findingResearchRequest`) and files its answer through the path `friction propose` uses (`filePlaneFinding`, the issue-tracker seam, an open issue with the finding's title a duplicate). `[gap]` the bot-side observation posts (`pr_tracked`, `child_sealed`, `approval`, `runner_status` onto the object) and the executors for `retitle`, `pr_open`, `rebase_round` and `reissue` land with the transport's later units.
11. **The chat column (record 0070, `docs/decisions/0070-the-control-plane-is-where-the-maintainer-works-the-plane-page-pins-a-chat-column-beside-the-panels-and-an-orchestrator-thread-answers-about-the-fleet-and-acts-on-it.md`).** From the wide breakpoint up the page is two columns: the panels beside a pinned chat — the existing web chat's composer, turns and cards ([web-chat.md](web-chat.md)), never a second chat implementation — bound to the viewer's orchestrator thread: one conversation per person, keyed on the session (`web:<sub>:orchestrator`), created on first open and continued ever after, served and sent through the web chat's own `/threads` routes. The seed carries both halves at one `at` (the table's), so a row the chat cites is the row the panel paints; the chat half never rides the JSON twin, and a chat that cannot be read costs the column, never the panels. A viewer without a session gets the panels full-width as before the column existed. The column defaults to 400 px, the divider drags within 320–640 px, and the chosen width is remembered per person in the browser's localStorage — a per-viewer convenience, never shared state; empty or blocked storage renders the default. Below the wide breakpoint the chat folds behind a floating button that opens it as a sheet; the panels' own rules are unchanged.
12. **The orchestrator preset (record 0070, criteria 3 and 5).** `orchestrator` is a preset in the capability tables (`src/agents/registry.ts`): no workspace, no shell, no credential — machine `none`, identity `none` — and a read tool set: `plane_show` (the plane's table through the ONE plane service, under the requester's own `runs:read` predicate, so a row the chat cites is the row the panel paints and a reader sees exactly what `plane show` would print them), the thread's session tools and the status card, and nothing that writes — no `submit_*`, no issue writes, and no run tool (those stay in the conductor toolset alone, [routing-and-config.md](routing-and-config.md) item 20); its writes are the registry's fenced commands through the door (record 0070's later units), never a tool. Its instructions speak record 0066's twelve nouns and make the tables the only source for a fleet fact: read before answering, cite the row read, and a question the tables cannot answer is answered "the tables do not say" instead of recalled; without the capability the tool itself refuses to recall. The preset resolves through the config layers like any other — `agent:orchestrator` works from any channel a grant admits, a plain fleet question reaches it through the router's table, and nothing hardcodes it to the plane page.
13. **The writes through the door (record 0070, criteria 4 and 6).** A write typed in the orchestrator [thread](../vocabulary.md#thread) is the Slack door's write: the operator binds the sentence to one registry command ([routing-and-config.md](routing-and-config.md) item 29), the policy table authorizes the PERSON the session names — a grant-less person is refused by the table, so the thread can do what its person can do and nothing a service actor could — and the blast-radius class the confirmation renders from is the same on every surface (record 0044). The two acts that had no command are registry commands born fenced (`src/core/commands/merge.ts`): `pulls merge` squash-merges one approved [pull request](../vocabulary.md#pull-request) at exactly its reviewed head and `pulls enqueue` puts exactly that approved head in the base branch's merge queue (GitHub atomically refuses a moved head) — both action `merge:write` (a grant, never a chat or browser baseline), destructive with a risk line naming the pull request, hidden without the `github` capability. Both refuse by reason: a head no review approves, a reviewer's changes-requested standing at it (their last word at that head, even beside another's approval), a red check at it (the merge also refuses one still running, and a head where no check has reported yet — the fresh-head window before CI registers never merges unverified, and a repository with no CI stays a person's click on GitHub; the queue runs pending checks itself), and a person nobody bound to a GitHub login (record 0062) — the App credential never merges as nobody; the merge that lands carries the person's bound login as the squash commit's `Merged-by:` trailer and the answer names them, and the enqueue's answer records who asked. The release pull request — release-please's branch or its `chore(main): release` title — is answered with the handoff card (record 0064's *Handed* phase: the pull request by name, "this deploys production", no merge called) on both commands: that click stays a person's. The thread holds no admission rule in prose: a move the decider owns is asked of the decider, and the preset's writes are exactly the registry commands its person's grants admit — the boundary is the tool list and the policy table, never preset prose. `[gap]` the merge attribution proven against a real pull request before the orchestrator preset holds the command (human-gated, plan 004 unit 3's validation).

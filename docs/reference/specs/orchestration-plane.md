# Orchestration plane

Switchboard can say **what is happening**: every live and recently ended run, every ship unit and every tracked pull request, each with its owner and its health, as one table read from the stores that already exist. The table is the first surface of the orchestration plane (record 0064, `docs/decisions/0064-the-plane-owns-every-runs-state-a-refusal-becomes-a-queue-position-an-ending-is-judged-by-the-ledger-that-saw-it-and-a-release-is-a-quiet-window-a-person-closes.md`, which merges beside this unit): the read-only projection the plane's later units (the queue, the windows, the watches and their moves) grow beside. Nothing in this feature decides, writes or steers.

**Pure table, thin reads (locked design).** One node-free module says what the rows mean, `src/core/plane/table.ts`, so the command's text, the page and the tests agree on every word; the service reads and hands the facts over. A health flag is derived from a fact the row already carries and never from a clock the plane owns: the stall facts are the runs index's ([live-view.md](live-view.md) item 32), the pull request facts are the merge door's ([agent-ship.md](agent-ship.md) item 9), a unit's ending is the coordinator's row ([run-history.md](run-history.md) item 50).

## Behavior

1. **Runs and their health.** The table lists every run live in this process or on the ledger under another generation, then every run finished within the recent window (one hour by default), each under the viewer's `runs:read` predicate, exactly the rows `runs list` would show. A row's owner is its requester, with the name the adapter resolved when it did, or the generation driving it when the row is live under another container. Its health flags come from the pace facts the live summary carries: `bound-exceeded` when the in-flight call ran past the bound it declared, `stalled` when no tool call landed for a whole pace window, `no-signal` for a row live under another generation, which carries no pace fact and is never read as stalled; a finished row reads `provisional`, `interrupted` or `failed` from its record, or nothing. Live rows sort first, stalled ahead of healthy, then rows with a flag, then the recently ended, newest first within each band.
2. **Pull requests and their health.** Every pull request a unit row or a run's record names is read once through the merge door's own GitHub reads (the facts, the checks at the head, the reviews), up to a bound (20 by default, the units' first), and judged in the merge door's order: `approved` when a review approves the head, `dirty` when GitHub reports a conflict with the base, `red` when a check at the head failed else `pending` when one is still running, `mistitled` when the title fails the repository's title rule, `merged` or `closed` for a closed one, and `unknown` alone when GitHub could not be read or the process holds no GitHub credential. A pull request is owned by the unit whose row names it, else by the run that opened it, else by a person.
3. **Units and the owner gap.** Every instance a listed run belongs to contributes its unit rows, under the same predicate the unit page applies, with the instance's facts beside them. A unit with no ending is `live` while a run of it is live and `waiting` otherwise; an ending record 0051 idles on reads `idle`; `merged` and `merge-ready` read as they are, and a merge-ready unit whose pull request is still open is also an `owner-gap`, the state record 0064 names; a pull request the plane could not read, on GitHub or past the read cap, leans open, so a read failure never hides the gap. A coordinator child is joined to its unit through the spawn's idempotency key, else through the unit whose thread it runs in.
4. **`plane show`.** One typed registry command, action `runs:read`, effect read, on every surface by derivation (`plane show` in chat and on the CLI, `GET /api/plane.show`, the `plane_show` MCP tool), answering the table as JSON and rendering it as three sections, aligned columns for a terminal and bullets for chat, each section saying `(none)` when empty. The router is offered it with its three fixtures.
5. **The panel.** `GET /plane` serves the shared web shell with the table as its seed and `GET /plane.json` answers the same table, one view in two encodings (record 0056), Access-gated beside `/runs` and `/costs`; a viewer the gate resolved to nobody sees nothing, a table that cannot be built is a 502 with the reason, never a 500. The page paints the three sections with the same words and links each run as the runs index does: a live run of this process through its capability token, every other run tokenless. **Plane** is a nav section beside Runs, always present because its rows are run facts under the same predicate.

# Settings page

`GET /settings` is the dashboard section where a customer configures what Switchboard already lets them configure, and sees what only `config.yaml` can change. It is an adapter over the command registry and nothing more ([record 0041](../../decisions/0041-the-settings-page-is-a-surface-over-the-registry-and-configures-the-shared-tiers.md)): every tab's seed is the answer of registry commands invoked as the viewer, every write the page makes is one `POST /api/<group>.<verb>` ([command-registry.md](command-registry.md), [dashboard-routes.md](../dashboard-routes.md)), and the page carries no rule of its own about who may do what. Three tabs: **MCPs** (`mcp list` as a table, an add form, a connect link, a remove button; [mcp-tools.md](mcp-tools.md) items 13 to 19), **Channels** (the index of configured channels, then one channel's scope as a form over `config show|set|clear|instructions channel`; [routing-and-config.md](routing-and-config.md) items 5, 12, 24) and **Installation** (a read-only projection of the running `config.yaml` and the capabilities that are on; [capabilities.md](capabilities.md)).

The dashboard configures the **shared tiers**, org and channel, and the viewer's own tier when the session is **linked** to its Slack person ([record 0042](../../decisions/0042-a-dashboard-session-is-the-person-its-email-names-identity-not-authority.md): the Access email names one active Slack user, resolved once in the gate). Unlinked, a browser session is `access:<sub>`, a run is requested as a chat user, and a personal setting written from the dashboard would land on a scope no run reads: the config and MCP handlers refuse a `me` write from such a session, naming chat as the place for it (routing-and-config item 5, mcp-tools item 14).

## Behavior

1. **Routes.** `/settings` opens on MCPs where the `mcp` capability is on, else on Channels; `/settings/mcps` (with `?channel=<id>` to list one channel's tier beside org and own), `/settings/channels`, `/settings/channels/<channel id>` (percent-encoded or not; a platform-namespaced id like `slack:C…`) and `/settings/installation` are the tabs. Anything else under `/settings` is not a route. The page sits behind the dashboard's one identity gate like `/runs*`; a method other than GET is a 405; a registry that throws is a 502 with a capped reason, never a 500.
2. **The seed is the registry's answer, as the viewer** — the viewer being the caller `resolveAccessActor` resolves, linked to its Slack person when the session's email names one ([record 0042](../../decisions/0042-a-dashboard-session-is-the-person-its-email-names-identity-not-authority.md)); the seed carries `asUser` then, the MCPs tab offers the `me` tier (the person's, defaulted when no channel is open) and marks the person's rows as the viewer's own and writable, and an unlinked session sees the `me` option disabled with the pointer to chat. The MCPs tab's rows are `mcp list` (with `--channel` when one is named), the Channels tab's index is `config overrides` and its open channel is `config show --channel <id>`, each invoked through the bound registry with the `/api` caller for the gate's identity (`callerFor`), so the page can see exactly what the same identity could read on the CLI. A refused or unavailable command puts its sentence on the seed in place of the rows (`unavailable`, `refused`) and the page shows it as is. The open channel's scope is `channelScopeView`: `config show` without the viewer's own user scope and without every `mcpServers` map (the MCPs tab shows servers through `McpServerView`, which carries no credential name).
3. **Installation is a projection by allow-list.** `installationSettings(config, capabilities)` writes every row out by name (`row(key, configured, default, how, note)`), nothing iterated off the config object except `defaults.models` and `defaults.efforts`, whose keys are preset names; each row carries the configured value or the default marked `isDefault`, and `how` says whether a channel overrides it at run time (`runtime`, the `defaults.*` rows) or `config.yaml` with `deploy config` and a restart changes it (`config`). The capability list names each capability's block in words, never an env var. The rendered view holds no `*Env` name, no URL, no `SHOUTING_CASE` identifier and no name from the deploy secrets manifest, whatever the config holds. The tab is gated on `config:read`.
4. **`canWrite` is the handler's question, asked early.** The seed carries `canWrite.org = authorize(actor, "mcp:write", config-scope org)`, `canWrite.channel = authorize(actor, "mcp:write", config-scope channel)` (false without a channel) on the MCPs tab and `authorize(actor, "config:write", config-scope channel)` on an open channel: the same calls the `mcp.*` and `config.*` handlers make. The page uses them to disable controls and say why; it decides nothing, and a write forced through anyway meets the handler's refusal.
5. **Every write is one command.** Add posts `mcp.add` with `name`, `url`, `scope` (`org`, or `channel` with `channel`), `agents` joined by commas and `auth` when chosen; Connect posts `mcp.connect` and Remove (after a confirm) posts `mcp.remove`, each naming the row's tier; Probe reads `mcp.show`. Save posts `config.set` with `scope: channel`, `channel` and only the filled fields (a `config set` patches; an empty field leaves the stored value alone); the instructions box posts `config.instructions` with its text, an empty text clearing them; Clear (after a confirm) posts `config.clear`. No request the page composes carries `scope: "me"`. A connect link comes back from `add` and `connect` and is shown as a link to the Access-gated connect page; a credential never passes through this page.
6. **The tabs follow the capabilities; the way in is the header's cog.** Settings is chrome, not a section of the dashboard: every page's header carries the settings cog (`web/src/components/SettingsLink.vue`, a same-tab link to `/settings`, `aria-current="page"` only on the settings page) beside the docs link, and the phone menu lists it in the docs' group; the site nav's sections are unchanged. The MCPs tab exists only where `mcp` is on or the viewer is on it; Channels and Installation always. The page without a seed renders its empty state, never a crash.
7. **Channels tab.** The index lists each channel that carries a scope with the names of its settings and where they come from (`config.yaml`, `runtime`, both), as links to the channel's page; an id field opens a channel with no scope yet. The open channel shows the effective agent, model and effort for a run there, the form over its scope (agent, model, per-agent models, effort, per-agent efforts, the boundary's three axes, instructions), the restricted agents marked, and the admins hint when the viewer may not write.
8. **MCPs tab.** Rows show name, tier, URL (origin and path only, as `McpServerView` gives it), agents, auth, state (`connected`, `awaiting credential`, `pinned in config.yaml`) and `added by you` for the viewer's own; Connect appears on a runtime row whose auth is not `none`, Remove on any runtime row, both disabled without the tier's write right; a static row has neither. The add form offers the org tier and, when a channel is open, the channel tier, whose agents are limited to the self-serve presets.

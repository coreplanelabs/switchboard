# Settings page

`GET /settings` is the dashboard section where a customer configures what Switchboard already lets them configure, and sees what only `config.yaml` can change. It is an adapter over the command registry and nothing more ([record 0041](../../decisions/0041-the-settings-page-is-a-surface-over-the-registry-and-configures-the-shared-tiers.md)): every tab's seed is the answer of registry commands invoked as the viewer, every write the page makes is one `POST /api/<group>.<verb>` ([command-registry.md](command-registry.md), [dashboard-routes.md](../dashboard-routes.md)), and the page carries no rule of its own about who may do what. Registry sections: **MCP servers** (`mcp list` as a table, an add form, a connect link, a remove button; [mcp-tools.md](mcp-tools.md) items 13 to 19), **Channels** (the index of configured channels, then one channel's scope as a form over `config show|set|clear|instructions channel`; [routing-and-config.md](routing-and-config.md) items 5, 12, 24) and **Installation** (a read-only projection of the running `config.yaml` and the capabilities that are on; [capabilities.md](capabilities.md)).

The dashboard configures shared org/channel tiers and the actual account's own tier. A signed Access account uses its `access:<sub>` scope and current grants; email matches and explicit conversation links do not lend Slack ownership or writes. A service token has no human `me` scope. The policy and command handlers decide every write; the page displays their answers.

## Behavior

1. **Routes.** The registry-settings adapter handles `/settings`, `/settings/mcps` (with `?channel=<id>`), `/settings/channels`, `/settings/channels/<channel id>` and `/settings/installation`. `/settings` opens on MCP servers when the `mcp` capability is on, else Channels. Other paths fall through to their own handlers: the replacement also has Identities and Settings → Runtime. The shared dashboard gate protects each route. A method other than GET is `405`; a throwing registry is `502` with a capped reason.
2. **The seed is the registry's answer under the actual account.** The production browser uses the freshly resolved native Access actor and that account's current grants. Its `me` settings and MCP tier remain `access:<sub>`, including when an email matches a Slack account or the accounts are explicitly linked. Email is display data; explicit links correlate future conversation projection, not Settings ownership, `self` aliases or borrowed Slack write rights. Person view is read-only; global work-view selection does not lend another person's command authority.
   MCP rows come from `mcp list` (with `--channel` when named); channel rows from `config overrides` and `config show --channel`. The bound registry receives the same actual caller as `/api`. A refused or unavailable command puts its sentence on the seed instead of rows. `channelScopeView` removes the viewer's user scope and every `mcpServers` map; server views carry no credential names. The retained legacy caller fixtures below exercise explicitly injected caller metadata only; they do not prove production email-to-Slack resolution.
3. **Installation is a projection by allow-list.** `installationSettings(config, capabilities)` writes every row out by name (`row(key, configured, default, how, note)`), the legacy projection iterates `defaults.models` and `defaults.efforts`, whose keys are preset names. The DSL projection uses the registered names and shared resolver to expose `agents.<name>.profile`, model and reasoning effort; each row carries the configured value or the default marked `isDefault`, and `how` says whether a channel overrides it at run time (`runtime`, agent model and effort defaults) or `config.yaml` with `deploy config` and a restart changes it (`config`). The capability list names each capability's block in words, never an env var. The rendered view holds no `*Env` name, no URL, no `SHOUTING_CASE` identifier and no name from the deploy secrets manifest, whatever the config holds. The tab is gated on `config:read`.
4. **`canWrite` is the handler's question, asked early.** The seed carries `canWrite.org = authorize(actor, "mcp:write", config-scope org)`, `canWrite.channel = authorize(actor, "mcp:write", config-scope channel)` (false without a channel) on the MCPs tab and `authorize(actor, "config:write", config-scope channel)` on an open channel: the same calls the `mcp.*` and `config.*` handlers make. The page uses them to disable controls and say why; it decides nothing, and a write forced through anyway meets the handler's refusal.
5. **Every write is one command.** Add posts `mcp.add` with `name`, `url`, `scope` (`me` — the viewer's own tier, defaulted when no channel is open — or `org`, or `channel` with `channel`), `agents` joined by commas and `auth` when chosen; Connect posts `mcp.connect` and Remove (after a confirm) posts `mcp.remove`, each naming the row's tier; Probe reads `mcp.show`. Save posts `config.set` with `scope: channel`, `channel` and only the filled fields (a `config set` patches; an empty field leaves the stored value alone); the instructions box posts `config.instructions` with its text, an empty text clearing them; Clear (after a confirm) posts `config.clear`. A connect link comes back from `add` and `connect` and is shown as a link to the Access-gated connect page; a credential never passes through this page.
   A held write displays its exact saved action and risk through the shared web API confirmation adapter. Confirm or Cancel sends only the saved id to the same command route; the core atomically claims it, rechecks current permissions and returns the original command JSON. Token and loopback dashboards use the same affordance without an Access approval link. A rejected or cancelled action changes nothing.

6. **Global Settings navigation and capability sections.** The replacement desktop sidebar and phone navigation drawer both link to `/settings`; the account menu links directly to Identities. Settings sections are Channels, MCP servers, Identities, Runtime and Installation. MCP servers appear only when configured or already selected; Runtime appears when resident environments are configured. Channels, Identities and Installation remain available. The selected section is marked current. A missing or mismatched seed shows Settings unavailable with a Reload button and no editable controls; Reload requests the current page again through the same gate.
7. **Channels tab.** *Never "no data"* (record 0041, accepted): the tab opens on the viewer's own settings — what a run they ask for outside any channel gets (`config show` without a channel: the installation defaults under their own scope, `ViewerSettingsView`), the defaults, and their scope or the sentence that nothing is theirs yet; a refusal of that read is shown as is beside the index. The index lists each channel that carries a scope with the names of its settings and where they come from (`config.yaml`, `runtime`, both), as links to the channel's page; an empty index says every channel runs on the defaults, and a **picker** opens any channel the viewer may read, by name: a combobox (`ChannelPicker.vue` over Nuxt UI's `UInputMenu`) — type a few letters of the name or the id, the list narrows, Enter or a click opens the channel at once (`config channels` → the seed's `pickable`: `#name` with the id under it, a private one marked; the bot's own channels plus the scoped ones, and the open channel even when the list lacks it); an id field stands in only when nothing could be listed; a note says when the bot could not list its channels and only the scoped ones are offered. Every other choice on the page (agent, effort, identity, tier, auth) is the same styled select (`SettingSelect.vue` over `USelect`, the empty "leave it" choice spelled out), never the browser's. *Names, not ids* (record 0042, the dashboard reads names): the seed carries each channel's name without its hash beside its id (`channelName`, from the core's `NameDirectory` — `src/core/names.ts`, the Slack directory `src/channels/slackNames.ts` over the adapter's cached `conversations.info` and `users.info` lookups; the static one knows nothing), asked once per channel, concurrently, a failure or an unknown id leaving the id alone; the index rows, the open channel's heading and a refusal line read `#name` with the id in the tooltip (and beside the heading), and the id alone when there is no name. A missing or mismatched seed shows an unavailable error and Reload, with no editable settings. The open channel shows the effective agent, model and effort for a run there, the form over its scope (agent, model, per-agent models, effort, per-agent efforts, the boundary's three axes, instructions), the restricted agents marked, and the admins hint when the viewer may not write.
8. **MCPs tab.** Rows show name, tier (a user row names its owner), URL (origin and path only, as `McpServerView` gives it), agents, auth, state (`connected`, `awaiting credential`, `pinned in config.yaml`), an **Added by** column that reads `you` for the viewer's own — the person's display name when the service resolved one, the id otherwise ([record 0042](../../decisions/0042-a-dashboard-session-is-the-person-its-email-names-identity-not-authority.md)); Connect appears on a runtime row whose auth is not `none`, Remove on any runtime row, both disabled without the tier's write right; a static row has neither. **Which rows** (record 0042): a viewer with the org write right sees every tier there is (the seed is `mcp list --all`, `allTiers: true`) and a **Promote** button on every person's runtime row that is not already shadowed, which asks first and posts `mcp.promote` with the row's name and owner, then shows the org's connect link (or reloads when `auth: none` connected at once). *Reading the table:* names, not ids — a user row's tier names its owner and `promoted from` names the person, through the view's `ownerName`/`promotedFromName`; the [agents](../vocabulary.md#agent) are the run page's colored agent chips (`AGENT_HUE`); a row a higher tier shadows carries a `shadowed by <tier>` mark and is dimmed; the action column has four fixed slots so buttons line up down the page. *The connect link opens in a new tab*, and while a link is out the page watches its row (one `mcp list` every few seconds, bounded by the link's ten-minute life) and reloads when the row's state changes — so closing the connect tab lands back on a current list; anyone else sees the org's, the open channel's and their own, plus the channel tiers of every channel whose config they may read — `config overrides` names them, one `mcp list --channel` each; a public channel, a granted one, or a private channel the current actual caller is permitted to read ([authorization.md](authorization.md) item 7) — and no Promote. The add form offers the org tier and the channel tier — the open channel's when one is open, else a picker of the channels the viewer may read appears in the form itself (`config channels`, the same `pickable`) and the add posts the picked channel; the channel field above the table is the same combobox — picking a channel opens its tier, the open channel stays offered even when the list lacks it, a Clear returns to the org's and the viewer's own, and an id field stands in only when nothing could be listed; Add stays disabled for the channel tier until a channel is open or picked, the picked channel's write right being the handler's to decide. A channel tier's agents are limited to the self-serve presets. The open channel (`?channel=`) and every channel-tier row read `#name` when the directory knows the channel (`channelName` on the seed and on the row, the service's `resolveChannelName` being the same directory), the id otherwise and always in the tooltip. While an admin views the dashboard as a person ([record 0053](../../decisions/0053-viewing-as-a-person-borrows-their-ceiling-and-keeps-your-name-on-the-line.md); [authorization.md](authorization.md) item 17) both tabs show what that person's session would and every write — Add, Remove, Save, Clear — is refused by the registry door with the one sentence naming the person, which the panel shows as its notice like any other refusal; the banner above the page says so before a click.

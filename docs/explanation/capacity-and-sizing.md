# Capacity and sizing

Why the containers are the size they are, and what "using the cores" means when every process here is one Node event loop on a fractional or single vCPU. The numbers below are measured, and the arithmetic that ties the resident's instance size to the disk it needs lives in a unit test, so a change to either side fails the build rather than the deploy.

Cores and parallelism: every container here is one Node process on a fractional/single vCPU — the bot on `basic` (¼ vCPU / 1 GiB, `max_instances: 1`), the resident on 1 vCPU. Node is single-threaded, so "using the cores" means (a) never serializing independent I/O and (b) not oversubscribing the one core with worker pools. What is in place: the runner executes side-effect-free tools from one turn concurrently and the Anthropic adapter caches the prompt prefix (`docs/reference/specs/run-loop.md` items 9–10); the dispatcher overlaps memory retrieval with repo resolution + executor attach, coalesces status-card edits, and sends the answer before the resident `/detach`; the Slack adapter fetches a follow-up's thread once, downloads a message's attachments concurrently, and scans catch-up channels with bounded fan-out; the HTTP server listens before the Slack handshake; SSE frames are serialized once per event and resumable (`id:`/`Last-Event-ID`). The resident image sets `CI=1`, `VITEST_MAX_WORKERS/THREADS/FORKS=1`, `UV_THREADPOOL_SIZE=2`, `NODE_OPTIONS=--max-old-space-size=1536` as environment defaults so a repo's test runner sizes its pool for the ONE vCPU it has, not the host's core count (a repo's own config still wins). Grow the bot from `basic` only on evidence — the event-loop CPU it burns is redaction regexes over tool output and JSON serialization, both now paid once per event; nothing here measured it CPU-bound.
Container sizing: thread-sandbox Worker `standard-3` (2 vCPU / 8 GiB — lives only for one run, so cents; observed peak 75% CPU / 1.4 GiB, so do not drop to standard-2), resident Worker custom `1 vCPU / 8 GiB / 16 GB` — ONE type for every resident, sized for the largest onboarded repo, and sized by DISK, not memory: Cloudflare caps disk at 2 GB per GiB of memory, so the disk a resident needs dictates the memory it pays for (effectively always-on; Cloudflare bills vCPU on active use only and memory/disk on provisioned size while awake, so memory is the 24/7 cost — ~$52/mo per resident at 8 GiB, ~$26 at 4 GiB — and vCPU is free until used). The arithmetic lives in `deploy/cloudflare-resident/instanceSizing.test.ts` and fails when `wrangler.jsonc` and the measured parts disagree (measured inside the resident of the largest onboarded repo, a pnpm monorepo, with one `du`, hardlinks counted once): image 552 MB + mirror 380 + warm checkout 2772 (history 380 + tree 94 + pnpm `node_modules` 2298) + the reserve the attach admission holds back (snapshot staging 0.6 × (mirror + checkout) = 1891, floor 1074) = 6669 MB base; a hardlinked thread tree 555 MB; a thread whose lockfile differs 2853 MB; the 16 000 MB instance mounts as 15 449 MB → 10 hardlinked + 1 installing trees fit, the pool maximum (16 + 2) fits neither it nor the 20 GB ceiling. **Disk is a budget** (`docs/reference/specs/resident-repos.md` item 55, `src/execution/residentDiskBudget.ts`): every cycle and attach measures it (`live.disk` on `/residents`, ` · disk x/y (pct%)` on `repo list`, `disk max` on the watchdog line), a new thread tree is admitted only under `free − reserve` — the coldest clean idle trees are evicted first, then the attach is refused `disk-pressure` with the math in the card note and the run goes cold — so the instance size decides how many concurrent trees run warm, not whether ENOSPC happens. The pnpm store does NOT duplicate deps (measured: `/home/worker1` is 4 KiB on a restored disk; hardlinked from the store where an install ran). How the size was reached: `standard-1` (½ vCPU / 4 GiB / 8 GB) was outgrown by a resident pinned at 100% of ½ vCPU with 2.2 GiB in use, so 1 vCPU; then 8 GiB for the 16 GB of disk it unlocks; then, with the budget in place, 16 GB was kept (the 12 GiB / 20 GB step, +$26/mo per resident, buys 16 + 1 or 12 + 2 concurrent trees — take it when the dash shows `disk-pressure` refusals). `basic` (1 GiB) dies running switchboard's vitest suite. The resident pool is 16 users and runs release theirs via `/detach` on finish — `docs/reference/specs/resident-repos.md` item 16a; the hourly sweep releases clean idle trees, a deploy that grows the pool self-applies via `reconcileImage`, and unused residents park their refresh so the container sleeps (item 16b). Residency GC (items 45–46): every refresh cycle reclaims worktrees whose ref is finished (branch pruned from the mirror, or PR merged/closed — a poll, since the GitHub App has webhooks off), and an over-cap `repo onboard … --evict-coldest` offboards the coldest eligible warm resident instead of 429 (admin opt-in per request, default off). `RESIDENT_CAP` is 6 (the team's concurrent-repo count); to exercise the over-cap path on prod without touching the constant, the admin debug op `set-test-overrides` lowers the effective cap/floor for the current build only (item 49) — never raise it that way, it can't.

# Operate production

Goal: change what runs in production without breaking a run that is in flight. Production is four Cloudflare Workers deployed on the release from CI; this page is the operator's rules for the moments a person is involved — a manual deploy, a rotated secret, a change to the fleet's shape. The everyday path is [Deploy and rotate a secret](deploy-and-rotate-a-secret.md); the ordering and selection logic is specified in [`features/release-and-deploy.md`](https://github.com/coreplanelabs/switchboard/blob/main/features/release-and-deploy.md).

- **Bot deploys are preflighted too:** `npm run deploy` in `deploy/cloudflare/` runs its own `preflight.mjs` first (pointed at the bot by `SWITCHBOARD_BASE_URL`, which `deploy all` sets from the profile — the dir's script run alone needs it in the env) and refuses while `GET /healthz` reports runs in flight or `draining: true`, or while the `switchboard-switchboardserver` container application is mid-rollout (`wrangler containers list --json` state not `active`/`ready`). A rollout SIGTERMs the container and the bot drains for up to 15 min, so ONE deploy over a run is fine — but a second deploy on a draining instance kills it at once (incident 2026-08-29 23:51Z: a review died at 153 s, card frozen, run gone from `/runs`). Needs no token (`/healthz` is public); fails closed on an unreachable bot, a wrangler failure, or a pre-item-8 Worker (bare `ok` body); `SWITCHBOARD_DEPLOY_FORCE=1 npm run deploy` bypasses with a warning. Live cards show `⏸ deploy in progress …` during a drain, and the next container's reconnect sweep closes any card a killed process left spinning as `❌ interrupted`. The drain closes the Slack socket at once and Cloudflare boots the replacement only after exit, so a deploy during an in-flight run **blacks Slack out for the run's remaining duration** (7.5 min observed); mentions posted in that gap are recovered by the reconnect catch-up, which covers up to its 30-min window (`DRAIN_DEADLINE_MS` + cold start ≤ window, `src/core/drain.ts`, #272) — prefer deploying at a quiet moment. `/healthz` reports `drainDeadlineMs` and, while draining, `drainStartedAt`. Details: `features/slack-channel.md` items 7–8.
- **Production deploys on the release, from CI — not from a laptop** (`features/release-and-deploy.md`): merging the release-please PR tags the version and `release-please.yml` calls `deploy-production.yml`, which runs `deploy all --affected` on the release commit. `--affected` judges each Worker against the commit it serves (`build.commit` on its `/healthz`; else the last `v*` tag; else unsure → deploy) and deploys only those whose inputs changed: the import closure of `deploy/<w>/worker.ts` (`src/deploy/affected.ts` crawls it — a `src/` file is a memory-Worker input because the memory Worker imports it), the Worker's dir, the PRODUCTION half of its lockfile, and for the bot everything the Dockerfile COPYs. Tests/docs/CI/deploy tooling are an explicit inert list; **a path no rule claims makes every Worker deploy and names itself** — classify it in `INERT_RULES` or a Worker's `inputs`, never by weakening the fallback. The release PR carries the plan as a sticky comment; every PR's `deploy targets` job shows what its diff would deploy (`--base HEAD^`). Manual: `gh workflow run deploy-production.yml --ref main -f targets=all|bot,resident [-f force=true]` — the same job, refused off `main`. CI secrets: `CLOUDFLARE_DEPLOY_TOKEN` (Workers Scripts + Containers + R2 + Account Settings, zone Workers Routes + DNS; the docs job's `CLOUDFLARE_API_TOKEN` is only the fallback), `RESIDENT_READ_TOKEN`, optional `SANDBOX_TOKEN`. `deploy all` checks the credential's capabilities (`containers list`, `r2 bucket list`) before any Worker deploys.
- **Deploy order is codified — `deploy all` is the only runner** (`deploy plan` shows what it would do): memory (state Worker, DO migrations first) → bot → resident → sandbox, from a clean checkout (at `origin/main` unless `--allow-branch`, which CI passes for the release commit), with `CLOUDFLARE_ACCOUNT_ID` stripped and the account asserted (`coreplane-infra` in `wrangler whoami`, or `CLOUDFLARE_API_TOKEN` verified against the account — an account-owned token lists no memberships; a foreign token is refused with wrangler's words, never silently replaced by a login). Preflight refusals are waited out (retry every 60 s, ≤30 min, a heartbeat per poll), never forced unless `--force` is passed explicitly; the bot step is done only when the NEW container is live (`/healthz` not draining + `build.commit` == the deployed commit). Never deploy the four Workers by hand in parallel — the bot must not write to a Durable Object whose migration has not landed. Selection (`src/deploy/affected.ts`), plan (`src/deploy/plan.ts`) and live decision (`src/deploy/liveGate.ts`) are pure and unit-tested; runner is `src/deploy/run.ts` behind the `deploy.all` command. The plan's check line reports which deploy dirs lack `node_modules` (the runner `npm ci`s them first) — it needs no `config/config.yaml`, so it runs from any worktree. **Rotating any bot secret requires a container restart**: `wrangler secret put` creates a new Worker version but the running container keeps the env it started with (a rotated `MEMORY_TOKEN` 401'd for ~2 h on 2026-08-30). Rotation runbook: `npm run secrets` (or `wrangler secret put`) in `deploy/cloudflare/`, then `npm run cli -- deploy restart` — no image build: the Worker's `POST /admin/restart` (bearer `$SWITCHBOARD_DEPLOY_TOKEN`, a `SWITCHBOARD_INGRESS_TOKENS` identity with `deploy:write`) makes the Container DO `stop()` the bot (SIGTERM → drain), and the next request (keep-alive cron, or the CLI's poll) starts it on the current env; refused while runs are in flight unless `--force`; done once `/healthz` reports a later `startedAt` (~30 s idle). `deploy all --only bot` also works but rebuilds the image for nothing.
- **Resident deploys are preflighted:** `npm run deploy` in `deploy/cloudflare-resident/` runs `preflight.mjs` first (pointed at the Worker by `RESIDENT_BASE_URL`, set by `deploy all` from the profile) and refuses while any resident has work in flight (a Worker deploy swaps the DO isolates and kills running threads). It needs a resident bearer in the env (`RESIDENT_ADMIN_TOKEN`, `RESIDENT_OPERATOR_TOKEN` or `RESIDENT_READ_TOKEN` — read is enough, and is what CI holds) and fails closed without one or when the Worker is unreachable; `RESIDENT_DEPLOY_FORCE=1 npm run deploy` bypasses with a warning. Details: `features/resident-repos.md` item 44.
- **Polylane topology discipline:** this repo is mapped into the [coreplanelabs Polylane workspace](https://console.polylane.com/coreplanelabs) — the context graph behind the "Polylane production impact" PR check and blast-radius/impact queries, so a stale graph under-reports what a change can break. Cloud resources (Workers, DO namespaces, domains) sync automatically; **cross-Worker call paths do not** — they are asserted logical edges. A PR that adds/removes a Worker, a Durable Object, or a call path between Workers (or changes what a path carries) asserts the delta in the same change cycle: `polylane api call cloud_infra.edges.post --body-file <edge.json>` (schema via `polylane api describe cloud_infra.edges.post`; an edge is `{workspaceId, source, target, relationship, properties}` with each node keyed `{id: "<script name>", provider: "cloudflare", account: "3c7b28f23cc93f09e77bb0a9ffcb7e6f", region: "earth", type: "cf.workers.script"}`; put the routes + auth bearer in `properties`), and a removed path is deleted with `cloud_infra.edges.delete`. Asserted edges as of 2026-08-30: `switchboard` → {`switchboard-memory`, `switchboard-resident`, `switchboard-sandbox`}, all `invokes`. Verify: `polylane service graph "cloudflare/3c7b28f23cc93f09e77bb0a9ffcb7e6f/earth/cf.workers.script/switchboard" --direction outbound`. Needs the signed-in `polylane` CLI (a scoped MCP credential may lack `cloud_infra:read`; the CLI user credential works).

## The deployment profile

Every place-specific fact the deploy tooling needs — the Cloudflare account, each Worker's script name and hostname, where the bot's runtime config comes from — is in `deploy/profile.json` (`deploy/profile.example.json` is the shape). `deploy plan` and `deploy all` read it; health URLs, the bot's admin route and the state Worker's URL are derived from it, never typed twice. Without a profile, `deploy plan` reads the example and says so; `deploy all` refuses to deploy the example. `SWITCHBOARD_DEPLOY_PROFILE=<path>` points both at another installation's profile.

`configSource` is where `deploy all` reads the bot's config from before the image builds: a path in the tree (the default), `github://owner/repo/path@ref` read with `CONFIG_REPO_TOKEN`, or `op://Vault/Item/field` read with the 1Password CLI and `OP_SERVICE_ACCOUNT_TOKEN`. The file lands at `config/config.production.yaml`, which the Dockerfile copies and the bot Worker points its container at; a source that cannot be read refuses the deploy before any Worker changes.

The Worker configs are rendered from the profile, not edited. Each `deploy/cloudflare*/wrangler.jsonc` is generated from the `wrangler.template.jsonc` beside it by `npm run deploy:gen` (`deploy init`): the account, script name, hostname, the bot's public URL and state-Worker URL, and the Access team domain and AUD are placeholders the profile fills. Change the template (a binding, a cron, an instance size) or the profile (a hostname, the account), run `npm run deploy:gen`, commit both; `npm run deploy:check` runs in `check:consistency` and fails on a rendered file that was edited by hand or not re-rendered. The templates are valid JSONC — editors and prettier treat them as the config they describe — and the rendered files are what wrangler reads.

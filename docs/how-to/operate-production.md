# Operate production

Goal: change what runs in production without breaking a run that is in flight. Production is four Cloudflare Workers deployed on the release from CI; this page is the operator's rules for the moments a person is involved — a manual deploy, a rotated secret, a change to the fleet's shape. The first deploy is [Deploy for the first time](deploy-for-the-first-time.md); the everyday path is [Deploy and rotate a secret](deploy-and-rotate-a-secret.md); the ordering and selection logic is specified in [`docs/reference/specs/release-and-deploy.md`](../reference/specs/release-and-deploy.md).

- **Bot deploys are preflighted too:** `npm run deploy` in `deploy/cloudflare/` runs its own `preflight.mjs` first (pointed at the bot by `SWITCHBOARD_BASE_URL`, which `deploy all` sets from the profile — the dir's script run alone needs it in the env) and refuses while `GET /healthz` reports runs in flight or `draining: true`, or while the `switchboard-switchboardserver` container application is mid-rollout (`wrangler containers list --json` state not `active`/`ready`). A rollout SIGTERMs the container and the bot drains for up to 15 min, so ONE deploy over a run is fine — but a second deploy on a draining instance kills it at once (the run dies mid-flight, its card freezes, and it vanishes from `/runs`). Needs no token (`/healthz` is public); fails closed on an unreachable bot, a wrangler failure, or a pre-item-8 Worker (bare `ok` body); `SWITCHBOARD_DEPLOY_FORCE=1 npm run deploy` bypasses with a warning. Live cards show `⏸ deploy in progress …` during a drain, and the next container's reconnect sweep closes any card a killed process left spinning as `❌ interrupted`. The drain closes the Slack socket at once and Cloudflare boots the replacement only after exit, so a deploy during an in-flight run **blacks Slack out for the run's remaining duration** (7.5 min observed); mentions posted in that gap are recovered by the reconnect catch-up, which covers up to its 30-min window (`DRAIN_DEADLINE_MS` + cold start ≤ window, `src/core/drain.ts`) — prefer deploying at a quiet moment. `/healthz` reports `drainDeadlineMs` and, while draining, `drainStartedAt`. Details: `docs/reference/specs/slack-channel.md` items 7–8.
- **Production deploys on the release, from CI — not from a laptop** (`docs/reference/specs/release-and-deploy.md`): merging the release-please PR tags the version and `release-please.yml` calls `deploy-production.yml`, which runs `deploy all --affected` on the release commit. `--affected` judges each Worker against the commit it serves (`build.commit` on its `/healthz`; else the last `v*` tag; else unsure → deploy) and deploys only those whose inputs changed: the import closure of `deploy/<w>/worker.ts` (`src/deploy/affected.ts` crawls it — a `src/` file is a memory-Worker input because the memory Worker imports it), the Worker's dir, the PRODUCTION half of its lockfile, and for the bot everything the Dockerfile COPYs. Tests/docs/CI/deploy tooling are an explicit inert list; **a path no rule claims makes every Worker deploy and names itself** — classify it in `INERT_RULES` or a Worker's `inputs`, never by weakening the fallback. The release PR carries the plan as a sticky comment; every PR's `deploy targets` job shows what its diff would deploy (`--base HEAD^`). Manual: `gh workflow run deploy-production.yml --ref main -f targets=all|bot,resident [-f force=true]` — the same job, refused off `main`. CI secrets: `CLOUDFLARE_DEPLOY_TOKEN` (Workers Scripts + Containers + R2 + Account Settings, zone Workers Routes + DNS; the docs job's `CLOUDFLARE_API_TOKEN` is only the fallback), `RESIDENT_READ_TOKEN`, optional `SANDBOX_TOKEN`. `deploy all` checks the credential's capabilities (`containers list`, `r2 bucket list`) before any Worker deploys.
- **Deploy order is codified — `deploy all` is the only runner** (`deploy plan` shows what it would do): memory (state Worker, DO migrations first) → bot → resident → sandbox, from a clean checkout (at `origin/main` unless `--allow-branch`, which CI passes for the release commit), with `CLOUDFLARE_ACCOUNT_ID` stripped and the account asserted (the profile's account in `wrangler whoami`, or `CLOUDFLARE_API_TOKEN` verified against it — an account-owned token lists no memberships; a foreign token is refused with wrangler's words, never silently replaced by a login). Preflight refusals are waited out (retry every 60 s, ≤30 min, a heartbeat per poll), never forced unless `--force` is passed explicitly; the bot step is done only when the NEW container is live (`/healthz` not draining + `build.commit` == the deployed commit). Never deploy the four Workers by hand in parallel — the bot must not write to a Durable Object whose migration has not landed. Selection (`src/deploy/affected.ts`), plan (`src/deploy/plan.ts`) and live decision (`src/deploy/liveGate.ts`) are pure and unit-tested; runner is `src/deploy/run.ts` behind the `deploy.all` command. The plan's check line reports which deploy dirs lack `node_modules` (the runner `npm ci`s them first) — it needs no `config/config.yaml`, so it runs from any worktree. **Rotating any bot secret requires a container restart**: `wrangler secret put` creates a new Worker version but the running container keeps the env it started with (a rotated shared bearer keeps failing with 401 until the container that holds the old value restarts). Rotation runbook: `npm run secrets` (or `wrangler secret put`) in `deploy/cloudflare/`, then `npm run cli -- deploy restart` — no image build: the Worker's `POST /admin/restart` (bearer `$SWITCHBOARD_DEPLOY_TOKEN`, a `SWITCHBOARD_INGRESS_TOKENS` identity with `deploy:write`) makes the Container DO `stop()` the bot (SIGTERM → drain), and the next request (keep-alive cron, or the CLI's poll) starts it on the current env; refused while runs are in flight unless `--force`; done once `/healthz` reports a later `startedAt` (~30 s idle). `deploy all --only bot` also works but rebuilds the image for nothing.
- **Resident deploys are preflighted:** `npm run deploy` in `deploy/cloudflare-resident/` runs `preflight.mjs` first (pointed at the Worker by `RESIDENT_BASE_URL`, set by `deploy all` from the profile) and refuses while any resident has work in flight (a Worker deploy swaps the DO isolates and kills running threads). It needs a resident bearer in the env (`RESIDENT_ADMIN_TOKEN`, `RESIDENT_OPERATOR_TOKEN` or `RESIDENT_READ_TOKEN` — read is enough, and is what CI holds) and fails closed without one or when the Worker is unreachable; `RESIDENT_DEPLOY_FORCE=1 npm run deploy` bypasses with a warning. Details: `docs/reference/specs/resident-repos.md` item 44.
- **Topology outside the tree:** if the deployment is mapped into an external infrastructure graph (the kind behind a production-impact PR check or blast-radius queries), a stale graph under-reports what a change can break. Cloud resources (Workers, DO namespaces, domains) sync from the provider automatically; **cross-Worker call paths do not** — they are asserted logical edges. A PR that adds or removes a Worker, a Durable Object, or a call path between Workers (or changes what a path carries) asserts the delta in that graph in the same change cycle, and a removed path is deleted there. The call paths to assert are the bot's: bot → state Worker, bot → resident Worker, bot → sandbox Worker, all `invokes`.

## The deployment profile

Every place-specific fact the deploy tooling needs — the Cloudflare account, each Worker's script name and hostname, where the bot's runtime config comes from — is in a deployment profile (`deploy/profile.example.json` is the shape). An installation writes its own to `deploy/profile.json` (gitignored). A profile can also live in a private infrastructure repository: the release workflow names it with `SWITCHBOARD_DEPLOY_PROFILE=github://<org>/<infra-repo>/switchboard/profile.json@main` and reads it with the App token it mints (`CONFIG_REPO_TOKEN`) — the same variable takes a path, or a secrets-manager reference. `deploy plan` and `deploy all` read it; health URLs, the bot's admin route and the state Worker's URL are derived from it, never typed twice. Without a profile, `deploy plan` reads the example and says so; `deploy all` refuses to deploy the example. From a laptop: `SWITCHBOARD_DEPLOY_PROFILE=github://… CONFIG_REPO_TOKEN=<a token that can read the infrastructure repo> npm run cli -- deploy plan`.

`configSource` is where the bot's config comes from: a path (the default), `github://owner/repo/path@ref` read with `CONFIG_REPO_TOKEN`, or `op://Vault/Item/field` read with the 1Password CLI and `OP_SERVICE_ACCOUNT_TOKEN`. The image carries no config. `deploy all` reads and validates the config before any Worker deploys and, right before the bot step, pushes it as the `base` document on the state Worker (with `MEMORY_TOKEN`); the bot's container reads that document when it starts (`SWITCHBOARD_CONFIG=state://base`). A config change without a release is `npm run cli -- deploy config` (the profile's source, or `--source <path|github://…|op://…>`) followed by `npm run cli -- deploy restart` — the running container keeps the config it started with, exactly as it keeps its secrets. An unreadable source, a config that does not validate, or a missing `MEMORY_TOKEN` refuses before anything changes.

The Worker configs are rendered from the profile, not edited. Each `deploy/cloudflare*/wrangler.jsonc` is generated from the `wrangler.template.jsonc` beside it by `npm run deploy:gen` (`deploy init`): the account, script name, hostname, the bot's public URL and state-Worker URL, and the Access team domain and AUD are placeholders the profile fills. The rendered files are gitignored: `npm test`, every Worker's `verify` and `deploy all` render them first from the profile in force (the example in a fresh clone or a pull request's CI, the real profile on a deploy), so the account and hostnames in them are never committed. Change the template (a binding, a cron, an instance size) and commit it; change the profile where it lives. `npm run deploy:gen` renders by hand (before `wrangler dev`, say); `npm run deploy:check` says whether a rendered file was edited by hand. The templates are valid JSONC — editors and prettier treat them as the config they describe — and the rendered files are what wrangler reads.
`secretsSource` is where `deploy secrets <worker>` (`npm run secrets` in each Worker's directory) reads the values of the secrets `deploy/secrets.manifest.json` lists for that Worker: a directory of `<NAME>` files (`~/.secrets/switchboard` when the profile names none) or a 1Password item, `op://Vault/Item`, with one field per secret name (needs `OP_SERVICE_ACCOUNT_TOKEN` or an `op signin` session). The command asks the source once which names it holds and refuses before any upload when a required one is absent; each value goes to `wrangler secret put` on stdin and is never printed. A shared bearer must be put on every Worker the manifest lists for it, and a bot secret is live only after `deploy restart`.

## Read the bot's span log

The bot container's stdout is not readable from outside Cloudflare, and `tracing.log` prints only roots there anyway. The bot keeps its own span log in the process — every span end, at every level, as the same JSON line the log sink prints, in a ring of the last 20 000 lines or 8 MiB — and serves it to an ingress bearer whose actor holds `trace:read` (`docs/reference/specs/tracing.md` item 26). Give the grant to the token's subject in `config.yaml` (`grants: { "http:<subject>": { actions: [trace:read] } }`), then:

```sh
# the last 50 GitHub calls, with their trace ids and routes
curl -sS -H "authorization: Bearer $SWITCHBOARD_INGRESS_TOKEN" \
  "$SWITCHBOARD_BASE_URL/admin/trace/log?span=github&limit=50"
# everything one run did, from its run_meta.traceId
curl -sS -H "authorization: Bearer $SWITCHBOARD_INGRESS_TOKEN" \
  "$SWITCHBOARD_BASE_URL/admin/trace/log?traceId=<32 hex>&limit=5000"
# what ended in the last ten minutes
curl -sS -H "authorization: Bearer $SWITCHBOARD_INGRESS_TOKEN" \
  "$SWITCHBOARD_BASE_URL/admin/trace/log?since=$(( $(date +%s) * 1000 - 600000 ))"
```

The answer is `{ ok, lines, matched, kept, dropped, oldestAt }`: `lines` oldest first (the newest `limit` of what matched), `dropped` how many the ring has let go since the container started, `oldestAt` how far back it reaches. Filters: `since` (epoch ms, on the span's end), `traceId`, `span` (a name, or a family: `github` matches `github.rest` and `github.token_mint`), `limit` (500 by default, 5 000 at most). A malformed filter is a 400; without a bearer the route is a 401, with a bearer that lacks `trace:read` a 403. The ring empties with the container: a restart starts it over, so read before you deploy.

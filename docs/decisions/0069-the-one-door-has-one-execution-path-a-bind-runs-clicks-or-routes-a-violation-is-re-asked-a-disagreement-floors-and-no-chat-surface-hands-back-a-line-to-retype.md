# The one door has one execution path: a bind runs, clicks or routes; a violation is re-asked, a disagreement floors, and no chat surface hands back a line to retype

**The ask.** Decide (the maintainer, after the operator's first day as the default door): everything after the operator's decision goes through one execution table — bind kind × surface → run / click / route / re-ask / refuse — owned by one module, with [record 0067](0067-one-seam-for-a-structured-answer-a-violation-is-re-asked-with-the-violation-named-and-the-callers-declared-floor-holds-never-a-refusal-shown-to-the-person.md)'s seam as the only re-ask and the route as the only floor. This is a survey-driven collapse, not another patch: the day's fourteen defects were fourteen branches of the same missing rule, each fixed (or in flight) at its own render site, and a fifteenth site is a matter of time. Written for an engineer who knows the dispatcher's stages, record 0057 and plan 002. Success criteria:

1. One module owns the outcome of every bind the operator or the route stage produces; no caller — the dispatcher, the operator executor, the route stage, admission, the verifier — renders a line for a person to type or decides a bind's fate on its own.
2. A registry command below the effective confirm class runs through the class ladder; at or above it, on a chat surface, it is offered as one click through record 0044's store — the same mint whichever caller asks, never a `To run this:` beside a button.
3. A preset bind runs the person's own request through the route stage; a typed registry line runs as the person typed it, never re-spelled; a steer folds under the owner rule, read before any directive.
4. Every shape or content violation is the seam's re-ask; every disagreement between the door's own models — the verifier's, or a transport failure standing in for one — floors to the route, which runs the request; neither is ever a sentence handed to the person.
5. Each of the day's fourteen defects is a replay fixture that holds, so the day's failures become the regression suite.

## TL;DR

On the operator's first day as the default door, production filed fourteen defects and every one is the same defect: after the model decides, five different modules each decide for themselves what to do with a bind, and four of them can end the conversation by printing a line for the person to retype. Preset binds were never executed; the verifier refused correct binds with misread reasons and handed the line back instead of falling to the route; a typed `runs stop` was re-bound into a spelling no chat grammar parses while a runaway run burned; a directive reply in a live pipeline's seed thread started a rival run; a refusal's text reached the person cut at its first parenthesis; and the hand-back lines themselves — bare `ship`, `ship --repo …`, `runs_stop --run …` — could not run as pasted. The bet: one execution table, bind kind × surface → run / click / route / re-ask / refuse, owned by one module every caller asks and none re-implements; the seam (record 0067) is the only re-ask, the route is the only floor, and on a chat surface no path renders text to retype — the click is the confirmation, the route is the recovery. It costs one module, the migration of eight render sites and three decide sites onto it, and fourteen fixtures. Doing nothing means the next defect lands at whichever site the last patch missed, and each fix ships as its own branch of a rule nobody wrote down.

## The shape

One module, `src/core/dispatch/execution.ts` (the plan names the files), owning the table every caller asks. (The maintainer's decision in the amendment of 2026-09-20 below collapses the deciders behind this table into one loop; the amendment's table supersedes this one.)

| Bind kind | On a chat surface (Slack, the web chat) | On a typed surface (CLI, HTTP, MCP) |
| --- | --- | --- |
| a registry bind below the effective confirm class | **run** through the class ladder, the receipt naming the line, the class verdict and the reason | run, the same |
| a registry bind at or above the confirm class | **click**: record 0044's row, minted by the one offer path, the full bound line on the button; a store unreachable or an unshowable line is a **refuse** naming why — never a line to retype | refuse naming the typed form — typing is that surface's native act, so naming the line there is the refusal's way forward, not a hand-back |
| a preset bind | **route**: the preset runs the person's own request through the route stage, the verifier's agreement on the receipt | route, the same |
| a steer bind | **run** as admission's fold under the owner rule — the thread's owner read before any directive | the same |
| a typed registry line (the person's own grammar parses it) | **run** as typed through the ladder — never re-spelled, never re-bound | run as typed |
| a shape or content violation (an unparseable line, dropped words, a mixed decision) | **re-ask** at the seam (record 0067), then the seam's declared floor: the route | the same |
| a verifier disagreement, failure or timeout | **route**: the readers' route runs the request, the disagreement on the record | the same |
| a model-authored refusal (`policy` or `request`) | **refuse** through record 0054's renderer — the text carried whole under the reason cap, never cut at a quote or a bracket; a `request` refusal is one question with the best guess | the same |

The properties the table enforces, which no site can enforce alone:

- **One owner.** Every caller — the route stage's answer, the operator executor, the confirm click, admission's fold, the verifier's return — asks the table and executes its cell; none renders its own line, so a new bind kind or surface is a new cell with a table test, not a new branch in five modules.
- **The seam is the only re-ask.** A bind the table cannot execute for a reason the model can repair (the parse, the dropped words, the mixed shape) is record 0067's violation, re-asked with the violation named; the table adds no second retry loop.
- **The route is the only floor.** When judgement fails — the seam's retries exhausted, the verifier disagreeing or failing — the request itself runs through the route stage, which is what the door did before the operator existed and what it fell back to on every patched path this week. A floored request never re-enters the operator (the floor is terminal for the event), so no loop.
- **No chat hand-back.** `To run this:` leaves every chat render; the cut note retires with it (a line never rendered to retype needs no unrunnability warning); the paste machinery retires when its input does. The click is the confirmation; the person's next message is the correction.
- **The owner rule is read before the bind.** A reply into a thread a live run or a pipeline owns is that owner's follow-up first — folded, or refused naming the thread to reply in — and only then a bind; a directive is honoured inside that rule, never around it (D9's fix as a table property, not an admission patch).

## One trace: a typed stop while a runaway run burns

The hard case is D8 and D9 together: the door's misreads created a runaway run, and the door then blocked the only chat path to stopping it.

1. A directive reply lands in a live pipeline's seed thread. Today: stage A reads `directives.agent` as typed intent, admission never asks the owner rule, and a rival coding run starts beside the pipeline (D9). After: the table's steer/owner row runs first — the thread's owner is the pipeline, so the reply folds into the unit's live child or is refused naming the unit thread; the directive is honoured inside that answer. No rival run exists.
2. Suppose it did (the world before the collapse): the person types `runs stop <id> --mode hard`. Today: the operator re-binds the typed line into `runs_stop --run <id> --mode hard`, the MCP spelling, and hands it back; the chat grammar does not parse the handed-back line, so typing it loops (D8). After: the typed-line row — the person's own grammar parsed it, so it runs as typed through the ladder. `runs stop` on one's own run is below the confirm floor for its requester: it runs; on another's run it is destructive: the click renders with the full line, one press stops the run.
3. Had the operator produced the bind instead (the person wrote "stop the runaway run" in prose), the same two rows answer it: a parsed `runs stop` bind runs or clicks by class; an unparseable paraphrase is the seam's re-ask, and after the retries the route floor runs the request — where the route stage's own reading of "stop the runaway run" gets its chance — never a `To run this:` that ends the ask.

The property: at no step does the person retype anything, and the worst model day degrades to the route, which is the door the product shipped with.

## The difficulty map

1. **Sequencing without a red day** (most care): the module lands first as a pure refactor — every site asks the table, every cell holding today's behavior byte for byte — and each behavioral change is one cell flipped in its own unit with its fixtures, so production is green between units and `routing.operator: off` stays the rollback lever throughout.
2. **The click on the operator's path**: record 0044's store holds one pending row per thread; the operator can produce several write binds in one decision, so the table must serialize them onto the one-row invariant (the first write clicks, the rest are refused naming the pending row) without double-minting.
3. **The route floor's re-entry**: a floored request runs the route stage after the operator already decided — the event must not re-enter the operator, the decision's attempts must ride the run that then runs, and the two `src/cli.ask.test.ts` process tests must pass through the floor unchanged.
4. **Retiring the paste machinery**: `outcome: pasted` rows, the web composer's hand-back prefill and the replay's paste counters all read the hand-back's existence; each retires with a spec row change in the same unit, or the ledger grows silent holes.

## Why not X

**Why not keep fixing each site?** The day produced fourteen defects and five fixes, each correct and each local; the survey shows eight render sites and three decide sites still standing after them. A rule enforced in eleven places is not a rule; the fifteenth defect lands at whichever site the sixteenth patch misses. The table makes the next defect a missing cell — a compile error or a failing table test — not a production incident.

**Why not let the operator render the outcome too?** Record 0057's split is the reason the door works at all: judgement in the model, determinism at the boundaries. Rendering is execution; an execution the model words is an interpretation of its own decision, which is the two-interpreters problem again from the other side.

**Why not floor to a question instead of the route?** A question spends the person's attention on the system's failure, which is record 0067's "never a refusal shown to the person" inverted. The route is a floor that acts: it runs the request with the reading the product shipped with, and the person corrects a wrong run — visible, steerable, stoppable — rather than answering for a parse.

**Why not delete the hand-back on typed surfaces too?** A terminal's native act is typing; naming the exact line there is the refusal's way forward, not a broken button. The guarantee is scoped to chat, where a rendered line to retype is a button that does not press itself.

## Boundaries

Not changed: the class ladder and `blastRadius` over parsed input, the authorization table, the seam's parsers and retry bound (record 0067), the intake gate (record 0058), admission's owner store and the durable inbox, the confirm store's invariants (one row per thread, consume-once, requester-bound). Not owned here: the confirm default's level (the narrowed U16's gates), plan 002's memory, briefs and image units, and the plane's queue (record 0064) — the table decides a bind's outcome, never its admission to capacity. Compatibility: a deployment sees fewer dead ends and no new surface; `routing.operator: off` remains the rollback lever, and under it the route stage asks the same table.

## What would change our mind

- *The click is friction the text was not.* If the confirmation rows' consumption rate says people abandon clicks where they used to paste (measured on the store's consume-vs-expire counts after one week), the write row's chat cell is re-argued by amendment — the table stays, the cell moves — and the pre-argued alternative is an undo window (run, then a bounded revert) for the writes that are provably reversible, never for a stop or a deploy.
- *The route floor loops or surprises.* If floored requests re-enter the operator through any path, or the route's reading of a floored request starts writes the person then reverts, the floor narrows to read-only presets by amendment and the rest becomes a named refusal.

## Amended 2026-09-20 — pressure-tested against the field; the maintainer decides for the one loop, and the record is accepted with the table changed

Before acceptance, the table was held against the best-known systems that separate a person's intent from execution — the evidence that led to the decision at the end of this note. For each: what runs without asking, what is confirmed, what is refused, and how a lost instruction is recovered — then the four questions the table must survive, and the decisive comparison the first night under this record forced.

**Model intent against deterministic execution — Claude Code and Anthropic's agent guidance.** Claude Code splits exactly where record 0057 does: the model proposes tool calls and a deterministic permission engine decides — rules "are enforced by Claude Code, not by the model", evaluated deny → ask → allow, read-only actions running unprompted, writes prompting ([permissions](https://code.claude.com/docs/en/permissions)). Two details corroborate the table's cells. The approval prompt shows the command in full, and where a prompt cannot show everything a standing rule would allow, the standing options are withheld and only a one-time approval is offered — the analogue of the table's refuse when the click cannot carry the full line. And a denial can carry a comment that is sent to the model "as the reason for the denial, and Claude continues working" — the violation named to the model, which repairs; never a line handed to the person. Anthropic's guidance draws the same line at design level: workflows are "orchestrated through predefined code paths" while agents direct their own process, with programmatic gates between steps and a separate model screening another's output ([building effective agents](https://www.anthropic.com/engineering/building-effective-agents)) — the verifier as a parallel judge, never a renderer.

**An ambiguous or malformed instruction — Devin, Cursor's agent, Copilot's coding agent.** Devin runs its best reading and puts the burden on the author: vague instructions "can lead Devin to implement solutions that don't align with your actual needs" and it "can get stuck without a clear path or when faced with too many interpretations" ([instructing Devin](https://docs.devin.ai/essential-guidelines/instructing-devin-effectively)) — recovery is the person steering a visible session, not retyping. Cursor's agent has a clarifying-question tool, but "while waiting for your response, the agent continues reading files, making edits, or running commands", and checkpoints give a local undo ([agent overview](https://cursor.com/docs/agent/overview)). Copilot's coding agent never hands text back at all: every outcome lands as a branch and a pull request a person reviews ([about the cloud agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent)), and its issue automations grade each action's confidence against a repository threshold — at or above it the action runs with a recorded rationale, below it the action is held as a one-click suggestion — with the docs' own caveat that "approvals are a workflow convenience, not a security control": permissions, not prompts, bound what the automation may do ([rationale, confidence, and approvals](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-automation-rationale-and-approvals)). Nobody in this field answers ambiguity by printing a line for the person to retype, and everyone records why it acted.

**A mistyped command — Unix shells and git.** The terminal is the one surface where the hand-back is native: `command not found` plus a suggestion — zsh's `CORRECT` option prompts before running a correction, bash exposes `command_not_found_handle` for the distributions' "did you mean" — leaves the fix to the typist ([zsh options](https://zsh.sourceforge.io/Doc/Release/Options.html), [bash manual](https://www.gnu.org/software/bash/manual/bash.html#Command-Search-and-Execution)). git grades the same decision as configuration: `help.autocorrect` defaults to showing the suggested command, and can prompt for confirmation, run it immediately, or run it "after specified deciseconds" ([help.autoCorrect](https://git-scm.com/docs/git-config#Documentation/git-config.txt-helpautoCorrect)). Two readings for the table. First, the field's most conservative tool ships a mode that runs the likely command with no confirmation at all, so the floor-to-route for non-destructive binds is not an outlier. Second, the delayed auto-run is sound only because the terminal has a native in-flight cancel — Ctrl-C during the delay; chat has none, which is why the table's chat answer to a destructive bind is the click rather than a countdown, and why its typed-surface refusals keep naming the line: exactly the scope the shells prove.

**A partial match — Slack's slash commands and Linear's command palette.** Slack routes `/command` and passes everything after it as one opaque `text` parameter; a malformed argument is the app's problem, the platform's recommended answer is an ephemeral error with usage guidance — a hand-back — and a name collision between apps silently runs whichever was "installed most recently" ([implementing slash commands](https://docs.slack.dev/interactivity/implementing-slash-commands/)): the two failure shapes the table removes, the retype loop and the arbitrary likely-intent. Linear's command menu narrows as you type and scopes on single-letter prefixes, but a partial match never executes — the person's Enter on a highlighted, fully rendered row is the act ([search and the command menu](https://linear.app/docs/search)). That is the click cell: resolution may be fuzzy, execution is an explicit selection of a fully shown candidate.

**Desired state against execution — Kubernetes and Temporal.** `kubectl apply` keeps the person's declared intent on the object itself (the `last-applied-configuration` annotation) and computes every change from declared against live, so a retry re-applies the same intent and never re-asks the person ([declarative management](https://kubernetes.io/docs/tasks/manage-kubernetes-objects/declarative-config/)). Temporal makes the instruction durable in the event history and replays code against it: commands that match history proceed, a mismatch is a non-determinism error — a refusal, never a guess ([workflow definition](https://docs.temporal.io/workflow-definition)). The table's counterparts hold: the floor is terminal for the event so no loop re-asks, the person's own words are the durable input the route runs, and a lost instruction cannot exist because the request, the decision and the attempts ride the run's record.

**The judgement on the four questions.**

1. *Is the floor-to-route right for non-destructive binds?* Yes. It is the shape of Copilot's above-threshold auto-apply and milder than git's `immediate`: what runs on the floor is not a model's correction but the deterministic route the product shipped with, reading the person's own words, visible and stoppable. The field's other answer — ask the person (Cursor's tool, zsh's prompt) — spends the person's attention on the system's failure, which this record already rejects; even Cursor keeps working while it asks.
2. *Is one click the right confirmation for a destructive write?* Yes. Claude Code's one-keypress prompt showing the full command, Copilot's one-click suggestion carrying its rationale, and Linear's Enter on a rendered row are the same act; the table's refuse-on-unshowable-line matches Claude Code withholding a standing option its prompt cannot fully display. An undo window (Cursor's checkpoints; git offers none) was weighed and rejected as the chat default: the door's writes — a stop, a deploy, a shared channel's config — are not reliably reversible, and chat has no dependable in-flight cancel; "What would change our mind" now names the undo window as the pre-argued alternative should the click's consumption data call it friction.
3. *Is the seam's re-ask the right treatment of a malformed bind?* Yes, and it is the field's better half: the shells hand the fix to a typist and Cursor asks the person, but Claude Code's deny-with-comment — the violation named to the model, which continues working — is exactly the seam, spending model retries rather than the person's attention, with a floor that acts when the retries run out.
4. *Does the field do anything the table misses?* A "did you mean" that runs after a delay — rejected: chat lacks the terminal's cancel affordance that makes git's deciseconds sound, and the click is chat's equivalent of the delay's escape hatch, while the route floor already runs the likely intent where nothing destructive rides on it. An undo window — rejected as the default, recorded as the re-argument path above. A rationale on every automatic act — already a table property: the run cells carry the receipt naming the line, the class verdict and the reason, and a floored event carries the disagreement on the record. What the field does do better is the decisive comparison below: it has one decider where this record still has four.

**The decisive comparison — Claude Code's own shape against the door's chain of deciders.** Claude Code is a single agent loop: one model, typed tool calls as the only way to act, read tools it may call before deciding, a question that keeps the turn open until the person answers, deterministic permission gating on each tool call — and no second model checking the first ([permissions](https://code.claude.com/docs/en/permissions); agents "are typically just LLMs using tools based on environmental feedback in a loop", gaining "ground truth from the environment at each step", with tools poka-yoked so the mistake cannot be expressed — [building effective agents](https://www.anthropic.com/engineering/building-effective-agents)). The door this record tables has four deciders in a chain: the operator's one-shot decide, a verifier model that can disagree with it, the readers' route as the floor, and the general preset as the fallback that answers in prose. The first night under this record, production filed three more defects (issues 2043, 2045, 2046) and every one landed at a hand-off between two of the four: two plain-words docs asks were refused as "privileged administrative updates" by a model-authored refusal no policy row backs, inventing an administrator that does not exist (2043); a bare `review` reply in a thread whose parent names the pull request drew "Review what?" plus a proposal that would fail if clicked (2045); and one ask crossed all four — the operator asked a question the coding child could have answered itself, the person's free-text answer could not be joined to the question, the route floor called the complete thread "unclear request", and general answered a write ask with "post a new top-level message" — the retype hand-back this record retires, produced by the fourth decider (2046). Each decider did its narrow job; the defects live between them, because every hand-off re-reads the situation without the previous decider's reasoning and without ground truth. The field's verdict is uniform: no system surveyed above puts a second model in judgement over the first's intent, and every failure class the chain produced is unrepresentable in the single loop — a malformed bind cannot be typed into a validated tool schema, a false refusal cannot be authored where only the policy table refuses, and an unjoinable answer cannot exist where the question is parked state the answer re-enters.

**The decision (the maintainer, 2026-09-20): the chain collapses into one loop, and the table changes.** The operator becomes an agent loop with typed tools — `bind_preset` (the preset and the person's request as typed arguments), `run_command` (a registry command with typed arguments), `ask` (one question, parked as the thread's pending question in durable state), or nothing — with read tools (the thread's owner and pending question, the repository's facts, the registry's own help) so it decides with ground truth. The table's rows become the loop's turn outcomes:

| Turn outcome | On a chat surface (Slack, the web chat) | On a typed surface (CLI, HTTP, MCP) |
| --- | --- | --- |
| `run_command` below the effective confirm class | **run** through the class ladder, the receipt naming the line, the class verdict and the reason | run, the same |
| `run_command` at or above the confirm class | **click**: record 0044's row, minted by the one offer path, the full bound line on the button; a store unreachable or an unshowable line is a **refuse** naming why — never a line to retype | refuse naming the typed form |
| `bind_preset` | **route**: the preset runs the person's own request through the route stage | route, the same |
| `ask` | **question**: one question, parked as the thread's pending question; the person's next message in that thread — mention or not — is joined to the original request with the question and its answer, and re-enters the loop as facts | the same |

| a typed registry line (the person's own grammar parses it) | **run** as typed through the ladder — the line never enters the loop, never re-spelled | run as typed |
| a steer into an owned thread | **run** as admission's fold under the owner rule — read before the loop sees the message | the same |
| a refusal | **refuse** only from the policy table, rendered through record 0054 naming the policy row it stands on; the model authors no refusal — a model's "cannot" is an `ask` or nothing | the same |

What the collapse deletes from the original table: the malformed-bind row — a shape violation is unrepresentable in a typed tool schema, so record 0067's re-ask narrows to the harness's own repair of a tool call that fails to validate, invisible to the person and to every caller; and the verifier row — the verifier retires, because a second model judging the first's intent is the two-interpreters problem this record already names, its every disagreement was already discarded to the floor, and deterministic gating per tool call (the ladder, the authorization table, the owner rule) is what the field uses in its place. The floor narrows to one cause: a turn that ends without a tool call. And general is never reached by a write ask — a write exists only as `run_command` through the ladder or a preset's route, so the fourth decider's prose can no longer end a write ask.

**What this replaces in [plan 2026-09-20-001](../plans/2026-09-20-001-feat-one-execution-path-plan.md).** The plan is rewritten so its first unit is the loop itself, at the top of the queue ahead of every other unit: E2 becomes that unit — the operator loop with typed tools and the table above as its turn-outcome surface — and it absorbs the separate bind, refusal, verifier and owner-rule repairs (E4, E5 and E6), whose test scenarios become the loop's fixtures. The verifier retires with `verifyOperatorBind` and `renderVerifierHandBack` rather than flooring. The fixtures from the first night's four door failures — the two false refusals of plain-words docs asks (issue 2043, the record-status ask and the pressure-test ask), the PR thread's "Review what?"

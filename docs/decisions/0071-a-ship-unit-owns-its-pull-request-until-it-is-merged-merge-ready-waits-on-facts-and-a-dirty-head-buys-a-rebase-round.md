# A ship unit owns its pull request until the pull request is merged: merge-ready waits on facts, a DIRTY head buys a rebase round, and anyone's merge ends the unit

*The title and filename predate the amendment below and name the withdrawn shape — the always-on rebase round bought by a DIRTY head; they are kept to preserve links.*

**Accepted 2026-09-20 05:45Z (22:45 PDT on the 19th)**, in the shape the amendment of #2048 gave it — the three mechanisms, in the order they ship: the rebase before every push (always, not configurable); the sweep a person runs with the two-rung resolver — git alone with the repository's own merge drivers and `git rerere`, then one bounded model round reading the repository's AGENTS.md; and watch-until-merge as an org setting with a per-repository override, off by default. Two calls are the maintainer's at acceptance: a stale-but-clean pull request is never rebased by the pipeline — DIRTY is the only trigger the sweep and the watch answer — and the resolver knows nothing about a repository's technology; what it may regenerate is only what the repository's own AGENTS.md names. The plan this record names in its rollout follows the record to accepted, with its first unit — the rebase before every push — ready to seed.

*Amended 2026-09-20 04:55Z (while proposed), on the maintainer's redesign: the always-on rebase round — one per base move per unit — is withdrawn. It makes the expensive behaviour the default, and its only softer variant, "rebase once at some later time", is arbitrary and cannot be explained to a person. Three mechanisms replace it: a rebase before every push (always, not configurable), a sweep a person runs with a two-rung resolver, and watch-until-merge as a setting, off by default. **The ask.** Decide (the maintainer, before the plan is written): how a ship unit's pull request stays mergeable as the base moves, without making the expensive behaviour the default. Written for an engineer who knows the plan runner's driver, the ship machine and the checks intake. Success criteria (*amended 2026-09-20 04:55Z — the criteria now state the three mechanisms; the original criteria 1 and 4 stated the withdrawn always-on round*):

1. Every head that reaches review is current when it lands: a coding or fix child fetches the base and rebases its branch onto it immediately before each push, resolves what it must with the thread context it already has, re-runs the fast gates, then pushes. This is not configurable.
2. One registry command — named in the user's twelve nouns, over the pull request noun — walks the open pull requests the pipeline owns, or one named pull request, and rebases each onto its base with the two-rung resolver. Rung one is git alone: `git rebase` with whatever merge drivers the repository itself declares in `.gitattributes`, and `git rerere` so a resolution made once replays on every later rebase of the same hunks; an empty `git range-diff` after the rebase carries the existing approval to the new head with no re-review. Rung two is one bounded model round with the thread's context and the repository's own AGENTS.md for any conflict git leaves — one per repository in flight, a short lease, a delta re-review.
3. Watch until merge is a setting, off by default, org-level with a per-repository override, on the config surface that exists. When on for a repository, the unit stays on its pull request after merge-ready and, on each push-to-base webhook that leaves it DIRTY, runs the two-rung resolver for that one pull request, fixes tests and re-requests review as needed, until the pull request is merged or the person ends it — capped at one rebase per repository in flight and a per-pull-request spend limit, both configurable. Off — the default — merge-ready ends the unit as today.
4. A stale-but-clean pull request is never rebased by the pipeline: it merges as it is. Nothing in the sweep or the watch suggests or makes structural changes to a person's repository.
5. The merge door's conflict refusal names the remedy that exists: the watching unit's own round where the setting is on, the sweep command otherwise — never a person's hand merge as the only way.

## The shape

*Amended 2026-09-20 04:55Z (while proposed): this section is rewritten whole. The earlier shape — the merge chain beside the walk for every unit, a dirty fact buying a rebase round, at most one round per base move per unit, always on — is withdrawn: it makes the expensive behaviour the default, and "rebase once at some later time" is arbitrary and cannot be explained to a person. The three mechanisms below replace it.*

**One — rebase before every push, always.** A coding or fix child fetches the base and rebases its branch onto it immediately before each push: it resolves what it must with the thread context it already has, re-runs the fast gates, then pushes. This extends the contract's existing pre-push re-fetch rule from "rebase once more when the base moved" to the unconditional form, and it is not configurable — a rebase against a base the child just fetched, with the conflict's context already in the child's window, is the cheapest rebase the system will ever run. Every head that reaches review is current when it lands; what this mechanism cannot do is keep a head current *after* it lands, which is the other two mechanisms' job.

**Two — a sweep a person can run.** One registry command — named in the user's twelve nouns, over the pull request noun (`pulls rebase`) — walks the open pull requests the pipeline owns, or takes one named pull request, and rebases each onto its base with a **two-rung resolver**. Rung one is git alone: `git rebase` with whatever merge drivers the repository itself declares in `.gitattributes`, and `git rerere` enabled, so a resolution made once replays on every later rebase of the same hunks; when the rebase completes and `git range-diff` over it is empty, the existing approval carries to the new head with no re-review — the branch's own change is byte-identical, only its parent moved. Rung two, for any conflict git leaves, is one bounded model round with the thread's context and the repository's own AGENTS.md — one per repository in flight, a short lease, and a delta re-review at the pushed head. The product never knows what a generator or a formatter is: a repository that wants a generated file regenerated rather than hand-merged says so in its AGENTS.md, and the model round reads it there.

**Three — watch until merge, as a setting.** Off by default; org-level with a per-repository override, on the config surface that exists. When on for a repository, the unit stays on its pull request after merge-ready — the merge-ready book beside the merge-wait book, registered with the pull request, head and base — and on each push-to-base webhook that leaves the pull request DIRTY (read once GitHub has recomputed `mergeable_state`, never on a clock), it runs the two-rung resolver for that one pull request, fixes tests and re-requests review as needed, until the pull request is merged or the person ends it. The loop is capped: one rebase per repository in flight, and a per-pull-request spend limit, both configurable; at a cap the DIRTY stands and the card names the sweep a person can run. A merged fact, whoever merged, ends the unit `merged` by other, and with the watch on the waiting unit owns its thread under the unfinished-unit clause, so an addressed reply is its turn and never the router's; with the watch off, `merge_ready` is an ended kind exactly as today.

**What the pipeline never does.** A stale-but-clean pull request is never rebased: it merges as it is — DIRTY, not staleness, is the only trigger the sweep and the watch answer. And nothing in the sweep or the watch suggests or makes structural changes to a person's repository: the resolver's whole brief is the conflict in front of it, and what it may regenerate is only what the repository's own AGENTS.md names. The merge door's conflict refusal changes its sentence to match the remedy that exists: the watching unit's own round where the setting is on, the sweep command otherwise.

## Why not X

**Why not fix the conflict refusal's wording (issue 1747's first ask)?** A better sentence still names a person as the mechanism. Tonight's cost was not confusion about the remedy — it was 14 minutes of directed child time and a wrong-branch attempt, the work itself. The wording fix survives only as criterion 5: the sentence changes because the remedy changed.

**Why not have the person re-issue ship after the base moves?** A re-issue re-runs an approved unit: a fresh pass, a fresh coding round on work that needed only a rebase, and a second instance splitting the unit's rows, its page and its grant count — the two-places problem 0051 already rejected twice.

**Why not GitHub's merge queue?** The queue rebases and re-runs checks, but the approval it carries forward is the one our reviewed-head gate deliberately voids: a required re-review at the new head is this pipeline's own rule, and only a live unit can run it. The queue also serializes the whole repository where the plane's admission serializes only the rounds that contend. Where a base *requires* a queue, the merge door already enqueues (agent-ship.md item 9); that path composes with this record — the wait watches the queue's outcome the same way.

**Why not the warm window, already designed?** It is a timer restarted by replies. Tonight's first DIRTY landed 45 minutes after an ending and the second after a rebase the window knows nothing about; a window lapses while the pull request is still open, and it wakes for a person's words, never for a repository fact. The window stays — for `merged`, where it belongs.

**Why not rebase on every base move, always on — this record's own first shape?** *(Added 2026-09-20 04:55Z.)* It makes the expensive behaviour the default: every sibling merge charges every open unit a model round whether or not anyone wanted that head current yet, and the only softer variant — "rebase once at some later time" — is arbitrary and cannot be explained to a person. The incident numbers above are the state at 03:53Z; by the end of that night the cascade had grown to five orphaned pull requests and eight model rebase rounds at about fifteen dollars (the maintainer's comments on issue 1747). Withdrawn; the sweep and the watch keep the round behind a person's command and a setting that is off by default, and rung one means most rebases cost git, not a model.

**Why not a resolver that understands each repository's technology?** *(Added 2026-09-20 04:55Z.)* A resolver that knows this stack's generators, that stack's formatters and the next one's lockfiles is a slippery slope with no end — the maintainer's words. The product never knows what a generator or a formatter is: a repository that wants a generated file regenerated says so in its own AGENTS.md, and rung two's model round reads it there — the same file every coding child already reads.

## What would change our mind

*Amended 2026-09-20 04:55Z (while proposed): rewritten for the three mechanisms; the earlier escape hatches — the plane-side watch, the `ship.ownUntilMerged` flag — are subsumed by the watch being a setting that ships off.* If rung two's one bounded round proves too small for real conflicts, the sweep reports the conflict and stops — it never grows into the technology-aware resolver rejected above.

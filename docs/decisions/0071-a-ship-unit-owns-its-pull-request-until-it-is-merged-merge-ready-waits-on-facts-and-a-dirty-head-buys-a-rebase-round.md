# A ship unit owns its pull request until the pull request is merged: merge-ready waits on facts, a DIRTY head buys a rebase round, and anyone's merge ends the unit

**The ask.** Decide (the maintainer, before the plan is written): a unit that reaches `merge_ready` is not finished — it stays its thread's owner ([record 0051](0051-a-thread-has-one-owner-for-its-life-a-message-is-one-event-in-a-chosen-mode-and-a-pipeline-idles-instead-of-ending.md)'s owner order) until its pull request is merged or the person ends it, and while it waits it reacts to facts and never to a timer. Written for an engineer who knows the plan runner's driver, the ship machine and the checks intake. Success criteria:

1. A merge-ready unit whose pull request goes DIRTY because the base moved runs a rebase round by itself: the same coding child, in the unit's thread and on the unit's own branch, resolving the conflicts by rebasing onto the base and regenerating any generated artifact with its gen script rather than hand-merging its lines, then pushing and re-requesting review at the new head. No person posts a directive.
2. The review's LGTM at the new head merges when the instance's merge field says `runner`, and re-reports merge-ready in one line when it says `person`; a pull request merged by anyone — auto-merge, a person, the runner — ends the unit `merged`.
3. Every transition is a fact — a DIRTY read, a posted approval, an observed merge — and the wait between facts spends nothing: no lease, no renewal, no timer that ends the ownership while the pull request is open (record 0051's idle economics).
4. Two units of different plans both merge-ready on the same file, with the base moving twice inside a minute, converge with no person and no rebase storm: at most one rebase round per base move per unit, the rounds serialized by the plane's admission ([record 0064](0064-the-plane-owns-every-runs-state-a-refusal-becomes-a-queue-position-an-ending-is-judged-by-the-ledger-that-saw-it-and-a-release-is-a-quiet-window-a-person-closes.md)), and each unit reading the state fresh before it spawns, so a round that finds a clean head spawns nothing.
5. The merge door's conflict refusal stops naming a person as the remedy for a unit that is still owned: the unit's own rebase round is the remedy, and the refusal's sentence says the unit is on it.

## TL;DR

Tonight, on 1.255.0 between 03:04Z and 03:53Z, three routed units (merge: person) ended `merge_ready` and their pull requests then went DIRTY when siblings merged first — #2029 (run ab8527aa), #2033 (plan the-verifier-s-floor-on-b4faed) and #2032 (plan write-the-next-decision-e5ac46, a two-row conflict on the generated decisions index) — and #2033 went DIRTY a second time after its rebase because #2029 merged in between. Nothing owned any of them: each unit had ended, a plain reply in the thread routes (issue 1878), and the merge door's conflict refusal says re-issue (issue 1747). Four rebases were posted by hand as `agent:coding` directives — 14 minutes of child time, about nine dollars, one wrong-branch attempt hard-stopped. The bet: a unit that reaches merge-ready is not finished. It keeps its instance, its thread and its pull request until the pull request is merged or the person ends it, and it reacts to facts — DIRTY buys a rebase round in the same pipeline, an LGTM at the new head merges or re-reports in one line, an observed merge ends the unit `merged`. The cost is one idle unit per open pull request, which spends nothing while it waits, and the conflict work moves from a person's directive to the pipeline. Doing nothing keeps the by-hand rebase as the answer to every sibling merge.

## The re-evaluation of record 0051: why this is a new record and not an amendment

The unit that asked for this record asked first whether 0051's acceptance reasoning already implies it. It does not, on two sentences of 0051's own. First, 0051 was accepted with the ending's line drawn at merge-ready: "a unit is ended when merged, merge-ready, blocked by a dependency, or refused at authorization: nothing a reply can change." Tonight shows a merge-ready ending has exactly one thing left that facts change — the pull request — and 0051's reasoning never weighed a repository fact, only a person's reply. Second, 0051's warm amendment already moved the line once, to a sixty-minute window restarted by replies, and in doing so **rejected** the unbounded shape by name: "why not no window? … an instance per unit alive indefinitely." This record reverses that rejection for the merge-ready ending, on a bound the amendment did not consider: not indefinite, but the pull request's own life — an open pull request is unfinished work, and merge or the person's stop ends it. A reversal of a rejected alternative is a new decision, not a note on the old one; the documentation rule (an accepted record only grows by an appended re-evaluation) is for a change checked against the record's reasoning, and this change contradicts it.

What survives of 0051 untouched: the owner order itself (this record needs no new clause — `merge_ready` stops being an ended kind, so the *unfinished unit* clause covers the waiting unit), the event and nudge machinery, idle and its lease rule, and the warm window — which now applies from `merged`, the one ending left where follow-ups arrive after the work is done. For `merge_ready` the window is subsumed: the unit owns its thread for the whole wait, so a "show me screenshots" reply during it is a turn of the waiting unit, as the warm design already specifies for a merge-ready unit's turn.

## The shape

**The ending becomes a wait.** A pass still ends `merge_ready` with today's report — the pull request, the rounds, the checks at the approved head, the pending human merge. But the unit is not ended: the driver holds the unit's **merge chain** beside the walk (the warm chain's shape from 0051's amendment: a list of per-unit promises `runPlan` awaits before `finish`), blocked on a `waitForEvent` typed with the unit's fact event, indexed per wait so no step name is reused. The walk's settlement is unchanged — a seeded plan's dependents were told `blocked` when the walk passed the merge-ready unit, and a merge during the wait unblocks nothing; a re-issue is their way back, exactly as today when a person merges after the walk moved on. The exits are the merge, `runs stop <unit key>` and the End action; there is no timer. The wait spends no lease and no renewal: waiting instances sit outside the platform's concurrency count, and the thread's worktree is released as it is after any round.

**The facts, from the checks reader.** Record 0055 gave the round one reader of repository truth: the check-run intake, which sends `checks-settled-<head>` to every instance registered at a head in the merge-wait book. This record gives that reader a second book, the **merge-ready book**: every unit entering the wait registers its pull request, head and base. The intake now also takes the pull request's own webhook facts — a push to the base branch, the pull request closed or merged — and on a base move reads the pull request's facts once GitHub has recomputed them (`mergeable: null` means still computing; the read repeats on the recompute, never on a clock): `mergeable_state: dirty` sends the unit a typed **dirty fact** naming the base's new tip; a merge sends a **merged fact** with the merge commit, whoever merged. The fact is level-triggered on the chain's side: on wake the chain reads the facts fresh, and a head that reads clean — a sibling's merge recomputed it, or a round already in flight rebased past it — spawns nothing. That read, not event-counting, is what bounds the cascade.

**The rebase round.** On a dirty fact the chain opens a rebase round: a coding child in the unit's thread, on the unit's own branch, write identity, under the fix round's lease, admitted by the plane like any round so simultaneous dirty facts across units queue instead of storming. Its brief is the conflict, not a feature: rebase onto the base's tip, resolve; a conflicted **generated artifact** (tonight's two-row conflict on the generated decisions index) is never hand-merged — take either side, run its gen script, commit what it writes; run the fast gates; re-fetch the base right before the push (the contract's existing rule, which folds a second base move that lands mid-round into the same rebase); push. The machine reads the handoff as it reads a fix round's and enters the review round at the pushed head — the resume transition the `review_pending` re-attempt already makes — because the reviewed-head gate voided the approval the moment the head moved. The re-entered pass carries the unit's `reviewRounds`, so `maxRounds` caps the unit across passes, and the grant's cost cap is consulted before every rebase round; at the cap no round runs, the DIRTY stands, and the card names the rebase a person can run — the one place the by-hand directive remains.

**The merge.** The re-review's LGTM at the new head runs today's ending: `merge: runner` squashes at the approved head under its existing guards; `merge: person` re-enters the wait and re-reports merge-ready **in one line** — the new head, the checks, the pending merge — never the full report again. A merged fact, at any point in the wait, ends the unit `merged` with `by: other`, the commit and the time, exactly as the pre-check reports a pull request merged before the attempt. The unit's ending is then final, and the warm window begins.

**The thread line.** With `merge_ready` out of the ended kinds, thread-admission's owner order needs no new clause: the waiting unit is the unfinished unit, so an addressed plain reply in its thread is a thread event nudged to the chain — answered as a turn of the waiting unit — and never the router's. The merge door's conflict refusal changes its sentence for an owned unit: the rebase round is running or queued, and the refusal says so instead of asking for a hand merge.

## One trace: tonight replayed — the cascade converges

Three units of three plans, all merge-ready on heads that touch the generated decisions index; the base moves twice inside the hour.

1. 03:04Z: the units behind #2029, #2032 and #2033 are all in their merge wait, registered in the merge-ready book.
2. A person merges #2029. The intake sends its unit the merged fact; that unit ends `merged`, by other. The base moved: the intake reads #2032 and #2033 once GitHub recomputes — both DIRTY — and sends each unit its dirty fact.
3. Both chains wake and read fresh: still DIRTY. Each opens a rebase round; the plane's admission serializes the two spawns. #2033's child rebases its branch onto the tip, hits the two-row conflict on the generated index, takes the base's side and reruns the index's gen script, pushes; #2032's does the same a few minutes later, on a base that now also carries nothing new of #2033's (its branch is unmerged), so the two rounds never touch each other's work — every rebase is onto the base only.
4. #2033's re-review approves at the new head; `merge: person` re-reports merge-ready in one line. A person merges it. The base moved again: the intake reads #2032 — DIRTY a second time. One more dirty fact, one more round: tonight this second DIRTY was a person's fourth directive; here it is the same chain's next wake. Had the second merge landed while #2032's first round was still in flight, the round's pre-push re-fetch would have folded it and the wake after the push would have read clean and spawned nothing.
5. #2032's re-review approves; merged by a person; the last unit ends `merged`. `finish` runs when the walk and every chain are done. Zero directives, at most one rebase round per base move per unit, and every round's cost on the unit's own spend.

## Why not X

**Why not fix the conflict refusal's wording (issue 1747's first ask)?** A better sentence still names a person as the mechanism. Tonight's cost was not confusion about the remedy — it was 14 minutes of directed child time and a wrong-branch attempt, the work itself. The wording fix survives only as criterion 5: the sentence changes because the remedy changed.

**Why not have the person re-issue ship after the base moves?** A re-issue re-runs an approved unit: a fresh pass, a fresh coding round on work that needed only a rebase, and a second instance splitting the unit's rows, its page and its grant count — the two-places problem 0051 already rejected twice.

**Why not GitHub's merge queue?** The queue rebases and re-runs checks, but the approval it carries forward is the one our reviewed-head gate deliberately voids: a required re-review at the new head is this pipeline's own rule, and only a live unit can run it. The queue also serializes the whole repository where the plane's admission serializes only the rounds that contend. Where a base *requires* a queue, the merge door already enqueues (agent-ship.md item 9); that path composes with this record — the wait watches the queue's outcome the same way.

**Why not the warm window, already designed?** It is a timer restarted by replies. Tonight's first DIRTY landed 45 minutes after an ending and the second after a rebase the window knows nothing about; a window lapses while the pull request is still open, and it wakes for a person's words, never for a repository fact. The window stays — for `merged`, where it belongs.

## What would change our mind

If merge-ready units routinely wait days, one instance per open pull request may strain the platform's instance economics (0051's open question on billing a waiting instance applies here doubled); the escape is moving the watch from the instance to the plane's decider, which already owns every run's state (record 0064). If rebase rounds' spend exceeds the hand rebases they replace, the cost-cap consult tightens or the round asks before running. If GitHub's mergeable recompute proves too slow or lossy to be the trigger, the intake falls back to reading the facts on every base push. Reversibility: a scope flag (`ship.ownUntilMerged`) off returns `merge_ready` to an ended kind byte for byte.
